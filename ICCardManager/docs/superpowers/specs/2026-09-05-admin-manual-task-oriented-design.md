# 管理者マニュアルの作業別再構成 設計書

**作成日**: 2026-09-05
**対象**: `ICCardManager/docs/manual/管理者マニュアル.md`（2,242 行）および新設する `IT担当者ガイド.md`

---

## 1. 背景と目的

現行の管理者マニュアルは「Issue を直すたびに該当節へ追記する」運用で育った結果、次の症状を持つ。

| 症状 | 現状 |
|---|---|
| 読者が混在している | 庶務担当者向けの手順と、IT 担当者向け（SMB 権限、`journal_mode`、`busy_timeout`）、開発者向け（Issue 番号 35 か所、SHA-256 ハッシュ、ログのカテゴリ名）が同居 |
| 手順と仕組みの説明が混ざる | §2.3 は 6 ステップの手順の間に SQLite の補足・リストアの注意・上書き動作の解説が割り込む |
| 変更履歴の文体 | 「Issue #1655 で改善」「これにより〜が解消されました」という CHANGELOG 調が本文に残る |
| 節の粒度が不揃い | §5.6（初期導入）だけで 340 行・5 階層、§4（職員管理）は 60 行 |
| 冒頭の逆引きが長い | クイックガイド＋年間作業表で 110 行。本文の前に「目次の目次」を読む |

**読者は「部署の庶務担当で IT 操作に必ずしも詳しくない人」1 種類に絞る**。この読者にとって必要なのは「なぜ変わったか」ではなく「いま何を押すか」である。

## 2. 方針

1. **管理者マニュアルを作業別（いつ発生する作業か）に再構成する**。機能別の章立て（職員管理／カード管理／データ管理…）をやめ、「はじめて使うとき」「毎月」「人やカードが増減したとき」「年に一度」「困ったとき」で並べる。
2. **IT 担当者向けの内容を `IT担当者ガイド.md` へ分離する**。管理者マニュアル側には「システム担当者に依頼してください」の一文と参照だけを残す。
3. **Issue 番号と改善経緯を本文から削る**。設計書への参照は IT 担当者ガイド側にだけ残す。
4. **各作業を固定型で書く**: 「この作業をするとき」「前提」「手順」「できたことの確認」。1 手順 1 文。押す場所（メニュー名・ボタン名・キー）は太字。
5. **冒頭の逆引きは 1 表に圧縮する**。作業別に章が並ぶため、詳細な逆引きは目次が担う。

```

├─ はじめに（このマニュアルの読み方、管理者の役割、動作環境）

│   ├─ 4.2 古いデータを削除する

│   ├─ 5.2 起動しない

│   ├─ 5.4 データがおかしい（残高の不整合、履歴の食い違い）
│   ├─ 5.5 共有モードの警告が出る
│   ├─ 5.6 バックアップ・リストアがうまくいかない
│   └─ 5.7 「ピッすいの更新が必要です」と表示される
├─ 第6部 データを取り出す・戻す
│   ├─ 6.1 手動バックアップ
│   ├─ 6.2 リストア（復元）
│   ├─ 6.3 CSV エクスポート
│   └─ 6.4 CSV インポート
└─ 付録
    ├─ A. 設定画面（F5）の項目一覧
    ├─ B. システム管理画面（F6）の項目一覧
    ├─ C. 管理者ダッシュボード（F8）の見方
    ├─ D. ショートカットキー
    └─ E. 用語集
```

## 5. IT担当者ガイド.md の章構成

```
IT担当者ガイド
├─ 1. このガイドの対象（情報システム担当者。管理者マニュアルとの分担）
├─ 2. 動作環境と配布形態（32bit ビルド、self-contained、DLL 依存）
├─ 3. 共有フォルダの構築（SMB 共有、NTFS 権限、GUI／PowerShell 例、推奨台数）
├─ 4. データベースの配置と接続（database_config.txt、UNC／ドライブレター、journal_mode、busy_timeout、ヘルスチェック、ネットワーク切断時の挙動）
├─ 5. 設定ファイル（appsettings.json、ログ設定、OrganizationOptions の全項目）
├─ 6. バックアップ・VACUUM の仕組み（保持ルール、月次 VACUUM ロック、実施記録）
├─ 7. バージョン管理（latest_version.txt、旧バージョンの起動ブロック、アンインストール時のデータ扱い）
├─ 8. セキュリティ（felicalib.dll の完全性検証、式インジェクション対策、監査ログの保存期間）
└─ 9. 障害対応（SQLite エラーコード、ログの読み方、接続診断の各項目の意味）
```

Issue 番号は本文には書かず、各章末に「設計書参照: 04_機能設計書 §x.y」の形で 1 行だけ置く。

## 6. 文体規約（両ファイル共通）

- 1 文は 60 文字程度まで。「〜する必要があります」は「〜してください」に置き換える。
- 手順は番号付きリスト。1 番号に 1 操作。押す場所は **太字**。画面遷移は「メニュー **データ** → **エクスポート/インポート**」の形。
- 補足は手順の外に置く。手順の中に `>` 引用を挟まない。
- 「〜で改善」「〜が解消されました」「Issue #」は書かない。
- 用語は `docs/design/00_用語集.md` に従う。「交通系ICカード」を「ICカード」と略さない（`UserFacingTextConventionTests` と同じ基準）。
- 既存のスクリーンショット（`docs/screenshots/`、27 か所の参照）は移動先の節でそのまま使う。新規撮影はしない。

## 8. 検証

- 既存の静的検査テスト（`AdminDashboardOtherSeriesCountManualConventionTests`、`OrganizationOptionsUsageConventionTests`）が緑であること。
- Markdown 内リンク（`#...` アンカー）が全件解決すること。scratchpad のスクリプトで見出しからアンカーを生成して照合する（使い捨て、リポジトリには入れない）。
- 現行マニュアルに含まれる **手順の情報が欠落していない**こと。現行の `###`／`####`／`#####` の全見出しについて、上記対応表の移動先に対応する本文が存在することを手作業で確認し、PR 本文にチェック済みの対応表を添える。
- 本文に「Issue #」「で改善」「解消されました」が残っていないことを `grep` で確認する。
- 用語ガードと同じ基準で、「ICカード」単独表記が増えていないこと（既存の許容複合語を除く）。

## 9. スコープ外

- ユーザーマニュアル・開発者ガイドの構成変更。
- スクリーンショットの新規撮影・差し替え。
- 機能の変更。マニュアルが実装と食い違っている箇所を見つけた場合は本 PR で直さず Issue を起票する。
