## 1. 目的と背景

**目的は、PR を出してからマージできる状態（CI がすべて緑）になるまでの待ちを短くすること**（ユーザーの言葉）。main への push の所要時間は主目的ではない。

## 2. ゴール・非ゴール・アンチゴール

**ゴール**
- PR の CI の壁時計（最後のジョブが終わるまで）を短くする。見込みは 1 回あたり **約 70〜90 秒**（現状 約 310〜400 → 約 240 秒）。根拠は §6
- Release と Debug の両方でテストする（#2099）。テストの件数・中身は変えない
- カバレッジ（Release、行・分岐）を、分割前と**同じ値**でジョブのサマリーへ出し続ける。閾値で合否を決めない方針（#2117）も変えない

**非ゴール**
- 遅いテスト自体を速くすること（待機の短縮などはテストの挙動変更であり、別途ユーザーの承認が要る）
- 有料の大きなランナー、変更箇所に応じたテストの絞り込み
- release.yml・test-count-sync-check.yml のテスト実行の分割

**アンチゴール（これが起きたら、技術的に動いていても失敗）**
- **テストが黙って実行されなくなること**（ユーザーがいちばん避けたいと明言した失敗）。分割のフィルタの隙間に落ちたテスト、0 件にマッチして緑で終わるシャード、後から足した名前空間が誰にも拾われない、などの形を含む
- カバレッジの数字が分割の影響で黙って下がる、または消える
- 規約テスト（`CiWorkflowConventionTests`）の検査を弱めて通すこと

## 3. 決めたこと（ユーザーは「お任せ」。以下はすべて実装者＝私の判断）

### 3.1 分割の単位と数 — 2 分割、`Services` 名前空間とその補集合

- build-and-test の matrix に `shard` 軸を足し、`configuration`（Release / Debug）× `shard`（2 つ）の 4 ジョブにする
- シャードの定義は **1 つの値（名前空間の接頭辞 `ICCardManager.Tests.Services.`）だけ**から作る:
  - シャード A: `Category!=UI&FullyQualifiedName~ICCardManager.Tests.Services.`
  - シャード B: `Category!=UI&FullyQualifiedName!~ICCardManager.Tests.Services.`
- **B は A の否定として書く**。これにより、後から足した名前空間・テストは必ずどちらかに入る（列挙した名前空間の和で書く形は、列挙漏れが「黙って実行されない」に直結するので採らない）
- 接頭辞は末尾の `.` まで含める（`ServicesX` のような別名前空間を誤って含めないため）
- 3 分割以上にしない理由: 最長のクラス（約 70 秒）が直列の下限になり、2 分割で既にテスト時間が下限に近づく。ランナーの同時実行数（無料枠は全体で 20）も、複数の PR を同時に開く運用では余裕が減る

### 3.2 ビルドはシャードごとに行う

- 1 回ビルドして成果物を各シャードへ配る形は採らない。Windows ではアップロード・ダウンロードに時間がかかり、ビルドジョブ → テストジョブの直列化でセットアップ（約 25 秒）を二重に払うため、各シャードでビルドし直すのと大差がなく、構成が複雑になる
- ビルドのコマンド（Release の PDB 生成の式を含む）は現行のまま

### 3.3 件数の検算 — 「全件がちょうど 1 回ずつ実行された」ことを CI で確かめる

アンチゴールを防ぐ柱。フィルタの構造（§3.1）が正しくても、検算を別に持つ。

- **正解（期待する全件）**: 本体のテストプロジェクトに対する `dotnet test --list-tests` の出力（構成ごと）。`--list-tests` はフィルタを無視して全件を列挙する（既知の挙動）。本体のテストプロジェクトには `Category=UI` / `Screenshot` のテストが 0 件なので、全件 = 実行すべき件数になる
  - 将来本体に `Category=UI` のテストが足されると、検算は「期待したのに実行されていない」で**失敗する**（黙って通るのではなく、大きな声で止まる側に倒れる）。そのときは検算から `Category=UI` を除く対応を入れる（エラーメッセージでその旨を案内する）
- **実行されたもの**: 各シャードの `dotnet test` に trx ロガーを付け、trx に記録されたテスト（成功・失敗・スキップのすべて）の表示名を集める
- **照合の単位**: 表示名から、理論テストの引数部分（末尾の `(名前: 値, …)`）を取り除いたもの。`--list-tests` は直列化できないデータの理論テストを 1 行にまとめて列挙し、実行時は引数ごとに展開するため、引数込みの名前では一致しない。`DisplayName` を指定したテストが 31 件あるので、クラス名やメソッド名ではなく表示名で照合する
- **判定は「名前の集合」の一致で行う**（実装者の判断）。件数（多重集合）は照合しない。フィルタは FQN（クラス・メソッド）単位で効くので、1 つのメソッドの理論の行の一部だけが落ちることは起きない。したがって欠落は必ず「名前が丸ごと無い」形で現れ、集合の比較で検出できる。理論の展開後の件数には正解が無い（`--list-tests` は直列化できないデータを展開しない）ため、件数の照合は誤検出の元になる
- **表示名の一意性を規約テストで固定する**（実装者の判断）。引数を除いた表示名が 2 つの異なるテストメソッドで同じだと、片方が落ちても集合の比較では見えない。テストアセンブリを反射で走査し、`DisplayName` を含めた「引数を除いた表示名」が全メソッドで一意であることを表明する規約テストを足す（現時点で衝突があれば、それも実装の中で解消する）
- **判定（構成ごと）**: ① 全シャードの和 = 正解、② シャード間に重なりが無い、③ 各シャードが 1 件以上。いずれかが崩れたら `::error::` で、欠けた／重複した名前（先頭の数十件）と件数を出して**失敗**させる
- **サマリーに出す件数**: 照合した名前の数（集合の大きさ）と、trx に記録された実行件数（理論の展開後。現行ログの「Total tests」に相当）の両方を、何を数えたかが分かる見出しで出す
- 照合のロジックは `run:` に直書きせず **PowerShell のスクリプトファイル**にし、単体テスト（既知の入力で、欠落・重複・空・理論の展開・`DisplayName` を検出できること）を置く。#1786「検査ロジック自体を既知のサンプル入力で固定する」に従う

### 3.4 カバレッジ — シャードの結果を正確に合算する

- 収集は従来どおり Release だけ。各 Release シャードで収集する
- `coverlet.runsettings` の `Format` に **json** を加える（cobertura は残す。手元での利用のため）
- 合算は coverlet の json を使い、**数え方は coverlet の cobertura と同じ定義に合わせる**（実装者の判断。分割前と同じ数字を出すことがゴールのため）。coverlet は行・分岐を**メソッドごと**に数え上げる（フィールド初期化子のように、同じ行がコンストラクタごとに別のメソッドとして計上されることがある）。したがってキーは:
  - 行: （モジュール・ファイル・クラス・メソッド・行番号）。ヒット数をシャード間で足す
  - 分岐: （モジュール・ファイル・クラス・メソッド・行・Offset・EndOffset・Path・Ordinal）。ヒット数を足す
  - そのうえで行カバレッジ = ヒットした行のキーの数 / 行のキーの総数、分岐カバレッジ = 同様。ファイル・行番号だけで重複を除く数え方はしない（値が分割前と変わる）
- **シャード間でキーの集合が一致することを確かめる**（実装者の判断）。各シャードは同じソースから別々にビルドするので、計装の対象（行・分岐のキー）は同じになるはず（SDK 既定の決定論的ビルド。csproj で `Deterministic` は無効にしていない）。キーの集合が食い違ったら、合算値は信用できないので `::warning::` で知らせ、合算値に「シャード間で計装が一致しない」と注記する（閾値で合否を決めない方針に合わせ、失敗にはしない）
  - cobertura（行ごとの「50% (1/2)」）を足し合わせる形は採らない。分岐の和集合が正確に出ないため
  - 外部ツール（ReportGenerator など）は使わない。新しい外部依存をサプライチェーンに足さず、照合と同じスクリプトの流儀で持てるため
- **合算の正しさの受け入れ基準**: 1 回分（分割しない実行）の json を合算スクリプトに通した値が、同じ実行の cobertura の `line-rate` / `branch-rate` と一致すること（手元で実測し、PR に記録する）。あわせて、分割後の合算値が分割前の main の値（直近では行 61.7%・分岐 60.9%）と一致すること（テストの追加分の差は説明できること）
- 報告は合算した値をジョブのサマリーへ出す。閾値で合否を決めない（#2117）。結果が見つからない・対象行が 0 のときの警告（現行の Report coverage と同じ趣旨）は残す

### 3.5 集約ジョブ

- 新しいジョブ（仮名 `test-summary`）を置き、全シャード（「正解の一覧」は `services` シャードが作る。§3.6）の完了を待って（`needs:`）、§3.3 の照合と §3.4 の合算・報告を行う
- シャードは trx（またはそこから抜き出した名前の一覧）とカバレッジの json を artifact として上げる。集約ジョブはそれを下ろす。`actions/upload-artifact` / `actions/download-artifact` を新たに使い、全ワークフロー共通の規約どおり commit SHA で固定し、版数のコメントを付ける
- 集約ジョブはシャードが失敗しても動かす（`if: always()` 相当）。ただしシャードのテスト失敗を集約ジョブが成功で覆い隠さないこと（シャード自体は失敗として残る。集約ジョブの照合は、失敗したテストも「実行された」として数える）
- 実行環境は ubuntu-latest と pwsh 7 を想定する（.NET もビルドも不要で起動が速い）。スクリプトは **pwsh 7 専用**とし、単体テストは `pwsh.exe` を起動して検証する（開発機には `C:\Program Files\PowerShell\7\pwsh.exe` があり、windows-latest のランナーにもある）。Windows PowerShell 5.1 は対象にしない（`ConvertFrom-Json` が数 MB 級のカバレッジの json で制約に当たり得るため。実装者の判断）。テストが `pwsh.exe` を見つけられない環境ではスキップではなく失敗させる（黙って検査が外れないため）
- **ゲートとしての扱い**: main のルールセット（Protect main branch）は削除と強制 push の禁止だけで、**必須のステータスチェックは無い**（2026-11-02 に確認）。したがってジョブ名が変わってもマージは止まらない。一方、集約ジョブの照合が赤でもマージ自体はできる — ただしこれは現状のすべてのジョブ（テストの失敗を含む）と同じで、運用（チェックがすべて緑であることを見てマージする）で担保している。必須チェックの導入はリポジトリ設定の変更であり、この設計の範囲外（ユーザーの判断事項として提示する）

### 3.6 「正解の一覧」を作る場所 — `services` シャードの中で作る（実装開始時に改訂）

- build-and-test の `services` シャード（2 つのうち軽い方。模擬で 79 秒 対 85 秒）で、テストの実行の後に `dotnet test <本体の csproj> --no-build --configuration ${{ matrix.configuration }} --list-tests` を実行し、一覧をそのシャードの artifact に含めて上げる。ビルドを足さずに済み、ランナーも増えない。クリティカルパスへの影響は数秒〜十数秒
- **当初案（警告ゼロのビルドのジョブに相乗り）を採らなかった理由**: そのジョブは Release と Debug を pwsh のループで回すため、既存の規約テスト「テストは Release と Debug の両方の構成で実行されること」（`dotnet test` を含むジョブは matrix の `configuration` で構成を選ぶこと）に反する。既存テストの期待を変えるにはユーザーの承認が要るので、既存の規約をすべて満たす配置を選んだ（実装者の判断。2026-11-02）

### 3.7 code-quality を 2 つのジョブに分ける

- シャード化すると、code-quality（約 240〜250 秒）が PR の最後に終わるジョブになり、効果の大半を食う
- 「整形の検査」（約 25＋94 秒）と「警告ゼロのビルド」（約 25＋106 秒）の 2 ジョブに分けて並列に動かす。**各ステップの中身は変えない**（整形の検査の `run:` は許可形のまま、警告ゼロの検証スクリプトもそのまま）
- 重複ビルドの解消（監査の #3）や整形の検査の短縮（#2）はこの設計の範囲外

### 3.8 UITests の GUI 不要のテスト

- 現行の「Run GUI-free tests in UITests project」ステップ（約 3 秒、42 件）は**各シャードでそのまま実行する**（同じテストが構成ごとに 2 回走る）
- シャードで分けない理由: このステップに `if:` を付けると規約テスト（直接実行のステップに `if:` を付けると片方の構成が素通りし得る）に反し、フィルタで分けると片方のシャードが 0 件にマッチして終わる形を新たに作るため。重複は約 3 秒で、欠落の危険を増やさない側を選ぶ
- 件数の検算（§3.3）の対象は本体のテストプロジェクトに限る。UITests の GUI 不要のテストは各シャードで全件が走るので、欠落の問題は生じない

## 4. 変えないこと（制約）

- `concurrency`（PR #2395）、SDK の条件付き導入、NuGet キャッシュ、`--locked-mode`、`--no-restore` / `--no-build`、`--blame-hang-timeout`、`timeout-minutes`、`permissions: contents: read`、アクションの SHA 固定
- `run:` の中では `matrix` / `strategy` / `runner` 以外の式を展開しない（開発者ガイド §5.9。シャードの接頭辞は matrix の値として持つか、ワークフローのファイルに固定した `env:` から環境変数で読む）
- `strategy:` の定義に式を書かない
- `fail-fast: false` を保つ（1 つのシャードの失敗で他を止めない）

## 5. 規約テストへの影響（ユーザーの承認が必要な点）

既存のテストの期待を変えるものは、**業務の言葉で「CI の動きがどう変わるか」**として PR 前に提示し、承認を得てから直す（プロジェクトの運用）。現時点で見えているもの:

| 既存の検査 | 何が変わるか |
|---|---|
| カバレッジの報告は収集と同じ構成と場所を読み、合否を決めないこと | 報告が「Release のテストジョブの中」から「全シャードの後の集約ジョブ」へ移る。読む場所が「その場の coverage フォルダ」から「各シャードから集めた結果」になる。合否を決めない点は変えない |
| カバレッジの収集は Release に限ること | 変えない見込み（収集のフラグの書き方は維持） |
| テストは Release と Debug の両方で実行されること | 変えない見込み（matrix に軸が 1 つ増えるだけ。読み取りが新しい matrix の形を読めることを確かめる） |
| ビルド警告ゼロ検証は Release と Debug の両方で行われること | 変えない見込み（ステップはジョブを移るだけ） |

**新たに足す検査**（承認は不要だが、検出力を変異で実測して PR に記録する）:
- シャードのフィルタが 1 つの接頭辞から「肯定」と「否定」で作られていること（片方を列挙に書き換える・接頭辞を食い違わせると赤）
- 集約ジョブが全シャードを `needs:` に持ち、照合と合算のスクリプトを実行していること
- §3.3・§3.4 のスクリプトの単体テスト（カバレッジの合算は、同じ行が複数のメソッドに計上される入力・シャード間でキーが食い違う入力を含める）
- 引数を除いた表示名がテストメソッド間で一意であること（§3.3）

テストの件数が変わるので、07_テスト設計書の件数（§1.1a・§2 のクラス別の行・§8.1）と `CiWorkflowConventionTests` の行を同じ PR で更新する。件数は Release 構成の `--list-tests` で実測する。

## 6. 効果の見込み（根拠）

- 各シャード: セットアップ約 25 ＋ ビルド 35〜60 ＋ テスト約 110〜130（現状のテスト 205〜225 秒を、所要時間の配分が半々の 2 つへ。固定の探索・起動約 20 秒は各シャードで払う）＋ アップロード数秒 ≒ **約 180〜215 秒**
- 集約ジョブ: 待機・起動・ダウンロード・照合で 約 20〜30 秒
- 整形の検査のジョブ 約 120 秒、警告ゼロ＋一覧のジョブ 約 150〜170 秒（いずれも集約ジョブの完了より前に終わる）
- PR の CI の壁時計: 現状 約 310〜400 秒 → **約 210〜245 秒**。テストの実行時間は回ごとに ±20 秒ほどばらつく
- ランナー時間（無料）は増える（シャードごとのセットアップ・ビルドの重複と、集約ジョブ）

## 7. 実装者に任せること

- 集約ジョブ・スクリプトの名前と置き場所（`ICCardManager/tools/` か `tools/` かは、既存のスクリプトとテストの置き方に合わせる）
- artifact の名前・保持日数（短くてよい）
- trx から名前を抜く方法（trx をそのまま上げるか、シャード内で一覧にしてから上げるか）
- エラーメッセージの文面（3 要素「何が／なぜ／どうすれば」を満たすこと）
- ドキュメントの更新箇所: 00a_技術スタック用語集の ci.yml の行、開発者ガイドの CI の記述、CHANGELOG（Unreleased の「開発基盤」）、07_テスト設計書

## 8. 受け入れ基準

1. PR の CI で、Release・Debug それぞれの 2 シャードと集約ジョブが緑になり、集約ジョブのサマリーに「全 N 件がちょうど 1 回ずつ実行された」とカバレッジが出る
2. 変異検査: シャードの片方のフィルタを列挙に書き換えて 1 名前空間を落とす／接頭辞を片方だけ変える、の各変更で、規約テストと集約ジョブの照合の**両方**が赤になる（照合はスクリプトの単体テストで再現する）
3. カバレッジの合算値が、分割しない実行の cobertura の値と一致する（§3.4）
4. PR の CI の壁時計を 2 回以上実測し、§6 の見込みと比べた結果を PR に記録する
5. Release / Debug のソリューションのビルドで警告 0、`dotnet format --verify-no-changes` が通る
