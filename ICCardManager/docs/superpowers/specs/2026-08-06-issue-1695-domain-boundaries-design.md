# Issue #1695 設計方針: シェア物品管理への横展開を見据えた設計境界の保全

作成日: 2026-08-06
対象 Issue: #1695（【Phase3・中長期】シェア物品管理への横展開を見据えた設計境界の保全）
実装範囲: **設計方針の文書化のみ**（汎用化そのものは行わない）

---

## 1. 背景と目的

本システムのコア（タッチ認証 → 貸出/返却 → 出納簿）は、「複数職員でシェアする物品の出納管理」として交通系ICカード以外（社用携帯・鍵・公用車両等）にも通用する構造を持つ。

一方で、交通系固有ロジック（摘要生成・バス判別・駅マスター・残高読取）がどこまでコアに食い込んでいるかは、これまで**どこにも書かれていなかった**。書かれていないため、改修のたびに「この処理をどこに置くべきか」を各自が判断しており、固有知識が汎用コアへ静かに染み出すリスクがある。

本 Issue のゴールは**汎用化ではなく、境界の可視化と保全**である。「官公庁向けシェア物品出納管理（オフライン対応）」という横展開の選択肢を、低コストで温存する。

### 非ゴール（YAGNI）

- 交通系固有ロジックの抽象化・インターフェース抽出は**行わない**
- `ic_card` テーブルのリネーム・汎用化は**行わない**
- プラグイン機構・設定による業務ドメイン切替は**行わない**

本格実施は具体的な横展開ニーズが顕在化してから。それまでは「境界を意識する」レベルに留める。

---

## 2. 事前調査で判明した実態

設計を書く前にコードを調査し、当初の想定と異なる点が3つ見つかった。境界モデルはこの実態に合わせて組み直している。

### 2.1 駅マスターと FeliCa デコーダは既に完全に閉じている

| 型 | 参照元 |
|---|---|
| `FelicaHistoryBlockDecoder` | `Infrastructure/CardReader/FelicaCardReader.cs` のみ |
| `IStationMasterService` / `StationMasterService` | `Infrastructure/CardReader/FelicaCardReader.cs` と `App.xaml.cs`（DI 登録）のみ |

駅名解決は「カード生データを読み取った直後に駅名文字列へ変換する」処理として `Infrastructure` 層に閉じており、`Services` / `ViewModels` は駅名を**ただの文字列**としてしか扱っていない。差替コストは想定より低い。

### 2.2 `SummaryGenerator` は境界をまたいでいる

`SummaryGenerator` は 1 クラスの中に 2 種類の責務を同居させている。

| 種別 | 例 |
|---|---|
| 汎用（物品出納簿の様式そのもの） | `GetLendingSummary`（貸出中）/ 繰越各種 / `GetMonthlySummary`（月計）/ `GetCumulativeSummary`（累計）/ チャージ / 払戻し |
| 交通系固有 | 駅名からの摘要組み立て（「鉄道（A駅～B駅）」）/ バス混在表記 / 往復・乗継・循環判定 / 残高不足パターン検出 |

したがって「クラス単位で固有/汎用を分類する」素朴なモデルはここで破綻する。境界はクラス境界ではなく**メソッド境界**を通る。

### 2.3 永続化層は既にクリーン

`Data/` 配下から交通系ロジックへの実コード参照は**ゼロ**（`LedgerRepository.cs:635` の `SummaryGenerator` 言及はコメント）。`Models/` からの実参照も `Ledger.cs` の `IsMidYearCarryoverSummary` 1 件のみで、これは繰越判定＝汎用概念。

## 3. 境界モデル: 3 リング

レイヤー（Presentation / Business / Data / Infrastructure）と**直交する縦串**として、3 つのリングを定義する。

```
┌──────────────────────────────────────────────┐
│ 外側リング: 交通系固有                         │
│   駅名摘要の組み立て / バス判別 /              │
│   往復・乗継・循環判定 / 残高不足パターン検出 / │
│   StationMasterService / FelicaHistoryBlockDecoder │
│  ┌────────────────────────────────────────┐  │
│  │ 中間リング: 交通系アダプタ               │  │
│  │   ICardReader 実装 / CardType /          │  │
│  │   LedgerDetail（乗車駅・降車駅・バス停）/ │  │
│  │   残高読取                                │  │
│  │  ┌──────────────────────────────────┐  │  │
│  │  │ 中心: 汎用コア                     │  │  │
│  │  │  staff / 貸出返却状態遷移 /        │  │  │
│  │  │  30秒ルール / 職員認証 /           │  │  │
│  │  │  ledger（受入・払出・残額）/       │  │  │
│  │  │  繰越・月計・累計 / 操作ログ /     │  │  │
│  │  │  バックアップ / 帳票骨格            │  │  │
│  │  └──────────────────────────────────┘  │  │
│  └────────────────────────────────────────┘  │
└──────────────────────────────────────────────┘
```

### リングの定義

| リング | 定義 | 横展開時の扱い |
|---|---|---|
| **中心（汎用コア）** | 「シェア物品の出納管理」として、交通系ICカードでなくても意味が通る概念 | そのまま流用 |
| **中間（交通系アダプタ）** | 汎用概念を交通系ICカードという具体物へ結びつけている層。名前と型は固有だが、構造は汎用 | 対象物品に合わせて読み替え・差替 |
| **外側（交通系固有）** | 交通系ICカードにしか存在しない概念。他の物品では等価物がない | 不要化、または対象物品固有の実装へ置換 |

### 唯一のルール

> **内側のリングに、外側リングの知識を持ち込まない。**

具体的には、汎用コアのコード（`LendingService` の状態遷移、`ledger` の集計、帳票骨格）に「駅」「バス」「チャージ」「IDm」といった交通系語彙の**分岐**を新設しない。必要なら外側リングに置いて、コアからは抽象的な値（摘要文字列・金額）としてだけ受け取る。

## 4. seam カタログ（拡張点一覧）

横展開時に差し替えることになる接続点と、その現在の抽象度。

| # | 拡張点 | 現在の実装 | 抽象度 | 差替コスト | 備考 |
|---|---|---|---|---|---|
| 1 | 物品の識別手段 | `FelicaCardReader` / `HybridCardReader` / `MockCardReader` | `ICardReader` で抽象済み | **低** | `CardReadEventArgs.Idm` は `string`。バーコード・QR・手動入力を別実装として DI 差替可能 |
| 2 | 利用履歴の読取 | `FelicaHistoryBlockDecoder` | `Infrastructure/CardReader` 内に閉じている | **低** | 物品によっては履歴読取自体が不要（手入力運用）。`ICardReader.TryReadHistoryAsync` が空リストを返せば成立する |
| 3 | 駅コード→駅名解決 | `StationMasterService`（CSV マスター） | `IStationMasterService` あり、参照元 2 箇所のみ | **低** | 交通系以外では不要化。DI 登録を外すだけで済む形を保つ |
| 4 | 摘要文字列生成 | `SummaryGenerator`（static クラス） | インターフェースなし・22 ファイルから直接呼び出し | **中** | 汎用メソッドと固有メソッドが同居（§2.2）。横展開時は固有メソッド群のみ抽出する |
| 5 | 利用内訳の項目 | `LedgerDetail`（`EntryStation` / `ExitStation` / `BusStops` / `IsBus`） | 固有列がモデルに直接生えている | **中** | 列名は交通系語彙だが構造は「1 回の利用の内訳」。物品に応じた読み替えで対応可能 |
| 6 | 物品マスター | `ic_card` テーブル / `IcCard` モデル | 交通系固有列は `card_type` のみ | **低** | 他の列（`is_lent` / `last_lent_at` / 繰越累計）はすべて汎用。`card_type` は物品種別として読み替え可能 |
| 7 | 残高の概念 | `ledger.balance` / `LedgerDetail.Balance` | 汎用（物品出納簿の「残額」） | **低** | 交通系固有ではない。鍵・車両なら残数、備品なら在庫数として同じ様式が成立する |

### 差替コストの読み方

- **低** = インターフェースがあり参照元が限定されている。DI 登録の差替、または削除で済む
- **中** = 抽象化されていないか参照元が多い。まとまった作業になるが、コアの構造変更は不要

「高」に相当する項目は現時点で存在しない。**この状態を維持することが本 Issue の目的**であり、新しい拡張点を「高」で作らないことが改修時の判断基準になる。

## 6. 規約テストの設計

### 6.1 何を固定し、何を固定しないか

**固定する（すべて現状 green）:**

1. `FelicaHistoryBlockDecoder` の参照元は `Infrastructure/CardReader/` 配下のみ
2. `IStationMasterService` / `StationMasterService` の参照元は `Infrastructure/CardReader/` と DI 登録（`App.xaml.cs`）のみ
3. `Data/` 配下に交通系固有の**判断ロジック**（`SummaryGenerator` / `StationMasterService` / `FelicaHistoryBlockDecoder` / `DetermineIsBusUsage`）への実コード参照がない
4. 上記 3 件の走査が実際に本番ソースを covering していること（走査件数と、検査対象記号が境界内に実在すること）

**固定しない:**

- `SummaryGenerator` 全体の参照制限 — 22 ファイルから使われており、汎用メソッド（繰越・月計・累計・貸出中）の利用は正当。ここを縛ると正しいコードが落ちる
- `LedgerDetail` の駅フィールドの参照制限 — 帳票・CSV・履歴編集画面からの利用が正当
- **`Data/` からの `EntryStation` / `ExitStation` / `BusStops` / `IsBus` 参照** — 当初の案では #3 の禁止語に含めていたが、実装時に `LedgerRepository` がこれらを DB 列へマッピングしていることが判明し、**設計を修正した**。永続化層が固有列を読み書きするのは正当な責務であり境界違反ではない。禁止すべきは「データの**形**」ではなく「データの**解釈**」

> 検査 #4 を追加したのは、パス解決が壊れると走査対象ゼロで #1〜#3 が無条件 green になるため（`.claude/rules/testing.md`「通るが目的を果たさないテスト」）。走査件数と、検査対象記号が境界内に実在することを併せて表明する。

### 6.2 実装方式

`UserFacingTextConventionTests` / `ToastPositionCommentConventionTests` と同じ **ソースファイルのテキスト静的検査** とする。Reflection によるアセンブリ依存解析ではなくテキスト検査を選ぶ理由:

- 既存の規約テスト群と実装方式が揃い、読む人が方式を学び直さなくて済む
- 違反箇所をファイル名・行番号で指摘でき、エラーメッセージが具体的になる
- コンパイル後には消えるコメントを除外できる（§2.3 のとおり、コメント言及と実コード参照を区別する必要がある）

### 6.3 コメント除外の方針

`Data/` の検査では実コード参照のみを対象とする。行頭が `//` または `///` の行、および `/* */` ブロック内はスキップする。`LedgerRepository.cs:635` のような**規約の理由を説明したコメント**を違反として検出してしまうため（`.claude/rules/development-conventions.md` の「禁止された要素の不在を検査するときは要素タグで照合する」と同じ落とし穴）。

### 6.4 失敗時のメッセージ

境界を越えた変更が**常に誤り**とは限らない。テストが落ちたときに開発者が取れる選択肢を明示する:

> `FelicaHistoryBlockDecoder` が Infrastructure/CardReader の外から参照されています（<file>:<line>）。
> FeliCa の生データ解釈は交通系固有ロジックであり、Infrastructure/CardReader に閉じる設計です（Issue #1695）。
> 意図的に境界を変更する場合は、docs/design/05_クラス設計書.md §2a の seam カタログを更新したうえで本テストを修正してください。

## 7. 影響範囲

コード（`src/`）への変更は**なし**。設計書・規約・テストの追加のみ。

したがって動作上のリグレッションリスクはなく、既存テストへの影響もない（新規テストクラス 1 件の追加のみ）。

## 8. 想定される反論と回答

**「早すぎる抽象化では？」**
抽象化は行わない。既に存在する境界を記述し、テストで現状を固定するだけ。新しいインターフェースも設定項目も増えない。

**「テストで縛ると将来の正当な設計変更が妨げられるのでは？」**
§6.4 のとおり、失敗メッセージに「seam カタログを更新したうえでテストを修正する」経路を明示する。テストは禁止ではなく**気づきの装置**として置く。

**「横展開しないなら無駄では？」**
境界の明示はテスタビリティ・保守性に直接効く。実際、本調査で「駅マスターが Infrastructure に閉じている」ことが判明したのは今回が初めてであり、この情報自体が今後の改修判断に使える。
