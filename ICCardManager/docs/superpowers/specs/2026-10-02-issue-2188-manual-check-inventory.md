# Issue #2188 棚卸し: 画面操作が必要な手動確認を、自動化できるものと人が要るものに分ける

- 作成日: 2026-10-02
- 対象 Issue: #2188
- 対象: `docs/design/07_テスト設計書.md` のうち「手動確認」「手動検証」「実機」に触れる記述（63 か所。うち実際に人の手を要する項目を下表へ整理した）

## 1. 目的

PR の手動確認手順（画面操作を伴うもの）は、毎回人が Windows 実機で行っている。手動として残った理由の多くは「STA の `Window` を xUnit から作れない」「仮想タッチは再現できない」だったが、

- FlaUI（`tests/ICCardManager.UITests`）は**別プロセスで起動した本物のアプリ**を操作するので、STA の制約を受けない
- Debug 構成では、デバッグパネルの仮想タッチを FlaUI から駆動して、貸出・返却・バス停名入力・同行者数入力まで操作できる（`TouchScreenshotTests`、ST-006b / ST-006c）

ため、手動確認の大半は置き換えられる見込みがある。本書は置き換えの対象と順序を決める。方針は `.claude/rules/testing.md`「手動確認をお願いする前に、成果物そのものを検証できないか検討する（Issue #1728）」の UI 版である。

## 2. 分類の基準

| 分類 | 手段 | 何を判定するか |
|---|---|---|
| **A** | FlaUI の UI テスト | **状態**: `IsEnabled`・座標（`BoundingRectangle`）・`FocusedElement`・ウィンドウの有無・UIA イベントで通知された内容・DB に書かれた値 |
| **B** | 撮影（`ScreenshotHelper`）した PNG を Claude が読んで判定 | **見た目**: はみ出し・重なり・色・描画の崩れ。幾何的に判定できるものは A と併用する |
| **C** | 人・実機環境 | 主観（聞きやすさ）・音・物理操作・ネットワーク・OS のセッション |

優先度: ◎ 既存の PageObject・仮想タッチで小さく作れて効果が大きい ／ ○ 作れる ／ △ 作れるが結果が揺れやすい・前提の調査が要る

## 6. 「UI テストを実行すること」自体が手動になっているもの

2.59（撮影スクリプトの `-Changed`）と 2.60（`StaffAuthDialogLiveRegionTests` の実機実行）は、自動テストはあるが**Windows デスクトップで誰かが実行しなければ走らない**項目である。UI テストは CI で走らない（`Category=UI` を除外、UITests の csproj はソリューション単位の実行から外れている）。

- PR を作る側（Claude）が WSL から `"/mnt/c/Program Files/dotnet/dotnet.exe" test ICCardManager/tests/ICCardManager.UITests/ICCardManager.UITests.csproj --filter Category=UI` を実行し、結果を PR 本文に書く。WSL から起動した `dotnet.exe` が Windows のデスクトップセッションで GUI を操作できることは 2026-10-02 に実測で確かめた（`AppLaunchTests` 6 件成功・18 秒。開発機の DB は `UiTestDatabaseGuard` が元に戻した）。テストは `dotnet run --no-build` でアプリを起動するため、UITests に加えて本体も同じ構成でビルドしておく
- 定期実行（`/loop`・スケジュール）は、上が成立してから検討する
