## 2a. 交通系固有ロジックの境界（Issue #1695）

### 2a.1 なぜこの節があるか

本システムのコア（タッチ認証 → 貸出/返却 → 出納簿）は、「複数職員でシェアする物品の出納管理」として交通系ICカード以外（社用携帯・鍵・公用車両等）にも通用する構造を持つ。

**現時点で汎用化する予定はない。** ただし交通系固有の知識がコアへ静かに染み出すと、将来その選択肢を取り戻すのに大規模改修が必要になる。この節は「どこまでが交通系固有か」を記述して、改修時の判断材料を残すためにある。

前節（§2 レイヤー構成図）が Presentation / Business / Data / Infrastructure の**横方向の層**を示すのに対し、本節の境界はそれと**直交する縦串**である。交通系固有性は特定の層に集まっておらず、`Infrastructure`（FeliCa 読取）・`Services`（摘要生成）・`Models`（乗車駅・降車駅）の 3 層すべてに分散している。

改修時の判断基準は `.claude/rules/domain-boundaries.md` を参照。

### 2a.2 3 リング境界モデル

| リング | 定義 | 横展開時の扱い |
|--------|------|----------------|
| **中心（汎用コア）** | 「シェア物品の出納管理」として、交通系ICカードでなくても意味が通る概念 | そのまま流用 |
| **中間（交通系アダプタ）** | 汎用概念を交通系ICカードという具体物へ結びつけている層。名前と型は固有だが、構造は汎用 | 対象物品に合わせて読み替え・差替 |
| **外側（交通系固有）** | 交通系ICカードにしか存在しない概念 | 不要化、または対象物品固有の実装へ置換 |

**唯一のルール: 内側のリングに、外側リングの知識を持ち込まない。**

汎用コアのコード（`LendingService` の状態遷移、`ledger` の集計、帳票骨格）に「駅」「バス」「チャージ」といった交通系語彙の**分岐**を新設しない。必要なら外側リングに置き、コアからは抽象的な値（摘要文字列・金額）としてだけ受け取る。

### 2a.3 境界はクラス境界ではなくメソッド境界を通る（`SummaryGenerator`）

`SummaryGenerator` は 1 クラスの中に 2 種類の責務を同居させており、**クラス単位で固有/汎用を分類する素朴なモデルはここで破綻する**。

| 種別 | メソッド例 |
|------|-----------|
| 汎用（物品出納簿の様式そのもの） | `GetLendingSummary`（貸出中）/ 繰越各種（`GetCarryoverFromPreviousYearSummary` 等）/ `GetMonthlySummary`（月計）/ `GetCumulativeSummary`（累計）/ `GetChargeSummary` / `GetRefundSummary` |
| 交通系固有 | 駅名からの摘要組み立て / バス混在表記 / 往復・乗継・循環判定 / `GetInsufficientBalanceNote`（残高不足） |

このため `SummaryGenerator` 全体への参照制限は規約テストで**かけていない**（§2a.5）。汎用メソッドは 22 ファイルから正当に使われている。

### 2a.4 seam カタログ（横展開時の拡張点）

「もし横展開するなら差し替えることになる接続点」と、その現在の抽象度。**差替コスト「高」の項目を新設しないこと**が改修時の判断基準になる。

| # | 拡張点 | 現在の実装 | 抽象度 | 差替コスト | 備考 |
|---|--------|-----------|--------|-----------|------|
| 1 | 物品の識別手段 | `FelicaCardReader` / `HybridCardReader` / `MockCardReader` | `ICardReader` で抽象済み | **低** | `CardReadEventArgs.Idm` は `string`。バーコード・QR・手動入力を別実装として DI 差替可能 |
| 2 | 利用履歴の読取 | `FelicaHistoryBlockDecoder` | `Infrastructure/CardReader` 内に閉じている | **低** | 物品によっては履歴読取自体が不要（手入力運用）。`ICardReader.TryReadHistoryAsync` が空リストを返せば成立する |
| 3 | 駅コード→駅名解決 | `StationMasterService`（CSV マスター） | `IStationMasterService` あり、参照元は `FelicaCardReader` と DI 登録の 2 箇所のみ | **低** | 交通系以外では不要化。DI 登録を外すだけで済む形を保つ |
| 4 | 摘要文字列生成 | `SummaryGenerator`（static クラス） | インターフェースなし・22 ファイルから直接呼び出し | **中** | 汎用メソッドと固有メソッドが同居（§2a.3）。横展開時は固有メソッド群のみ抽出する |
| 5 | 利用内訳の項目 | `LedgerDetail`（`EntryStation` / `ExitStation` / `BusStops` / `IsBus`） | 固有列がモデルに直接生えている | **中** | 列名は交通系語彙だが構造は「1 回の利用の内訳」。物品に応じた読み替えで対応可能 |
| 6 | 物品マスター | `ic_card` テーブル / `IcCard` モデル | 交通系固有列は `card_type` のみ | **低** | 他の列（`is_lent` / `last_lent_at` / 繰越累計）はすべて汎用。`card_type` は物品種別として読み替え可能 |
| 7 | 残高の概念 | `ledger.balance` / `LedgerDetail.Balance` | 汎用（物品出納簿の「残額」） | **低** | 交通系固有ではない。鍵・車両なら残数、備品なら在庫数として同じ様式が成立する |

差替コストの読み方:

- **低** = インターフェースがあり参照元が限定されている。DI 登録の差替、または削除で済む
- **中** = 抽象化されていないか参照元が多い。まとまった作業になるが、コアの構造変更は不要
- **高** = コアの構造変更を伴う。**現時点では該当なし。この状態を維持することが Issue #1695 の目的**

### 2a.5 規約テストで固定している境界

`DomainBoundaryConventionTests` が以下をソースの静的検査で固定する（いずれも現状 green）。

| # | 検査内容 | 意図 |
|---|----------|------|
| 1 | `FelicaHistoryBlockDecoder` の参照元が `Infrastructure/CardReader/` 配下のみ | FeliCa 生データの解釈が上位層へ漏れない |
| 2 | `IStationMasterService` / `StationMasterService` の参照元が `Infrastructure/CardReader/` と DI 登録（`App.xaml.cs`）のみ | 駅名解決が「読取直後の変換」に留まり、`Services` / `ViewModels` は駅名を文字列としてのみ扱う |
| 3 | `Data/` 配下に交通系固有の**判断ロジック**（`SummaryGenerator` / `StationMasterService` / `FelicaHistoryBlockDecoder` / `DetermineIsBusUsage`）への実コード参照がない | 永続化層に交通系知識が入らない |
| 4 | 上記 3 件の走査が実際に本番ソースを covering していること（走査件数と、検査対象記号が境界内に実在すること） | パス解決が壊れると 3 件すべてが無条件 green になるため（`.claude/rules/testing.md`「通るが目的を果たさないテスト」） |

#### 検査対象に含めないもの（重要）

**`EntryStation` / `ExitStation` / `BusStops` / `IsBus` は #3 の禁止語に含めない。** `LedgerRepository` がこれらを DB 列へマッピングするのは永続化の正当な責務であり、境界違反ではない。禁止するのは「データの**形**」ではなく「データの**解釈**」——摘要生成・駅名解決・バス判別といった判断ロジックが `Data/` に入ること。

#### コメントは検査対象外

検査は実コードのみを対象とし、`//` / `///` / `/* */` のコメントは除去してから照合する。`LedgerRepository.cs` には「`SummaryGenerator.GetMidYearCarryoverSummary` の生成結果で検証している」という**規約の理由を説明したコメント**があり、単純な文字列一致ではこれを違反として誤検出するため（`.claude/rules/development-conventions.md` の「禁止された要素の不在を検査するときは要素タグで照合する」と同じ配慮）。

意図的に境界を変更する場合は、本節の seam カタログを更新したうえでテストを修正する。テストは禁止ではなく**気づきの装置**として置いている。

**共有フォルダモード対応:**

- `IsSharedMode`: DBパスが **UNCパス**（`\\server\share\...`）または **マップドネットワークドライブ**（`DriveInfo.DriveType == DriveType.Network`）の場合に `true`。判定は `DbContext.IsSharedModePath(string path)` に一元化されており、ローカルフルパス指定では `false`（Issue #1559 / #1597。「パス設定の有無」だけで判定していた旧実装を是正）。共有フォルダモードかどうかを判定する
- `ConfigurePragmas()`: 接続時に `PRAGMA foreign_keys = ON`、`PRAGMA busy_timeout`（ローカルモード: 5000ms / 共有モード: 15000ms、Issue #1107）を設定。共有モード時は `PRAGMA journal_mode = DELETE` を試行し、失敗時は TRUNCATE → PERSIST の順にフォールバック（`ConfigureJournalMode()`、Issue #1107）
- `ExecuteWithRetry<T>()`: SQLITE_BUSY/SQLITE_LOCKED発生時に指数バックオフでリトライ。ローカルモードは最大3回（100ms → 500ms → 2000ms）、共有モードは最大5回（200ms → 500ms → 1000ms → 2000ms → 5000ms、ジッター付き、Issue #1107）。詳細は [§5.5b](#55b-接続リーストランザクションスコープissue-1243) 参照
- 接続の正常性確認と定期ヘルスチェックは **`DbContext` ではなく `SharedModeMonitor`**（上記クラス一覧参照）が担う。共有フォルダモード時のみ **15秒間隔**（`SharedModeMonitor.HealthCheckIntervalSeconds = 15`、Issue #1493）でタイマーを起動（`Start()` → `ExecuteHealthCheckAsync()`）し、`DbContext.CheckConnection()` で接続を確認、接続断時は自動再接続を試行する。`DbContext` 自身はヘルスチェック用のメソッド（旧記載の `CheckConnectionHealth()` / `StartHealthCheck()`）を持たない
- `CheckConnection()`: 軽量クエリ（`SELECT COUNT(*) FROM sqlite_master`）**かつ** DB ファイルへの実到達（`ProbeDatabaseFileReachable()` → `File.Exists`）の両方が成功したときのみ `true`。**クエリ単独では到達性の証明にならない**（開きっぱなしの接続ではスキーマ情報が SQLite のページキャッシュから応答され、ネットワーク切断後も成功し続ける。Issue #1110 の意図が達成できていなかったことを Issue #1716 で是正）。インメモリDB（`:memory:`）とパス未設定はファイル実体を持たないため到達確認の対象外、接続一時停止中（Issue #1166）は従来どおり `true`。ファイル確認はリース解放後に行い、死んだ UNC パスの SMB タイムアウト中に接続セマフォを占有しない。到達確認は `protected virtual` のテスト継ぎ目（`ConnectionDiagnosticsService.ProbeDatabaseFileReachable` と同じ設計）
- **疎通確認全体の上限時間**（Issue #1716）: 疎通確認は「接続リース取得 → 接続オープン → クエリ → ファイル到達確認」と複数のネットワーク待ちが直列に並び、**どの区間も下位の TCP/SMB タイムアウトまで戻らない**（実機ログでクエリ段階が 82.3 秒、直後の再確認は 3ms / 0ms）。区間ごとに上限を設けても塞ぎ残しが生じるため、確認**全体**を `Task.Run` で実行し `AppConstants.DatabaseConnectionCheckTimeoutSeconds`（10秒。`ConnectionCheckTimeout` で仮想化しテストから短縮可能）以内に完了しなければ「接続なし」とみなす。上限で打ち切っても下位の呼び出しは中断できないため、**進行中の確認は 1 本に限定**し（`_pendingConnectionCheck`）、ブロック済みスレッドの累積と接続セマフォ待ちの行列を防ぐ。失敗時・1秒超過時は段階別の所要時間を `LogInformation` で記録する（`appsettings.json` の既定フィルタが Information のため `LogDebug` は本番のログファイルに残らない）。**UI スレッドから呼ばないこと**（上限までの待機が呼び出しスレッドをブロックする）。詳細は 04_機能設計書 §18.4
- `Vacuum()`: 戻り値を `bool` に変更。共有モードで他PCが接続中の場合はVACUUMが失敗しうるため、失敗時は `false` を返す（例外にしない）
- `InitializeDatabaseAsync()` / `CleanupOldDataAsync()` / `VacuumAsync()` (#1356): `App.OnStartup` など UI スレッドから呼び出すと Issue #1281 の `LeaseConnection()` ガードで例外になるため、`Task.Run` で既存 sync 実装へ委譲する非同期版を提供する。テスト経路（スレッドプール/xUnit）は従来どおり sync 版を直接使用

> **接続リース・トランザクションの正しい使い方**: `DbContext` の接続を借りる際は、`using` 文でリースを取得する `LeaseConnectionAsync()` / `BeginTransactionAsync()` を利用する。詳細は [§5.5b 接続リース・トランザクションスコープ](#55b-接続リーストランザクションスコープissue-1243) を参照。

### 5.5b 接続リース・トランザクションスコープ（Issue #1243）

`DbContext` の接続ライフサイクルとトランザクション境界を型安全に管理する 3 つの RAII 的ラッパクラス。いずれも `Data/DbContext.cs` に定義される `public sealed class` であり、`using` 文での利用を前提としている。

```mermaid
classDiagram
    class ConnectionLease {
        +SQLiteConnection Connection
        -Action _onDispose
        -bool _disposed
        +Dispose() void
    }

    class TransactionScope {
        +ConnectionLease Lease
        +SQLiteTransaction Transaction
        -bool _disposed
        +Commit() void
        +Rollback() void
        +Dispose() void
    }

    class ConnectionSuspensionScope {
        -DbContext _dbContext
        -bool _disposed
        +Dispose() void
    }

    TransactionScope --> ConnectionLease : holds
    TransactionScope --> SQLiteTransaction : holds
    ConnectionSuspensionScope --> DbContext : suspends
```

#### 責務一覧

| クラス | 責務 | 取得元 | 解放契機 |
|--------|------|--------|----------|
| `ConnectionLease` | **接続ライフサイクル管理**: `SQLiteConnection` を貸与し、`Dispose` でセマフォを解放して次の呼び出し者へ譲る | `DbContext.LeaseConnectionAsync()` / `LeaseConnection()` | `using` 文を抜けたとき |
| `TransactionScope` | **トランザクション境界制御**: `ConnectionLease` と `SQLiteTransaction` を束ね、`Dispose` で**トランザクション→リースの順に**解放する | `DbContext.BeginTransactionAsync()` | `using` 文を抜けたとき |
| `ConnectionSuspensionScope` | **接続一時停止制御**: リストア中など接続再オープンを禁止したい期間を RAII 的に表現し、`Dispose` で自動的に解除する（Issue #1166） | `DbContext.SuspendConnections()` | `using` 文を抜けたとき |

#### TransactionScope.Dispose() の自動ロールバック仕様

**重要**: `Commit()` も `Rollback()` も呼ばずに `Dispose` された場合、`SQLiteTransaction.Dispose()` は **未コミットのトランザクションを自動的にロールバック** する。このため、例外経路でも明示的な `Rollback()` 呼び出しは不要である。

```mermaid
sequenceDiagram
    participant Caller
    participant Scope as TransactionScope
    participant Tx as SQLiteTransaction
    participant Lease as ConnectionLease

    Caller->>Scope: using var scope = await BeginTransactionAsync()
    Note over Scope: リース + トランザクションを取得
    Caller->>Scope: （業務処理）
    alt 正常系
        Caller->>Scope: scope.Commit()
        Scope->>Tx: Commit()
    else 例外発生
        Note over Caller: 例外でブロック脱出
        Note over Scope: Commit/Rollback 未呼び出し
    end
    Caller->>Scope: Dispose()（using 脱出）
    Scope->>Tx: Dispose()
    Note over Tx: 未コミットなら自動ロールバック
    Scope->>Lease: Dispose()
    Note over Lease: セマフォを解放
```

この仕様により、典型的な try/catch 定型文を省略できる:

```csharp
// ❌ 冗長（Dispose が自動ロールバックする）
using var scope = await _dbContext.BeginTransactionAsync();
try
{
    // 処理
    scope.Commit();
}
catch
{
    scope.Rollback();
    throw;
}

// ✅ 簡潔（例外時も Dispose が自動ロールバックする）
using var scope = await _dbContext.BeginTransactionAsync();
// 処理
scope.Commit();
// 例外時は Commit() が呼ばれないまま using を抜け、自動ロールバック
```

#### 典型的な使用パターン

**1. 読み取り専用の接続借用（単発クエリ）**

```csharp
using var lease = await _dbContext.LeaseConnectionAsync();
var connection = lease.Connection;

using var command = connection.CreateCommand();
command.CommandText = "SELECT value FROM settings WHERE key = @key";
command.Parameters.AddWithValue("@key", key);
return (string?)await command.ExecuteScalarAsync();
// using 脱出時にリースを解放、セマフォ返却
```

**2. 複数操作を 1 トランザクションで実行（書き込み系の推奨形）**

```csharp
await _dbContext.ExecuteWithRetryAsync(async () =>
{
    using var scope = await _dbContext.BeginTransactionAsync();

    await SetAsync(KeyWarningBalance, settings.WarningBalance.ToString());
    await SetAsync(KeyFontSize, FontSizeToString(settings.FontSize));
    // ...複数のキー更新...

    scope.Commit();
    // 例外発生時は Commit() に到達せず Dispose で自動ロールバック
});
```

`ExecuteWithRetryAsync` と組み合わせることで、`SQLITE_BUSY` / `SQLITE_LOCKED` 発生時に指数バックオフ + ジッター付きでリトライする（共有モードでは最大 5 回）。

**3. 接続の一時停止（リストア中など）**

```csharp
using var suspension = _dbContext.SuspendConnections();
// この間、バックグラウンドタスクからの GetConnectionInternal() は
// InvalidOperationException をスロー（Issue #1166）
await RestoreFromBackupAsync(backupFile);
// using 脱出時に ResumeConnections() が自動呼び出しされる
```

#### 排他制御（内部実装の注意点）

- `BeginTransactionAsync()` は `DbContext._semaphore` を取得する（`SemaphoreSlim(1, 1)`）。トランザクション中は他の書き込み系呼び出しがブロックされる
- `LeaseConnectionAsync()`（非同期版）は現在セマフォを取得しない。同一 `SQLiteConnection` を複数タスクが共有する前提
- `LeaseConnection()`（同期版）はセマフォを取得し、同一スレッド内でリエントラント（`AsyncLocal<int>` でカウント）
- 結果として、**書き込み系は必ず `BeginTransactionAsync` 経由** で実行することで、他の書き込みとのレース条件を防げる

#### 複数文を発行する書き込みメソッドの 3 分岐（Issue #1724）

`ReplaceDetailsAsync` のように **1 メソッドで 2 文以上（DELETE→INSERT 等）を発行する**リポジトリメソッドは、次の 3 分岐を必ず実装する。分岐を欠くと「片方だけ確定して片方が失敗する」非原子的な経路が生まれる。

| 状況 | 実装 | commit/rollback の責任 |
|------|------|----------------------|
| 引数で `SQLiteTransaction` を受け取った | その tx を全文に適用する | 呼び出し元（介入しない） |
| 引数は null だが `_dbContext.HasActiveTransactionScope == true` | `LeaseConnectionAsync()` で接続だけ借り、`command.Transaction` は null のまま発行して**接続の活性トランザクションへ暗黙参加**する | 外側スコープ（介入しない） |
| 引数が null かつ外側スコープも無い | 自前で `BeginTransactionAsync()` する | **自分で持つ**（成功なら Commit、失敗・例外なら Rollback） |

- **2 番目の分岐を省略してはならない**（Issue #1575）。`BeginTransactionAsync()` は `SemaphoreSlim(1,1)` を取るため、外側スコープ内で自前 tx を開くと自己デッドロックする
- **SQLite は接続に活性トランザクションが無いと各文を autocommit で即確定する**。`command.Transaction` を設定し忘れた文は、同メソッド内の後続文が失敗しても巻き戻らない。Issue #1724 はこれで `ledger_detail` の明細が全消失した（Issue #1456 で INSERT 側だけを tx 化した際、DELETE が tx 外に取り残されたことが原因）
- 実装は `LedgerRepository.InsertDetailsAsync` / `ReplaceDetailsAsync` が参考。いずれも「分岐を持つ公開メソッド」と「接続・tx を引数で受け取り commit/rollback しない `*Core`」に分離している
- 回帰は実 SQLite で固定する（テスト設計書 §2 UT-075）。失敗注入は `BEFORE INSERT ... RAISE(ABORT)` トリガーで行い、タイミング依存にしない


| クラス | 責務・設計上のポイント |
|--------|----------------------|
| `FolderWriteAccessProbe` | フォルダへの書込可否を**実測**する。`Directory.Exists` だけでは「見えるが書けない」読み取り専用共有を検出できず、ACL 解析は SMB 越しでは実効権限と一致しないため、一時ファイルを実際に作成する。`FileOptions.DeleteOnClose` により、途中で例外が起きてもハンドルが閉じられた時点で OS が削除するため、診断がゴミファイルを残さないことを構造的に保証する |
| `DiagnosticStatusPresenter` | 判定 → アイコン／日本語ラベル／文字色リソースキーの写像を 1 か所に集約。ダイアログ表示とクリップボード出力で判定の呼び方がずれるのを防ぐ。色値リテラルではなくリソースキー名を返す（Issue #1392 / #1461） |
| `DiagnosticReportFormatter` | `DiagnosticReport` → 共有用プレーンテキスト。クリップボード API に触れない純関数のため単体テストで書式を固定できる。罫線・表組みは等幅フォント以外で崩れるため使わない |
| `DiskSpaceHelper`（既存、Issue #1689） | 空き容量の取得。`DriveInfo` が UNC を扱えないため Win32 `GetDiskFreeSpaceEx` を P/Invoke する。接続診断の項目 7 でも再利用 |
