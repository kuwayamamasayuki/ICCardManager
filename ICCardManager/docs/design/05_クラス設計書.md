> **`LedgerDetail.SequenceNumber` の順序規約（Issue #1822）**: DB の rowid から取得する値で、**小さい値ほど新しい（＝後に利用した）**。交通系ICカードの利用履歴サービスが新しい順（block 0 ＝ 最新）で返す並びをそのまま rowid へ写すためで（`FelicaCardReader.ReadHistoryAsync`）、`LendingService` は挿入時に時系列順（古い順）の並びを `Reverse()` してこの順序を維持している。したがって「最新の明細」は**最小**の `SequenceNumber` であり、時系列（古い順）へ並べ替えるには降順ソートが要る（`SummaryGenerator.SortChronologically`）。
>
> **例外**: 残高不足マージ（Issue #978。`LendingService.CreateUsageLedgersAsync`）で作られる台帳は、チャージ明細を先に挿入するため利用明細の側が大きい値になる。この台帳の残高は明細の並びからではなく `Ledger.Balance`（利用後の実残高）から決まるため実害はない。
>
> `LedgerMergeService.MergeAsync` の残高選択は「最大 `SequenceNumber` ＝ 最新」を前提としており本規約と食い違う。挙動を伴う整理は #1822 のスコープ外として別途扱う。

## 2a. 交通系固有ロジックの境界（Issue #1695）

### 2a.1 なぜこの節があるか

本システムのコア（タッチ認証 → 貸出/返却 → 出納簿）は、「複数職員でシェアする物品の出納管理」として交通系ICカード以外（社用携帯・鍵・公用車両等）にも通用する構造を持つ。

**現時点で汎用化する予定はない。** ただし交通系固有の知識がコアへ静かに染み出すと、将来その選択肢を取り戻すのに大規模改修が必要になる。この節は「どこまでが交通系固有か」を記述して、改修時の判断材料を残すためにある。

前節（§2 レイヤー構成図）が Presentation / Business / Data / Infrastructure の**横方向の層**を示すのに対し、本節の境界はそれと**直交する縦串**である。交通系固有性は特定の層に集まっておらず、`Infrastructure`（FeliCa 読取）・`Services`（摘要生成）・`Models`（乗車駅・降車駅）の 3 層すべてに分散している。

改修時の判断基準は `.claude/rules/domain-boundaries.md` を参照。

| リング | 定義 | 横展開時の扱い |
|--------|------|----------------|
| **中心（汎用コア）** | 「シェア物品の出納管理」として、交通系ICカードでなくても意味が通る概念 | そのまま流用 |
| **中間（交通系アダプタ）** | 汎用概念を交通系ICカードという具体物へ結びつけている層。名前と型は固有だが、構造は汎用 | 対象物品に合わせて読み替え・差替 |
| **外側（交通系固有）** | 交通系ICカードにしか存在しない概念 | 不要化、または対象物品固有の実装へ置換 |

**唯一のルール: 内側のリングに、外側リングの知識を持ち込まない。**

汎用コアのコード（`LendingService` の状態遷移、`ledger` の集計、帳票骨格）に「駅」「バス」「チャージ」といった交通系語彙の**分岐**を新設しない。必要なら外側リングに置き、コアからは抽象的な値（摘要文字列・金額）としてだけ受け取る。

### 2a.3 境界はクラス境界ではなくメソッド境界を通る（`SummaryGenerator`）

`SummaryGenerator` は 1 クラスの中に 2 種類の責務を同居させており、**クラス単位で固有/汎用を分類する素朴なモデルはここで破綻する**。

| 種別 | メソッド例 |
|------|-----------|
| 汎用（物品出納簿の様式そのもの） | `GetLendingSummary`（貸出中）/ 繰越各種（`GetCarryoverFromPreviousYearSummary` / `IsMidYearCarryoverSummary` / `GetMidYearCarryoverLikePattern`〔SQL 用 LIKE パターン導出、Issue #1749〕等）/ `GetMonthlySummary`（月計）/ `GetCumulativeSummary`（累計）/ `GetChargeSummary` / `GetRefundSummary` |
| 交通系固有 | 駅名からの摘要組み立て / バス混在表記（`BusLabel` / `BusPlaceholder` / `FormatBusSummary` / `GetBusStopExtractionPattern` / `TryExtractBusStops` / `ContainsBusLabel` / `HasIncompleteBusStop` / `IsBusStopPlaceholder`〔いずれも Issue #1818〕）/ 往復・乗継・循環判定 / `GetInsufficientBalanceNote`（残高不足） |

このため `SummaryGenerator` 全体への参照制限は規約テストで**かけていない**（§2a.5）。汎用メソッドは 22 ファイルから正当に使われている。

### 2a.4 seam カタログ（横展開時の拡張点）

「もし横展開するなら差し替えることになる接続点」と、その現在の抽象度。**差替コスト「高」の項目を新設しないこと**が改修時の判断基準になる。

| # | 拡張点 | 現在の実装 | 抽象度 | 差替コスト | 備考 |
|---|--------|-----------|--------|-----------|------|
| 1 | 物品の識別手段 | `FelicaCardReader` / `HybridCardReader` / `MockCardReader` | `ICardReader` で抽象済み | **低** | `CardReadEventArgs.Idm` は `string`。バーコード・QR・手動入力を別実装として DI 差替可能 |
| 2 | 利用履歴の読取 | `FelicaHistoryBlockDecoder` | `Infrastructure/CardReader` 内に閉じている | **低** | 物品によっては履歴読取自体が不要（手入力運用）。`ICardReader.TryReadHistoryAsync` が空リストを返せば成立する |
| 3 | 駅コード→駅名解決 | `StationMasterService`（CSV マスター） | `IStationMasterService` あり、参照元は `FelicaCardReader` と DI 登録の 2 箇所のみ | **低** | 交通系以外では不要化。DI 登録を外すだけで済む形を保つ |
| 4 | 摘要文字列生成 | `SummaryGenerator`（static クラス） | インターフェースなし・22 ファイルから直接呼び出し | **中** | 汎用メソッドと固有メソッドが同居（§2a.3）。横展開時は固有メソッド群のみ抽出する。`Data/` からの参照は汎用の繰越 LIKE パターン導出（`GetMidYearCarryoverLikePattern`、Issue #1749）のみ許可（§2a.5）。バスのラベル・未入力プレースホルダ（Issue #1818）は交通系固有のため `Data/` からは参照させず、`GetBusStopSuggestionsAsync(string busStopPlaceholder)` のように**値を引数で受け取る**形にしている |
| 5 | 利用内訳の項目 | `LedgerDetail`（`EntryStation` / `ExitStation` / `BusStops` / `IsBus`） | 固有列がモデルに直接生えている | **中** | 列名は交通系語彙だが構造は「1 回の利用の内訳」。物品に応じた読み替えで対応可能 |
| 6 | 物品マスター | `ic_card` テーブル / `IcCard` モデル | 交通系固有列は `card_type` のみ | **低** | 他の列（`is_lent` / `last_lent_at` / 繰越累計）はすべて汎用。`card_type` は物品種別として読み替え可能 |
| 7 | 残高の概念 | `ledger.balance` / `LedgerDetail.Balance` | 汎用（物品出納簿の「残額」） | **低** | 交通系固有ではない。鍵・車両なら残数、備品なら在庫数として同じ様式が成立する |

差替コストの読み方:

- **低** = インターフェースがあり参照元が限定されている。DI 登録の差替、または削除で済む
- **中** = 抽象化されていないか参照元が多い。まとまった作業になるが、コアの構造変更は不要
- **高** = コアの構造変更を伴う。**現時点では該当なし。この状態を維持することが Issue #1695 の目的**

### 2a.5 規約テストで固定している境界

`DomainBoundaryConventionTests` が以下をソースの静的検査で固定する（いずれも現状 green）。

| # | 検査内容 | 意図 |
|---|----------|------|
| 1 | `FelicaHistoryBlockDecoder` の参照元が `Infrastructure/CardReader/` 配下のみ | FeliCa 生データの解釈が上位層へ漏れない |
| 2 | `IStationMasterService` / `StationMasterService` の参照元が `Infrastructure/CardReader/` と DI 登録（`App.xaml.cs`）のみ | 駅名解決が「読取直後の変換」に留まり、`Services` / `ViewModels` は駅名を文字列としてのみ扱う |
| 3 | `Data/` 配下に交通系固有の**判断ロジック**（`SummaryGenerator` / `StationMasterService` / `FelicaHistoryBlockDecoder` / `DetermineIsBusUsage`）への実コード参照がない。ただし汎用メソッドの完全修飾呼び出し `SummaryGenerator.GetMidYearCarryoverLikePattern(`〔繰越 LIKE パターン導出、Issue #1749〕のみ許可 | 永続化層に交通系知識が入らない |
| 4 | 上記 3 件の走査が実際に本番ソースを covering していること（走査件数と、検査対象記号が境界内に実在すること） | パス解決が壊れると 3 件すべてが無条件 green になるため（`.claude/rules/testing.md`「通るが目的を果たさないテスト」） |

##### バスのラベル・プレースホルダを `Data/` から参照させない理由（Issue #1818）

`SummaryText.BusLabel`（既定「バス」）/ `BusPlaceholder`（既定「★」）は、生成側だけが設定値を使い、
判定・抽出側が「バス（…）」「★」を直書きしていた（Issue #1604 / #1749 と同型の乖離）。
是正では `SummaryGenerator` に導出ヘルパーを置き 15 箇所を委譲したが、
**`LedgerRepository.GetBusStopSuggestionsAsync` の SQL（`bus_stops != '★'`）だけは扱いを分けた**。

繰越 LIKE パターン（#1749）は§2a.3 の**汎用**群に属するため `Data/` からの参照を許可できたが、
バスのラベル・プレースホルダは**交通系固有**であり、同じ許可リストに載せると境界の意図が崩れる。
そこでリポジトリは判断を持たず、除外する文字列を引数で受け取る
（`GetBusStopSuggestionsAsync(string busStopPlaceholder)`。呼び出し元の `BusStopInputViewModel` が
`SummaryGenerator.BusPlaceholder` を渡す）。§2a.2 の決定木「汎用コアからは抽象的な値としてだけ受け取る」に従う形。

直書きの再発は `BusTextLiteralConventionTests` がリポジトリ全体のソーステキストで検出する
（直書きが許されるのは既定値を宣言する `OrganizationOptions.cs` と、そこから全体を導出する
`SummaryGenerator.cs` の 2 ファイルのみ）。

#### 検査対象に含めないもの（重要）

**`EntryStation` / `ExitStation` / `BusStops` / `IsBus` は #3 の禁止語に含めない。** `LedgerRepository` がこれらを DB 列へマッピングするのは永続化の正当な責務であり、境界違反ではない。禁止するのは「データの**形**」ではなく「データの**解釈**」——摘要生成・駅名解決・バス判別といった判断ロジックが `Data/` に入ること。

#### 汎用メソッドの完全修飾呼び出しは #3 の例外（Issue #1749）

繰越除外の SQL（`'%月から繰越'`）が組織設定 `MidYearCarryoverFormat` に追従しない乖離（Issue #1749）を塞ぐため、`LedgerRepository` は `SummaryGenerator.GetMidYearCarryoverLikePattern()` をパラメータバインドで参照する。繰越判定は交通系固有の「データの解釈」ではなく**物品出納簿の様式に属する汎用ロジック**（§2a.3 の汎用群）であり、境界の意図（交通系知識の染み出し防止）には反しない。ただし記号一致では汎用/固有メソッドを区別できないため、規約テストは**完全修飾の呼び出し形**（`GenericSummaryGeneratorCallsAllowedInDataLayer`、開き括弧まで）に限定して許可し、許可ロジック自体をサンプル入力で固定している（同一行に固有メソッドが同居した場合・許可メソッド名を前方に含む別メソッドは従来どおり検出される）。

#### コメントは検査対象外

検査は実コードのみを対象とし、`//` / `///` / `/* */` のコメントは除去してから照合する。`LedgerRepository.cs` には「`SummaryGenerator.GetMidYearCarryoverSummary` の生成結果で検証している」という**規約の理由を説明したコメント**があり、単純な文字列一致ではこれを違反として誤検出するため（`.claude/rules/development-conventions.md` の「禁止された要素の不在を検査するときは要素タグで照合する」と同じ配慮）。

意図的に境界を変更する場合は、本節の seam カタログを更新したうえでテストを修正する。テストは禁止ではなく**気づきの装置**として置いている。

#### 5.1a カード登録時の台帳書き込みの原子性・失敗通知（Issue #1727 / #1763）

カード登録時、履歴が読み取れた場合の初期残高行は **カードの現残高ではなく、履歴最古エントリから逆算した「その取引の前の残高」**（`CardManageViewModel.CalculatePreHistoryBalance`）である。つまり初期残高行は「この後に履歴行が入る」ことを前提とした値であり、**単独では正しくない**。

そのため次の 3 点を守る。

| 守るべきこと | 実装 |
|-------------|------|
| 初期残高行と履歴行を同時に確定させる | `CardManageViewModel` は `BuildInitialLedgerAsync` で行を**組み立てるだけ**にして、`ImportHistoryForRegistrationAsync(..., initialLedger)` へ渡す。サービス側が 1 つの `BeginTransactionAsync` スコープで両方を INSERT する（リポジトリは同一接続を借りるため暗黙参加する） |
| 一過性の競合で落とさない | トランザクション全体を `DbContext.ExecuteWithRetryAsync` で包む（他の書込み経路と同じ扱い） |
| 失敗を呼び出し元へ届ける | `Success=false` に加えて `FailureReason`（「なぜ」のみ）を設定する。「何が」「どうすれば」は復旧手段を知っている ViewModel が組み立てる |

> **`FailureReason` が「なぜ」だけを持つ理由**: カード登録直後の履歴インポートは、失敗しても**同じ操作をやり直せない**（カード行は既に登録済み）。`LendingService.GetUserFriendlyErrorMessage`（Issue #1110）は「再度○○をお試しください」で終わるため行動指示として誤りになり、既定分岐が生の `Exception.Message` を含む点も Issue #1614 に反する。そこで専用の `GetHistoryImportFailureReason` を設け、行動指示（「履歴画面のCSVインポートで補完してください」）は ViewModel 側に置いた。

> **失敗理由は動作モードで書き分ける**: `GetHistoryImportFailureReason` は `DbContext.IsSharedMode` を受け取り、ローカルモードでは「他のPC」「ネットワーク共有フォルダー」に言及しない。単一 PC でも VACUUM・バックアップ・接続ヘルスチェックといった**自プロセス内の別接続**と競合して SQLITE_BUSY は起こり得るため、存在しない相手を原因として案内すると原因究明が止まる。「なぜ」が正確であることは 3 要素（`.claude/rules/error-messages.md`）の前提。

> **コミット確定後の後処理は成否から切り離す**: 完全性チェック（`CheckHistoryCompleteness` と最古日付の算出）は `scope.Commit()` の**後**に走る。ここでの例外を外側 `catch` に拾わせて `Success=false` にすると、呼び出し元は「台帳には1行も記録されていません。CSVインポートで取り込んでください」と**事実に反する**案内をし、職員がそれに従うとコミット済みの行の上に同じ利用が二重計上される。完全性チェックは「不足しているかもしれない」という助言でしかないため、判定できなければ助言を出さない扱い（`MayHaveIncompleteHistory = false`）で足りる。

> **失敗の通知は、失敗したサブシステムに依存させない**: `CardManageViewModel` は書き込み失敗の通知を後処理（`LoadCardsAsync` → `CancelEdit` → `SelectAndHighlight`）のあとに出すが、`LoadCardsAsync` は書き込み失敗と**同じ原因**（共有フォルダの切断・DB のロック）で例外になり得る。例外フィルタ `catch (Exception ex) when (ledgerFailure != null)` で失敗時のみ握り、通知を必ず到達させる。成功パスの挙動は変えない（成功時まで握ると、一覧が古いまま「登録しました」と表示される）。

##### 履歴が無い経路も同じ仕組みに乗せる（Issue #1763）

カード内に取り込む履歴が無い登録では、初期残高行は逆算値ではなく**カードの実残高そのもの**なので「単独では正しくない行」問題は起きない。しかし**書き込みの失敗を無言にしてよい理由にはならない**。ここで失われる行は「新規購入 / ○月から繰越」＝**そのカード唯一の受入行**で、欠落すると台帳が 0 行のまま払出だけが積み上がり、月次帳票（物品出納簿）で「受入 − 払出 = 残額」が年度を通して成立しなくなる。

`CardManageViewModel` はこの経路でも `ImportHistoryForRegistrationAsync(cardIdm, 空リスト, importFromDate, initialLedger)` を呼ぶ。同メソッドは「`filtered.Count == 0` かつ `initialLedger != null`」の分岐を既に持つため、**リトライ（`ExecuteWithRetryAsync`）・トランザクション・`FailureReason` をそのまま再利用できる**。修正前はこの分岐だけが `_ledgerRepository.InsertAsync` を直接呼び、例外を `LogWarning` で握りつぶしていた。

> **「同じ書き込みを 2 通りの方法で行わない」**: 経路ごとに書き込み方法が分かれていると、片方に足した防御（リトライ・失敗通知）がもう片方に届かない。#1727 でリトライと失敗通知を足したときに履歴なし経路が取り残されたのは、この分岐が別の書き込み手段を持っていたからである（`.claude/rules/error-messages.md`「同じ制約違反は『すべての経路』で同じ例外へ変換する」と同じ判断）。

> **`BuildInitialLedgerAsync` が返す null は書き込みの失敗ではない**: 残額を読み取れなかった（カード未タッチ・読み取りエラー）ことの表現であり、この場合は初期レコードを作らずカード登録のみ成功させる（Issue #1282 の判断を維持）。**通知の対象は「書き込もうとして失敗した」場合だけ**である。

> **ロールバックは個別の `try/catch` で包む**（Issue #1745 の作法をこの経路へ適用）: `COMMIT` が SQLITE_BUSY 等で失敗した後は SQLite 側が自動ロールバック済みで `SQLiteTransaction` が無効化されており、`catch` の中の素の `scope.Rollback()` は `InvalidOperationException` になる。その二次例外が本来の `SQLiteException(Busy)` を置き換えて抜けると、**`ExecuteWithRetryAsync` の判定（`SQLiteException` かつ Busy/Locked）に一致せずリトライが一度も行われず**、`GetHistoryImportFailureReason` も既定分岐へ落ちて「なぜ」が退化する。`TryRollbackRegistrationImport` で包み、ロールバックの失敗は Warning ログに留める（書き込みが確定するのは `Commit()` の成功時だけで、未コミットのトランザクションは `TransactionScope.Dispose()` でも巻き戻るため、握りつぶしてもデータは確定しない）。

> **「どうすれば」は経路で分ける**: 文言は `Common/RegistrationLedgerFailureMessage` に集約し、`ForHistoryImport`（#1727）/ `ForInitialBalance`（#1763）の 2 ファクトリに分ける。「なぜ」は共通（`GetHistoryImportFailureReason`）だが、履歴なし経路には取り込むべき利用履歴が存在しないため「CSVインポートで取り込んでください」が**実行できない指示**になる。この経路の復旧手段は「履歴画面から残高の行を手動で追加」だけ。ダイアログ本文・タイトル・ステータス欄を 1 つのオブジェクトに束ねているのは、表示先ごとに別々の場所へ書くと片方だけ更新されて食い違うため（#1759 の「所在」と「順序」の教訓）。

**共有フォルダモード対応:**

- `IsSharedMode`: DBパスが **UNCパス**（`\\server\share\...`）または **マップドネットワークドライブ**（`DriveInfo.DriveType == DriveType.Network`）の場合に `true`。判定は `DbContext.IsSharedModePath(string path)` に一元化されており、ローカルフルパス指定では `false`（Issue #1559 / #1597。「パス設定の有無」だけで判定していた旧実装を是正）。共有フォルダモードかどうかを判定する
- `ConfigurePragmas()`: 接続時に `PRAGMA foreign_keys = ON`、`PRAGMA busy_timeout`（ローカルモード: 5000ms / 共有モード: 15000ms、Issue #1107）を設定。共有モード時は `PRAGMA journal_mode = DELETE` を試行し、失敗時は TRUNCATE → PERSIST の順にフォールバック（`ConfigureJournalMode()`、Issue #1107）。**PRAGMA の適用まで済んでから `_connection` へ代入する**（Issue #1809）。適用中に例外（共有モードの SQLITE_BUSY 等）が出た接続は破棄して null のままにし、次回の取得で再構成させる。先に代入すると Open 済み・PRAGMA 未適用の接続がプロセス全体で再利用され続け、busy_timeout 未設定（既定 0）で SQLITE_BUSY が多発し、`CurrentJournalMode` も未設定のまま degraded 検出（Issue #1172）が働かない。`protected virtual` はこの失敗をテストから注入するための継ぎ目（`ProbeDatabaseFileReachable` と同じ設計）
- `SuspendConnections()`（Issue #1166 / #1809）: リストア中に接続を閉じ、スコープの Dispose まで新規接続の取得を拒否する。**使用中の接続を他スレッドから Close+Dispose しない**ため、閉じる前に (1) 接続セマフォを取得して進行中の `BeginTransactionAsync` / `LeaseConnection()` の完了を待ち、(2) セマフォを取らない `LeaseConnectionAsync` の進行中リースが解放されるまで（上限 `AsyncLeaseDrainTimeout`＝既定 10 秒。超過時は Warning ログを残して従来どおり閉じる＝解放漏れがあってもリストアを永久に止めない）待つ。セマフォはスコープの Dispose まで保持するため、停止中に到着した `BeginTransactionAsync` / `LeaseConnection()` は失敗せず解除後に成功する（`GetConnection()` / `LeaseConnectionAsync` は従来どおり `InvalidOperationException`）。セマフォを同期取得するため **UI スレッドから呼ばない**（`LeaseConnection()` と同じガードで拒否。UI 層は `BackupService.RestoreFromBackupAsync` を使う）
- `LeaseConnection()` は接続の確立（Open / PRAGMA）に失敗したとき取得済みのセマフォを必ず返す（Issue #1809）。返さないと以後の `BeginTransactionAsync`（全書き込み）が永久に待機する。`BeginTransactionAsync` には同じ catch が元からあり、こちらだけ欠けていた
- `ExecuteWithRetry<T>()`: SQLITE_BUSY/SQLITE_LOCKED発生時に指数バックオフでリトライ。ローカルモードは最大3回（100ms → 500ms → 2000ms）、共有モードは最大5回（200ms → 500ms → 1000ms → 2000ms → 5000ms、ジッター付き、Issue #1107）。ジッターの生成は `Common/RetryJitter.GetJitter()` に集約（スレッドごとの `Random`。Issue #1823、詳細は 02_DB設計書 §11.2）。詳細は [§5.5b](#55b-接続リーストランザクションスコープissue-1243) 参照
- 接続の正常性確認と定期ヘルスチェックは **`DbContext` ではなく `SharedModeMonitor`**（上記クラス一覧参照）が担う。共有フォルダモード時のみ **15秒間隔**（`SharedModeMonitor.HealthCheckIntervalSeconds = 15`、Issue #1493）でタイマーを起動（`Start()` → `ExecuteHealthCheckAsync()`）し、`DbContext.CheckConnection()` で接続を確認、接続断時は自動再接続を試行する。`DbContext` 自身はヘルスチェック用のメソッド（旧記載の `CheckConnectionHealth()` / `StartHealthCheck()`）を持たない
- `CheckConnection()`: 軽量クエリ（`SELECT COUNT(*) FROM sqlite_master`）**かつ** DB ファイルへの実到達（`ProbeDatabaseFileReachable()` → `File.Exists`）の両方が成功したときのみ `true`。**クエリ単独では到達性の証明にならない**（開きっぱなしの接続ではスキーマ情報が SQLite のページキャッシュから応答され、ネットワーク切断後も成功し続ける。Issue #1110 の意図が達成できていなかったことを Issue #1716 で是正）。インメモリDB（`:memory:`）とパス未設定はファイル実体を持たないため到達確認の対象外、接続一時停止中（Issue #1166）は従来どおり `true`。ファイル確認はリース解放後に行い、死んだ UNC パスの SMB タイムアウト中に接続セマフォを占有しない。到達確認は `protected virtual` のテスト継ぎ目（`ConnectionDiagnosticsService.ProbeDatabaseFileReachable` と同じ設計）
- **疎通確認全体の上限時間**（Issue #1716）: 疎通確認は「接続リース取得 → 接続オープン → クエリ → ファイル到達確認」と複数のネットワーク待ちが直列に並び、**どの区間も下位の TCP/SMB タイムアウトまで戻らない**（実機ログでクエリ段階が 82.3 秒、直後の再確認は 3ms / 0ms）。区間ごとに上限を設けても塞ぎ残しが生じるため、確認**全体**を `Task.Run` で実行し `AppConstants.DatabaseConnectionCheckTimeoutSeconds`（10秒。`ConnectionCheckTimeout` で仮想化しテストから短縮可能）以内に完了しなければ「接続なし」とみなす。上限で打ち切っても下位の呼び出しは中断できないため、**進行中の確認は 1 本に限定**し（`_pendingConnectionCheck`）、ブロック済みスレッドの累積と接続セマフォ待ちの行列を防ぐ。失敗時・1秒超過時は段階別の所要時間を `LogInformation` で記録する（`appsettings.json` の既定フィルタが Information のため `LogDebug` は本番のログファイルに残らない）。**UI スレッドから呼ばないこと**（上限までの待機が呼び出しスレッドをブロックする）。詳細は 04_機能設計書 §18.4
- `CheckWritable()`（Issue #1686、`IDatabaseInfo` 実装）: `CheckConnection()`（到達性＝読み取り）と対で「読み取り→書き込み」の 2 段確認を構成する。`user_version`（本アプリが業務データとして未使用の DB ヘッダ領域）へ +1 を書き込み即 `ROLLBACK` する**実書き込みプローブ**。`BEGIN IMMEDIATE`（RESERVED ロック取得）だけでは読み取り専用ファイルでも成功してしまう（`SQLITE_READONLY` は実際のページ書き込みで初めて発生する）ことを実測で確認済みのため、実書き込み方式を採る。接続一時停止中と**書き込みトランザクション進行中**（`HasActiveTransactionScope`）は `true`（後者は BEGIN の二重開始で失敗し「書込不可」と誤報告するのを避けるため。書き込みが現に機能している状況である）
- **書込可否確認の失敗理由は `LogInformation` で残す**（Issue #1730）: 失敗時に例外種別・SQLite 結果コード（`SQLiteException.ResultCode`）・メッセージ・DB パスを記録する（`LogWritableCheckFailure`）。`CheckWritable()` は `bool` しか返さないため、接続診断の画面は原因**候補**（読み取り専用属性／アクセス権不足／他プログラムの占有）を並べるにとどまり、**候補を 1 つに絞れるのは結果コードだけ**である。`LogDebug` は本番の既定フィルタ（Information）で落ちて痕跡にならないため、`ExecuteConnectionCheck`（Issue #1716）と同じく **`LogDebug` を残したまま Information を併設**する（置き換えないことで、レベルをピン留めした既存テストを弱めずに済む）。失敗時のみの出力かつ本番の呼び出し元は接続診断のオンデマンド 1 経路のみのためログ肥大化は起きない。詳細は 04_機能設計書 §19.2
- `Vacuum()`: 戻り値を `bool` に変更。共有モードで他PCが接続中の場合はVACUUMが失敗しうるため、失敗時は `false` を返す（例外にしない）
- `InitializeDatabaseAsync()` / `CleanupOldDataAsync()` / `VacuumAsync()` (#1356): `App.OnStartup` など UI スレッドから呼び出すと Issue #1281 の `LeaseConnection()` ガードで例外になるため、`Task.Run` で既存 sync 実装へ委譲する非同期版を提供する。テスト経路（スレッドプール/xUnit）は従来どおり sync 版を直接使用

> **接続リース・トランザクションの正しい使い方**: `DbContext` の接続を借りる際は、`using` 文でリースを取得する `LeaseConnectionAsync()` / `BeginTransactionAsync()` を利用する。詳細は [§5.5b 接続リース・トランザクションスコープ](#55b-接続リーストランザクションスコープissue-1243) を参照。

### 5.5b 接続リース・トランザクションスコープ（Issue #1243）

`DbContext` の接続ライフサイクルとトランザクション境界を型安全に管理する 3 つの RAII 的ラッパクラス。いずれも `Data/DbContext.cs` に定義される `public sealed class` であり、`using` 文での利用を前提としている。

```mermaid
classDiagram
    class ConnectionLease {
        +SQLiteConnection Connection
        -Action _onDispose
        -bool _disposed
        +Dispose() void
    }

    class TransactionScope {
        +ConnectionLease Lease
        +SQLiteTransaction Transaction
        -bool _disposed
        +Commit() void
        +Rollback() void
        +Dispose() void
    }

    class ConnectionSuspensionScope {
        -DbContext _dbContext
        -bool _disposed
        +Dispose() void
    }

    TransactionScope --> ConnectionLease : holds
    TransactionScope --> SQLiteTransaction : holds
    ConnectionSuspensionScope --> DbContext : suspends
```

#### 責務一覧

| クラス | 責務 | 取得元 | 解放契機 |
|--------|------|--------|----------|
| `ConnectionLease` | **接続ライフサイクル管理**: `SQLiteConnection` を貸与し、`Dispose` でセマフォを解放して次の呼び出し者へ譲る | `DbContext.LeaseConnectionAsync()` / `LeaseConnection()` | `using` 文を抜けたとき |
| `TransactionScope` | **トランザクション境界制御**: `ConnectionLease` と `SQLiteTransaction` を束ね、`Dispose` で**トランザクション→リースの順に**解放する | `DbContext.BeginTransactionAsync()` | `using` 文を抜けたとき |
| `ConnectionSuspensionScope` | **接続一時停止制御**: リストア中など接続再オープンを禁止したい期間を RAII 的に表現し、`Dispose` で自動的に解除する（Issue #1166） | `DbContext.SuspendConnections()` | `using` 文を抜けたとき |

#### TransactionScope.Dispose() の自動ロールバック仕様

**重要**: `Commit()` も `Rollback()` も呼ばずに `Dispose` された場合、`SQLiteTransaction.Dispose()` は **未コミットのトランザクションを自動的にロールバック** する。このため、例外経路でも明示的な `Rollback()` 呼び出しは不要である。

```mermaid
sequenceDiagram
    participant Caller
    participant Scope as TransactionScope
    participant Tx as SQLiteTransaction
    participant Lease as ConnectionLease

    Caller->>Scope: using var scope = await BeginTransactionAsync()
    Note over Scope: リース + トランザクションを取得
    Caller->>Scope: （業務処理）
    alt 正常系
        Caller->>Scope: scope.Commit()
        Scope->>Tx: Commit()
    else 例外発生
        Note over Caller: 例外でブロック脱出
        Note over Scope: Commit/Rollback 未呼び出し
    end
    Caller->>Scope: Dispose()（using 脱出）
    Scope->>Tx: Dispose()
    Note over Tx: 未コミットなら自動ロールバック
    Scope->>Lease: Dispose()
    Note over Lease: セマフォを解放
```

この仕様により、典型的な try/catch 定型文を省略できる:

```csharp
// ❌ 冗長（Dispose が自動ロールバックする）
using var scope = await _dbContext.BeginTransactionAsync();
try
{
    // 処理
    scope.Commit();
}
catch
{
    scope.Rollback();
    throw;
}

// ✅ 簡潔（例外時も Dispose が自動ロールバックする）
using var scope = await _dbContext.BeginTransactionAsync();
// 処理
scope.Commit();
// 例外時は Commit() が呼ばれないまま using を抜け、自動ロールバック
```

#### 典型的な使用パターン

**1. 読み取り専用の接続借用（単発クエリ）**

```csharp
using var lease = await _dbContext.LeaseConnectionAsync();
var connection = lease.Connection;

using var command = connection.CreateCommand();
command.CommandText = "SELECT value FROM settings WHERE key = @key";
command.Parameters.AddWithValue("@key", key);
return (string?)await command.ExecuteScalarAsync();
// using 脱出時にリースを解放、セマフォ返却
```

**2. 複数操作を 1 トランザクションで実行（書き込み系の推奨形）**

```csharp
await _dbContext.ExecuteWithRetryAsync(async () =>
{
    using var scope = await _dbContext.BeginTransactionAsync();

    await SetAsync(KeyWarningBalance, settings.WarningBalance.ToString());
    await SetAsync(KeyFontSize, FontSizeToString(settings.FontSize));
    // ...複数のキー更新...

    scope.Commit();
    // 例外発生時は Commit() に到達せず Dispose で自動ロールバック
});
```

> **リトライラムダは冪等にする（Issue #1733）**: `ExecuteWithRetryAsync` は SQLITE_BUSY/LOCKED でラムダ**全体**を再実行する。ロールバックで巻き戻るのは DB だけであり、ラムダ内でメソッド外のオブジェクト（結果 DTO のリスト等）へ追記すると、失敗した試行の分が残ったまま成功分が積み増され、試行回数分だけ累積する（`LendingService.PersistReturnAsync` が `result.CreatedLedgers.AddRange` をラムダ内で行っていたため、返却リトライ時にバス停入力ダイアログへ同一バス乗車行が2重表示された）。対処は次のいずれか:
>
> - **代入で受ける**: ラムダ内ではローカル変数への代入（上書き）だけを行い、呼び出し元オブジェクトへの反映はリトライ境界の外に置く（`LendingService.PersistReturnAsync` / `LendAsync` の形）
> - **冒頭で初期化する**: ラムダ内で累積が必要な場合は、ラムダ冒頭でカウンタ・リストを毎回初期化する（`RepairLentStatusConsistencyAsync` の `repairCount = 0` の形）

> **`LendingResult.Success` は「記録が確定した」ことだけを表す（Issue #1805）**: `ReturnAsync` は `PersistReturnAsync` のコミット後に残額の解決（`ResolveReturnBalanceAsync`）と残額警告の付与（`ApplyBalanceWarningAsync`）という DB I/O を行う。`Success` と 30秒ルール用の処理情報（`LastProcessedCardIdm` / `LastProcessedTime` / `LastOperationType`）は**コミット直後に確定**させ、以降の例外は `catch (Exception) when (result.Success)` で吸収して `HasPostCommitFailure = true` にする（`Success` / `ErrorMessage` は変えない）。後処理の後ろに置くと、後処理の失敗で「返却失敗・再タッチ」と案内され、案内どおりの再タッチが（`is_lent = 0` のため）貸出として新規に記録される。`LendAsync` はコミット直後に処理情報を確定し後処理の DB I/O を持たないため対象外。呼び出し元（`MainViewModel.HandleReturnSuccessAsync`）は `HasPostCommitFailure` のとき残額付きの返却通知を出さず「記録済み・再タッチしない」を案内する（→ `04_機能設計書.md` §2.5.1）

`ExecuteWithRetryAsync` と組み合わせることで、`SQLITE_BUSY` / `SQLITE_LOCKED` 発生時に指数バックオフ + ジッター付きでリトライする（共有モードでは最大 5 回）。

**3. 接続の一時停止（リストア中など）**

```csharp
// Task.Run 先（非 UI スレッド）で実行すること。セマフォを同期取得するため UI スレッドでは
// LeaseConnection() と同じガードで InvalidOperationException になる（Issue #1809）
using var suspension = _dbContext.SuspendConnections();
// 進行中の BeginTransactionAsync / LeaseConnection() / LeaseConnectionAsync の完了を待ってから接続を閉じる。
// この間、GetConnection() / LeaseConnectionAsync は InvalidOperationException をスロー（Issue #1166）、
// BeginTransactionAsync / LeaseConnection() はセマフォ待ちになり、解除後に成功する（Issue #1809）
ReplaceDatabaseFile(backupFile);
// using 脱出時に ResumeConnections() が自動呼び出しされ、セマフォも返る
```

> **使用中の接続を他スレッドから閉じない（Issue #1809）**: 一時停止の初版（#1166）は `_connectionLock` だけを取って `Close()` + `Dispose()` していたが、`_connectionLock` が守るのは `_connection` フィールドの代入だけで、既に払い出された `SQLiteConnection` 上で実行中のコマンドは守らない。`_isSuspended` も新規取得しか止めない。リストア中（UNC では `File.Move` + `File.Copy` で数秒）に進行中の貸出・返却トランザクションや共有モードの 15 秒ヘルスチェックが同一接続でコマンドを実行していると `ObjectDisposedException` で落ちる。「新規取得を止めるフラグ」と「使用中の接続を守るロック」は別物であり、閉じる前に**使用中でないこと**を待って確かめる。

#### 排他制御（内部実装の注意点）

- `BeginTransactionAsync()` は `DbContext._semaphore` を取得する（`SemaphoreSlim(1, 1)`）。トランザクション中は他の書き込み系呼び出しがブロックされる
- `LeaseConnectionAsync()`（非同期版）は現在セマフォを取得しない。同一 `SQLiteConnection` を複数タスクが共有する前提。進行中件数だけを `_activeAsyncLeaseCount`（`Interlocked`）で数え、`SuspendConnections()` が解放を待てるようにしている（Issue #1809）
- `LeaseConnection()`（同期版）はセマフォを取得し、同一スレッド内でリエントラント（`AsyncLocal<int>` でカウント）。接続の確立に失敗したときはセマフォを返してから例外を伝播する（Issue #1809。`BeginTransactionAsync()` と同じ形）
- `SuspendConnections()` もセマフォを取得し、スコープの Dispose まで保持する（Issue #1809）。取得順は「セマフォ → `_isSuspended = true` → 非同期リースの解放待ち → `_connectionLock` で Close」。フラグを立ててから件数を読むこと（逆だと待っている間に新しいリースが入り続ける）、フラグ書き込みと件数読み取りの間に `Interlocked.MemoryBarrier()` を置くこと（`LeaseConnectionAsync` 側の「件数増加 → フラグ読み取り」と交差させない）
- 結果として、**書き込み系は必ず `BeginTransactionAsync` 経由** で実行することで、他の書き込みとのレース条件を防げる

#### 複数文を発行する書き込みメソッドの 3 分岐（Issue #1724）

`ReplaceDetailsAsync` のように **1 メソッドで 2 文以上（DELETE→INSERT 等）を発行する**リポジトリメソッドは、次の 3 分岐を必ず実装する。分岐を欠くと「片方だけ確定して片方が失敗する」非原子的な経路が生まれる。

| 状況 | 実装 | commit/rollback の責任 |
|------|------|----------------------|
| 引数で `SQLiteTransaction` を受け取った | その tx を全文に適用する | 呼び出し元（介入しない） |
| 引数は null だが `_dbContext.HasActiveTransactionScope == true` | `LeaseConnectionAsync()` で接続だけ借り、`command.Transaction` は null のまま発行して**接続の活性トランザクションへ暗黙参加**する | 外側スコープ（介入しない） |
| 引数が null かつ外側スコープも無い | 自前で `BeginTransactionAsync()` する | **自分で持つ**（成功なら Commit、失敗・例外なら Rollback） |

- **2 番目の分岐を省略してはならない**（Issue #1575）。`BeginTransactionAsync()` は `SemaphoreSlim(1,1)` を取るため、外側スコープ内で自前 tx を開くと自己デッドロックする
- **SQLite は接続に活性トランザクションが無いと各文を autocommit で即確定する**。`command.Transaction` を設定し忘れた文は、同メソッド内の後続文が失敗しても巻き戻らない。Issue #1724 はこれで `ledger_detail` の明細が全消失した（Issue #1456 で INSERT 側だけを tx 化した際、DELETE が tx 外に取り残されたことが原因）
- 実装は `LedgerRepository.InsertDetailsAsync` / `ReplaceDetailsAsync` / `DeleteAsync` / `UnmergeLedgersAsync`（Issue #1806）が参考。いずれも「分岐を持つ公開メソッド」と「接続・tx を引数で受け取り commit/rollback しない `*Core`」に分離している
- **「別メソッドの書き込みと束ねる必要がある」なら tx を受け取るオーバーロードを用意し、呼び出し元（サービス層）が 1 つのスコープで両方を呼ぶ**（Issue #1806）。`UnmergeLedgersAsync` は旧実装が内部で `Commit()` して返り、呼び出し元がその**あと**に別接続で `MarkMergeHistoryUndoneAsync` を呼んでいたため、マークだけが失敗（共有モードの SQLITE_BUSY / UNC 断）すると「台帳は復元済み・履歴は未取消」の状態が残り、案内どおりに再実行した管理者の操作で統合元が**もう一度 INSERT** された（月次帳票の二重計上）。`LedgerMergeService.UnmergeAsync` は `MergeAsync`（Issue #1458）と同じ形で `BeginTransactionAsync` のスコープ内から両方の tx オーバーロードを呼び、どちらかが `false` ならロールバックする
- 回帰は実 SQLite で固定する（テスト設計書 §2 UT-075 / UT-076）。失敗注入は `BEFORE INSERT ... RAISE(ABORT)` トリガーで行い、タイミング依存にしない

#### 更新・削除は影響行数で競合を検出する（Issue #1753）

共有モードでは**読み取りと書き込みが別トランザクション**になるため（サービス層が `GetByIdAsync` で読み、その後 `BeginTransactionAsync` で書く）、その間に他 PC が同じ行を変更・削除し得る。行ロックによる悲観ロックは持たないので、**書き込み時の影響行数で競合を検出する**（楽観ロック）。

- **`ExecuteNonQueryAsync()` の戻り値を捨てない**。UPDATE / DELETE が 0 行なら対象は既に消えている。`MergeLedgersAsync` は 3 文の影響行数を一つも見ずに無条件 `true` を返しており、そのために `LedgerMergeService` の競合エラー分岐が**到達不能なデッドコード**になっていた（Issue #1753）
- **SQLite の `changes()` は WHERE に一致した行を、値が変わらなくても数える**（MySQL と異なる）。したがって「0 行＝行が存在しない」と断定でき、同じ値での冪等な再実行を競合と誤判定しない
- **0 行が正常な文では検証しない**。例: 統合手順1の `UPDATE ledger_detail SET ledger_id` は、明細を持たない ledger（「新規購入」「○月から繰越」）では 0 行が正しい。**どの文で競合を検出するかを決めてコメントに残す**
- **`bool` を返すリポジトリメソッドの戻り値も捨てない**。`UpdateAsync` は `result > 0` を正しく返すのに、`LedgerSplitService` と `LedgerDetailViewModel` が破棄していた（Issue #1753）。「リポジトリは正しいのに呼び出し元が握りつぶす」形の抜けに注意する
- **競合を検出したら UI 側で一覧を再読込する**。エラー文言で「画面を最新の状態に更新してから再度お試しください」と案内する以上、失敗経路でも再読込しないと利用者は同じエラーを繰り返す（`MainViewModel` の統合コマンド・統合取り消しコマンドが該当）
- **暗黙 rowid で行を特定する UPDATE は、所属（親 ID）も WHERE に含める**（Issue #1806）。`ledger_detail` は INTEGER PRIMARY KEY を持たない暗黙 rowid のテーブル（AUTOINCREMENT なし）で、表末尾の行が消えると次の INSERT が同じ rowid を再利用する。統合取り消しの `UPDATE ledger_detail SET ledger_id = … WHERE rowid = @rowid` は、統合後に統合先の明細が編集（`ReplaceDetailsAsync` の DELETE + INSERT）されて rowid が振り直されると、①該当行が無く 0 行のまま「取り消しました」と報告する（統合元が明細ゼロで復活）、②空いた rowid を無関係な別台帳の明細が再利用していればその明細を復活先へ移す（交差破損）、の 2 通りで壊れた。`WHERE rowid = @rowid AND ledger_id = @targetId`（同ファイルの `UpdateDetailBusStopsAsync` と同じスコープ）にして影響行数 0 を競合として `false` を返す。**Undo データが「rowid」という再利用され得る識別子しか持たない以上、統合後に明細が作り直された履歴は取り消せない**（明細の同一性を rowid 以外で確かめる手段が無い）。この場合は復元を拒否して「統合後に編集・分割・削除された可能性」を案内する
  - **例外**: 統合先の明細が編集後も**表末尾**にあり、DELETE + INSERT で Undo データが指す rowid がすべて統合先に再び割り当てられた場合は検出できない（rowid も所属も一致するため。ガードは「その rowid が今も統合先に属するか」しか見ないので、明細の内容・順序・件数が変わっていても通る）。この形は「返却直後に統合し、他の返却が入る前に明細を編集する」ときにだけ成立し、移動先を取り違えても統合先・統合元の組の内側での明細の入れ替わりに留まる（他の台帳には波及しない）。Undo データに明細の内容を含めれば検出できるが、`ledger_merge_history.undo_data` の形式変更を伴うため本 Issue では扱わない
  - `MarkMergeHistoryUndoneAsync` は `WHERE id = @id AND is_undone = 0` として影響行数で「既に取り消し済み」を検出する。2 台の PC が同じ履歴を同時に取り消すと両方が「未取消」を読んでから書き込みに来るため、後着の UPDATE を 0 行にして復元ごとロールバックする

#### UPDATE の SET 句は「その経路で本当に編集する列」に限る（Issue #1726）

エンティティを引数に取る `UpdateAsync(TEntity)` は、**引数のモデルが全列について正しい値を持っている**ことを暗黙の前提にする。呼び出し元が画面の入力だけからモデルを組み立てる場合、その前提は崩れ、**触っていない列がモデル既定値で上書きされる**。

- `ic_card` の `starting_page_number`（Issue #510）/ `carryover_income_total` / `carryover_expense_total` / `carryover_fiscal_year`（Issue #1215）は**登録時にのみ確定し、編集 UI を持たない**。`CardRepository.UpdateAsyncInternal` はこれら4列も無条件に SET していたため、カード管理画面が備考の修正だけを目的に組んだ `IcCard`（当該4項目は既定値 1 / 0 / 0 / NULL）で保存すると、紙出納簿移行カードの繰越累計と出納簿の開始ページ番号が静かに消えていた（Issue #1726）
- **対処は「呼び出し元に引き継がせる」ではなく「SET 句から外す」**。引き継ぎを義務にすると、`UpdateAsync` を呼ぶ経路が増えるたびに同じ抜けが再発する（実際に ViewModel 経路と CSV 経路の2系統があり、片方だけが欠けていた）。列を外せば呼び出し元の実装に依存せず構造的に防げる
- 外した列の扱いは**インターフェースの XML doc に明記する**（「設定しても DB へは反映されない」）。反映されないことを知らずに値を渡す実装が現れると、今度は逆向きの静かな不整合になる
- **登録時専用列を後から更新する要件が出たら専用メソッドを新設する**（`UpdateAsync` の SET 句へ戻さない）。現時点では該当する呼び出し元が無いため、使われないメソッドは作らない
- 操作ログ（`OperationLogger.LogCardUpdateAsync`）は `IcCard` 全体を JSON 化して `BeforeData` / `AfterData` に記録するため、**DB を守るだけでは足りない**。ViewModel 側でも既定値のモデルを渡さないようにする（渡すと「開始ページ番号 7 → 1」という実際には起きていない変更が監査ログに残る）
- **ViewModel 側の引き継ぎは「編集対象の列」以外を網羅する**。カード管理画面が編集するのはカード種別・管理番号・備考の3項目だけなので、残り全部（繰越累計3項目・開始ページ番号・`IsLent` 系3項目・`IsRefunded` 系2項目）を引き継ぐ。一部だけ直すと同じ虚偽差分が別の列で残る（Issue #1726 の初版は繰越4項目だけを直し、`IsRefunded` / `IsLent` の虚偽差分を残していた）
- **引き継ぎ元はキャッシュ由来の一覧（DTO）ではなく、直前に読んだ DB の最新値**。カード一覧は `GetAllAsync` のキャッシュで自動更新されないため、共有モードでは他 PC の貸出が反映されず「貸出中: はい → いいえ」という虚偽の返却を記録し得る
- **「読み取りが null のときのフォールバック」を安易に足さない**。`GetByIdmAsync`（`is_deleted = 0`）が null を返す状況では `UpdateAsync` の WHERE（同じ述語）も一致せず 0 行 → `false` になり、操作ログも記録されない。つまり代替値は**本番で観測されない**。到達不能な分岐とその回帰テストは「競合が手当てされている」という誤った安心感を与えるだけなので置かない（実在する穴は「更新が成功したのに操作ログが残らない」ケースで、Issue #1760 で扱う）
- **モデルにプロパティを足したら `OperationLogExcelExportService.GetFieldNameMap` にも足す**。`FormatJsonToReadable` / `GetChangeSummary` はマップに無いプロパティを読み飛ばすため、載せ忘れると生 JSON には値があるのに操作ログの画面・Excel に一切現れず監査で追跡できない
- 回帰はテスト設計書 §2 UT-021 No.20/21（リポジトリ）・UT-025 No.28（ViewModel）・UT-033 No.9/10（操作ログの可視性）で固定

### 5.5c 保守タスクの直列実行と settings 書き込みの保護（Issue #1737）

`DbContext` は `SQLiteConnection` を **1 本しか持たない**。`LeaseConnectionAsync`（非同期版）はセマフォを取らないため、複数の処理を並列に走らせると同一接続上で `SQLiteCommand` が並列実行される（Issue #1452 の規約）。この規約は Service / ViewModel 層向けに書かれていたが、**起動シーケンス自身がそれを破っていた**。

#### 起動時タスクは直列 await する

`App.PerformStartupTasksAsync` は `_ = backupService.ExecuteAutoBackupAsync();` と戻り値を捨てていた。バックアップ本体（`BackupDatabaseTo`）は同期 `LeaseConnection()` でセマフォを取るため後続タスクはどのみち待たされるが、**セマフォ解放後の継続**が野放しになる:

| 並走していた処理 | 結果 |
|---|---|
| `RecordBackupSuccessAsync`（Issue #1689）の `settings` への INSERT × 2 | `CleanupOldData` が開いているトランザクションの内側に潜り込み、cleanup のロールバックで**記録ごと消える** |
| 同 INSERT が `VACUUM` 実行中に届く | `cannot VACUUM - SQL statements in progress`（`ResultCode=Error`） |

- 実処理は `Services/StartupTaskRunner` に切り出し、**実行順と直列性を単体テストで固定する**（テスト設計書 UT-078）。「順序」ではなく**同時実行数**で表明する
- **await 化のコストはほぼゼロ**。重い部分（DB のコピー）は既にセマフォで直列化されており、増える待ち時間は「古い世代の削除（ファイル走査）＋ INSERT 2 件」分のみ
- **バックアップの呼び出しだけは個別に catch する**。fire-and-forget 時代は「バックアップが落ちても削除・VACUUM は動く」性質があり、単純な await 化はこれを失わせる
- **`Vacuum()` は SQLite 由来の失敗を理由を問わず false（当月スキップ）に畳み、`ResultCode` を Warning ログに残す**。呼び出し元は CAS ロック（Issue #1482）を**消費してから**ここへ来るため、例外を投げ返してもロックは戻らず当月は誰も再試行しない。Busy / Locked だけを catch していると上表の `Error` が素通りし、ログには「起動時タスクでエラー」しか残らなかった

#### `settings` の書き込みはセマフォ保護下で行う

`settings` は、UI 操作を伴わない保守処理（起動時バックアップの成功記録、月次 VACUUM の CAS ロック）から書かれる**唯一のテーブル**である。`SettingsRepository` の書き込みは `WriteGuardedAsync` に集約し、§5.5b の分岐規約に従う:

| 分岐 | 条件 | 動作 |
|---|---|---|
| ① | 呼び出し元が `TransactionScope` を引き渡した | そのトランザクションを全文に適用（commit/rollback は呼び出し元の責務） |
| ② | 引数 null かつ `HasActiveTransactionScope == true` | 接続だけ借りて暗黙参加（自己デッドロック回避の backstop） |
| ③ | それ以外 | 自前で `BeginTransactionAsync`（＝セマフォを取る）→ 実行 → commit |

- **入れ子になる経路は①で明示的に引き渡し、②に頼らない**。`HasActiveTransactionScope` は `DbContext` の**プロセス全体のカウンタ**（`_activeTransactionCount`）であり、**「自分のスコープか他フローのスコープか」を区別できない**。②に依存すると、無関係な別フローがスコープを保持しているだけで書き込みが無保護になり、そのロールバックで消える —— #1737 が直そうとした欠陥そのものが別の形で復活する。`SaveAppSettingsAsync` / `SaveWindowSettingsToDbAsync` は①でスコープを渡す
- **②自体は残す**。`BeginTransactionAsync` は `SemaphoreSlim(1,1)` を取るため、自分のフローが開いたスコープの内側で開き直すと自己デッドロックする（Issue #1575）。①への移行漏れがあってもデッドロックさせないための backstop として維持する
- **③は `ExecuteWithRetryAsync` で包む**。1 文の autocommit だったものが BEGIN → INSERT → COMMIT になり共有モードの SQLITE_BUSY 面が広がるため、既存の同種経路（`SaveAppSettingsAsync`）と同じ防御を掛ける（Issue #1727 の「リトライの適用範囲は経路ごとに確認する」）
- **`CleanupOldData` は同期 `LeaseConnection()` を使うため `HasActiveTransactionScope` は立たない**。したがって cleanup 実行中の `SetAsync` は③に入り、セマフォ待ちで正しく直列化される。テストで外側の保持側を再現するときは `BeginTransactionAsync` で代用せず、実際と同じ同期リースで作ること（代用すると②に入り、検証したい経路を通らない）
- **他リポジトリ（Card / Ledger / Staff）の同型の書き込み（計17箇所）は本 Issue の対象外**。いずれもユーザーの単一操作を起点とし、アプリの状態機械で直列化されるため、保守処理と並走する経路が無い。将来これらをバックグラウンド処理から呼ぶ場合は同じ保護を検討すること

#### 失敗の伝え方

- **`ExecuteAutoBackupAsync` の失敗は「例外」ではなく「null 戻り値」**（内部で全例外を catch する）。`StartupTaskRunner` が戻り値を捨てると、バックアップ先が到達不能でも起動シーケンスのログは正常に見える。**戻り値を観測して Warning を残す**こと。個別の `try/catch` は「将来 `BackupService` が例外を投げるようになっても後続タスクを止めない」ための backstop であり、現在の実装では到達しない
- **`StartupTaskRunner` の DI 解決は `App` 側の `try/catch` で囲む**。`RunAsync` の内部 catch は自分自身の解決を覆えない。保守タスクの依存が構築できないだけで窓口業務（貸出・返却）まで止めない
- **`Vacuum()` の失敗はログレベルで「待てば直るか」を区別する**。`Busy` / `Locked` / `Error`（"SQL statements in progress"）は Warning、`ReadOnly` / `Full` / `Corrupt` / `NotADb` / `CantOpen` / `Perm` は **Error**。CAS ロックは VACUUM 実行前に消費されるため、恒久的な失敗を「来月再試行します」の Warning に紛れさせると、書き込み不可・破損した DB が放置される。判定は `DbContext.IsPermanentVacuumFailure` に集約し、実機で再現困難な `ReadOnly` / `Full` / `Corrupt` は分類そのものをテストで表明する

#### 5.7.2 文字コード判別（`TextEncodingDetector`、Issue #1744）

CSV の読み取り（`CsvImportService.ReadCsvFileAsync`）は、全インポート経路（カード／職員／利用履歴／利用履歴詳細の Import・Preview 計 8 か所）が共有する唯一の入口である。ここで文字コードを誤ると、化けた日本語が `staff` / `ic_card` / `ledger` / `ledger_detail` へそのまま入る。

| クラス | パス | 種別 | 責務 |
|-------|-----|------|-----|
| `TextEncodingDetector` | `Common/` | public static | バイト列の文字コード判別と復号（`Decode` / `GetDisplayName`） |
| `DetectedTextEncoding` | `Common/` | public enum | 判別結果（`Utf8WithBom` / `Utf16*` / `Utf32*` / `Utf8` / `ShiftJis` / `Undecidable`） |
| `TextDecodeFailure` | `Common/` | public enum | 失敗理由（`None` / `Undecidable` / `DeclaredEncodingUnreadable`） |
| `TextDecodeResult` | `Common/` | public sealed | 判別結果・復号済みテキスト・失敗理由（失敗時は `Text` が null） |

**判別順序**: BOM（UTF-32 LE/BE → UTF-8 → UTF-16 LE/BE）→ BOM なし UTF-8 → BOM なし Shift_JIS（cp932）→ 判別不能。

- **UTF-32 LE の BOM（`FF FE 00 00`）は UTF-16 LE の BOM（`FF FE`）と前方一致する**ため、長い BOM から照合する（`StreamReader` の内部判定と同じ順序）
- **UTF-8 を Shift_JIS より先に試すのは仕様**。UTF-8 の日本語（例: `E3 81 82`）は cp932 としても偶然復号できてしまうため、逆順にすると UTF-8 のファイルが化ける。一方 Shift_JIS の日本語はトレイルバイトが `0x40`–`0x7E` を取り得るため、ほぼ確実に不正な UTF-8 になる
- **復号はすべて例外フォールバック**（`throwOnInvalidBytes` / `DecoderFallback.ExceptionFallback`）。既定の `Encoding.UTF8` は不正バイトを U+FFFD へ置換して**成功を返す**ため、呼び出し元が「読めたのか化けたのか」を区別できない。これが Issue #1744 の本体だった
- **BOM なしの復号結果に NUL 文字（U+0000）が含まれたら判別不能とする**。UTF-16 の ASCII 部分（`41 00` 等）は**すべて妥当な UTF-8 バイト**であるため厳格 UTF-8 の検査を素通りし、U+0000 混じりのゴミ文字列が「成功」として返る。CSV に NUL 文字は現れないため、これを中断のシグナルに使う（BOM 付きの経路には適用しない — そちらは文字コードが確定しており、NUL は判別の問題ではなく内容の問題）
- **「判別できない」と「判別できたが読めない」を区別する**。BOM がある時点で文字コードは確定しており曖昧ではないため、BOM 付きで復号に失敗した場合は `DeclaredEncodingUnreadable` とし、**判別された文字コードを結果に残す**。両者を混ぜると、破損した自前エクスポート（UTF-8 BOM 付き）に対して「判別できませんでした／CSV UTF-8 形式で保存し直してください」という誤診断＋無意味な指示になる
- 中断時の例外は理由で使い分ける: 判別不能 → `FileOperationException.UndecidableEncoding`（FILE008）、宣言された文字コードで読めない → `UnreadableDeclaredEncoding`（FILE009）。いずれもインポートを 1 行も実行せずに中断する
- **中断は必ず `LogWarning` で記録してから投げる**。呼び出し元の `catch` は結果オブジェクトへ文言を写すだけでログを書かないため、記録できるのは `ReadCsvFileAsync` の中だけ。成功時（Shift_JIS 判別）だけ Information を出して中断時が無言だと、調査が必要な側の痕跡が残らない
- Shift_JIS 等と判別した場合のみ `LogInformation` を出す（文字化けの相談を受けたときの切り分け材料。`LogDebug` は本番のログレベル設定では出力されない／Issue #1716）。**BOM の有無を文言で断定しない** — UTF-16 / UTF-32 は BOM があるからこそ判別できており、表示名（「UTF-8（BOM付き）」等）が既にそれを示す
- **ファイル全体は長さぶんのバッファ 1 つで読む**。`MemoryStream` + `ToArray()` は倍々バッファと連続配列の二重確保になり、`PlatformTarget=x86` の 2GB 空間で数十MB の台帳 CSV を扱う際に不要なピークを生む

**例外 → ユーザー向け文言の対応表は `CsvImportService.ToUserFacingErrorMessage` の 1 か所**に集約する。以前は共通ハンドラー 2 つと利用履歴の Import / Preview に同じ ladder が計 4 回書かれており、Issue #1744 で `FileOperationException` を足す際も 4 か所すべてに同じ catch を書く必要があった。**次に対応表を変える人が利用履歴経路を取りこぼす**（＝この Issue が直したのと同じ形の欠陥）ため、`catch (Exception)` 1 つから共通の変換関数を呼ぶ形へ統一した。`AppException` は `UserFriendlyMessage` を使い、生の `ex.Message` を UI へ出さない（Issue #1614）。

> **DB 制約違反のドメイン例外は `AppException` を継承させる**（Issue #1757）。`DuplicateCardNumberException`（カード種別＋管理番号の UNIQUE 制約違反、`CARD001`）は `CardRepository` の INSERT / UPDATE / 復元の 3 経路すべてが投げ、カード登録・カード編集・カード復元・カードCSVインポートが `UserFriendlyMessage` をそのまま案内に使う。継承させる意味は、①文言を例外クラス 1 か所に集約して経路ごとの食い違いを防ぐこと、②捕捉漏れがあっても本表の `AppException` 分岐と `App.OnDispatcherUnhandledException` が拾うため「予期しないエラー（SYS999）」へ落ちないこと（多層防御）。一括処理では加えて**行番号付きの `CsvImportError`** へ変換する（`AppException` 継承は文言だけを守り、**行番号は守らない**ため、ループ内の捕捉は省略できない）。
>
> **文言の集約は「経路ごとに取れる行動が同じ」ときにだけ成立する**。復元経路には管理番号の入力欄が無く「別の番号を指定してください」は実行不能な指示になるため、`ForRestore` ファクトリで「どうすれば」だけを差し替える（「何が」「なぜ」は共通のまま）。集約を理由に実行できない指示を出さないこと。

> **`SettingsViewModel.LoadConfigFile` と統合しない**: あちらは Inno Setup が ANSI で書く `database_config.txt` を対象とし「BOM なし＝Shift_JIS」と決め打ちしてよい。CSV は UTF-8（BOM なし）も現実に存在するため判別が要る。**同じ「BOM を見る」処理でも方針が異なる**ので、共通化すると片方の前提がもう片方を壊す。

> **エクスポート側は UTF-8 BOM 付き固定**（`CsvExportService.CsvEncoding = new UTF8Encoding(true)`）。自作ファイルの往復は BOM 付きで成立するが、日本語版 Excel で「CSV（コンマ区切り）」として保存し直すと BOM が失われ ANSI（Shift_JIS）になる。この往復こそがマニュアル §5.6.5 の推奨手順だったため、判別なしでは推奨運用が文字化けの経路になっていた。

#### 5.7.3 インポートの原子性（トランザクション境界、Issue #1745）

**インポートの投入ループは経路を問わずトランザクションで囲み、「全か無か」で確定させる。**

| 経路 | 実装 | 失敗時 |
|------|------|--------|
| `ImportCardsInternalAsync` | `BeginTransactionAsync` | `errors > 0` → `Rollback`、`ImportedCount = 0` |
| `ImportStaffInternalAsync` | 同上 | 同上 |
| `ImportLedgersAsync` | 同上（Issue #1745 で追加） | 同上（`importedCount` と `updatedCount` の両方を 0 に戻す） |

- **書き込みは必ず `scope.Transaction` を引き渡す**（§5.5b の「①」経路）。`InsertAsync(Ledger)` / `UpdateAsync(Ledger)` の tx なしオーバーロードは `LeaseConnectionAsync()` で接続を借りて **autocommit** で書くため、途中行の失敗（共有モードの SQLITE_BUSY・接続断）で部分コミットが残る。`HasActiveTransactionScope` による暗黙参加（②）は backstop であって正規手段ではない（Issue #1737）
- **投入ループに行ごとの `try/catch` を置かない**。例外を握って続行すると、ロックが取れない状況では後続行も同じ理由で失敗して同一のエラーが行数分だけ並び、かつ `ex.Message` が UI のエラー一覧へ直接載る（Issue #1614 違反）。例外はメソッド冒頭の `catch` へ抜けさせ、`ToUserFacingErrorMessage` の集約済み対応表で 3 要素文言へ変換する（§5.7.2）
- **`SQLiteException` は `DatabaseException.QueryFailed` へラップしてから再スローする**。生の `SQLiteException` は `ToUserFacingErrorMessage` の `default` 分岐に落ちて `ex.Message` が漏れる
- **`catch` の中では素の `scope.Rollback()` を呼ばず、`TryRollbackImportTransaction` を使う。ログはロールバックより先に書く**。ロールバック自体が失敗し得るため（`COMMIT` が SQLITE_BUSY 等で失敗すると SQLite 側は既に自動ロールバック済みで `SQLiteTransaction` が無効化されており、続く `Rollback()` は例外になる。接続断でも同様）、素で呼ぶと**二次例外が本来の失敗要因を置き換えて抜け**、①その `catch` の `LogError` が実行されず障害調査の手掛かりが残らない、②`DatabaseException` へのラップも飛ばされて `default` 分岐から生の英語メッセージが UI へ出る（Issue #1614 違反）、という二重の害になる。握りつぶしても**データが確定することはない** — 書き込みが確定するのは `Commit()` の成功時だけで、未コミットのトランザクションは `TransactionScope.Dispose()` で必ず巻き戻る（カード／職員／利用履歴の 3 経路すべてに適用）
- **コミット後のキャッシュ無効化はカード／職員だけに要る**。`LedgerRepository` は `ICacheService` を参照しておらず `CacheKeys` にも ledger 系プレフィックスが無いため、履歴では行わない（「倣う」ことを理由に存在しないキーを足さない）
- 部分コミットが無くなるため、失敗時は `ImportedCount = 0` となり `DataExportImportViewModel.BuildPartialImportGuidance(0)`（Issue #1781）の「登録が確定した行はありません」経路に入る。プレビューも `importCommitted = false` で保持され、修正せずそのまま再実行できる
- **`ImportedCount = 0` は「完了」と通知しない**。`HandleImportResultAsync` のエラー付き終了は無条件に「部分成功」とみなされ、タイトル「インポート完了（一部エラー）」・本文「インポートが完了しましたが」と表示していた。本節の変更で `ImportedCount = 0` が**通常の失敗形**になったため、本文の「登録が確定した行はありません」と見出しが同一ダイアログ内で矛盾する。判定には**新しい条件式を立てず `importCommitted` に相乗りさせる**（同じ判断を2か所に分けない、Issue #1728。この分岐では `Success = false` のため `importCommitted` は `ImportedCount > 0` と等価）。ステータス欄も `IsStatusError = true` にする。カード・職員のインポートも同じ分岐を通るため 3 種別に効く（`ImportLedgerDetailsAsync` はトランザクションを持たず `ImportedCount > 0` になり得るため従来どおり「完了（一部エラー）」）

> **`ImportLedgerDetailsAsync`（`CsvImportService.Detail.cs`）は本節の対象外**。明細インポートは `NewLedgerFromSegmentsBuilder` 経由で `ledger` 行も生成するため、トランザクション境界の検討が別途必要（Issue #1745 のスコープ外）。

#### 5.11a 設定項目は「読まれている」ことを規約テストで担保する（Issue #1820）

`OrganizationOptions` の全プロパティが本番コードから実際に読まれていることを、
`OrganizationOptionsUsageConventionTests` がリフレクション＋ソーステキストの静的検査で固定する。

- **検査対象はリフレクションで導出する**（ファイル名・項目名で列挙しない）。項目を足した人が
  検査の追加を忘れても、自動的に検査対象へ入る（`.claude/rules/development-conventions.md`
  「ガードを書くときは経路を列挙する」）
- **検査はコメント除去後に行う**（`TestSourceInspection.RemoveCommentsPreservingLines`）。
  除去しないと「この項目は未使用」と説明したコメント自体が「使用されている」と判定される（極性の反転）
- **照合は所有者ごと**（`ReportLayout.TitleText` の形）に行う。プロパティ名だけで照合すると、
  XAML から生成される同名の識別子（`ToastNotificationWindow.TitleText`）を拾って空振りする
- 本テストは「読まれているか」だけを見る。読まれた値が**効いている**ことは、消費側の個別テストが
  **既定と異なる値を設定してから**表明する（`ReportFileNameConfigurationConsumerTests` /
  `BusTextConfigurationConsumerTests`）

**背景**: `TemplateMapping` は 18 項目中 5 項目しか読まれておらず、`ReportService` は同名の
ローカル `const` と列リテラルを使っていた。管理者マニュアル §7.4 が設定可能と案内していたため、
「設定できるのに反映されない」状態（dead config）が広告されていた。未実装の 13 項目は削除した。

  **ファイル名としては不正だがパスとしては不正でない**ため `Path.GetInvalidPathChars()` に
  含まれず、`Path.GetFileName` を素通りする。`IndexOfAny(Path.GetInvalidFileNameChars())` で
  先に弾かないと `workbook.SaveAs` の時点で例外になり、「管理者の設定ミスで帳票作成を止めない」
  という本クラスの目的そのものが果たせない。**「不正な文字」を扱う API はパス用とファイル名用で
  集合が違う**ことを、どちらを使うか決める前に確認する
- **縮退したことを Information で記録する**（同）。フォールバックは**正常終了する**ため、
  記録が無いと管理者から見て「設定したのに反映されない」＝本 Issue が是正した状態と区別が付かない
  （`.claude/rules/development-conventions.md` #1744「フォールバックが働いたことを呼び出し元が
  知れるか」、#1819「縮退を伴う処理では規模を記録する」）。ログには**設定値と実際に使った既定書式の
  両方**を載せる（片方だけでは突き合わせられない）。一括出力ではカード枚数ぶん呼ばれるため
  **同一書式につき 1 回**に絞る（#1819 のヘルスチェックと同じ判断）。**空設定はログを出さない** —
  空欄は「既定を使う」という正当な指定であり、出すと既定配布の全環境で帳票のたびにログが出て
  本当の設定ミスが埋もれる

**統合バリデーション（`Validate`）**: 以下の統合を拒否する。

| 条件 | 理由 |
|------|------|
| 異なるカードの履歴 | カードごとの残高チェーンが壊れる |
| 貸出中レコードを含む | 返却時に物理削除されるプレースホルダのため |
| チャージと利用の混在（受入と払出の混在） | 月次帳票は「チャージと利用は別行」（Issue #837） |
| チャージとポイント還元の混在（Issue #1736） | 両者とも受入のみで上の3条件を通過するが、混在した詳細集合は `SummaryGenerator.Generate` がどの摘要パターンにも該当せず空文字を返し、摘要が空欄の行が保存される。集計はチャージ／ポイント還元行を摘要文字列の完全一致で分類するため（`business-logic.md`「ledger を集計するときの前提」）、結合摘要を新設せず統合自体を拒否する。暗黙のポイント還元（Issue #942: 負金額・フラグなし）も `SummaryGenerator.IsImplicitPointRedemption` で同じ分類とし、摘要生成との判定一致を保つ |

**摘要再生成の空文字ガード（Issue #1736）**: 統合先の摘要は `SummaryGenerator.Generate` で再生成するが、空文字が返った場合（明細を持たない手入力行同士の統合等）は統合先の元の摘要を維持する（`LedgerSplitService` の分割時ガードと同じパターン）。摘要が空欄の行は物品出納簿でどの取引か判別できなくなるため、空欄のまま保存しない。

**統合の取り消し（`UnmergeAsync`、Issue #1806）**: 台帳の復元（`ILedgerMergeRepository.UnmergeLedgersAsync(undoData, tx)`）と「取り消し済み」マーク（`MarkMergeHistoryUndoneAsync(historyId, tx)`）を `MergeAsync` と同じ形で 1 つの `BeginTransactionAsync` スコープに束ね、どちらかが `false`（競合）ならロールバックする。

| 段階 | 競合の検出 | 利用者への案内 |
|------|-----------|---------------|
| 履歴の取得（`GetMergeHistoryEntryAsync`） | `is_undone = 1` の履歴は対象外（null） | 「統合履歴が見つかりません。他のPCまたは他の操作で既に取り消された可能性…」 |
| 台帳の復元 | 明細の移動 `UPDATE … WHERE rowid = @rowid AND ledger_id = @targetId` と統合先の `UPDATE … WHERE id` の影響行数が 1 でない（統合後の明細編集・分割・削除、統合先の削除） | 「統合の取り消しに失敗しました。統合後にこの履歴の内容が編集・分割・削除されたか、他のPC…で先に取り消された可能性…」 |
| 取り消し済みマーク | `UPDATE ledger_merge_history … WHERE id = @id AND is_undone = 0` が 0 行（他 PC が同時に取り消した） | 「…この統合は他のPCまたは他の操作で既に取り消されています…」 |
| 例外 | — | `ExceptionMessageFormatter.ToUserMessage(ex, "統合の取り消し")`（生の `ex.Message` は UI へ出さない。Issue #1614） |

失敗時は `MainViewModel.ExecuteUnmergeAsync` が履歴一覧と「統合を元に戻す」ボタンの有効状態を再読込する（統合コマンドの失敗分岐と同じ #1753 の作法）。復元だけを先に確定させない理由と、rowid スコープの根拠は §5.5b を参照。

`HandleImportResultAsync` 内に残す。**分岐を追加するときは `_dialogService.ShowXxx` を直接呼ばず、戻り値の `Action` に載せること**（ダイアログ種別の列挙を持たない形にしてあるため、新分岐で表示地点を書き足し忘れて無表示になる経路は生まれない）。この規約は `DataExportImportViewModelImportPathSharingTests` がソーステキスト検査で固定する — 挙動テストは既存分岐しか通らないため、新しい分岐だけが規約から外れても緑のまま通るためである。遅延させた表示は `try`/`catch` インポート）のみで、カード管理・職員管理・システム管理の各 ViewModel には未是正の箇所が計10か所残っている（Issue #1793）。**
2. **記録の失敗を業務処理の失敗として通知しない。** 本 API 群は `OperationLogRepository` まで含めて例外を握りつぶさないため、共有モードでは `SQLITE_BUSY` が実際に送出される。データの書き込みが確定した後に呼ぶ以上、例外を業務処理の `catch` へ流すと**確定済みの操作が「失敗」と通知され、再実行による二重登録**を招く（#1727「コミット確定後の後処理を、成否の判定に巻き込まない」）。呼び出し元は記録だけを個別に `try/catch` し（`DataExportImportViewModel.TryLogImportAsync` が参考実装）、失敗時は「処理は完了済み・再実行しない・管理者へ連絡」を案内する。**無言で握りつぶさない**（技術的詳細はログへ）。
3. **payload に項目を足したら表示側2か所にも足す。** 一括操作の payload は**対象テーブルではなく Action で形が決まる**ため、テーブル別の仕組みからは漏れる。① `OperationLogExcelExportService.GetFieldNameMap` は全テーブルのマップへ一括操作項目（`BulkOperationFieldNames`）を併合する（マップに無いプロパティは読み飛ばされ、Excel の「変更前 / 変更後」列が空欄になる。#1726 と同型） ② `OperationLogSearchViewModel.GenerateTargetDisplayName` は payload に `FileName` があればそれを「対象詳細」列に表示する（テーブル別の生成メソッドはエンティティ項目しか見ないため必ず空になる）。`RESTORE` は DB 丸ごとリストアと `LogStaffRestoreAsync`（レコード単位復元）で共用されるため、**Action ではなく `FileName` の有無で振り分ける**。

- `DataExportImportViewModel.ExportAsync` / `HandleImportResultAsync`（`ExecuteImportAsync`・`ImportAsync` の両コマンドが `RunImportAsync` 経由で到達する共通の結果処理、Issue #1785） — CSV 操作の成功時（部分成功時も `ImportedCount > 0` なら記録）

- リストア成功後の `operation_log` は**リストア後の新 DB** に記録される（既存 DB 接続が同一パスの新ファイルを参照するため）

#### 5.18a モーダル表示には必ずオーナーを渡す（Issue #1794）

`MessageBox.Show(message, title, button, image)` のようにオーナーを渡さないオーバーロードでは、WPF が `GetActiveWindow()` でオーナーを解決する。**呼び出しスレッドがフォアグラウンドでないときこれは NULL になり**（ownerless）、下位のウィンドウが無効化されない。

処理中オーバーレイ（`Border Grid.RowSpan="6"`）は視覚要素であると同時に**全面クリックシールド**でもあり、`IsBusy=true` の間は下位のボタンへのクリックを遮っていた。Issue #1383 / #1784 / #1793 で「オーバーレイを閉じてから結果ダイアログを表示する」構造へ是正したことにより、このシールドも同時に外れる。結果、職員が alt-tab した状態でエラーダイアログが出ると、**背後の「インポート実行」ボタンが有効なまま押せてしまい、モーダルのメッセージループ内側で処理が再入する**。

- 表示は必ず `DialogService.Show`（private）へ集約し、そこで `ResolveOwner()` の結果を `ShowMessageBoxCore` へ渡す。**`MessageBox.Show` の直呼びを増やさないこと**（`DialogServiceOwnerTests` の静的検査が検出する）
- オーナーの選択規則は `Common/DialogOwnerResolver` が持つ。優先順位は **アクティブ → モーダル子に塞がれていない（Win32 `IsWindowEnabled`）ウィンドウのうち最後 → 使用可能な最後のウィンドウ**。`Application.MainWindow` を特別扱いしない（**モーダルダイアログが開いている間にメイン画面をオーナーにすると、そのダイアログが無効化されず欠陥がそのまま残る**）
  - 「モーダル子に塞がれているか」は **WPF の `Window.IsEnabled` では判定できない**。`ShowDialog()` も Win32 `MessageBox` も無効化は `EnableWindow(FALSE)` で行い、WPF の `Window` は `WM_ENABLE` を扱わないため `IsEnabled` 依存関係プロパティは true のまま。P/Invoke の `IsWindowEnabled(hwnd)` を使う（`IsEnabled` で書くとこの段は「最後に生成されたウィンドウ」に退化し、生成順とモーダルの重なり順が一致する間だけ偶然正しく動く）
- **WPF 以外のウィンドウ（表示中の `MessageBox` / `OpenFileDialog` 等）がアクティブなときは null を返し、WPF の解決（`GetActiveWindow()`）に委ねる**（`ShouldDeferToNativeActiveWindow`）。是正前の ownerless は入れ子の `MessageBox`（確認ダイアログ表示中の職員証タッチで別の確認が出る経路等）で外側の `MessageBox` をオーナーとし外側を無効化していた。ここで WPF ウィンドウを選ぶと外側が押せたまま残る。非フォアグラウンド時は `GetActiveWindow()` が NULL なので選択規則を妨げない
- 候補は「ウィンドウハンドルを持ち（表示済みでクローズ前）、**アクティブ化する**（`ShowActivated`）」ものに限る。ハンドルを持たない（未表示・クローズ済み）ウィンドウを `MessageBox.Show(owner, ...)` へ渡しても例外にはならず、WPF は黙って `GetActiveWindow()` へ退化する（＝オーナーを渡したつもりで ownerless）。`IsLoaded` ではなくハンドルの有無で判定する（クローズ後も `IsLoaded` が true のまま残る場合があるため）。**`IsVisible` は条件に含めない** — オーナー（メイン画面）の最小化で Win32 が所有ウィンドウを隠す（`SW_PARENTCLOSING`）と WPF は所有ダイアログの `IsVisible` を false にするため、含めると最前面のモーダルダイアログだけが候補から落ち、無効化済みのメイン画面がオーナーになって復元後にダイアログのボタンが押せたまま残る（本アプリは `Hide()` を使わないため「ハンドルあり」＝「表示済みでクローズ前」）
- **`ShowActivated="False"` のウィンドウを候補から外す理由**: `ToastNotificationWindow` は `Topmost` かつ `ShowActivated="False"` の非モーダルウィンドウで、貸出・返却のたびに**最後に生成されて** `Application.Windows` に載る。除外しないと、アプリが非フォアグラウンドのとき（＝本 Issue の故障シナリオ）に「アクティブが無い → 有効なウィンドウのうち最後」の分岐が**トーストをオーナーに選ぶ**。①Win32 の `MessageBox` は**オーナーだけ**を無効化するため業務画面は有効なまま残り欠陥が是正されない、②トーストは 3 秒（`DefaultDisplayDurationMs`）で自動的に閉じ、**オーナーが破棄されると Win32 は所有ウィンドウも破棄する**ため表示中の `MessageBox` が消えて `ShowConfirmation` が `MessageBoxResult` 0 を受け取り無言で「いいえ」を返す、③エラー通知のトーストは `autoClose: false` のため①②が持続する。判定は型名ではなく性質（`ShowActivated`）で行う
- **優先順位の網羅だけでは足りない。候補を絞る述語（`IsUsableOwnerState`）も同じ粒度で切り出して検査する**。順位づけのテストは代役オブジェクトの「使用可能」フラグを直接与えるため、本番の絞り込み述語を一度も通らない
- **解決できないときは従来どおり ownerless で表示する**。表示しないより、クリックシールドが無い状態でも表示するほうが望ましい
- 選択規則を WPF 非依存の署名（ジェネリック＋述語）にしているのは、`Window` が STA スレッドでしか生成できず、規則を単体テストで網羅できないため。**「継ぎ目を通っているか」だけを `Window` 実体つきの 1 テストで確かめ、規則の網羅は代役オブジェクトで行う**
- **`Window.ShowDialog()`（`INavigationService.ShowDialog<T>`）は本項の対象外**。WPF の `ShowDialog` はアプリケーション内の他ウィンドウをすべて無効化するため、`Owner` は z 順・タスクバー表示にしか効かない
- **本 Issue のスコープは `DialogService` のみ**。`MainViewModel` / `ReportViewModel` / `ErrorDialogHelper` 等に残る `MessageBox.Show` の直呼び（約34か所）は同じ形の欠陥を持つが、性質の異なる経路（致命エラー・`Window` コードビハインド）を含むため段階的に移行する（Issue #1837）

> `OnHealthCheckTimerElapsed` の catch は `LogTrace` のみで、`appsettings.json` の既定フィルタ（`Logging:LogLevel:Default = Information`）により本番のログファイルに一切出力されていなかった。`SetConnectionState` は `ConnectionStateChanged` を同期発火するため、購読者（`MainViewModel.OnCardReaderConnectionStateChanged`）の例外もこの catch に集まる。「リーダーを挿しても警告が消えない」という問い合わせの手掛かりがゼロになるため、Issue #1730 の規約どおり **`LogTrace` を残したまま `LogWarning(ex, …)` を併設**する。
> ヘルスチェックは 10 秒周期（`HealthCheckIntervalMs`）で走るため毎回出すとログが肥大化する。連続失敗回数（`_consecutiveHealthCheckFailures`）を数え、**初回と `HealthCheckFailureLogIntervalCount`（=30。約 5 分）ごと**にのみ出力する。判定は実機 felicalib に依存せず検証できるよう純関数 `ShouldLogHealthCheckFailure` へ切り出している（回帰は `FelicaCardReaderHealthCheckLoggingTests`）。失敗が止んだことも `LogInformation` で残し、失敗の Warning と対で継続期間を追えるようにする。**読み取り開始（`StartHealthCheckTimer`。再接続ボタン経由を含む）では連続失敗回数を 0 に戻す** — 監視セッションの区切りであり、持ち越すと「初回は必ず残す」保証が効かず（持ち越した回数が間隔の倍数に達するまで無言になる）、「連続N回目」も再接続をまたいだ値になって継続期間を追えなくなる。カウンタとタイマー起動はいずれも private かつ実機依存のため、この不変条件はソーステキストの静的検査で固定する（抽出範囲の妥当性も併せて表明。#1794 の教訓）。

#### Dispose のキュー排出順序（Issue #1732）

`Dispose()` は **`CompleteAdding()` → `_outputTask.Wait(2秒)` → タイムアウト時のみ `Cancel()`** の順で終了する。この順序は変更しないこと。

### 9.5 WpfDispatcherService（Issue #1725）

`IDispatcherService` の本番実装。UI スレッドへ処理をマーシャリングする。**ディスパッチした処理の例外を必ず観測してログへ残す**責務も持つ。

#### なぜ観測が必要か

`Dispatcher.InvokeAsync` は fire-and-forget に見えるが、**例外を握り潰す経路が 2 段ある**。

| 段 | 何が起きるか |
|----|-------------|
| 1. `DispatcherOperation` | `Dispatcher.InvokeAsync` は例外を戻り値の `DispatcherOperation.Task` に格納する。`Invoke`（同期版）と違い `Application.DispatcherUnhandledException` は**発火しない** |
| 2. 内側の `Task` | `InvokeAsync(Func<Task>)` は `InvokeAsync<TResult>` として解決され `DispatcherOperation<Task>` を返す。`.Task` は `Task<Task>` であり、**外側だけ観測しても async lambda 本体の例外は取りこぼす** |

どちらも観測しないと `TaskScheduler.UnobservedTaskException`（`App.xaml.cs`）が **GC ファイナライズ時に遅れて発火するだけ**で、操作と無関係なタイミングで「バックグラウンド処理エラー」トースト（Issue #1742 以前はモーダルダイアログ。§10.1a 参照）が出る一方、障害調査に使えるログは残らない。Issue #1725 で `MainViewModel` の `Processing` 固着が無言のまま起きた原因の半分がこれ。

#### 実装

```csharp
public void InvokeAsync(Func<Task> asyncAction)
{
    var app = Application.Current;
    if (app == null) return;
    // Task<Task> を Unwrap() して内側まで 1 本の Task として観測する
    ObserveTask(app.Dispatcher.InvokeAsync(asyncAction).Task.Unwrap());
}

internal void ObserveTask(Task task) =>
    task?.ContinueWith(
        t => _logger?.LogError(t.Exception, "UIスレッドへディスパッチした処理が例外で終了しました"),
        CancellationToken.None,
        TaskContinuationOptions.OnlyOnFaulted | TaskContinuationOptions.ExecuteSynchronously,
        TaskScheduler.Default);
```

- `ObserveTask` を `internal` 公開しているのはテストのため。`InvokeAsync` 本体は `Application.Current` を必要とし単体テストから駆動できないので、観測ロジックだけを切り出して検証する（`WpfDispatcherServiceTests`）
- ログレベルは `LogError`。`LogDebug` では本番の `Logging:LogLevel:Default = Information` によりファイルへ一切出力されず、「無言で握りつぶさない」という目的を果たせない（Issue #1716 の教訓）。失敗時のみ出力するのでログ肥大化は起きない
- `ILogger` はコンストラクタで省略可能。DI 未登録の環境でも動作させるため
- **`ObserveTask` は状態を復元しない。** 例外の可視化が責務であり、`Processing` 固着のような状態の巻き戻しは各 ViewModel の `try/finally` が担う（Issue #1725 の修正は両方を含む。→ `03_画面設計書.md` §3.2）

`TaskScheduler.UnobservedTaskException` のハンドラ本体。このイベントは Task のファイナライズ時（＝**ファイナライザスレッド**）に発火するため、ハンドラの振る舞いには通常のエラー提示と異なる制約がある。

| 制約 | 理由 |
|------|------|
| 同期ディスパッチ（`Dispatcher.Invoke`）禁止 | UI 処理が完了するまでファイナライザスレッドがブロックされ、プロセス全体のファイナライザキュー（SQLite 接続等の後始末）が停止する |
| モーダル表示（`ErrorDialogHelper` の Show 系 → `MessageBox.Show`）禁止 | 無人の共用端末では [OK] が押されるまで長時間放置され、上記ブロックが継続する |
| 例外を一切外へ漏らさない | ファイナライザから例外が漏れるとプロセスが異常終了する |
| シャットダウンガード（`HasShutdownStarted` / `HasShutdownFinished`）必須 | Dispatcher 停止後のポストは実行されず、例外の温床になるだけ |
| 通知はクールダウン（`NotificationCooldown` = 5分）で間引く | エラートーストは自動消去されない（クリックで閉じる）ため、共有モードのヘルスチェック失敗のような繰り返し発生する障害で発火のたびに通知すると、無人の共用端末にトーストが際限なく積み上がる。**ログは間引かず毎回記録する** |

- **通知は `Dispatcher.BeginInvoke`（非同期）＋トースト（`IToastNotificationService.ShowError`、非モーダル）**。文言は `ExceptionMessageFormatter.ToUserMessage(ex, "バックグラウンド処理")` で**例外種別に応じて**組み立てる（固定文言だと「管理者に連絡」と案内された管理者へ原因が伝わらない。トースト本文は `TextWrapping="Wrap"` のため長めでも切れない）
- **ログ記録は `Action<Exception, string>` デリゲートで受け、App 側の配線が経路を選ぶ**: `_logger`（ILogger）が使えればそちら、DI コンテナ構築前・構築失敗時は `ErrorDialogHelper.LogException`（DI 非依存のファイルログ `error_YYYYMMDD.log`、ダイアログ非表示）へフォールバックする。旧実装は `ErrorDialogHelper.ShowError` が DI 非依存でログも書いていたため、単純に ILogger へ寄せると**ロガー未初期化の時期の発火が無痕跡になる**（本 Issue のコードレビューで検出）
- WPF 非依存のデリゲート注入とし、単体テストから駆動できるようにする（`WpfDispatcherService` が `Application.Current` 依存の本体から `ObserveTask` を切り出したのと同じ判断）。時刻も `Func<DateTime>` で注入し、クールダウンを決定論的にテストする
- `App.OnUnobservedTaskException` は `e.SetObserved()` を**最初に**呼んでから本クラスへ委譲する。委譲の `?.` は意図的な fail-safe（配線順の退行でハンドラ未生成のまま発火しても、ファイナライザスレッドで NullReferenceException を投げるよりログ喪失の方が被害が小さい。SetObserved 済みのためプロセスは守られる）。配線の制約は `AppUnobservedTaskExceptionConventionTests` がソーステキストの静的検証で固定し、本体の挙動は `UnobservedTaskExceptionHandlerTests` が検証する（07_テスト設計書 UT-080）

### 10.4 競合検出時のユーザー向け文言（Issue #1759）

```mermaid
classDiagram
    class ConcurrencyConflictMessage {
        <<static>>
        +ForUpdate(target, listName)$ string
```

`ICardRepository` / `IStaffRepository` の `UpdateAsync` / `RestoreAsync` / `DeleteAsync` が `false` を返すのは、WHERE 句（`is_deleted = 0` または `is_deleted = 1`）に **1 行も一致しなかった場合だけ**である（影響行数による競合検出、§5.5b / Issue #1753）。つまり「原因不明の失敗」ではなく**競合の検出**であり、原因を具体的に案内できる。

| 論点 | 設計判断 |
|------|---------|
| なぜ 1 クラスに集約するか | 同じ形の分岐が `CardManageViewModel`（更新・復元×2）と `StaffManageViewModel`（更新・復元×2・削除）に計 7 か所あるため。呼び出し側へ直接書くと「次に対応表を変える人が一部の経路を取りこぼす」（`.claude/rules/error-messages.md`） |
| なぜ原因を断定しないか | 「他のパソコンで削除されました」と断定すると、ローカルモード（単一 PC）で同じ分岐に到達したとき職員が存在しない相手を探すことになる。「他のパソコンや別の操作で〜した可能性があります」とモード中立に書く |
| 操作ごとに「なぜ」を変える理由 | 復元できなかった原因は「先に**復元**された」であって「削除された」ではない。取り違えると利用者を真の原因から遠ざける（Issue #1744 の「判別できない／判別できたが読めない」と同じ判断） |
| 「なぜ」が同じでもファクトリを分ける場合 | `ForRefund` の「なぜ」は `ForUpdate` と同じ（対象行が削除された）だが、**「何が」は利用者が実際に行った操作で述べる**。払い戻しを試みた職員に「更新できませんでした」と出すと、自分の操作と結果が結び付かない（Issue #1760） |
| 呼び出し側の責務 | 文言が「一覧を再読み込みしました」と述べるため、**一覧の再読込を先に行ってから**設定する。再読込しないと案内どおりの操作ができず同じエラーを繰り返す（Issue #1753）。あわせて `CancelEdit()` を呼ばない（入力内容を消さない。Issue #1757） |

**表示領域の要件**: 本文言は 90 文字程度になるため、ステータス欄は `TextWrapping="Wrap"` を持ち、かつ `IsEditing` に連動して畳まれる領域の**外側**に置く必要がある（03_画面設計書 §3.3 職員管理ダイアログ／§3.4 カード管理ダイアログ、Issue #1727 / #1759）。とくに削除の結果表示は**非編集時**に設定されるため、編集フォーム内に置くと一度も表示されない。

**適用対象外**: `InsertAsync` が `false` を返す経路（カード・職員の新規登録失敗）は、INSERT の影響行数が 0 になる状況が実質存在せず（制約違反は例外として送出される）原因を断定できないため、本クラスの対象にしない。原因を特定できないまま「他のパソコンで…」と案内すると誤誘導になる。

### 10.4a 監査ログを残せない書き込みを行わない（Issue #1760）

カード・職員の編集／払い戻し／削除は、`operation_log` 用に更新前データを `GetByIdmAsync`（`is_deleted = 0`）で読んでから書き込む。**この読み取りが null を返したら、書き込みを試みずに §10.4 の競合として扱う。**

対象経路は**画面の動詞ではなく、テーブルへの書き込み文で数える**（Issue #1757 の教訓）。`ic_card` / `staff` への UPDATE は 4 種あり、それぞれ扱いが決まる。

| 書き込み文 | 画面の操作 | 事前読み取りが null のとき | 書き込み後の再読取が null のとき |
|-----------|-----------|--------------------------|--------------------------------|
| `UPDATE`（編集項目） | カード編集・職員編集 | 中止して競合案内（`ForUpdate`） | （再読取しない） |
| `UPDATE`（`is_refunded`） | カードの払い戻し | 中止して競合案内（`ForRefund`）。台帳も作らない | `CreateRefundedSnapshot` で記録 |
| `UPDATE`（`is_deleted = 1`） | カード削除・職員削除 | 中止して競合案内（`ForDelete`） | （再読取しない） |
| `UPDATE`（`is_deleted = 0`） | 復元（各3か所） | （復元前データは `includeDeleted: true` で取得済み） | `CreateRestoredSnapshot` で記録 |

| 論点 | 設計判断 |
|------|---------|
| なぜ「ログだけ諦める」ではいけないか | 通常は読み取りが null なら書き込みの WHERE も 0 行になるが、**読み取りと書き込みの間に他 PC が対象行を復元すると書き込みだけが成功**する。`if (before != null)` でログを飛ばす実装では、この経路で**変更が確定したのに監査記録に何も残らない**。`operation_log` は 6 年保存される唯一の監査記録であり、記録の漏れは誤った記録が残るのと同等以上に問題になる |
| なぜ「`BeforeData=null` で記録する」を採らなかったか | 更新経路の `IcCard` は編集 3 項目以外を更新前データから引き継いで組み立てる（§5.5b / Issue #1726）。更新前データが無いまま記録すると `AfterData` に既定値（開始ページ番号 1／繰越累計 0／払戻済いいえ）が入り、**実際には書き換えていない列の虚偽の差分**が監査ログに残る。`UPDATE` の SET 句は 3 列だけなので DB は無事だが、ログだけが嘘をつく |
| 読み取りの位置 | **書き込みより前**に置く。払い戻しは従来「払戻台帳 INSERT → 更新前データ取得 → `SetRefundedAsync`」の順で、競合時に**払戻台帳だけが残る**中途半端な状態を作り得た |
| 書き込み後の再読取が null のとき | 払い戻し・復元は既に確定しているため記録を落とさない。**その操作が変えた列だけ**を読み取り済みデータへ適用したスナップショット（`CreateRefundedSnapshot` / `CreateRestoredSnapshot`）で記録する。全列を既定値にすると #1726 と同じ虚偽の差分になる |
| 競合案内の集約 | 「ラベル確定 → キャッシュ破棄 → 一覧再読込 → 文言設定」の順序を守る箇所が各 ViewModel で複数になったため、`NotifyConflictAsync` / `NotifyDeleteConflictAsync` へ集約する（順序を呼び出し側へ書き写さない） |
| なぜキャッシュ破棄が要るか | 書き込みを中止する経路は**リポジトリの書き込みを 1 回も通らない**ため、影響行数 0 でのキャッシュ破棄（§10.4 / Issue #1759）が働かない。`GetAllAsync` はキャッシュ経由なので、`InvalidateCache()` を再読込より**前**に呼ばないと「一覧を再読み込みしました」が事実にならない。**早期 return は、呼ばなくなったメソッドが担っていた副作用ごと飛ばす** |
| 検出タイミングで文言を変えない | 事前読み取りで検出した場合と影響行数 0 で検出した場合は同じ条件（対象行が無い）なので同じ文言にする。カード削除の `CardOperationResult.NotFound` も同じ案内へ寄せる（Issue #1757） |

> **この判断は「読み取り → 判断 → 書き込み」を分けて行う他の経路にも当てはまる。** 読み取り結果を使って書き込み内容を組み立てているなら、読み取りの失敗は書き込みの中止であって、付随処理（ログ・通知）だけを省く理由にはならない。

### 10.4b 編集対象は選択状態ではなく主キーで特定する（Issue #1761）

`CardManageViewModel` / `StaffManageViewModel`（`IsEditing` を持つ ViewModel はこの 2 つだけ）に共通する不変条件。ただし **`Selected*` を `await` の後ろで参照しない**という後半の規約は編集フォームの有無と無関係で、`SystemManageViewModel.RestoreAsync`（`SelectedBackup`）も同じ対象である（洗い出しは「`IsEditing` を持つか」ではなく「`await` の後ろに `Selected*` の参照があるか」で行う。`.claude/rules/development-conventions.md` 参照）。

> **編集フォームが開いている間、編集対象を指すのは `EditCardIdm` / `EditStaffIdm`（主キー）であって `SelectedCard` / `SelectedStaff` ではない。**

`SelectedItem="{Binding SelectedCard}"` は TwoWay バインドのため、**選択行の Ctrl+クリック**や **`Cards.Clear()`（一覧の再読込）による選択解除の書き戻し**で選択だけが null に戻る。編集フォームは `IsEditing` にのみ連動するため開いたままで、入力内容も残る（画面の見た目は何も変わらない）。

| 論点 | 設計判断 |
|------|---------|
| 選択が外れたらフォームを閉じるか | **閉じない**（Issue #1761 の案A）。選択解除は利用者の明示的な操作以外でも起きるため、閉じると入力途中の備考・氏名が予告なく消える。`OnSelected*Changed(null)` はコマンドの実行可否の再評価だけを行う |
| 競合案内での名指し | 編集開始時（`StartEdit`）および編集中の対象切替時（`OnSelected*Changed(value != null)`）に**一覧の表記を退避**する（`_editTargetCardType` / `_editTargetCardNumber`、`_editTargetName` / `_editTargetNumber`）。`NotifyConflictAsync` はこの退避値を受け取る |
| なぜ「選択があれば選択、無ければ入力値」ではいけないか | §10.4 は「未保存の入力値で名指ししない」（Issue #1759）を定めたが、選択優先＋入力値フォールバックの形は**選択が外れた瞬間に、まさに禁じた形へ落ちる**。フォールバックが書いてあることは、それが正しく機能していることを意味しない |
| 削除・払い戻しの識別情報 | **最初の `await` より前**にローカル変数へ確定させる。`RefundAsync` の残高取得（`GetLatestLedgerAsync`。`BeginBusy` の外＝オーバーレイ無し）が**実際に選択状態の変わり得る待機点**で、待機中に一覧をクリックすると確認ダイアログの組み立てが `NullReferenceException` になっていた。`DeleteAsync` の認証（職員証タッチ待ち）は、現行の `StaffAuthService.RequestAuthenticationAsync` が内部に `await` を持たず（モーダル `ShowDialog()` 後に `Task.FromResult`）モーダル中は他ウィンドウが無効化されるため**現時点では選択が外れない**。同じ形に揃えるのは不変条件の遵守と、認証サービスが非同期化された場合の退行防止のため |
| `!` 演算子について | 本プロジェクトは nullable 参照型を有効にしていないため `SelectedCard!` の `!` は**コンパイル後に何も残らず実行時チェックにならない**。null 安全は「参照しない設計」で担保する |

**残存する `Selected*` の参照**（いずれも同期的で `await` をまたがない）:

- `CanEdit` / `CanDelete` / `CanRefund` の述語（コマンドの実行可否）
- 各コマンド冒頭の null ガードと、その直後のローカル変数への確定

回帰は `CardManageViewModelTests` / `StaffManageViewModelTests` の Issue #1761 region（07_テスト設計書 §2 UT-085）が固定する。画面側の規約は 03_画面設計書 §3.4.2。

> **`ApplyMigration` が `internal`（`~`）である理由**（Issue #1738）: 「他 PC が同じバージョンを先に記録済みの状態で適用する」経路を、`MigrateTo` 冒頭のバージョン読み取り（＝スキップ判定）を経由せずに検証できるようにするため。production コードからは `MigrateTo` 経由でのみ呼ばれる。Issue #1484 で `DbContext.BackfillLegacyMigrationVersion1` を `internal static` へ切り出したのと同じ意図。
>
> **`RecordMigration` / `MigrationRecordExists`**（Issue #1738）: 適用記録の INSERT は `INSERT OR IGNORE` で、複数 PC 同時起動時の PRIMARY KEY 衝突を正常系として扱う。ただし `OR IGNORE` は `NOT NULL` / `CHECK` 違反も握りつぶすため、影響行数が 0 のときは `MigrationRecordExists` で行の有無を読み戻し、「他 PC が先に記録した（正常）」と「書き込めなかった（異常）」を区別する。後者は `MigrationException` とする。詳細は `.claude/rules/migrations.md` および 02_DB設計書 §4 を参照。
