# Gitワークフロー（厳守）

## ブランチルール
- **mainブランチへの直接コミットは禁止**（バージョン更新等の軽微な変更も含む）
- すべての変更は必ずブランチを作成し、PRを経由してマージすること
- ブランチ命名規則: `fix/issue-XXX-短い説明`、`feat/issue-XXX-短い説明`、`docs/issue-XXX-短い説明`、`chore/短い説明`

## スタックした PR は、親をマージしたら base を付け替えてからブランチを消す（Issue #2019 / PR #2020）

段階的な作業で PR を積む（子 PR の base を親 PR の head ブランチにする）ときは、**親をマージした直後、
「Delete branch」を押す前に**子 PR の base を `main` へ付け替えること。

```
gh pr edit <子PR番号> --base main
```

- **base ブランチが消えると GitHub は子 PR を自動でクローズする**。PR #2020 は親 #2017 のマージ（22:55:51）の
  8 秒後にブランチが削除され、同秒で `base_ref_deleted` → `closed` が記録された。**リポジトリの
  `delete_branch_on_merge` は無効**なので、これは自動削除ではなく手動操作で起きた＝順序を守れば完全に防げる
- **クローズされても誰も気付かない**。CI は走らず通知も埋もれ、#2020 は 1 か月近く「マージされたつもり」で
  放置された。さらに Issue #2019 が**別 PR の cross-reference で誤ってクローズ**されたため、
  「対応済みに見えるが実際は未実装」の状態になっていた
- **付け替えはどのみち必要な操作**。親の差分が子 PR から消えて、レビューすべき差分だけが残る
- **取りこぼしの洗い出しは「マージされずに閉じた PR」で行う**。open PR を見ても、これから起きる事故しか
  分からない
  ```
  gh pr list --state closed --limit 300 --json number,title,mergedAt,baseRefName \
    --jq '.[] | select(.mergedAt == null) | "\(.number)\tbase=\(.baseRefName)\t\(.title)"'
  ```
- **滞留した PR は、そのままでは載せ直せないことがある**。#2020 の中身を `main` へ載せ直した #2024 では、
  滞留中にマージされた PR が入れた**静的検査に新規コードが適合せず実際に赤になった**（#2018 の
  `TestConstants` マーカー必須化）。載せ直しでは必ずフルビルド・全テストを実測すること

## コミット時のステージング
- **`git add -A` や `git add .` は使用禁止** — 意図しないファイル（.env、credentials、大きなバイナリ等）が含まれるリスクがあるため
- 必ず `git add <ファイル名>` で個別にステージングすること
- 多数のファイルがある場合でも、変更内容を確認した上で個別に指定する
