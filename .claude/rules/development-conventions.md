# 開発規約

## 環境制約
- インターネット非接続環境で動作する（クラウドサービス利用不可）
- Microsoft 365 E3のみ例外的に利用可能
- Windows 10/11対応（クロスプラットフォーム対応不要）
- 自己完結型ビルド（single-file publish）で配布
- **共有フォルダモード**: SMB共有フォルダ上にDBを配置し、複数PC（最大約20台）で共有可能。UNCパスまたはマップドネットワークドライブ指定時に自動判定（Issue #1559）。ローカルフルパス指定では共有モードにならない

## DB設計原則
- 日付はTEXT型（ISO 8601形式: YYYY-MM-DD HH:MM:SS）で保存
- 表示時に和暦変換（WarekiConverter使用）
- IDmは16進数文字列（16文字）として保存
- 外部キー制約を有効化
- 削除方式はテーブルごとに異なる（→「論理削除の方針」参照）
- **1 メソッドで 2 文以上（DELETE→INSERT 等）を発行するリポジトリメソッドは 3 分岐にする**（Issue #1724）。SQLite は接続に活性トランザクションが無いと各文を autocommit で即確定するため、`command.Transaction` を設定し忘れた文は同メソッド内の後続文が失敗しても巻き戻らない（`ReplaceDetailsAsync` はこれで `ledger_detail` の明細が全消失した）。分岐は ①tx 引数あり → その tx を全文に適用（commit/rollback は呼び出し元）②引数 null かつ `_dbContext.HasActiveTransactionScope` → 接続だけ借りて暗黙参加（同上、外側スコープに委ねる）③それ以外 → 自前 `BeginTransactionAsync` で commit/rollback まで持つ。**②は省略不可** — `BeginTransactionAsync` は `SemaphoreSlim(1,1)` を取るため入れ子で開くと自己デッドロックする（Issue #1575）。実装例は `LedgerRepository.InsertDetailsAsync` / `ReplaceDetailsAsync` / `DeleteAsync`、詳細は `ICCardManager/docs/design/05_クラス設計書.md` §5.5b
  - **②は backstop であって、入れ子経路の正規手段ではない**（Issue #1737）。`HasActiveTransactionScope` は `DbContext` の**プロセス全体のカウンタ**（`_activeTransactionCount`）で、**「自分のスコープか他フローのスコープか」を区別できない**。②を主たる保護手段にすると、無関係な別フローがスコープを保持しているだけで書き込みがセマフォ無しで実行され、そのロールバックで消える。**入れ子になる経路は必ず①で tx を明示的に引き渡す**こと。②は①への移行漏れがあってもデッドロックさせないための保険として残す
  - **①を用意せず②＋③だけで書くと、この誤りは「動いているように見える」**。#1737 の初版は `SaveAppSettingsAsync`（1 スコープ内で `SetAsync` を10回以上呼ぶ）が②を通っており、テストも既存テストも緑だった。**②を通る本番経路が 1 つでもあるなら、それは①にすべき経路である**と考えること
- **UPDATE / DELETE は影響行数で競合を検出する**（Issue #1753）。共有モードでは読み取り（`GetByIdAsync`）と書き込みが別トランザクションになるため、その間に他 PC が同じ行を変更・削除し得る。`ExecuteNonQueryAsync()` の戻り値を捨てず、0 行なら競合として `false` を返すこと。SQLite の `changes()` は WHERE に一致した行を値が変わらなくても数えるため「0 行＝行が存在しない」と断定できる（MySQL と異なる）。ただし **0 行が正常な文では検証しない**（例: 明細を持たない ledger に対する `UPDATE ledger_detail`）。`MergeLedgersAsync` は3文とも影響行数を見ずに無条件 `true` を返しており、`LedgerMergeService` の競合エラー分岐が到達不能なデッドコードになっていた。**`bool` を返すリポジトリメソッドの戻り値を呼び出し元が握りつぶす形の抜けにも注意**（`UpdateAsync` は正しく返すのに `LedgerSplitService` / `LedgerDetailViewModel` が破棄していた）。競合検出時は UI 側で一覧を再読込すること（文言で「画面を更新して再試行」と案内する以上、再読込しないと同じエラーを繰り返す）
  - **影響行数 0 のときこそキャッシュを無効化する**（Issue #1759）。`CardRepository` / `StaffRepository` の `InvalidateCardCache` / `InvalidateStaffCache` は `if (result > 0)` の内側にあり、**競合（0 行）では呼ばれていなかった**。`GetAllAsync` はキャッシュ経由（既定 TTL 60 秒／共有モードはカード 15 秒・職員 30 秒）のため、UI が案内どおり一覧を再読込しても削除済みの行が並んだままになり、「一覧を再読み込みしました」という文言が事実にならない。**0 行は「自分の持っている行の状態が古い」と確定した瞬間**であり、書き込みが成功したときより無効化の根拠が強い。`if (result > 0)` は「変更したから捨てる」という発想だが、正しくは「古いと分かったから捨てる」
  - **再読込は選択状態を壊す**（同）。`ItemsSource` を `Clear()` すると、DataGrid の `SelectedItem="{Binding SelectedX}"`（TwoWay）が選択解除を書き戻し `SelectedX` は null になる。**再読込より後で `SelectedX` を参照する実装は本番でのみ `NullReferenceException` になる**（View を持たない ViewModel 単体テストは素通りする）。エラー文言に載せる識別情報は**再読込より前に**ローカル変数へ確定させ、回帰テストは `CollectionChanged` の Reset を購読して書き戻しを再現する
  - **エラー文言で対象を名指しするときは、未保存の入力値ではなく一覧に載っている値を使う**（同）。氏名や管理番号を書き換えている途中に競合すると、編集後の値は一覧のどこにも存在せず「一覧で状態を確認して」という案内が実行できなくなる
  - **握りつぶしの検出は grep ではなく静的検査で固定する**（Issue #1944）。#1753（`LedgerSplitService` / `LedgerDetailViewModel`）→ #1808（`CsvImportService` の兄弟ファイル）→ #1944（`MainViewModel` の履歴削除 2 経路）と **3 度再発**しており、そのたび「横断で洗う」と書いてきたが、洗う手段が人手の grep である限り次の経路で再発する。`RepositoryWriteResultConventionTests`（#1953 で `UpdateLentStatusAsync` を追加し `RepositoryDeleteResultConventionTests` から改称）は `.DeleteAsync` の呼び出し位置の直前を遡り、文の先頭（直前が `;` / `{` / `}`）なら戻り値を捨てていると判定する。**判定できない前方の形は fail-open にせず違反として報告する**（絞り込みが fail-open だとガードは緑のまま無力化する。#1764）
  - **握りつぶしは、モックを使う既存テストからは見えない**（同）。`Verify` されるだけの loose モックは `Task<bool>` に既定 `false` を返すため、**戻り値を捨てるコードと受けるコードでテストの結果が変わらない**。#1944 の 2 経路は「削除できたら監査ログを記録する」テストが**修正前も修正後も緑**であり、赤くなるのは「削除**できなかったら**記録しない」側だけだった。**競合側（`false` を返す側）の表明を書かない限り、この family の欠陥は検出できない**
  - **監査ログの記録有無は、ログ記録クラスのモックでは表明できない**（同）。`OperationLogger` のメソッドは `virtual` ではないため `Mock<OperationLogger>` の実体は本物を実行する。**本物が書き込む `IOperationLogRepository` のモック**で `InsertAsync` の呼び出しを見る（#1760 が定めたのと同じ作法）
  - **同じ書き込みが 2 経路にあるなら、片方を直すのではなく 1 つへ寄せる**（同）。#1944 の 2 経路（履歴一覧の削除コマンド `DeleteLedgerRow`／行編集ダイアログの削除要求）は DELETE →監査ログ→ commit →`is_lent` リセット→再読込 4 連まで**完全に同型の写し**だった。しかも後者は `Views.Dialogs.LedgerRowEditDialog` を実体化するため **ViewModel 単体テストから 1 件も踏めない**。寄せない限り、その経路の正しさは静的検査でしか担保できない（#1763）
  - **読み取りが null になる経路も、同じ競合として同じ案内を出す**（同）。`GetByIdAsync` が null を返す原因は DELETE が 0 行になる原因と同一（他 PC が先に削除した）である。旧実装は前者を `if (fullLedger == null) return;` で無言で戻しており、**同じユーザー操作・同じ故障原因が経路によって「案内あり」と「削除ボタンを押しても無反応」に分かれていた**（`error-messages.md`「同じ制約違反はすべての経路で同じ例外へ変換する」と同じ形）
  - **例外を `bool` へ畳むときは、「もう一度実行すれば成功し得る失敗」を巻き込んでいないか確かめる**（Issue #1951）。`CardRepository` / `StaffRepository` の `InsertAsyncInternal` にあった `catch (SQLiteException) { return false; }` は、制約違反だけでなく **SQLITE_BUSY / SQLITE_LOCKED まで畳んでいた**。`DbContext.ExecuteWithRetryAsync` は `when (ex.ResultCode == Busy || Locked)` で判定するため、**例外が `false` に化けた時点でリトライ対象から外れる** — 共有モードで他 PC が書き込みロックを持っている一瞬に当たっただけの登録が、恒久的な失敗として職員に報告されていた。#1763「二次例外は例外の型で分岐している上位の判定をすべて外す」が、**意図的な握りつぶしの側からも**起きる形。
    - **`false` へ畳んでよいのは「同じ条件で何度やっても失敗する」ものだけ**。例外フィルタ（`when (!DbContext.IsTransientLockError(ex))`）で除外し、UNIQUE 制約違反・主キー重複の従来どおりの扱いは対のテストで固定する。除外だけを書くと catch を丸ごと消した実装でも緑になる
    - **一過性かどうかの判定は 1 か所に置く**（#1763）。Busy / Locked の判定は `ExecuteWithRetryAsync` と `CleanupOldData` に既に書き写されており、リポジトリ側にもう 2 つ足すと「片方だけが新しい ResultCode を知っている」状態が生まれる。`DbContext.IsTransientLockError` を唯一の定義とする
    - **再スローしても、届く先が無ければ何も変わらない**。カード・職員の登録経路はどれも `ExecuteWithRetryAsync` で包まれていなかった。**「リトライに届くようにする」修正は、その経路にリトライが実在することを確かめてから完了とする**。包む位置はトランザクションを持たない公開オーバーロードで、外側スコープが開いているとき（暗黙参加）は包まない（他フローの tx の内側で同じ文を再実行することになる。#1724 の②）
    - **`false` を投げる側へ変えたら、受け皿の有無を呼び出し元すべてで数える**（コードレビューで検出）。`StaffManageViewModel.SaveAsync` は包括的な `catch (Exception)` を元から持っていたが `CardManageViewModel.SaveAsync` は持たず、**この修正だけでは「登録に失敗しました」が「予期しないエラー（SYS999）」＋スタックトレースのモーダルへ悪化する**ところだった（#1757 が避けたのと同じ状態）。**戻り値を例外へ変える修正は、その例外を誰が受けるかを確かめて初めて完了する** — 上の項目「届く先が無ければ何も変わらない」の裏面にあたる。受け皿は一過性ロックだけを狙った `catch` にする（メソッド全体を包むと、コミット確定後の後処理の失敗を別扱いで報告する #1727 / #1805 / #1816 を飲み込む）
    - **ガードを「語の存在」で書かない**（同）。`filter.Contains("IsTransientLockError")` は、極性が反転した `when (IsTransientLockError(ex))`（＝一過性ロック**だけ**を畳む、この Issue の欠陥そのもの）を適合として通す。否定を伴う参照だけを適合とし、**反転形が違反になること**をサンプル入力で固定する（#1786「極性の反転」／#1843「ガードは綴りではなく資源で書く」）
    - **兄弟メソッド間の非対称は、それ自体が合図**。同じテーブルへ書く `UpdateAsyncInternal` / `RestoreAsyncInternal` はこの catch を持たず、同じ故障原因が経路によって `false` と例外に分かれていた（#1808「兄弟ファイルでも同じ欠陥が起きる」の裏返しで、**片方だけが余計な防御を持っている**形）
    - **ロック競合の回帰テストは、保持時間を「1 回目の試行が実際に失敗する」ことから逆算する**。`PRAGMA busy_timeout = 0` にしても System.Data.SQLite は内部で約 2.8 秒再試行してから SQLITE_BUSY を返す（実測）。保持を 250ms にした初版は 1 回目の試行がそのまま成功し、**修正前のコードでも緑**だった。**「ロックを保持した」ことは「相手が Busy を受け取った」ことを意味しない**
    - 回帰は `SQLiteBusySwallowConventionTests` が「フィルタ無しで `return false;` へ畳む catch の不在」と「一過性ロックを除外するフィルタの実在」を対で静的検査する（#1764。個別の挙動テストは経路の追加に追随できない）
  - **`bool` を返す書き込みを、業務トランザクションの内側で捨てない**（Issue #1953）。#1753 / #1808 / #1944 は「呼び出し元が戻り値を捨てる」形だったが、`LendingService` は**同じトランザクションの中**で `CardRepository.UpdateLentStatusAsync` の戻り値を捨てており、**競合した片方だけがコミットされていた**。貸出では `ledger` に貸出中レコードだけが入って `is_lent = 0` のまま確定し（手元に無いカードが次のタッチで新規貸出として再記録される）、返却では逆に `is_lent = 1` が残る（返却済みカードが長期未返却として督促され続ける）。**トランザクションで束ねることは「全部成功する」ことを意味しない — 束ねた各文が失敗を伝えているかは別の問題**であり、`business-logic.md` が「`is_lent` と貸出中レコードは**一時的に**ずれる（起動時に修復される）」と書いていた前提が恒久的に崩れていた。
    - **巻き戻すには例外が要る**。`if (!updated) return false;` では `scope.Commit()` の手前で抜けても、書いた側の文はトランザクションの中に残るだけで**呼び出し元が「何が起きたか」を知る手段が無い**。例外の型は `AppException` の派生にする — `LendingService.GetUserFriendlyErrorMessage` の `AppException` 分岐が `UserFriendlyMessage` を尊重するため、捕捉漏れがあっても「予期しないエラー（SYS999）」へ落ちない（#1757）。`SQLiteException` ではないので `ExecuteWithRetryAsync` のリトライ対象にもならず、同じ競合で無駄に再試行しない
    - **経路ごとに「0 行のときに何をすべきか」は違う**。貸出・返却は巻き戻す。起動時の整合性修復は**件数に数えないだけ**でよい（他 PC が削除しただけなら、そのカードの不整合はもはや運用に影響しない）。コミット確定後の後処理（`MainViewModel.ResetIsLentIfNoOtherLentRecordsAsync`）は成否に巻き込まない（#1805）。**同じ「0 行」でも扱いが 3 通りに分かれる**ので、握りつぶしを是正するときは経路ごとに決めること
    - **`false` へ変えた瞬間、loose モックの既定値に依存していた既存テストが表面化する**。#1953 では「貸出成功」を表すはずのテストが `UpdateLentStatusAsync` を設定しておらず、**既定値 `false` のまま緑だった**。逆に言えば、その欠陥がある間は「成功を表すフィクスチャ」と「競合を表すフィクスチャ」がテストから区別できなかった（`testing.md`「モックの既定値で通っていないか」）
    - **キャッシュ無効化も同時に見る**（#1759）。`UpdateLentStatusAsync` の `InvalidateCardCache()` は `if (result > 0)` の内側にあり、**競合したときだけ破棄されない**という #1759 とまったく同じ形が残っていた。0 行は「手元の一覧が古い」と確定した瞬間であり、破棄の根拠は成功時より強い
  - **暗黙 rowid で行を特定する UPDATE は、所属（親 ID）も WHERE に含める**（Issue #1806）。`ledger_detail` は INTEGER PRIMARY KEY を持たない暗黙 rowid のテーブル（AUTOINCREMENT なし）で、表末尾の行が消えると次の INSERT が同じ rowid を再利用する。統合取り消しの `UPDATE ledger_detail SET ledger_id … WHERE rowid = @rowid` は、統合後に統合先の明細が編集（`ReplaceDetailsAsync` の DELETE + INSERT）されて rowid が振り直されると、0 行のまま「取り消しました」（統合元が明細ゼロで復活）か、再利用された rowid を持つ**無関係な台帳の明細を復活先へ移す**（交差破損）かのどちらかになった。`WHERE rowid = @rowid AND ledger_id = @targetId`（`UpdateDetailBusStopsAsync` と同じ）にして影響行数 0 を競合とする。**後から参照する識別子が再利用され得るなら、その識別子だけで行を特定しない**
  - **「同じ論理操作」を構成する複数メソッドの書き込みは、呼び出し元が 1 つの tx に束ねられる形で公開する**（同）。`UnmergeLedgersAsync` は内部で `Commit()` して返り、呼び出し元がその**あと**に別接続で `MarkMergeHistoryUndoneAsync` を呼んでいたため、マークだけが失敗（共有モードの SQLITE_BUSY / UNC 断）すると「台帳は復元済み・履歴は未取消」が残り、案内どおりの再実行で統合元が**もう一度 INSERT** された（月次帳票の二重計上）。両方に `SQLiteTransaction` を受け取るオーバーロードを用意し、`LedgerMergeService.UnmergeAsync` が `MergeAsync`（#1458）と同じ形で 1 スコープから呼ぶ。マークは `AND is_undone = 0` の影響行数で「他 PC が先に取り消した」競合も検出し、後着の復元ごと巻き戻す。**片方が成功したあとで、もう片方の失敗を「再実行してください」で回収できるか**を、書き込みを 2 つに分けた時点で確かめること
  - **`bool` の握りつぶしは「同じサービスの兄弟ファイル」でも起きる**（Issue #1808）。`CsvImportService.Ledger.cs` は `var success = await UpdateAsync(...)` で正しく受けていたのに、`CsvImportService.Detail.cs` の親 Ledger 更新は `await _ledgerRepository.UpdateAsync(ledger);` と戻り値を捨てていた。共有モードで他 PC が履歴を削除していると、明細だけ差し替わって（実際は `ON DELETE CASCADE` で親ごと消えて）UI は「インポート完了」と表示する。#1753 の横断洗い出しで `grep "await .*UpdateAsync("` のように**戻り値を受けていない呼び出し**を機械的に列挙し直すこと（`Verify` されるモックは既定値 false を返すため、テストは「握りつぶし」があると緑のまま通る ― `.claude/rules/testing.md`「モックの既定値で通っていないか」）
- **「2 文以上」は同じ文を N 回発行する形も含む**（Issue #1945）。`UpdateDetailBusStopsAsync` は明細ごとに `UPDATE ledger_detail` を発行するが `command.Transaction` を設定しておらず、途中の 1 件が競合しても先行する明細の更新だけが autocommit で確定していた。**ループで書く形は「1 文だけ」に見えるため、#1724 の適用対象から漏れやすい** — 数えるのは文の種類ではなく、実際に発行される文の本数。
  - **失敗を伝えられない型（`Task`）で書き込みメソッドを公開しない**。このメソッドは影響行数を捨てたうえで `Task` を返していたため、呼び出し元 2 か所が失敗を知る方法が**存在しなかった**。`bool` の握りつぶし（#1753 / #1808 / #1944）は grep や静的検査で見つけられるが、**戻り値そのものが無い形は「握りつぶし」として検出できない**
  - **同じ事実を 2 か所に持つなら、書き込み順で手当てが変わる**。`ledger.summary` と `ledger_detail.bus_stops` は同じ事実（どのバス停から乗ったか）を持ち、片方だけ確定すると 6 年保存の台帳が自己矛盾する（摘要は「バス（天神～博多）」・明細は `★`）。**どちらの経路も両方の書き込みを 1 つのトランザクションで囲む**（#1806）。順序は「どちらが先に壊れるか」を変えるだけで、不整合そのものは消えない — 明細 → 摘要の順（バス停入力ダイアログ）は戻り値を見れば競合時に摘要へ到達せず戻れるが、**明細が確定したあとで摘要の書き込みが失敗**すれば明細だけが新しい鏡像の不整合が残る。「順序を工夫すれば戻り値の確認だけで足りる」で止めない。後者は `scope.Commit()` の後ろで tx の外に置かれており、「SMB 共有モードのロック競合を避けるため」というコメントが付いていた — **同一 tx にするほうがロックの保持は短い**。「別トランザクションにする理由」がコメントに書いてあっても、それが整合性を壊していないかは別途確かめる
  - **回帰テスト自身が故障の起点を作れているかを表明する**。SQLite の暗黙 rowid は `max(rowid)+1` で採番されるため、表末尾の行が消えると同じ番号が再利用される。「全置換で rowid が振り直される」テストは、対象台帳より**大きい rowid の行を残しておかない**と再採番が起きず、修正前のコードでも緑になる（初版が実際にそうだった）。前提そのものをテスト内で assert する
- **エクスポート → インポートの往復で値が変質しないことを、変換を足した時点で確かめる**（Issue #1808）。`CsvExportService` は式インジェクション対策（#1267）で全テキスト列の先頭に `'` を付け得るが、取り込み側は同じ `Sanitize` を掛けていた（`'` 始まりには冪等）ため、UI から入力した `-異動予定` がエクスポート→取り込みで `'-異動予定` に恒久変化した。**管理者マニュアルが推奨する「エクスポート CSV を編集して取り込む」運用がそのまま汚染経路**だった
  - **出力側で付ける変換には、入力側で剥がす逆変換を対で用意する**（`FormulaInjectionSanitizer.Sanitize` ↔ `Unsanitize`）。逆変換の適用範囲は「出力側が変換する列すべて」に揃える（備考だけ剥がしても、管理番号・駅名で同じ非対称が残る）。読み取りは 1 つのヘルパー（`CsvImportService.ReadTextField`）へ寄せ、列を足すたびに配り忘れる形を残さない（#1763）
  - **「防御多層化」の名目で入力側にも同じ変換を掛ける前に、その層が実際に何を守るかを確かめる**。UI 入力を通さない入力側サニタイズは sink 側の防御を代替できず、往復非対称の原因にしかならなかった。防御は sink 側（CSV／Excel エクスポート・帳票・操作ログ・ダッシュボード出力）に一本化し、DB には UI 入力と同じ自然な値を保存する
  - **往復の回帰テストは、出力側の実出力を入力側の実処理に通す形で書く**（`CsvImportServiceTests` の「エクスポートした CSV をそのまま取り込む → 全項目一致で Skip」）。単体の `Unsanitize(Sanitize(x)) == x` だけでは、取り込み側が別の列で `Sanitize` を掛け直している退行を検出できない
- **null と空文字を「同じ未設定」として保存する列は、比較でも同じ正規化を通す**（Issue #1808）。職員番号は保存時に `IsNullOrWhiteSpace ? null : value` で null へ落とすのに、`DetectStaffChanges` は CSV の `""` と DB の `null` を生で比較していたため、職員番号未設定の職員が同一 CSV の再取り込みで毎回「更新」に数えられ、プレビューに実在しない差分「職員番号: (なし) → （空）」が出た。**同じ関数内で備考だけ正規化済み（#1370）で職員番号が取り残されていた**形。保存時の正規化式と比較時の正規化式は同じヘルパー（または同じ式）を使い、「保存経路で正規化している列」を grep で列挙して比較側を揃えること
- **読み取りが null なら、書き込みも行わない**（Issue #1760）。「読み取り → 判断 → 書き込み」を別トランザクションで行う経路で、**読み取り結果を使って書き込み内容や付随処理（操作ログ・通知）を組み立てているなら、読み取りの失敗は書き込みの中止であって、付随処理だけを省く理由にはならない**。`CardManageViewModel` / `StaffManageViewModel` は操作ログ用の更新前データが null のとき `if (before != null)` でログ記録だけを飛ばして書き込みを続行しており、**読み取りと書き込みの間に他 PC が対象を復元すると書き込みだけが成功**して、6 年保存される `operation_log` に「誰がいつ何を変更したのか分からない変更」が残った
  - **「その分岐は到達しない」で済ませない**。通常は読み取りの述語（`is_deleted = 0`）と書き込みの WHERE が同一なので 0 行 → 失敗になるが、**両者が別トランザクションである以上、間に状態が戻る競合が成立する**。同一述語であることは到達不能の証明にならない
  - **対象経路は「画面の動詞」ではなく「テーブルへの書き込み文」で数える**。#1760 の初版は「編集・払い戻し」という画面の言葉で 3 経路を数え、**同型の削除 2 経路と復元 6 経路を取りこぼした**（コードレビューで検出）。`ic_card` / `staff` への UPDATE を列挙すれば、編集項目・`is_refunded`・`is_deleted = 1`（論理削除）・`is_deleted = 0`（復元）の 4 種すべてが視野に入る。**これは #1757 が「部分ユニークインデックスは復元でも評価される」で記録したのと同じ数え間違い**であり、規約に書いてあっても対象領域（例外変換 → 監査ログ）が変わると再発する。横断で洗うときは、まず対象テーブルへの書き込み文を grep で列挙すること
  - **代替値で埋めて記録する案を採る前に、その代替値が何になるかを見る**。#1760 の案B（`BeforeData=null` で記録）は、更新経路の `IcCard` が編集項目以外を更新前データから引き継ぐ構造（#1726）のため、`AfterData` に既定値（開始ページ番号 1／繰越累計 0／払戻済いいえ）が入る。**SET 句が 3 列に絞られているので DB は無事だが、監査ログだけが虚偽の差分を残す**。「記録が無い」を避けようとして「嘘の記録」を作らない
  - **読み取りの位置そのものが仕様になる**。払い戻しは「台帳 INSERT → 更新前データ取得 → 払戻済へ更新」の順だったため、競合時に**払戻台帳だけが残ってカードは払戻済にならない**中途半端な状態を作り得た。読み取りを書き込み群の先頭へ移すと、競合を検出した時点で何も書かずに戻れる
  - **確定した操作の記録を、後続の読み取り失敗で落とさない**。書き込み成功後の再読取が null になるのは「直後に他 PC が削除した」場合だけで、操作自体は成立している。**この操作が変えた列だけを更新前データへ適用したスナップショット**で記録する（全列を既定値にすると #1726 と同じ虚偽の差分になる）
  - **書き込みをやめると、書き込みに紐付いていた副作用もやめたことになる**。#1759 の「影響行数 0 のときこそキャッシュを無効化する」は `CardRepository.UpdateAsync` の**内側**にあるため、`UpdateAsync` を呼ばずに戻る #1760 の経路では働かない。破棄しないまま一覧を再読込すると `GetAllAsync` のキャッシュ（既定 TTL 60 秒／共有モード カード 15 秒・職員 30 秒）から削除済みの行を含む古い一覧が返り、「一覧を再読み込みしました」という案内が再び事実でなくなる。**早期 return を足すときは、飛ばした呼び出しが担っていた副作用（キャッシュ破棄・通知・ログ）を数え上げる**（`ICardRepository.InvalidateCache` / `IStaffRepository.InvalidateCache` を新設して呼び出し元から明示的に破棄する）
  - **「ログが残ったか」の検証は、ログ記録クラスのモックではできない**。`OperationLogger` のログ記録メソッドは `virtual` ではないため `Mock<OperationLogger>` の実体は本物の実装を実行する。**本物が書き込む `IOperationLogRepository` のモック**で、実際に挿入された `OperationLog` の中身を表明する
- **「別トランザクションで先に書いた行」が後続の書込みを前提にしていないか確認する**（Issue #1727）。カード登録時の初期残高行は**カードの実残高ではなく、履歴最古エントリから逆算した「その取引の前の残高」**で、直後の履歴インポートが入って初めて正しくなる。それが別トランザクションで先にコミットされ、履歴インポートだけが失敗すると、実カードと合わない行だけが残り残高チェーンが恒久的にずれた。**単独では正しくない行を単独でコミットしない** — 後続処理と同一トランザクションに束ねる。束ねられない事情があるなら、なぜ整合が崩れないのかをコメントに書く
  - **失敗を返す結果オブジェクトは、呼び出し元が見ているかを grep で確かめる**。`bool` の握りつぶし（#1753）と同じ欠陥が結果クラスでも起きる。`HistoryImportResult.Success` はどの呼び出し元からも参照されておらず（参照されていたのは `MayHaveIncompleteHistory` だけ）、例外は `LogError` に出るだけで UI へ一切伝わらなかった。**「ログには出ている」は無言失敗の免罪符にならない**（現場は業務中にログを見ない）
  - **失敗の理由を返すなら「なぜ」だけにし、「どうすれば」は呼び出し元に組み立てさせる**。サービス層は復旧手段を知らない。登録直後の履歴インポート失敗に「しばらく待ってから再度実行してください」と付けると、カード行は既に登録済みで**同じ操作をやり直せない**ため誤った指示になる（正解は「CSVインポートで補完」）。既存の `LendingService.GetUserFriendlyErrorMessage`（#1110）は行動指示まで含み、かつ既定分岐が生の `ex.Message` を返す（#1614 違反）ため、新規経路へ流用しないこと
  - **リトライの適用範囲は経路ごとに確認する**。共有モード対策の `DbContext.ExecuteWithRetryAsync` は貸出・返却・整合性修復には掛かっていたが、履歴インポートだけ抜けていた。**書込みトランザクションを新設したら、既存の同種経路と同じ防御が掛かっているかを見る**
    - **防御を配って回るより、書き込み手段を 1 つに寄せる**（Issue #1763）。上の項目は #1727 の時点で書かれていたのに、**同じ `if` の反対側**（カード内に取り込む履歴が無い登録）を防げなかった。その分岐はトランザクションを持たず `_ledgerRepository.InsertAsync` を 1 文だけ直接呼んでおり、「書込みトランザクションを新設した経路」として数えられなかったからである。ここで欠落するのは「新規購入 / ○月から繰越」＝**そのカード唯一の受入行**で、月次帳票の「受入 − 払出 = 残額」が年度を通して崩れる
    - **「同じ論理的な書き込みに手段が 2 通りあるか」を先に見る**。手段が分かれている限り、リトライ・失敗通知・トランザクションを足すたびに片方へ配り忘れる余地が残り続ける。#1763 の対処は「履歴なし経路にもリトライと通知を足す」ではなく、**両経路を同じサービスメソッドへ寄せる**（`ImportHistoryForRegistrationAsync` に空の履歴リストを渡す）ことだった。#1726 が「呼び出し元に引き継がせる」ではなく「SET 句から外す」を選んだのと同じ判断で、**呼び出し経路が増えるたびに再発する形を残さない**
    - **寄せた先の入力は、既存の挙動を変えない値を選ぶ**。#1763 では `historyDetails` にフィルタ前の履歴ではなく**空リスト**を渡す。この引数は `CheckHistoryCompleteness` の入力でもあるため、履歴を渡すとこの経路で従来出していなかった「履歴が不足している可能性があります」の助言が出る。**共通経路へ寄せるときは、共通側が引数から派生させている副次的な振る舞いを数え上げる**
  - **ロールバックの検証はモックでは観測できない**。「モックの `InsertAsync` が呼ばれた」ことは記録できても、巻き戻ったかは分からない。実リポジトリを噛ませて**実際の行数**を表明する（`LendingServiceHistoryImportTests` が参考実装）。失敗注入は `SQLiteException(Busy)` ではなく `InvalidOperationException` を使うとリトライ待機を挟まず 1 回で確定する
  - **`catch` の中の後始末は、それ自体が失敗し得ることを前提に書く**（Issue #1745）。`scope.Rollback()` は `COMMIT` が SQLITE_BUSY 等で失敗した後だと例外になる（SQLite 側は既に自動ロールバック済みで `SQLiteTransaction` が無効化されている。接続断でも同様）。`catch` の先頭で素の `Rollback()` を呼ぶと、**二次例外が本来の失敗要因を置き換えて抜け**、①その `catch` に書いた `LogError` が実行されず障害調査の手掛かりが残らない、②`DatabaseException` へのラップも飛ばされて `default` 分岐から生の `ex.Message` が UI へ出る（#1614 違反）、という二重の害になる。**ログを後始末より先に書き、後始末は個別の `try/catch` で包む**（`CsvImportService.TryRollbackImportTransaction` が参考実装）
    - 握りつぶしてよいかは「握りつぶすと何が残るか」で判断する。ロールバックの場合、書き込みが確定するのは `Commit()` の成功時だけで、未コミットのトランザクションは `TransactionScope.Dispose()`（`Transaction?.Dispose()`）で必ず巻き戻るため、失敗を握りつぶしてもデータは確定しない。**この「二重の巻き戻し」を確認せずに握りつぶさない**
    - **二次例外は「ログが出ない」だけでなく、例外の型で分岐している上位の判定をすべて外す**（Issue #1763 のコードレビューで顕在化した 3 つ目の害）。`DbContext.ExecuteWithRetryAsync` は `catch (SQLiteException ex) when (ex.ResultCode == Busy || Locked)` でリトライするため、`SQLiteException(Busy)` が `Rollback()` の `InvalidOperationException` に置き換わると**共有モード対策のリトライが丸ごと効かなくなる**。同様に「例外 → ユーザー向け文言」の対応表（`GetHistoryImportFailureReason` 等）も既定分岐へ落ち、原因を名指しできる文言が汎用文へ退化する。**`catch` の中で例外の型が変わり得る処理を書くときは、その例外を型で見ている上位の `when` 句と変換表を数え上げる**（`.claude/rules/error-messages.md` #1757「例外型の変更は、その型を前提にしていた上位の分岐を静かに外す」と同じ形が、意図しない差し替えでも起きる）
    - 同じ形は `finally` の中の `Dispose()`・通知・キャッシュ無効化にもある。**「エラー処理の途中で別のエラーが起きたらどうなるか」を、エラー処理を書いた時点で一度考える**
    - **巻き戻しの手段は `Common/SafeRollback.TryRollback` ただ 1 つに寄せる**（Issue #1831）。#1745（`CsvImportService`）→ #1763（`LendingService` の登録時取込）と経路ごとに private ヘルパーを増やした結果、**同型の未是正が 13 か所残った**（貸出・返却・整合性修復・`LedgerRepository` 5 か所・`SettingsRepository`・`DbContext` 2 か所・`MigrationRunner` 2 か所・`DebugDataService`）。クラスごとにヘルパーを置く形は、次に規約を変える人が一部を取りこぼす形をそのまま残す（#1763「同じ論理的な書き込みに手段が 2 通りあるか」）
      - **`ILogger` を持たない層（リポジトリ・マイグレーション）でも痕跡は残す**。`SafeRollback` は logger が null のとき `ErrorDialogHelper.LogException` へ委譲する（error-messages.md #1817「ILogger を持たない層では `ErrorDialogHelper.LogException`」）。ロガーが無いことを「ログを出さない理由」にしない（#1819「`grep LogDebug` はそもそもロガーを持たない箇所を見つけられない」）
      - **回帰は `SafeRollbackConventionTests` の静的検査で固定する**。3 度再発した形は経路ごとの個別テストでは守れない（error-messages.md #1764）。検査は「`catch` ブロック直下の素の `Rollback()` が無いこと」と「正規手段が実際に使われていること」を**対で**表明する（前者だけだと `catch` ごと消して無言で握りつぶす実装や、走査対象が 0 件に縮んだ状態でも緑になる）
      - **`catch` の外の `Rollback()` は対象外**。`if (ok) Commit(); else Rollback();` の業務的失敗による巻き戻しは、先行する `COMMIT` の失敗が無いためトランザクションは有効で、置き換える「本来の失敗要因」も存在しない
  - **エラー通知を、失敗したサブシステムに依存させない**。#1727 の初版は取込失敗の通知を後処理（一覧の再読込）のあとに置いたが、`LoadCardsAsync` は取込失敗と**同じ原因**（共有フォルダの切断・DB のロック）で例外になるため、**修正が対象とするまさにその状況でだけ通知が失われた**。通知は失敗した資源より前に出すか、後処理を例外フィルタで囲って通知を必ず到達させる（`catch (Exception ex) when (<失敗フラグ>)` にすると成功パスの挙動を変えずに済む）。テストも「1 か所だけ壊れる」前提を置かず、**障害が波及したケース**を 1 件書く
  - **コミット確定後の後処理を、成否の判定に巻き込まない**。`scope.Commit()` の後に走る集計・付帯情報の算出で例外が出たとき、それを同じ `catch` で拾って `Success=false` にすると、**書き込みは成功しているのに「1 行も入っていない」と報告**することになる。呼び出し元が復旧作業（再インポート等）を案内すれば二重計上を招く。後処理は `try` の外に出し、失敗しても「その付帯情報が得られなかった」だけの扱いにする
    - **規約を新設したら、規約が書かれる前から存在した同型の経路を横断で洗う**（Issue #1805）。#1727 で上の規約を書いた時点で、`LendingService.ReturnAsync` は `PersistReturnAsync` のコミット後に残額の解決（`GetLatestLedgerAsync` フォールバック）と残額警告の付与（`GetAppSettingsAsync`）という DB I/O を持ち、`Success` と 30秒ルール用の `LastProcessed*` を**その後ろ**で設定していた。ここでの例外は「返却失敗・もう一度タッチ」と案内され、案内どおりの再タッチが `is_lent = 0` のため貸出として新規に記録される（手元に無いカードが「貸出中」になり督促対象にもなる）。`grep "scope.Commit()"` で列挙し、コミットの後ろに await があるメソッドはすべて確認すること
    - **「成功」の意味を 1 つに定め、その確定位置をコミット直後へ置く**。`Success` を「記録が確定した」ことだけを表す値にし、`LastProcessed*` と併せて `PersistReturnAsync` の戻り直後で確定させる。以降の例外は `catch (Exception ex) when (result.Success)` で吸収して `HasPostCommitFailure = true` にする（`Success` / `ErrorMessage` は変えない）。例外フィルタで書くと、**コミット後に新しい後処理を足しても既定で保護される**（保護側の列挙を義務にしない。#1739 の「クリア側を列挙する」と同じ fail-safe の向き）
    - **付帯情報の欠落は別のフラグで伝え、呼び出し元はその情報を表示しない**。`Balance` は既定値 0 のまま返り得るため、`Success` だけ見て残額を表示すると「残額 0 円」という虚偽を出す。`MainViewModel.HandleReturnSuccessAsync` は `HasPostCommitFailure` のとき残額付き通知を出さず「返却は記録済み／残額を確認できませんでした。再タッチしないでください。」＋ `SoundType.Warning` にする（#1725 と同じ判断）
    - **上流の「記録済み」判定が何に依存しているかを確認する**。#1725 の `recorded` 判定は `result.Success` に依存するため、サービス側が `Success` を落とすと ViewModel 側の救済は届かない。**層をまたぐ判定は、依存する値の意味がその層で保証されているかまで見る**
    - **統合テストの失敗注入は「1 回だけ」に絞る**。`GetAppSettingsAsync` を常に throw させると、返却後のダッシュボード更新も同じ原因で失敗して #1725 の経路（「画面の更新に失敗しました」）と重なり、本 Issue の分岐が出した通知か判別できない。呼び出し回数カウンタで初回だけ throw する（`MainViewModelIntegrationTests.ArrangeSettingsReadFailsOnce`）。恒常的に失敗するケースは**別テスト**で「同題の案内を重ねて出さない」ことを `Times.Once` で固定する（`HandleReturnSuccessAsync` の案内後に `NotifyProcessingFailure(recorded: true)` へ流れる経路。`alreadyNotified` でログのみ残す）
    - **その横断は「同じ tx で書かない」と明記された処理をすくい上げない**（Issue #1954）。#1805 は `grep "scope.Commit()"` で列挙する手順を定めたが、`LedgerMergeService.MergeAsync` は取りこぼされていた。Undo 情報の保存はコメントで「独立した tx。Undo データは別系統のため tx に含めない」と**意図的に外してあった**ため、読むと「別系統だから別扱いでよい」と映る。**「同じ tx に入れない」という判断は、「成否の判定から外す」という判断を含まない** — 別 tx にした処理こそコミット後に走り、そのまま成否へ巻き込まれる
    - **取り消し（undo）情報の欠落は、付帯情報の欠落の中でもとりわけ回復不能**。残額のような表示値と違い、undo レコードが無い統合は**将来にわたって取り消せない**。しかも案内どおりの再実行は「統合対象の履歴が見つかりません」に行き着く（統合元は DELETE 済み）ため、職員は自分の操作が成功したのか失敗したのかを判断できない。UI は「完了・取り消せない・やり直す必要はない」と代替手段（分割・編集）まで案内する（#1725）
  - **エラー文言で原因を断定する前に、その原因が成立する構成かを確認する**。共有モード前提の「他のPCが使用中」「ネットワーク共有フォルダー」をローカルモードで出すと、職員は存在しない相手を探して原因究明が止まる。単一 PC でも VACUUM・バックアップ・接続ヘルスチェックといった**自プロセス内の別接続**と競合して SQLITE_BUSY は起こり得る。「なぜ」が正確であることは `error-messages.md` の 3 要素の前提であり、モードごとに文言を分けるかモード中立な表現にする
- **「並列起動しない」規約は「fire-and-forget しない」も含む**（Issue #1737）。`DbContext` は `SQLiteConnection` を 1 本しか持たず、`LeaseConnectionAsync` はセマフォを取らない。`Task.WhenAll` を書かなくても、**戻り値を捨てた `async` メソッドの継続**が後続処理と同一接続上で並走する。起動処理は自動バックアップを `_ =` で捨てたまま古いデータ削除と VACUUM へ進み、バックアップ末尾の settings への INSERT が削除処理のトランザクション内側に潜り込んで、ロールバックで記録ごと消えていた
  - **「fire-and-forget が稼ぐ時間」を測ってから判断する**。await 化は起動を遅くすると思われがちだが、#1737 では重い部分（DB のコピー）が同期 `LeaseConnection()` でセマフォを取るため**後続タスクは元から待たされており**、増える待ち時間はミリ秒オーダーだった。トレードオフに見えるものが実在するとは限らない
  - **await 化するときは「失敗が後続を巻き添えにしないか」を確認する**。fire-and-forget には「前段が落ちても後段は動く」という副次的な性質がある。単純な `await` はこれを失わせるため、必要なら**その呼び出しだけを個別に catch** して性質を明示的に保存する
  - **保守処理（UI 操作を伴わない処理）から書かれるテーブルは、書き込みをセマフォ保護する**。`settings` は起動時バックアップの成功記録・月次 VACUUM の CAS ロックから書かれる唯一のテーブルで、他テーブル（card / ledger / staff）の書き込みはユーザーの単一操作を起点とし状態機械で直列化される。**どのテーブルが背景処理から書かれるかを把握し、そこだけ保護する**（全リポジトリを一律に変えるとレビュー範囲が膨らみ退行リスクだけが増える）
    - **その「把握」は、書き込み側ではなく保守処理の側から数え直す**（Issue #1984）。#1737 は「背景処理が書くテーブル」を `settings` 1 つと数えて保護したが、危険の実体は**逆向き**で、保守処理が開いたトランザクションへ**業務側の書き込みが巻き込まれる**ことだった。`CleanupOldData` は同期 `LeaseConnection()`（セマフォを取る）で始まるので `BeginTransactionAsync` 経由の書き込みとは直列化されるが、**セマフォを取らない `LeaseConnectionAsync` 経由の単文書き込み**（`LedgerRepository.InsertAsync` / `OperationLogRepository.InsertAsync`）は同一接続上でそのトランザクションへ暗黙参加し、cleanup のロールバックで消える。数えるべきは「背景処理が書くテーブル」ではなく「**背景処理がトランザクションを開いている間に、同じ接続へ文を発行し得る経路**」である
    - **対処は「新規の取得を止める」と「進行中を待つ」の 2 段**（#1809 が `SuspendConnections` で確立した形）。片方だけでは、フラグを立てた瞬間に既に進行中だったリースが残る。ゲートを保持したまま進行中件数を増やすと、「ゲートを閉じた後に 0 件を観測した」ことが「もう誰も文を発行しない」ことの証明になる（通過後に数えると隙間が残る）
    - **ドレインの上限に達したときの倒し先は、処理ごとに決める**。#1809 は「従来挙動へ退化させて続行」だが、#1984 で同じ選択をすると**是正しようとしている窓がそのまま残る**。6 年経過データの削除は次回起動で再試行されるため、当回スキップが安全側。**「上限を置く」を機械的に真似ると、上限に達した経路だけが未修正のまま残る**
    - **「カウンタに載せれば消費側が気付く」を検算せずに採らない**（#1984）。Issue の受け入れ条件は「保守トランザクションを `HasActiveTransactionScope` に反映すること」だったが、Repository の 3 分岐（#1724）はこのフラグが true のとき分岐②（`transaction: null` で外側スコープへ commit を委ねる）を選ぶ。保守トランザクションはその「外側スコープ」ではないので、載せると複数文の書き込みが commit の主体を失って autocommit で 1 文ずつ確定し、**原子性を失う**。現在③を通る経路はセマフォ待ちで既に安全であり、**載せる変更は保護を外す方向にしかならない**。観測が要るなら別の計数（`HasActiveMaintenanceTransaction`）を足す。**受け入れ条件も仮説であり、消費側の分岐を読んで検算してから採る**（#1932「Issue に書かれた修正方針も、対のテストで検算するまでは仮説である」の再演）
    - **危険な取得口が「呼び出し元ゼロで生き残っている」形を残さない**。非推奨の `DbContext.BeginTransaction()` は誰も呼んでいなかったが、セマフォも計数も通らないため復活すれば同じ欠陥が再生する。`grep -n "BeginTransaction()"` で取得口を数え、使われていないものは削除する（#1726「使われないメソッドは先に作らない」の裏面）
      - **数える単位は「その口が返すもの」まで遡る**（#1984 のコードレビューで検出）。`BeginTransaction()` を消しても `GetConnection()`（生の共有接続を返す・本番の呼び出し元ゼロ）が残っている限り、`GetConnection().BeginTransaction()` ＝**削除したメソッドの本体そのもの**が書ける。**「危険な口を 1 つ消した」と「危険な口が無い」は別であり、後者を主張するなら同じ資源へ到達する別の綴りを数え上げてからにする**（#1843「ガードは綴りではなく資源で書く」）。消しきれない事情があるなら、主張のほうを実態に合わせる（#1924「ドキュメントの主張はコードで検算してから書く」）
    - **「新規取得を止める」ゲートは、止める対象を選り分けられないことがある**（#1984）。`LeaseConnectionAsync` はそのリースが書き込みに使われるか読み取りに使われるかを知らないため、読み取りまで止まる。読み取りは巻き戻らないのでゲートの利得が無く、待機は純粋な代償である。**この代償が許容できるかは呼び出し文脈に依存する**（#1984 では cleanup がメイン画面の表示前に完了するので許容できる）。同じゲートを使う経路を増やすときは、その前提を毎回確かめる
    - **上限で「当回スキップ」に倒したら、スキップが呼び出し元から見分けられるかを確かめる**（#1984 のコードレビューで検出）。削除件数 0 は「対象なし」と同じ値なので、上位のログは何も語らない。**「なぜ実施されなかったか」を伝えるのがログ 1 行だけになるなら、その 1 行に原因の候補まで載せる**（#1730）
  - **失敗を「例外」で表さないメソッドに `try/catch` を足しても、失敗は扱えていない**（Issue #1737）。`BackupService.ExecuteAutoBackupAsync` は全例外を内部で catch して **null を返す**ため、呼び出し元に足した `catch` は本番で一度も実行されず、真の失敗シグナル（null 戻り値）は捨てられていた。結果、バックアップ先が到達不能でも起動シーケンスのログは正常に見えた。**catch を書く前に「このメソッドは実際どうやって失敗を伝えるのか」を実装で確認する**（`bool` #1753 / 結果オブジェクト #1727 と同じ family の抜け）
    - **その状態はモックを使うテストで隠れる**。`ThrowsAsync` で例外を注入したテストは緑になるが、**本番が示し得ない性質を表明している**。失敗の表し方が戻り値なら、戻り値を返すテストを書くこと
    - **「壊れた入力を黙って代替値に置き換えて成功を返す」API も同じ family**（Issue #1744）。`Encoding.UTF8.GetString` は不正バイトを U+FFFD へ置換して**正常に戻る**ため、`ReadCsvFileAsync` の呼び出し元は「読めたのか化けたのか」を区別できず、化けた氏名・摘要が 6 年保存の台帳へ入った。**フォールバック付きの API を使うときは、フォールバックが働いたことを呼び出し元が知れるかを確認する**。知れないなら厳格版（`new UTF8Encoding(false, throwOnInvalidBytes: true)` / `DecoderFallback.ExceptionFallback` 等）に替え、**失敗を例外や判別結果として観測可能にする**
    - **置換が起きたかを「結果文字列に U+FFFD が含まれるか」で後から探らない**。正当なデータが U+FFFD を含む場合と区別できず、判定が入力依存になる。判定は復号の時点で決める
  - **`HasActiveTransactionScope` を「経路の識別子」に使わない**。このフラグが立つのは `BeginTransactionAsync` を通ったときだけで、同期 `LeaseConnection()` でセマフォを取る `CleanupOldData` では立たない。テストで「外側がトランザクションを保持している状態」を `BeginTransactionAsync` で代用すると、SUT が本番と**別の分岐**（暗黙参加）を通り、検証したい経路を一度も踏まないテストになる。外側の再現は本番と同じ API で作ること
- **「新規取得を止めるフラグ」と「使用中の接続を守るロック」は別物**（Issue #1809）。リストア中の接続一時停止（`DbContext.SuspendConnections`、#1166）は `_isSuspended` と `_connectionLock` だけで `Close()` + `Dispose()` していたが、フラグは**これから**取る側しか止めず、`_connectionLock` は `_connection` フィールドの代入しか守らない。既に払い出された `SQLiteConnection` 上で実行中の貸出・返却トランザクションやヘルスチェックは何にも守られておらず、UNC 上のリストア（数秒）に巻き込まれて `ObjectDisposedException` で落ちた。共有資源を他スレッドから破棄するときは「これから使う人を止める」だけでなく「**今使っている人がいなくなった**」ことを待って確かめる（接続セマフォの取得＋セマフォを取らない `LeaseConnectionAsync` の進行中件数のドレイン）
  - **待つ側を UI スレッドに置かない**。セマフォの同期取得は #1281 と同じデッドロック経路になるため、`SuspendConnections` にも `LeaseConnection()` と同じ UI スレッドガードを掛け、呼び出し元（`RestoreFromBackup`）は `CreateBackupAsync`（#1361）と同じ `Task.Run` 委譲の非同期版へ寄せる。**同期 API に待機を足したら、その API を UI スレッドから呼んでいる経路を grep で数える**
  - **ドレインには上限を置き、超過は Warning で残して従来挙動へ退化させる**。解放漏れが 1 か所でもあると上限なしの待機はリストアを永久に止める。上限到達で起きるのは「進行中の読み取りが失敗し得る」という修正前と同じ状態であり、データは壊れない
  - **失敗し得る初期化を挟んで公開する資源は、初期化が済んでから公開する**。`GetConnectionInternal` は `Open()` の直後・PRAGMA 適用前に `_connection` へ代入していたため、`ConfigurePragmas` の throw（共有モードの SQLITE_BUSY）で「Open 済み・busy_timeout 未設定（既定 0）」の接続が以後ずっと再利用された。ローカル変数で組み立て、成功したときだけフィールドへ代入する
  - **`Wait()` の直後に throw し得る呼び出しがあるなら、`Release()` を `catch` に書く**。`LeaseConnection()` は `_semaphore.Wait()` の後で `GetConnectionInternal()` が throw するとセマフォを持ったまま抜け、以後の全書き込みが永久に待機した。**兄弟メソッド（`BeginTransactionAsync`）には同じ `catch` が元からあり、こちらだけ欠けていた**（#1808 の「`bool` の握りつぶしは兄弟ファイルでも起きる」と同じ形）。`grep -n "_semaphore.Wait\|WaitAsync"` で取得箇所を列挙し、各々の直後の失敗経路に解放があるかを見る
  - **待機の回帰テストは「待っている」だけでなく「待っている間も資源が生きている」を実操作で表明する**。`IsCompleted` の観測だけでは「待ってはいるが先に Dispose 済み」を検出できない。セマフォ漏れの再現は `Task.Run` で別フローを作らず**同一フロー**で行う（`_reentrancyCount` は `AsyncLocal` で子フローへ継承され、漏れたカウントを子も見てセマフォを素通りする）
- **UPDATE の SET 句は「その経路で本当に編集する列」に限る**（Issue #1726）。`UpdateAsync(TEntity)` が全列を SET すると、**呼び出し元が画面の入力だけからモデルを組んだとき、触っていない列がモデル既定値で上書きされる**。`ic_card` の `starting_page_number`（#510）/ `carryover_income_total` / `carryover_expense_total` / `carryover_fiscal_year`（#1215）は**登録時にのみ確定し編集 UI を持たない**のに `CardRepository` の UPDATE が無条件 SET していたため、備考の誤字を直して保存しただけで紙出納簿移行カードの繰越累計と開始ページ番号が既定値（1 / 0 / 0 / NULL）へ落ち、5月以降の月次帳票の年度累計から紙時代の累計が丸ごと欠落した。**対処は「呼び出し元に引き継がせる」ではなく「SET 句から外す」**（引き継ぎを義務にすると呼び出し経路が増えるたびに再発する）。外した列は**インターフェースの XML doc に「設定しても DB へは反映されない」と明記**し、後から更新要件が出たら専用メソッドを新設する（SET 句へ戻さない／使われないメソッドは先に作らない）。加えて **`OperationLogger` はエンティティ全体を JSON 化して `BeforeData` / `AfterData` に記録するため DB を守るだけでは足りない** — ViewModel 側でも既定値のモデルを渡さないこと（渡すと「開始ページ番号 7 → 1」という実際には起きていない変更が監査ログに残る）。**この種の消失は静かで UI からの復旧手段が無い**ため、リポジトリ・ViewModel の両方で回帰テストを持つ
  - **監査ログへ渡す「変更前」は、変更対象と別のインスタンスにする**（Issue #1959）。`OperationLogger` は**渡された変数を保持した時点ではなく `SerializeToJson` が呼ばれた時点**の状態を写す。`LedgerMergeService.MergeAsync` は統合前の状態を `ledgers.ToList()`（**リストの**浅いコピー）で採っていたが、統合先は `ledgers[0]` そのものを in-place で書き換えるため、`BeforeData[0]` に統合**後**の値が入り、統合先について「変更前」と「変更後」が同一になっていた。**参照を保持しただけの「変更前」は、書き換えが同一インスタンスに走れば意味を失う**
    - **複製は「JSON 化される範囲」まで行う**。`Ledger.Details` は全エントリで共有されるインスタンスで、統合中に`BusStops` の同期と `SequenceNumber` の一時再採番を受ける。スカラー列だけの複製は「半分だけ正しい監査記録」になり、次に読む人が `BeforeData` を信用してよいか判断できない。**中途半端に直すくらいなら、どこまでが正しいかを明記する**
    - **複製の生成手段は 1 か所に寄せる**（#1763）。`LedgerSplitService` は同じ用途で private な `CloneLedger` を持っており、「片方だけが正しい」状態だった（#1808 の裏返し）。手段が 2 通りある限り、モデルへ列を足したとき片方だけが更新される。寄せ先は `Common/LedgerCloner`
    - **コピー漏れは静的な列挙ではなくリフレクションで検出する**。列を足してコピーへ書き足し忘れても**コンパイルは通り、既存テストも緑のまま**で、記録だけが静かに古い値になる。モデルの書き込み可能プロパティを走査する検査（`LedgerClonerCoverageTests`）を置き、**未対応の型が現れたら例外**にして fail-open を避ける（#1944）
    - **回帰は「複製されること」と「別インスタンスであること」を対で置く**。値の一致だけを見ると、同じ参照を持ち回る実装（＝この欠陥そのもの）でも緑になる。あわせて `AfterData` が変更**後**であることを固定する（before だけを直して after まで巻き戻す退行を検出する）
    - **親への逆参照は複製しない**。監査ログは `JsonSerializer` で JSON 化するため、複製すると循環参照になる
    - **「変更前」を充実させたら、対になる「変更後」が同じ粒度で組み立てられているか確かめる**（同 Issue のコードレビューで検出）。`LedgerSplitService` の `AfterData` は分割後の台帳を**そのまま** JSON 化するが、`originalLedger.Details` は分割前の全明細を保持したまま（`ReplaceDetailsAsync` は DB を書き換えるだけで in-memory のコレクションを更新しない）で、新しい台帳の `Details` は既定の空リストだった。`BeforeData` に明細が載るようになったことで、監査ログは「グループ1が全明細を保持し、新しい台帳は明細ゼロ」という**分割の逆**を主張し始めた。**片側を正確にする変更は、それまで見えていなかった対側の粗さを可視化する**（#1739「反転したら除去の責任も生成元へ移る」と同じ形）
    - **記録の充実は、その記録を読む経路が対応していて初めて監査に届く**（同）。`OperationLogExcelExportService.GetFieldNameMap` の `"ledger"` に `Details` のエントリが無いため、記録した明細は**操作ログ画面・Excel からは読めない**まま残っていた（マップに無いプロパティは読み飛ばされる ＝ #1726 が禁じた状態）。設計書・PR に「明細まで記録される」と書くときは、**どこから読めるのか**まで確かめて書く。Issue #1979 で是正済み — その過程で分かったことを次に記す
  - **マップに 1 行足すだけで読めるようになるとは限らない**（Issue #1979）。#1726 の規約は「モデルにプロパティを足したら `GetFieldNameMap` にも足す」だが、`FormatPropertyValue` は**スカラー値しか扱えない**ため、配列 of オブジェクト（`Ledger.Details`）は載せても描画できない。**規約が想定していない形の値を足したときは、規約の手順を踏んだだけで満足しない**
    - **整形の手段は 1 か所へ寄せる**（#1763）。操作ログ画面（`OperationLogSearchViewModel`）と Excel（`OperationLogExcelExportService`）は元から別々のフィールド名マップを持っており、明細の整形まで各々に書くと片方だけが更新される日が来る。`Common/OperationLogDetailFormatter` を唯一の手段とし、区間表記はさらに `RouteDisplayFormatter` へ委譲する（バスのラベル・プレースホルダは組織設定由来。#1818）
    - **既定値が空コレクションのプロパティは「常に出る行」を作る**。`Ledger.Details` の既定は空リストなので、素直に足すとすべての台帳ログへ「利用明細: 0件」という情報量ゼロの行が付く。値が無いときは行そのものを出さない（整形関数が `null` を返し、呼び出し側が飛ばす）
    - **表示先ごとに「何を担うか」を決めてから書式を決める**。Excel の「変更前 / 変更後」列は内容の展開、「変更内容」列は変化した明細だけの差分、画面の「詳細」列は件数の推移と要約。**展開ブロックどうしを `→` でつなぐと読めない**ので、差分は明細を索引で突き合わせて 1 行ずつ並べる
    - **回帰は「内容が出ること」と「明細を持たない台帳で余計な行が出ないこと」を対で置く**。後者が無いと、常に「0件」を出す実装でも緑になる。検出力は実測する（#1979 ではマップの `Details` を外すと 5 件赤・対の表明 2 件は緑、0 件でも行を出す形へ戻すと対の表明 2 件が赤）
    - **見えていなかった値を見えるようにする修正は、記録側が正しいかを先に確かめる**（#1979 のコードレビューで検出）。表示を直しただけでは終わらない — 記録が誤っていれば、可視化は「監査から見えない誤り」を「**監査が主張する誤り**」へ格上げする。#1979 では記録側 3 経路が誤っており、そのままなら履歴の行編集・詳細編集で**全明細が「（なし）→ …」という起きていない変更**として並び、統合では**明細の件数が嘘**（2件・1件 → 2件）になるところだった。#1959 の「片側を正確にする変更は、それまで見えていなかった対側の粗さを可視化する」が、**表示側から記録側へ**という向きでも成立する
      - **「変更前」の複製は、そのインスタンスが書き換えられる前に採る**。`LedgerDetailViewModel` は保存時に `item.Detail`（＝ `_ledger.Details` と同一インスタンス）の `GroupId` を書き換えるため、複製を書き換えの後ろへ置くと「変更前」が変更後を写す（#1959 と同型）
      - **手組みのコピーが残っていたら、それは複製の手段が 2 通りあるということ**（#1763）。`LedgerCloner` を作った #1959 の時点で、`LedgerRowEditViewModel`（15 フィールドを手で並べる）と `LedgerDetailViewModel`（5 フィールド）が取り残されていた。**モデルに列を足したとき片方だけが更新される**形は、列の数が多いほど気付きにくい
      - **「同じトランザクションに入れた」は「記録が正しい」を意味しない**。`OperationLogger` は `SerializeToJson` が呼ばれた時点を写すので、同一 tx でも**記録より後ろの書き込みは AfterData に載らない**。#1979 ではバス停名の同期が記録の後ろにあり、この Issue が可視化しようとした「書き戻し」がまさに監査から抜け落ちていた。加えて同期は DB だけを書き換えていたため、記録の前へ移すだけでは足りず in-memory の明細も揃える必要があった
      - **摘要生成のために一時的に書き換える値は、生成の直後に戻す**。`LedgerMergeService` は `SequenceNumber` を 1..N へ振り直す（DB へは永続化しない）が、戻さないまま JSON 化すると **DB に存在しない順序の変更**が 6 年保存の監査記録へ入る
      - **その種の回帰テストは「集合」で書くと検出力を失う**（実測）。2 件の明細が順序番号を入れ替えただけの状態は、値の集合で比べると「一致」になる。**「どの明細がどの値を持つか」の対応**で表明する（#1855「間接参照の一意性を、参照先の値の相違の代理にしない」と同じ形）
  - **ViewModel 側の引き継ぎは「編集対象の列」以外を網羅する**。一部だけ直すと同じ虚偽差分が別の列で残る（#1726 の初版は繰越4項目だけを直し、`IsRefunded` / `IsLent` の虚偽差分を残していた）。引き継ぎ元は**キャッシュ由来の一覧 DTO ではなく直前に読んだ DB の最新値**にする（一覧は自動更新されず、共有モードで他 PC の貸出が反映されないため「貸出中: はい → いいえ」という虚偽の返却を記録し得る）
  - **「読み取りが null のときのフォールバック」を安易に足さない**。`GetByIdmAsync`（`is_deleted = 0`）が null を返す状況では `UpdateAsync` の WHERE（同じ述語）も一致せず 0 行 → `false` になり操作ログも記録されない。つまり代替値は本番で観測されない。**到達不能な分岐とその回帰テストは「競合が手当てされている」という誤った安心感を与える**
  - **モデルにプロパティを足したら `OperationLogExcelExportService.GetFieldNameMap` にも足す**。`FormatJsonToReadable` / `GetChangeSummary` はマップに無いプロパティを読み飛ばすため、載せ忘れると生 JSON には値があるのに操作ログの画面・Excel に一切現れず監査で追跡できない

## ロギング

**本番のログファイルに残したい事象に `LogDebug` を使わない**（Issue #1716）。`appsettings.json` の `Logging:LogLevel:Default` は `"Information"` のため、**`LogDebug` は本番でファイルに一切出力されない**。`FileLogger.IsEnabled` が `LogLevel.None` 以外を通すため一見出力されそうに見えるが、その手前で `ILoggerFactory` のフィルタが落としている。

- 「無言で握りつぶさない」ための痕跡ログを `LogDebug` で書くと、**本番では実質無言のまま**になる（Issue #1282 で `DbContext.CheckConnection` に入れた `LogDebug` が該当。Issue #1716 の調査で実機ログから切断の痕跡を追えず判明した）
- 判断基準は「**障害調査でこの行が無いと困るか**」。困るなら `LogInformation` 以上にする。失敗時・状態遷移時のみ出力する設計なら、正常運用中のログ肥大化は起きない
- 逆に、正常時も高頻度で出る内容（毎ループの経過報告等）は `LogDebug` のままでよい（本番では出力されない前提を織り込む）
- ログレベルを変更したら、その理由をコード上のコメントに残す（後から「なぜ Information なのか」を再検討させない）

### 「観測している」ことと「調査に使えるログが残る」ことは別（Issue #1873）

`Task.Exception` が返す `AggregateException` は **TPL が組み立てたもので一度も throw されていない**ため `StackTrace` が `null`。これをそのままログ機構へ渡すと、残るのは `AggregateException: One or more errors occurred.` ＋**空のスタックトレース**だけになる。

- **例外の種別で分岐する下流（`ErrorDialogHelper.GetErrorInfo` の `SYS00x` 分類、`AppException` の `ErrorCode` / `UserFriendlyMessage`）はすべて既定分岐へ落ちる**。#1757 が「例外型の変更は、その型を前提にしていた上位の分岐を静かに外す」で記録したのと同じ形が、**ラップした型を渡す側からも起きる**
- `AggregateException` は `Flatten()` してから、失敗要因が 1 つならその例外を記録する（`Common/DispatcherObservation.UnwrapAggregate`）。複数なら情報を落とさないよう平坦化した集約のまま渡す
- **「無言だった失敗を可視化する」修正では、可視化した先に何が残るかまで見る**。#1873 の初版は観測経路を通すところで満足しており、残るログが `SYS999` ＋空のスタックトレースであることに気付いていなかった（コードレビューで検出）。**この Issue が消そうとしていた状態そのもの**に着地しかけた
- **その欠陥はテストの表明にも写る**。#1873 の初版のテストは `log[0].Exception.InnerException.Should().BeOfType<InvalidOperationException>()` と書かれており、**`AggregateException` で記録されることを前提に置いて欠陥を追認していた**。記録されたものを「そのまま」表明する形（`log[0].Exception.Should().BeOfType<InvalidOperationException>()`）にすると、この取り違えが表面化する

### IDm はログへ生で出さない — 規約は静的検査で固定する（Issue #1852）

職員証の IDm は本システム唯一の認証要素であり、平文のログファイル（インストーラが `users-full` ACL を付与）へ生で残すとローカルユーザーが認証クレデンシャルを収集できる（CWE-532）。ログへ出す IDm は必ず `IdmMasker.Mask()`（Issue #1704）を通す。

- **規約を定めたら、それを守らせる検査を同時に用意する**。`IdmMaskerTests` は**マスカー自体**の単体テストであり、「すべての IDm ログがマスクを通っているか」は誰も見ていなかった。結果、起動時に毎回走る整合性修復ログ（#790）2 箇所が生の IDm を出し続け、PR #1851 で新規追加されたログも同じ違反を含んだまま全テストを通過した（セキュリティレビューで検出）。**「規約に書いてある」は守られていることを意味しない**
- **検査は「呼び出しの引数リスト全体」を丸括弧の対応で切り出して判定する**。単一行の grep では検出できない — 実際 #1851 の違反は `LogWarning(` と IDm 引数が別行にあった。抽出は `TestSourceInspection.ExtractInvocationArguments` に集約する（私的コピーを増やさない。`.claude/rules/testing.md`）
- **判定は引数ごとに行う**。呼び出し単位で `IdmMasker` の有無を見ると、マスク済みと生が混在する形（`Mask(a), b`）を見逃す
- **文字列リテラルを捨てる前処理は、補間式（`$"…{card.CardIdm}"`）まで捨てていないか確かめる**。`ToCodeOnlyPreservingLines` は既定でリテラルの中身ごと捨てるため、値を補間式へ直接埋め込んだ形が検査を素通りする（本 Issue の初版が実際にそうだった）。値の露出を見張る検査は `preserveInterpolationHoles: true` を使い、**補間式の中身だけ**を残す（書式指定子の `{CardIdm}` は捨てたままにしないと、すべての構造化ログが違反になる）
- **除外パターン（「これは違反ではない」側）は、規約を守っている書き方を全部通すか確かめる**。`Log…` で始まるメソッドの**定義**を除外する条件を「型 名前」の 2 トークンに限ると、既定値付きの仮引数（`string cardIdm = null`）を持つ定義で赤になる。誤検出はガード自体の寿命を縮める（`.claude/rules/testing.md`「違反の確定を早まらない」）
- **受け手はフィールド名ではなく「`Log` で始まるメソッド呼び出し」で照合する**。ログ出力を包む自前のヘルパーへ生の IDm を渡す形も同じ欠陥であり、`_logger.` を直書きすると別の綴りで素通りする（#1843「ガードは綴りではなく資源で書く」）
- **走査対象は `src/` 配下の全 `.cs` から導出し、ファイル名で列挙しない**（#1786）。検出力は既知のサンプル入力で固定し、実データが空でも空振りしないようにする

### マスクで「残す位置」は、識別に使える情報がどこにあるかで決める（Issue #1940）

上の規約は「マスクを通したか」を見張るが、**通した結果が役に立つか**は見ていない。`IdmMasker` は #1704 以来 IDm の**先頭 4 文字のみ**を残していたが、FeliCa の IDm は上位 2 バイトが**製造者コード**、下位 6 バイトが**カード識別番号**で、**個体差は下位側にしか無い**。同一事業者から同時期に購入したカードはログ上で同じ文字列になり、設計書が掲げていた「トラブルシュート時の識別性（どのカードかの相関）確保」は成立していなかった（実測: 交通系ICカード 7 枚の先頭 4 文字が 5 種類、職員証 7 枚が 3 種類）。

- **同じ安全性で役に立たないほうを選んでいないか確かめる**。先頭 4 文字を残しても末尾 4 文字を残しても**伏せるのは同じ 48 bit** で、識別性だけが正反対だった。マスク幅を決めるときは「伏せる量」と「残る情報の有用性」を**別々に**評価する — 伏せる量が同じなら、有用な側を残さない理由はない
- **残す位置は、その識別子の内部構造を調べてから決める**。「先頭を残す」は多くの識別子で無難に見えるが、**上位バイトが発行体系を表す ID 体系ではほぼ無意味**（IDm・MAC アドレスの OUI・クレジットカードの BIN などが該当）。逆にクレジットカードの下 4 桁表示は、個体差が下位に入るという同じ理由で下位を残している
- **「識別できること」の回帰は、衝突する 2 件を並べて表明する**。単一の入力に対する期待値（`Mask(x) == "0123********CDEF"`）だけでは、全件が同じ値に潰れる欠陥を検出できない。**先頭が同一で末尾が異なる 2 件が異なるマスク値になること**を書く
- **対で「伏せる量が減っていないこと」も表明する**。識別性のテストだけだと、マスクを一切やめて全部見せる実装でも緑になる。ただし**その期待値は本番の定数から読まずリテラルで書く**（#1884）— #1940 の初版は `Should().Be(IdmMasker.MinimumMaskedLength)` と書いており、可視幅と最小マスク幅を同時に動かす変更（`prefix=6` / `suffix=6` / `min=4`）で **16 文字中 12 文字が露出するのに緑のまま通った**。マスク幅の表明は定数どうしの関係で決まるため、**この family の中でもとりわけ自己充足しやすい**（コードレビューで検出）
- **可視幅を広げたら、短い入力の全マスク境界も一緒に動かす**。「4 文字以下は全マスク」は可視 4 文字を前提にした値で、可視 8 文字のまま据え置くと 9〜15 文字の入力がほとんど露出する。境界は**マスクの最小文字数**（`MinimumMaskedLength`）から導出し、可視幅と連動させる
- **この欠陥は「規約に書いてある」でも「テストが緑」でも見つからなかった**。#1852 の静的検査は全経路がマスクを通っていることを確かめており、`IdmMaskerTests` はマスク結果を固定していたが、**どちらも「その結果でカードを区別できるか」を問うていない**。実データで数えて初めて分かる種類の欠陥であり、**設計書に目的が書いてあることは、その目的が達成されていることを意味しない**（#1728「フォールバックが書いてあることは、それが機能していることを意味しない」／#1855「間接参照の一意性を、参照先の値の相違の代理にしない」と同じ形）

### 是正するときは `LogDebug` を消さず Information を併設する（Issue #1730）

`LogDebug(ex, …)` は例外オブジェクトごと渡せてスタックトレースが残るため、開発時の価値がある。**置き換えではなく併設**にすること。既存テストが `LogLevel.Debug` をピン留めしていても緑のまま通り、レベル引き上げのために回帰テストを弱める必要がなくなる（`ExecuteConnectionCheck` / `CheckWritable` はいずれもこの形。`DbContextCheckConnectionLoggingTests` と `DbContextCheckConnectionReachabilityTests` が Debug と Information を別テストで共存させている）。

- **規約を新設したら、同種の既存箇所を横断で洗う**。#1716 は `DbContext.CheckConnection` を是正したが、**並行して別 Issue（#1686）で追加された兄弟メソッド `CheckWritable`** が取り残され、#1730 として再発した。「同じ判断が要る箇所」は `grep "LogDebug(ex"` のような機械的な洗い出しで列挙し、対象外とした箇所は**なぜ対象外か**を Issue／PR に書く（例: `MainViewModel` の定期リフレッシュ失敗は切断中 15 秒ごとに出続け、かつ同じ切断を `LogConnectionCheckOutcome` が Information で既に記録しているため据え置き）
- **Information ログには「調査を先に進める値」を載せる**。レベルだけ上げて「失敗しました」とだけ書くと、出力されるようになっただけで切り分けはできない。`CheckWritable` は bool しか返さないため画面は原因**候補**を並べるにとどまり、それを 1 つに絞れるのは `SQLiteException.ResultCode`（`ReadOnly` / `Full` / `Busy` / `Locked`）だけだった。**UI が候補を並べている箇所は、ログが候補を絞れているかを確認する合図**
- **テストはレベルだけでなく載っている値まで表明する**。`LogLevel.Information` が呼ばれたことの確認だけでは、原因を切り分けられない空虚なログでも通る。あわせて**成功時に出さないこと**も固定する（後から「常に出す」実装へ緩めてもテストが通ってしまうため）
- **`grep LogDebug` は「そもそもロガーを持たない箇所」を見つけられない**（Issue #1819）。`StationMasterService` は `ILogger` の注入自体がなく、失敗の痕跡が `#if DEBUG` の `Debug.WriteLine` だけだったため、**Release ビルドで完全に無言**だった。#1716 / #1730 の横断洗い出しは `LogDebug` / `LogTrace` を検索語にしていたので、この形は 2 度の横断を素通りしている。ログレベルの棚卸しでは `grep -n "#if DEBUG" -A3` や「`catch` を持つのに `_logger` フィールドを持たないクラス」も併せて数えること（#1817 が「UI 文言とログを対で数える」で記録したのと同じ、**出口がゼロ**の形）
- **縮退（フォールバック）を伴う処理では、正常時にも規模を記録する**（同）。異常時のログだけでは「縮退したのか、元からその規模なのか」を判別できない。駅マスタは正常 5,988 件 / フォールバック約 136 件で、両方をログに残して初めて件数の比較で切り分けられる。**フォールバックが働いたことを呼び出し元が知れるか**（#1744）の運用ログ版にあたる
- **高頻度で回る処理のログは、出す・出さないの判定を純関数へ切り出す**（同）。`FelicaCardReader` のヘルスチェックは 10 秒周期で、毎回 Warning を出すとログが肥大化して他の事象が埋もれる。「初回」と「一定間隔ごと」だけを残す判定を `ShouldLogHealthCheckFailure` として切り出せば、実機（PaSoRi / felicalib）に依存せず境界を単体テストで固定できる（#1794 の「判断を純関数へ切り出す」と同じ形）。**失敗が止んだことも記録する** — 失敗の Warning と対にならないと、障害が何分続いたのかを後から追えない

## ビルド警告は「抑制」ではなく「是正」で消す（Issue #1786）

警告ゼロは**二段構え**で担保する。警告の**発生**は CI の「ビルド警告ゼロ検証」ステップ（`.github/workflows/ci.yml` の code-quality ジョブ。`: warning ` を含む行を数えて 1 件でもあれば fail）が止める。警告を消した**手段**が是正だったか抑制だったかは `BuildWarningSuppressionConventionTests` が静的検査で見張る。

- **`NoWarn` へ追加したら、同じファイルのコメントに ID と理由を書く**。抑制自体は禁じない（テスト特有の表現に対する抑制は正当）が、理由の無い抑制が積み上がると「ビルド警告ゼロ」が実態を伴わなくなる。コメントでは `CS8600/8602/8603` のような圧縮表記を使わず `CS8600, CS8602, CS8603` と完全な形で列挙する（照合は語境界一致のため）
- **CS8618（未初期化の非 Null 許容フィールド）は抑制しない**。テストフィクスチャの初期化漏れという実バグを示し得る。宣言側を是正すること
- **`= null!` は「必ず非 null」という宣言**であり、実際に null チェックしているフィールドに付けると意図とコードが食い違う。null になり得るなら `?` を付ける（#1786 の `CleanupSimulator._worker` は `StartAndWaitUntilTransactionOpenAsync` 前は実際に null で、`RollbackAndCompleteAsync` も null チェックしていた → `Task?` が正解）
- **`<Nullable>enable</Nullable>` を外して黙らせない**。Null 許容系の警告が一括で消え、個別に理由を書く規約ごと無効化される。MSBuild は後勝ち評価のため、既存行を残したまま後ろへ `disable` を足す形も同じ結果になる
- ビルド警告を伴う変更をしたら、**Release / Debug 双方**でソリューションビルドし 0 警告を実測する（`"/mnt/c/Program Files/dotnet/dotnet.exe" build ICCardManager/ICCardManager.sln -c Release`）

### ガードを書くときは「守りたい性質」ではなく「その性質を破れる全経路」を列挙する

#1786 の初版は csproj の `<NoWarn>` だけを検査しており、**4 テストすべてが緑のまま規約を破れる経路が 5 通り**残っていた。ガード系のコードは経路の網羅で設計する。

| 迂回経路 | 見落とした理由 |
|---|---|
| 同一 csproj 内の 2 つ目（構成条件付き）の `<NoWarn>` | `Regex.Match`（単数形）が最初の要素しか返さない |
| `Directory.Build.props` | 各 csproj の `<NoWarn>` が `$(NoWarn)` で始まり、その継承値を抽出器が除外していた |
| 走査対象から漏れたプロジェクト（`ICCardManager.UITests`） | sln のプロジェクト数を確認せず 3 つと思い込んだ |
| 後勝ちで上書きされる `<Nullable>` | リテラル文字列の存在だけを検査し、MSBuild の実効値を見ていなかった |
| ソース中の `#pragma warning disable` | csproj だけを抑制手段とみなした（既に 7 箇所で使われている確立した手段だった） |

- **「禁止語がコメントに現れるか」を単純な部分文字列一致で書かない**。「この ID は抑制しない」という**戒めのコメント自体**が、その ID の抑制を正当化してしまう（極性の反転）。否定語を含む行を除外し、語境界付きで照合する（`CS862` が既存の `CS8620` の記述で「理由あり」になる前方一致の誤りも同時に防げる）
- **空振り検出を「各対象が非空であること」で書かない**。規約が推奨する方向の変更（抑制の解消）でテストが赤になり、修正者を「対象から外す」方向へ誘導する。外された対象は他の検査からも静かに落ちる。**検査ロジック自体を既知のサンプル入力で固定**すれば、実データが空でも空振り検出は働き続ける

## 保存順が意味を持つなら、並べ替えを呼び出し元に配らない（Issue #1913）

`ledger_detail` は暗黙 rowid のテーブルで、`LedgerRepository.InsertDetailsAsync` / `ReplaceDetailsAsync` は**渡された順にそのまま INSERT する**（後者は DELETE + INSERT なので rowid が再採番される）。`LedgerDetail.SequenceNumber` の規約は FeliCa 互換で「**小さい rowid ＝ 新しい**」（#548 / #880 / #1822）なので、呼び出し元は時系列昇順（古い→新しい）の並びを `Reverse()` してから渡す必要がある。この「呼び出し元ごとに同じ並べ替えを配る」形が、**3 経路での配り忘れ**（履歴詳細ダイアログの保存・詳細 CSV の取り込み・CSV からの新規 Ledger 作成）を生んだ。

- **本システムが明細を保持している並びは例外なく時系列昇順**（`GetByIdAsync` の残高チェーンソート、`SplitAtChargeBoundaries`、`CsvExportService` の出力順）。つまり「そのまま渡す」は**常に**規約の反転を意味する。**規約の向きと、手元にある唯一の並びが逆なら、その規約は配って守れない**
- **症状が書き込みの直後に出ないと、配り忘れは長く残る**。保存時点の摘要はメモリ上の古い `SequenceNumber` から生成されるため正しく、**再読込のあと**で摘要のブロック順が逆になる（`SummaryGenerator.SortChronologically` は同一日付内で `SequenceNumber` 降順をタイブレークに使う。#1904）。**「保存した画面で確かめた」は、保存順の規約の検証にならない**
- **並べ替えは DB 呼び出しにだけ適用し、同じメソッド内の摘要生成・金額再計算には元の並びを渡す**。回帰は「渡した並びが逆順であること」と「生成された摘要のブロック順は昇順のままであること」を**対で**表明する — 前者だけだと**摘要ごと逆順にした**実装でも緑になる
- **モックでは検証できない**。rowid の再採番は DELETE + INSERT で初めて起きるため、実害（再読込後の逆転）は実 SQLite を通さないと再現しない。`LedgerDetailSaveOrderingIntegrationTests` が参考実装
- **回帰は全呼び出しの静的検査で固定する**（`LedgerDetailInsertOrderConventionTests`）。個別の挙動テストは経路の追加に追随できない（`error-messages.md` #1764）。検査は `TestSourceInspection.ExtractInvocationArguments` で**引数リスト全体**を切り出し、引数ごとに判定する（呼び出しが複数行にまたがるため行単位の grep では見られない。#1852）。転送メソッド（`LendingService.InsertDetails`）のような正当な例外は理由付きで許可し、**許可件数も表明する**（許可が静かに増えるのを防ぐ）
- **「リポジトリ側で反転して手段を 1 つに寄せる」（#1763）が常に取れるとは限らない**。#1913 では参照が 179 か所あり貸出のホットパスを含むため、契約の反転は退行リスクだけが大きいと判断して見送った。**寄せられないなら、配り忘れを検出する検査を同時に用意する**

## 「規約どおりの並び」を、規約の例外がある場所で唯一の根拠にしない（Issue #1932）

`LedgerDetail.SequenceNumber` は FeliCa 互換で「**小さい値ほど新しい**」（#548 / #880 / #1822）。
`LedgerMergeService.MergeAsync` は統合後の残額をこの規約の**逆**（最大 `SequenceNumber` ＝最新）で採っており、
6 年保存の `ledger.summary` / 残額列と月次帳票（物品出納簿）へ**最古の明細の残額**が入っていた。

- **同じ台帳から 2 つの値を導くなら、並び順の定義は 1 つに寄せる**。残額の選択と摘要の再生成が別々の並べ方
  （前者は `SequenceNumber` 昇順、後者は `UseDate` 降順・`Balance` 昇順）に載っていたため、片方だけが規約と食い違った。
  定義を `OrderChronologically` 1 つにすると、「最新」は必ずその結果の末尾になる
  （#1763「同じ論理的な処理に手段が 2 通りあるか」）
- **規約に明示的な例外があるなら、規約より強い根拠を先に試す**。残高不足マージ（#978）で作られた台帳は
  「チャージ → 利用」の順に挿入する**規約の例外**で、この台帳だけ最大 `SequenceNumber` が最新になる。
  Issue の修正方針どおり `SummaryGenerator.SortChronologically` の末尾を最新とすると、この台帳では
  チャージ後の残高（＝利用前の過大な値）が選ばれる。**同一日内は残高チェーンを先に試し、解けたときはそれを正とする**
  （`LedgerDetailChronologicalSorter.TrySortByBalanceChain`。`LedgerRepository.GetByIdAsync` が明細の並びを
  決めるのに使っているのと同じ定義で、通常の台帳も例外の台帳も同じ手順で解ける）。解けないときは**台帳ごとに分け直して**台帳の中を再びチェーンで解く（台帳どうしの順序だけを規約で決める）
- **「必ず結果を返す」API は、解けたかどうかを呼び出し元へ伝えられない**。既存の `Sort` はチェーンが途中で切れても
  残りを残高降順で継ぎ足して**必ず並びを返す**ため、そこから採った残額が「チェーンで決まった値」なのか
  「継ぎ足しの副産物」なのか区別できない。判定を使う側には `null` を返す strict 版を別に用意する
  （#1744「フォールバック付きの API を使うときは、フォールバックが働いたことを呼び出し元が知れるかを確認する」の再演）。
  strict は開始点・後続がそれぞれ**一意**であることまで確かめる — `FirstOrDefault` は候補が複数でも黙って 1 つ目を選ぶ
- - **フォールバックの粒度が、規約の例外を巻き戻していないか確かめる**（コードレビューで検出）。#1932 の初版は統合対象**全体**を 1 本のチェーンに掛け、解けなければ規約へ**丸ごと**倒していた。ところが選択されなかった台帳が間に挟まるだけでチェーンは切れる（履歴一覧はチェックボックス選択なので通常操作で起きる）ため、そこで規約へ倒すと規約の例外である台帳がチャージ側を最新と判定し、**修正が消したはずの値がそのまま戻ってきた**（実測 800 円）。**「解けなかった」ときに何へ倒すかは、倒す単位まで含めて決める** — 台帳の中の並びは統合対象の選び方に左右されないので、そこはチェーンが常に解ける。倒すのは台帳どうしの順序だけでよい（#1814「修正の中に、修正対象と同じ欠陥への経路を残さない」の再演）
- **回帰は「欠陥を突く側」と「規約の例外を壊していない側」を対で置き、両方の検出力を実測する**。#1932 では
  欠陥を突く 2 件が修正前のコードで赤、例外の台帳を守る 1 件は緑（＝修正前は偶然正しかった）。
  その 1 件は Issue の修正方針をそのまま採った実装へ変異させると赤になることを確かめた。
  **「Issue に書かれた修正方針」も、対のテストで検算するまでは仮説である**
- 上位のコメント・設計書が規約の食い違いを「スコープ外」と記録しているときは、**その記録を消す**（追跡先が解消したことを
  次に読む人が確かめ直さずに済むように）。#1932 では `LendingService` のコメント・07_テスト設計書 UT-095 / #1913 の
  「スコープ外（別途追跡）」・04_機能設計書 §5.6.3 の「最新Detail = 最大 SequenceNumber」の 4 か所が対象だった

## SQLite の接続文字列は 1 か所で組み立てる（Issue #1924）

**SQLite はバックスラッシュの UNC パス（`\\server\share\x.db`）を開けない。** `Data Source` にそのまま渡すと `SQLiteException: unable to open database file`（SQLITE_CANTOPEN）になる。フォワードスラッシュ（`//server/share/x.db`）へ変換すると開くことができ、`SQLiteConnection.FileName` は元の UNC 形式に解決される。この差は `SQLiteConnectionStringBuilder` を経由しても変わらない（実機で確認）。

`DbContext` のコンストラクタにはこの変換が**コメント付きで**存在したが、`BackupService.CopyDatabaseTo` がコピー先の接続を `$"Data Source={destinationPath}"` で自前に組み立てていたため、**データベース本体は共有フォルダーで開けるのにバックアップだけが必ず失敗する**状態だった。

- **接続文字列の組み立ては `DbContext.BuildConnectionString` ただ 1 つに寄せる**。手段が 2 つあると、片方だけが知識を持つ状態が生まれる（#1763「同じ論理的な処理に手段が 2 通りあるか」／#1808「兄弟ファイルでも同じ欠陥が起きる」）。**先に書かれた側にコメントで理由が書いてあっても、後から書く側はそのファイルを読まない**
- **「同じ資源を扱う処理が他にもないか」を、資源の名前（`Data Source=` / `SQLiteConnection`）で grep して数える**。画面の動詞やクラスの役割で数えると、バックアップは「ファイルのコピー」に見えて接続文字列の話だと気付けない（#1760「画面の動詞ではなくテーブルへの書き込み文で数える」と同じ数え方）
- **本体と付随機能で同じ資源の扱いが違うと、本体が動くぶん発見が遅れる**。共有モードは主機能として使われており DB は開けていたため、「共有フォルダーは使える」という前提が成立し、バックアップの失敗が別原因（権限・パス設定）に見えていた
- **回帰は静的検査で固定する**。UNC への実接続は共有が必要で CI から実行できず、経路が増えたときの追随漏れは個別テストでは検出できない（`error-messages.md` #1764）。検査は「禁止された形（自前組み立て）の不在」と「正しい形（`BuildConnectionString` の変換）の存在」を**対**で表明する — 前者だけだと `DbContext` 側の変換ごと消した実装でも緑になる
- **プラットフォーム由来の制約は、実機で確かめてから書く**。#1924 では実際の共有フォルダーに対して 4 通りの接続文字列を試し、「バックスラッシュは失敗・スラッシュは成功・`SQLiteConnectionStringBuilder` を通しても失敗」を実測してから修正した。推測で「たぶんエスケープの問題」と決めると、`Builder` を通す・引用符で囲むといった効かない対処に流れる

## 「存在するか」を「到達できるか」の代わりに使わない（Issue #1924）

**存在チェック 1 回で 2 つの問いに答えさせない。** `Directory.Exists` の `false` は「共有へ到達できない」と「そのフォルダーがまだ無い」を区別できず、片方の意味で書いた分岐がもう片方まで巻き込む。

`PathValidator.ValidateBackupPath` の UNC 到達性チェック（#1269）は**パス全体**に `Directory.Exists` を掛けていたため、共有フォルダーにバックアップ用サブフォルダーを作る前に `\\server\share\backup` を設定すると、アクセス権が正しくても「ネットワーク共有に到達できません」と判定され、無言でローカル既定パスへ退避していた。

- **検査対象は、その問いが本当に掛かる単位まで狭める**。「到達できるか」は共有ルート（`\\server\share`）の問いであって、保存先フォルダーの問いではない。**エラー文言（「サーバー名・共有名を確認」）が既に正しい単位を述べているのに、実装だけが広い単位を見ていた**ことに注意する — 文言と検査対象がずれていないかは、文言を読めば分かる
- **同じ検証の中で、パスの形（ローカル／UNC）によって同じ入力の可否が変わっていないか確かめる**。ローカルパスは未作成フォルダーを許容する（ドライブ準備状態のみ見て、書き込み権限は親フォルダーへ退避する）設計で、作成は後段（`BackupService.EnsureDirectoryExists`）が担う。UNC だけが「存在しなければ致命」だった。**非対称は仕様として意図された箇所以外では欠陥**であり、検証の項目ごとに「この項目は UNC とローカルで同じ判断をするか」を見る
- **退避（フォールバック）は、退避したことが利用者に見えて初めて完結する**。#1727 の「『ログには出ている』は無言失敗の免罪符にならない」がそのまま当てはまる。ここでは退避先でバックアップが**成功する**ため長期未成功の警告（#1689）にも掛からず、「共有フォルダーに世代が増えない」という症状だけが残った。**退避しても成功を返す経路は、失敗を返す経路より発見が遅れる**
- 退避の理由を返すときは**検証が返した理由をそのまま載せる**。原因は到達不可・権限不足・パス形式の誤りなど複数あり、「保存先を使用できません」と丸めると原因へ到達できない（`error-messages.md` の「なぜ」）
- 回帰は「未作成でも通ること」と「ルート到達不可なら従来どおり弾くこと」を**対**で置く。前者だけだと到達性チェックを丸ごと素通しにした実装でも緑になる
- **検証を緩めるときは、その検証関数を使い回している呼び出し元をすべて数える**（同 Issue のコードレビューで判明）。`PathValidator.ValidateBackupPathAsync` は名前に反して**データベース保存先**の検証にも使われており（`SettingsViewModel`）、「保存先フォルダーが未作成でもよい」という緩和はそちらへも波及する。バックアップ先なら実行時に作ればよいが、DB では未作成のフォルダーを指定して再起動すると SQLite が**新しい空の DB** をそこに作り、既存の共有データベースから切り離される（台帳分裂）。**緩和は加えた場所ではなく、その検証が到達する全経路で評価する** — `grep` で呼び出し元を列挙し、各々にとってその条件が何を意味するかを見る（#1786「その性質を破れる全経路を列挙する」の裏返しで、**性質を緩める側**でも同じ数え上げが要る）
  - 波及先の是正は、**その経路にとっての意味**で選ぶ。DB 保存先を「存在必須」に戻すと初回セットアップ（未作成フォルダーへの新規作成）を塞ぐため、上の「曖昧な入力は『塞ぐ』より『解決結果を見せる』」に従い確認ダイアログで利用者へ判断させる
- **「条件を満たさないので検査を省略する」分岐は、省略が安全かを条件ごとに確かめる**（同）。`CheckWritePermission` は保存先が無いとき直近の親だけを見て、それも無ければ**検査を省略して成功を返す**。緩和前は未作成の UNC が到達性で弾かれていたためこの経路に入らなかったが、緩和後は `\\server\share\a\b` が素通りし、共有が作成を許可していなければ `EnsureDirectoryExists` が例外 → **バックアップがどこにも作られない**（従来は既定パスへ退避して残っていた）。検査対象は「実際に書き込みが起きる場所」＝ `Directory.CreateDirectory` の起点になる**実在する最も近い祖先**に合わせる
- **ドキュメントの「一本化した」という主張は、コードで検算してから書く**（同）。`GetBackupFilesAsync` は「設定値 → 検証 → 既定パスへ退避 → 正規化」の写しを持ったままで、正規化の有無と `settings` が null のときの扱いが本体と食い違っていた。**主張が実装より先に進んだ状態**は、次に読む人が「もう寄せてある」と信じて別の写しを増やす

## 書き込み途中のファイルに「最終名」を与えない（Issue #1748）

**あとから列挙・選択される場所へファイルを作るときは、一時名で書き切ってから最終名へリネームする。** 最終名で書き始めると、書き込み中および中断後の中途半端な状態が、そのまま「完成品」として観測される。

`BackupService.BackupDatabaseTo` は `backup_yyyyMMdd_HHmmss.db` へ直接 SQLite Backup API を実行していた。Backup API は**ページ 1（`"SQLite format 3\0"` のマジックヘッダを含む）から昇順にコピーする**ため、UNC 断で中断したファイルは必ず「頭だけ正しい」形になり、先頭 16 バイトしか見ない `IsValidSqliteFile` を通過した。結果、①保持世代（30）のカウントを消費して正常な最古世代が余分に削除され、②リストアで 6 年保存の台帳が破損コピーに置き換わった。

- **判断基準は「そのファイルを誰かが列挙・選択するか」**。ログのような追記専用ファイルは対象外だが、バックアップ世代・帳票の出力ファイル・エクスポート結果のように**存在そのものが状態を意味する**ものは対象。`ReportService` の xlsx 出力は `ReportExportStatusService` がファイル走査で「出力済み」を判定するため同じ構造を持つ（本 Issue のスコープ外・未対処）
- **一時名は「最終名の検索パターンに一致しない」ことが要件**。`backup_*.db` に対する `.tmp` のように、拡張子または接頭辞で確実に外す。Win32 のワイルドカード照合は 8.3 短縮名にも一致し、拡張子がちょうど 3 文字のときは前方一致で拾うため、**推論で済ませず実際の列挙結果をテストで固定する**
- **共有モードで同じフォルダーへ書く経路では、一時名にランダムな識別子を含める**。秒単位のタイムスタンプは最大 20 台の同時起動で衝突し、複数台が同一の一時ファイルを開いて互いのコピーを壊す。ただし **GUID 全体（32桁）を足すとパス長上限（260文字）に早く到達する**。パス長の検証がフォルダーに対してだけ行われている場合、検証を通ったフォルダーでも一時ファイルのフルパスが上限を超えて処理全体が失敗する。衝突回避に必要な長さ（8桁で十分）だけを足すこと
- **一時ファイルに付随して生まれるファイル（SQLite のロールバックジャーナル等）も後始末の対象**。`<一時ファイル>-journal` は回収処理の検索パターン（`.tmp` で終わる）に一致しないため、明示的に消さないと誰も消さない。成功時にも取り残され得るので、削除は `catch` ではなく `finally` に置く
- **リネーム段で失敗したときは一時ファイルを消さない**。中身は完全なコピーであり、消すと移動先も一時ファイルも無い状態になる。列挙されないので実害はなく、後述の回収に委ねる
- **一時ファイルの回収を用意する**。失敗時の削除は `catch` が動く場合にしか効かず、プロセス強制終了（電源断・タスクマネージャー）では残る。DB 本体大のファイルが溜まるため、**十分に古いものだけ**を定期的に消す（進行中の他 PC のファイルを消さないため）。削除の失敗は Warning ログに留める（「catch の中の後始末」と同じ理由）
- **生産者側を直しても、既に作られた壊れたファイルは消えない**。既存環境の保存先には修正前の破損世代が残り得るため、**消費側の検証も併せて強化する**。ただし検証の重さは呼び出し文脈で決める（`RestoreFromBackup` は UI スレッド上で走るため、`PRAGMA integrity_check` のような全長読み取りではなくヘッダ 100 バイトの整合チェックにした）
- **「判定できない」を異常に丸めない**。SQLite ヘッダのページ数はオフセット 24 と 92 が一致するときだけ有効で、不一致時に「破損」と断じると正当なバックアップのリストアを塞ぐ

## fire-and-forget の本体は、それ自体が最後の受け皿（Issue #1816）

`Dispatcher.InvokeAsync(async () => …)` は `DispatcherOperation<Task>` を返し、**`await` しても内側の `Task` の例外は観測されない**（`Unwrap()` が要る。#1725）。呼び出し元が観測しないなら、**例外の受け止めはラムダ本体側の責任**であり、本体全体を `try/catch` で包む。

`CardManageViewModel` / `StaffManageViewModel` / `DataExportImportViewModel` の `OnCardRead` はいずれも戻り値を捨てており、共有モードで DB がロック中にタッチすると `EditCardIdm` と `IsWaitingForCard = false` だけが確定して以降が中断した。画面上は「読み取れたように見える」まま止まり、通知は GC 契機の `TaskScheduler.UnobservedTaskException`（#1742）まで遅れる。

- **UI スレッドへ投げる本体はメソッドへ切り出す**（`HandleCardReadAsync`）。`Application.Current.Dispatcher` に依存する `OnCardRead` は ViewModel 単体テストから到達できないため、切り出さないとこの経路を 1 件も検査できない（#1807 が `StaffManageViewModel` で先行した形）
- **失敗したら入力待ちの状態へ戻す**。`IsWaitingForCard = false` のまま止めると以後のタッチが無視され、キャンセル以外に復旧手段が無い。確認の済んでいない IDm はフォームに残さない
- **文言は `ExceptionMessageFormatter.ToUserMessage` を通す**（#1614）。生の `ex.Message` は英語の SQLite エラーになる
- **`Task` を捨てる箇所は兄弟ファイルにも同じ形で存在する**（#1808）。`grep -n "Dispatcher.InvokeAsync"` で列挙して同時に洗う
- **本体全体を包む `catch` は、コミット確定後の後処理の失敗まで飲み込む**（#1816 のコードレビューで判明）。削除済みカード／職員の復元は `RestoreAsync` の時点でコミット済みで、その後の操作ログ記録・一覧再読込の失敗を「読み取りに失敗しました。もう一度タッチしてください」と案内すると、案内どおり再タッチした職員は「既に登録されています」に行き着く。`restoreCommitted` を立てて `catch (Exception ex) when (restoreCommitted.Value)` で**先に**受け、「記録済み」＋「再タッチしないでください」＋入力待ちへ戻さない形にする（#1727 / #1805 の「コミット確定後の後処理を、成否の判定に巻き込まない」が、**受け皿を広げた `catch` の側からも破られる**という形）。例外フィルタで書くと、後処理を後から足しても既定で保護される。**このフラグは呼び出しごとのローカルで持つ**（`StrongBox<bool>` を本体へ渡す）— インスタンスフィールドに置くと、後処理の await 中に始まった別の読み取りがその先頭で false へ戻し、確定済みの操作が読み取り失敗として案内される（防ごうとしている状態そのもの）
- **入口ゲートは取得地点で再判定する**（同）。`OnCardRead` の `IsWaitingForCard` 判定はカードリーダースレッドで行われ、解除は UI スレッドの本体で初めて行われるため、連続タッチでは 2 件目もゲートを通過済みで queue される（#1807 の「抑制の判定は入口 1 か所で終わらせない」と同じ形）
- **受け皿を本体に置いても、ディスパッチした側の観測を省かない**（Issue #1843）。本体全体を包む `catch` は「例外が抜けない」ことを保証しない — `catch` ブロック自身（`CancelEdit()` の `_messenger.Send`、`StatusMessage` / `IsStatusError` 代入の `PropertyChanged`）が投げれば再び無言になる（上記 #1745「`catch` の中の後始末は、それ自体が失敗し得ることを前提に書く」）。**受け皿は 1 つでは足りない**。UI スレッドへの非同期ディスパッチは生の `Application.Current.Dispatcher.InvokeAsync` ではなく `IDispatcherService.InvokeAsync` を使う（`Task<Task>` を `Unwrap()` して観測しログへ残す。#1725）
  - **注入は必須引数にする**。省略時の既定（`null`）は本来の値と一致しないため、DI の配線漏れが「カードをタッチしても何も起きない」という形で潜在化する（#1820「依存を省略可能にしてよい条件」）
  - **生の `Dispatcher` は ViewModel をテスト不能にする**。`Application.Current` に依存する `OnCardRead` は ViewModel 単体テストから 1 件も踏めず、#1816 / #1807 の回帰テストはいずれも本体（`HandleCardReadAsync`）を直接呼ぶしかなかった。**入口ゲートを含む経路が 1 件も検査されていない**状態は、抑制や再判定を足すたびに広がる
  - **テスト用の代役は本番と同じ失敗の伝え方にする**。`SynchronousDispatcherService` は例外を再スローするため、「本体の `catch` 自体が失敗した」ケースで例外がテストメソッドまで伝播し、「観測されたか」を表明できない。本番（記録して再スローしない）と同じ `RecordingDispatcherService` を使う（#1737「本番が示し得ない性質を表明しない」）
  - 回帰は `CardReadDispatchConventionTests` が「生の `InvokeAsync` の不在」と「`_dispatcherService.InvokeAsync` の存在」を**対で**静的検査する。不在だけを見ると、ディスパッチごと消して同期実行へ倒した実装でも緑になる
  - **ガードは「受け手」を起点に照合し、そこへ至る参照経路を直書きしない**（#1843 のコードレビューで判明）。初版は `Application\.Current\.Dispatcher\.InvokeAsync` を直書きしていたため、`Application.Current?.Dispatcher`（本リポジトリでは `App.xaml.cs` が使用）・`Dispatcher` をフィールドへ退避した形・`BeginInvoke` が**同じ欠陥のままガードを素通り**した。**同じ資源へ別の綴りで到達できるなら、ガードは綴りではなく資源で書く**（#1786「その性質を破れる全経路を列挙する」／#1837「移行前後の両方の綴りで grep する」の再演。**規約を引用しながら同じ誤りを犯し得る**ことに注意）
  - **View コードビハインドは `Common/DispatcherObservation` へ寄せる**（Issue #1873）。`Views/` は `IDispatcherService` を注入できない（`Window` は自分自身の `Dispatcher` を持つ）ため、`Dispatcher.InvokeAsyncObserved(…, operationName, priority)` を唯一の観測手段とする。観測の実体は `WpfDispatcherService.ObserveTask` からも呼ばれる同一の `Observe` で、層ごとに違うのは記録先だけ（ViewModels は `ILogger`、Views は `ErrorDialogHelper.LogException`。#1817）。`CardReadDispatchConventionTests` の走査対象は `Views/` を含む。**是正と走査拡大は同じ PR で行う** — 先に広げると既存違反で赤になり抑制を積む形（＝#1786 の形骸化）を招くため、`grep` で `Views/` の全 10 か所を列挙して一度に寄せた（同期ラムダを渡す `InvokeAsync(Action)` / `BeginInvoke` も例外を `DispatcherOperation` の `Task` へ格納するだけで誰も観測しない点は同じ）

### 同じ状態表現に 2 つの意味を持たせない（同 Issue）

`LedgerDetailViewModel.MergeAll` は「すべての分割線を消す」ことで統合を表現していたが、`RecalculateGroupsFromDividers()` は**分割線が 1 つも無いとき全項目の `GroupId` を null（＝自動検出）にする**ため、「自動検出に戻す」と完全に同一動作になっていた。ボタンもメッセージも ToolTip も「1 つのグループにします」と述べており、**文言だけが実装から独立して正しかった**。

- **「何もない状態」を既定の意味に割り当てたら、利用者が明示的に選んだ同じ見た目の状態と区別できるかを確かめる**。区別が要るなら明示的な値（`GroupId = 1`）を書き込む
- **派生計算（分割線 → グループ）に委ねる操作と、結果を直接書き込む操作を混ぜない**。`MergeAll` は派生計算を呼ばずに自分で書き込む形にした
- **利用者の明示指定は、下流の自動判定より優先されているかまで見る**。`SummaryGenerator` はグループ内の摘要生成を自動判定へ委ねていた（往復を「A～A」にしないため。#548）ので、`GroupId` を付けただけでは非連続区間が分かれたままだった。指定を摘要へ届けるには畳み込み（`CollapseExplicitGroupSummary`）が要る。**ただし畳み込みが従来の判定結果（往復・乗継）を壊していないことを対のテストで固定する**
  - **「既定値を決める定数」を「利用者の指定に対する上限」へ流用しない**（Issue #1921）。管理者ダッシュボードの残高推移グラフは `AppConstants.AdminDashboardMaxSeries`(=5) を、初期選択の枚数（初回表示の可読性のため。妥当）と**描画の上限**（チェックを付けたカードを先頭 5 枚で切る）の両方に使っていたため、6 枚目以降のチェックが無言で無視されていた。**同じ定数が「自動判定の既定値」として妥当であることは、「利用者の指定を否定する根拠」としての妥当性を意味しない** — 前者が正しいぶん、後者の不当さが隠れる
    - **超過分の行き先があるかを見る**。同じ定数を使う月別利用額グラフでは超過分が集約系列（「その他（N 名）」）へ畳まれて画面に残るが、残高推移では**どこにも現れず、なぜ描かれないのかを伝える表示も無かった**。上限で切る実装を書くなら、切った分の行き先か理由の表示を対で用意する（#1727「『ログには出ている』は無言失敗の免罪符にならない」の UI 版）
    - **上限を撤去するテストは「上限が効いていた側」も対で固定する**。「超過分も描かれること」だけを表明すると、初期選択の上限まで消した実装でも緑になる
- **「見た目が同じなら、保存される内容も同じ」を保て**（同 Issue のコードレビューで判明）。`MergeAll` だけを直しても、分割線を 1 回 ON→OFF すると `RecalculateGroupsFromDividers()` の「分割線なし＝自動検出」分岐へ落ちて**統合が黙って取り消される**（画面は統合直後と区別が付かないのに、保存時の摘要だけが分かれる）。**明示的な値を書き込む側だけでなく、同じ状態を再計算する側も揃える** — 分割線の操作から到達する経路では常に明示グループを割り当て、自動検出へ戻す経路は専用の操作（「自動検出に戻す」）だけにする
- **下流の判定条件を「上流が組み立てた文字列の見た目」で書かない**（同 Issue のコードレビューで判明）。畳み込みの条件を「区切り文字『、』が残っているか」で書いたため、**「A～B 往復、C～D」（往復＋別区間）まで対象になり**、往復の情報が失われるうえ「A～D」という**実際には乗っていない区間**が 6 年保存の台帳へ入った。文字列は上流の書式が増えるたびに意味がずれる。畳まない条件（往復を含む／始点＝終点／端点が駅名不明の「?」）を明示し、**対のテストは「1 グループがちょうど往復だけ」ではなく「往復に別の要素が混じる」形で書く** — 前者だけだと条件が広すぎる実装でも緑になる

## 「処理中」フラグの解除は `finally` で保証する（Issue #1725）

**入力を止めるフラグを立てたら、解除は必ず `try/finally`（または `IDisposable`）に置く。** 成功分岐と失敗分岐の末尾に解除を書く形は、その 2 つの分岐の途中で例外が出たときに解除されない。

`MainViewModel.ProcessLendAsync` / `ProcessReturnAsync` は `SetInternalState(AppState.Processing)` の解除（`ResetState()`）を各分岐の末尾に置いていたため、**記録が確定した後の画面更新**（貸出中カード一覧・残高ダッシュボード・履歴の再取得、警告再チェック、バス停入力ダイアログ）で例外が出ると `Processing` のまま抜け、以後の全カードタッチが無視された。

- **「復帰手段が他にあるか」を確認する。** `Processing` にはタイムアウトが無く、カードタッチは冒頭で破棄され、タイムアウトタイマーは停止済み、Esc は別状態専用、共有モードの定期リフレッシュもスキップする。**復帰手段が 1 つしかない状態は `finally` 以外で解除してはいけない**
- **fire-and-forget の呼び出し元は例外を観測しない前提で書く。** `WpfDispatcherService.InvokeAsync(Func<Task>)` は `Dispatcher.InvokeAsync` の戻り値も内側 `Task` も await していなかったため、例外が `TaskScheduler.UnobservedTaskException` で GC 契機に遅延発火するだけだった。`Task<Task>` は `Unwrap()` してから観測する（外側だけでは async lambda 本体の例外を取りこぼす）
- **「処理は成功したが後処理が失敗した」を区別して案内する。** 記録済みなのに「もう一度タッチしてください」と案内すると、30秒ルールの逆処理で記録済みの操作が取り消される。記録が確定したかをローカル変数で追跡し、確定後は「◯◯は記録済み」＋「再タッチしないでください」＋中立的な `SoundType.Warning` にする（エラー音は事実と矛盾する）
- **状態値だけでなく「次の操作が効くこと」をテストで表明する。** `CurrentState` の値を見るだけでは、固着の実害（以後の全タッチが破棄される）を表現できていない

### 入力を止めるフラグは「取得」も処理範囲と一致させる（Issue #1807）

上の規則の裏面。**モーダルダイアログ（`Window.ShowDialog()` / `MessageBox.Show`）は「止まる」のではなく入れ子のメッセージポンプで「回り続ける」**ため、表示中もカードリーダーのイベント購読は生きている。「モーダルだから他は動かない」という直感で抑制を省くと、表示中の別カードタッチが `MainViewModel.HandleCardReadAsync` に届き、種別選択ダイアログが多重に開く／背後で貸出・返却が進む／事前読み取り中の再入で `Error -=` が no-op になり `finally` の `+=` が二重購読になる。

- **抑制（`CardReadingSuppressedMessage` / `_suppressionSources`）の取得と解放は、ダイアログの表示範囲と一致させる**。「1 枚読み取ったら解放」は、ダイアログがまだ開いている限り早すぎる（`StaffManageViewModel` は IDm 読み取り直後に解放し、氏名入力中のタッチが背後で処理された）。解放は `CancelEdit` / `Cleanup` のような「登録モードの終わり」に限る（`CardManageViewModel.OnCardRead` が参考実装。保存成功時も `CancelEdit` を経て解放され、一覧だけのアイドル状態に戻ったダイアログの背後ではメイン画面がタッチを処理する ― これは #852 以来の意図で、本項の「表示範囲」は登録モードの範囲を指す）
- **抑制の判定は「入口 1 か所」で終わらせない**。`HandleCardReadAsync` の入口ゲートから抑制を取得する地点までに await（職員・カードの `GetByIdmAsync`）が挟まるなら、その待機中に届いた 2 件目は入口ゲートを通過済みで、1 件目が取得した抑制をすり抜ける。取得地点の直前で `IsCardReadingSuppressed` を再判定し、`BeginCardReadingSuppression` は同一ソースの二重取得を no-op スコープにする（内側の Dispose が外側の抑制を解かない）
- **同じ画面へ入る経路が複数あるなら、全経路で取得する**。「新規登録」ボタン（`StartNewStaff`）は取得していたが、未登録カード経由（`StartNewStaffWithIdmAsync` / `StartNewCardWithIdmAsync`）は一度も送っていなかった。#1760 の「画面の動詞ではなく書き込み文で数える」と同じで、**取得の有無は「モードに入る関数」を grep で列挙して確かめる**
- **ViewModel 自身がモーダルを出す経路は `IDisposable` スコープ（`using`）で囲む**（`MainViewModel.BeginCardReadingSuppression`）。解放が Dispose で保証され、早期 return や後から足す分岐で漏れない
- **モーダル中の再入はテストで再現できる**。`ShowDialog` モックの `Callback` 内でカード読み取りイベントを発火すると、`SynchronousDispatcherService` が本番と同じ「ダイアログ呼び出しの最中に別のタッチが処理される」形になる。修正前のコードでは Callback → 再入 → `ShowDialog` → Callback… と無限に入れ子になるため、発火は 1 回に限定するフラグを置く。二重購読は「`Error` を 1 回 Raise して警告が 2 件」で観測できる（`MainViewModelTests` の「カード読み取り抑制テスト」region）
- **入口ゲートの再判定は「抑制」だけでなく「状態」も見る**（Issue #1842）。#1807 は待機窓の再判定を `HandleUnregisteredCardAsync` の先頭（＝未登録カード分岐）にだけ置いたが、窓そのものは呼び出し元の `GetByIdmAsync` にあり、**職員証分岐にも同じ交錯が成立する**。交錯の順序は 2 通りあり、①未登録カードが先に抑制を取る順は「抑制」で、②職員証が先に認識される順は「状態」でしか検出できない。②では、あとから再開した未登録カード処理の末尾の `ResetState()` が**確定済みの操作者を消し**、職員は認識されたつもりで次の交通系ICカードタッチが履歴表示になる。**片方だけ塞ぐと Issue の故障シナリオがそのまま残る** — 再判定を書くときは「この待機中に変わり得る前提」を列挙し、その全部を取り直すこと
  - **再判定は分岐ごとではなく、分岐する前の共通位置へ置く**。分岐先に配ると、分岐が増えるたびに配り忘れる形が残る（#1763「同じ論理的な書き込みに手段が 2 通りあるか」と同じ判断）
  - **副作用を起こす前に判定を終える**。`HandleCardInIcCardWaitingStateAsync` の `StopTimeout()` が再判定より前にあると、中止する経路で**タイマーだけが止まり `WaitingForIcCard` から抜ける手段を失う**。判定を前へ出すのではなく、副作用を判定の後ろへ下げる
  - **中止したタッチは通知せず捨てる**。再タッチで通常どおり処理されるため、副作用を残さない側へ倒す。ただしこれは挙動変更であり、正当な連続タッチも 1 件捨て得ることを設計書に明記する
- **同じ欠陥は「登録モード」以外の抑制ソースにも残る — 抑制ソースの単位で洗う**（Issue #1952）。#1807 は `StaffManageViewModel` / `CardManageViewModel` を是正したが、`CardReadingSource.DataImport`（データ入出力ダイアログ F4 のカードタッチ指定）は同じ形のまま残っていた。`DataExportImportViewModel.HandleCardReadCoreAsync` は `IsWaitingForCardTouch = false` を `GetByIdmAsync` の `await` と未登録カード警告モーダルより**前**に置いており、その区間はメイン画面が無抑制で、警告ダイアログの背後で貸出・返却が 6 年保存の台帳へ確定し得た。**洗い出しは画面名ではなく `CardReadingSource` の全メンバーで数える**（`grep -n "CardReadingSource\." src/`）。#1952 時点の 6 ソースの内訳は、`StaffRegistration` / `CardRegistration`＝#1807・#1844 で是正済み、`UnregisteredCardDialog` / `BalanceMismatchCheck`＝`using` スコープ（Dispose ＝ `finally` 相当）で解放、`Authentication`＝`StaffAuthDialog` の `Loaded` で取得し `Closed` で解放（表示範囲と一致）、残る `DataImport` だけが未是正だった
  - **入口ゲートと抑制ソースを 1 つの状態が兼ねていると、解放位置が両立しない**（#1858「同じ状態表現に 2 つの意味を持たせない」）。`IsWaitingForCardTouch` は ①`OnCardRead` の入口ゲート ②`OnIsWaitingForCardTouchChanged` 経由の抑制ソース を兼ねており、①の都合（再入を塞ぐため即座に false）が②の要件（モーダル中も抑制を維持）を壊していた。解放を後ろへ移し、再入は**専用フラグ**（`_isHandlingCardRead`、`finally` で解除）で塞いで役割を分ける
  - **解放を `finally` に置かない**。`finally` に置くと失敗時にも解放され、「タッチ待ちへ戻して再試行を案内する」（#1816）のに抑制だけが外れる。解放は成功パスの末尾に置き、失敗時は待機＝抑制 ON のまま呼び出し元の `catch` に委ねる。ただし**再入フラグの解除は `finally`** — 解除を忘れると 1 度の失敗でカード指定がアプリ再起動まで不能になる（#1725）
  - **解放を後ろへ移すと、その状態に束縛された UI の「操作できる窓」も一緒に広がる**（コードレビューで検出）。`IsWaitingForCardTouch` は「キャンセル」ボタンの `Visibility` にも束縛されており、解放を `await` の後ろへ移した結果、**照合（`GetByIdmAsync`）の待機中もキャンセルが押せる状態で残った**。共有モードの照合は秒単位かかり得るため、この窓でキャンセル／指定のクリア／データ種別の切替／`Cleanup` が起きて抑制が解放され、**続きの処理が未登録カード警告モーダルを抑制 OFF のまま開く** — 塞いだはずの欠陥がこの経路から再現する（#1814「修正の中に、修正対象と同じ欠陥への経路を残さない」）。`await` の直後・**副作用より前**に入口ゲートを再判定し、中止したタッチは通知せず捨てる（#1842）
  - **「その状態を読んでいるのは自分だけ」と決めてかからない**。解放位置を動かす前に、その状態が束縛されている XAML を `grep` で数える（`grep -n "IsWaitingForCardTouch" Views/`）。ViewModel のテストは表示条件を見ないため、この波及はテストからは見えない（#1727「所在」と同じ形）
  - **回帰は「解放しないこと」と「解放されること」を対で置く**。前者だけだと解放を丸ごとやめた実装（＝ダイアログを閉じるまでメイン画面が固着する）でも緑になる。あわせて再入ガードとその解除も対で表明する（片方だけだと、ガードを持たない実装／解除を落とした実装がそれぞれ素通りする）
- **対象は「未登録カード〜登録」の経路と登録モードに限定した**。F2/F3 等から開く一般のモーダル表示中にメイン画面がタッチを処理する挙動は運用上の意味を持ち得るため、この Issue では変えていない
- **解放の契機が「成功したときにしか来ない出来事」なら、失敗経路の回収を別に用意する**（Issue #1844）。#1807 は抑制の取得を登録モードの入口（`StartNew*WithIdmAsync` の先頭）へ移したが、解放を担う `CancelEdit` / `Cleanup` はどちらも「登録モードに入った」「ダイアログを閉じた」ことが前提で、**その手前で例外が抜けるとどちらも走らない**。共有フォルダーの一時断で直後の `GetByIdmAsync` が失敗すると、編集フォームも出ていない画面が残り、その間メイン画面は全カードタッチを無言で無視する（音も出ない）。復帰手段が「職員が自分でダイアログを閉じる」1 つしかない＝#1725 が禁じた形
  - **回収は「取得側」と「器側」の 2 段で書く**。①取得側（ViewModel）は本体を `try` で囲み、例外時に解放を送ってから**再スローする**（呼び出し元が失敗を観測して閉じられるよう握りつぶさない）。②器側（View）は `Loaded` の `catch` の中の `finally` で `Close()` し、`Closed → Cleanup` と呼び出し元の `using` スコープの両方を回収する。**取得より前の失敗（一覧の読み込み）は①へ到達しない**ため、②が要る。解放の受け手が `HashSet` なら二重解放に副作用はない
  - **`Close()` は `catch` の中の `finally` に置く**。案内の表示（`MessageBox`）自体が失敗し得るため、後始末をその後ろに書くと二次例外で飛ばされる（#1745）
  - **初期化失敗は「致命エラー」ではない**。`ErrorDialogHelper.ShowError`（`GetErrorInfo`＝`SYS00x`＋スタックトレース）は継続不能時のための表示で、開き直せば復旧する経路に転用しない（`error-messages.md` の役割分担）。`ExceptionMessageFormatter.ToUserMessage` の 3 要素文言に「画面を閉じます。復旧したら、もう一度開いてください。」を添え、技術的詳細は `ErrorDialogHelper.LogException` でログへ残す。**自動で閉じるようにしたら、閉じたことを文言で伝える**（黙って消えると職員は自分の操作が届かなかったのか判断できない）
  - 回帰は `RegistrationDialogInitializationFailureConventionTests` が静的検査する。走査対象は**ファイル名ではなくコードの形**（`StartNew*WithIdmAsync` を呼ぶコードビハインド）から導出し、同型のダイアログが増えても検査から漏れないようにする（#1786）。検査ロジック自体もサンプル入力で固定する（実データが変わっても空振りしない）

## 値を丸め込んだら、その値に依存して取得したデータも取り直す（Issue #1814）

**入力を有効範囲へ丸め込む（クランプする）処理を書いたら、「丸め込む前の値で既に何かを取得していないか」を確認する。** 取得済みなら、それは**丸め込み前の値に基づく古い結果**であり、丸め込み後の値で作られる表示と食い違う。

`MainViewModel.LoadHistoryLedgersAsync` は**クランプ前**の `HistoryCurrentPage` で `GetPagedAsync` を実行してから総ページ数を再計算し、ページ番号をクランプするだけで**再取得しなかった**。一方で件数表示（「N～M件を表示（全X件）」）とページ表示（「N / M」）は**クランプ後**の値で作られるため、履歴の個別削除（#635）や統合（#1458）で総件数が減ると**一覧が空なのに「1～30件を表示（全30件）」「1 / 1」**と表示された。ページ送りボタンも `CanExecute=false` で無効になるため、期間変更か履歴の開き直し以外に復旧手段が無かった。

- **「丸め込みを取得の前へ移す」が常に取れるとは限らない**。丸め込みの基準（総ページ数）が取得結果からしか分からない場合、前へ移すには基準を先に取る別クエリが要り、共有モードでは 2 クエリの間に状態がまた変わって同じ穴が残る。**構造に素直なのは「取得 → 丸め込み → 取り直し」**
- **再取得のループには上限を置く**（#1809 の「ドレインには上限を置く」と同じ向き）。共有モードでは取り直しの最中にも他 PC の変更で基準が動き得るため、上限が無いと理論上ループが終わらない
- **ただし「上限に達したら壊れた状態で妥協してよい」ではない — 打ち切り経路にも同じ不変条件を成立させる**。#1814 の初版は打ち切り時に「丸め込んだが取り直さない」で抜けており、**一覧は丸め込み前の無効な値の結果（＝空）、ページ番号だけが丸め込み後**という、まさに直そうとしていた状態に着地し得た（クランプ先が 1 ページ目だとページ送りが全て `CanExecute=false` になり復旧不能）。**修正の中に、修正対象と同じ欠陥への経路を残さない**
  - **打ち切り先には「必ず成功すると分かっている入力」を選ぶ**。#1814 では 1 ページ目（**総件数が 1 件以上なら必ず行を返す** ＝ OFFSET 0）へ落として 1 回だけ取り直す。丸め込み先（最終ページ）はその間にまた減っていれば再び空になり得るため保証にならない。**「決定的に収束する入力が存在するか」を先に探す**と、上限の設計が「妥協」から「保証」に変わる
  - **打ち切りで何かを失うなら、失うものと失わないものを明示する**。#1814 は利用者のページ位置を失うが、整合しない表示・復旧不能な状態は作らない。この優先順位をコメントと設計書に書く
- **上限を設ける実装のテストは「止まること」で満足しがちだが、止まった先の状態こそが本体**。#1814 の初版のテストは要求ページの並びと現在ページだけを固定しており、**「丸め込んだが取り直さない」実装を許す表明**になっていた。打ち切り経路でも一覧・件数・ページ番号が整合することを具体値で表明する
- **再入（再帰呼び出し）で書く前に、そのメソッドが持つスコープが入れ子に耐えるかを確認する**。`BusyScope` は #1836 で入れ子に対応した（深さを数え、最外の `Dispose()` だけが解除する）が、入れ子の内側では**メッセージが外側のまま**になる。表示が意図どおりかを確認すること（#1814 は同一スコープ内のループにしてこの判断ごと避けている）
- **「丸め込み後の値」を条件にした処理が他にもないか数える**。#1814 では 1 ページ目へクランプされたとき、繰越行の挿入（#1155）と残高チェーンのシード（#1740）が `HistoryCurrentPage == 1` を見ているため、**取り直さないとこれらも空の一覧に対して判定していた**
- **回帰テストのモックは、実装（`GetPagedAsync` の OFFSET/LIMIT）と同じ振る舞いで応答させる**。「要求ページが総ページ数を超えていれば空を返す」を再現しないと、故障の起点そのものが発生しない。固定の戻り値を返すモックでは緑のまま通る
- **「丸め込みが不要なときは取り直さない」を対のテストで固定する**（#1757 の「正当な操作を塞いでいないことを対で固定する」）。片側だけだと「常に 2 回問い合わせる」実装でも緑になる

## 巡回する値（月・曜日・角度）は、折り返した後の値どうしで大小比較しない（Issue #1812）

**「12→1 に折り返す量」で前後関係を判定すると、折り返しをまたいだ瞬間に比較の意味が失われる。** 折り返しの起きない値（年込みの絶対量、または折り返し前の元の値）で判定し、桁上がりは専用の API（`DateTime.AddMonths` 等）に任せる。

`SummaryGenerator.GetMidYearCarryoverDate` は先に `nextMonth = (carryoverMonth % 12) + 1` を求め、`nextMonth > registrationDate.Month` で「前年のデータか」を判定していた。繰越月＝登録月では `nextMonth = month + 1 > month` が**必ず真**になるため、紙出納簿移行カードの繰越レコードが 1 年前へ落ち、当年度の月次帳票から繰越行が消えて残高チェーンが切れた。是正は「繰越月そのものが属する年を先に確定し、その 1 日に `AddMonths(1)`」で、折り返しの特別扱いそのものを無くした。

- **「翌月」「前日」のような相対位置を自前で計算したら、それを比較に使う前に折り返しの有無を確かめる**。`(x % n) + 1` のような式が出てきたら合図
- **境界テストは「折り返しが起きる入力」と「起きない入力」を対で置く**。#1812 の既存テストは過去月のケース（1月繰越／12月繰越／11月繰越／3月繰越）を 4 件持っていたが、**繰越月＝登録月のケースが 1 件も無かった**ため、6 年保存の台帳へ入る日付の境界が固定されていなかった
- **入力の全域を走査する不変条件テストを 1 件置く**。個別ケースの列挙では、次に条件式を触った人が別の境界を壊しても気付けない。#1812 では「全 12 か月について、繰越レコード日付の前月が選択した繰越月と一致し、その年が登録月以前の直近である」を `[InlineData]` 12 件で表明した
- **定義域外の入力を黙って別の値に丸めない**。`(month % 12) + 1` は `month = 13` を 2 月として受け入れていた。`ArgumentOutOfRangeException` で弾く

### 曖昧な入力は「塞ぐ」より「解決結果を見せる」

同 Issue で、繰越月コンボから当月以降を除外する案は採らなかった。「繰越月＞登録月」は**正当な運用**（2 月登録で「11 月から繰越」＝前年 11 月まで紙運用）と**誤選択**（2 月登録で「5 月から繰越」）の両方を含み、入力値だけでは区別できないためである。機械的に塞ぐと正当な運用まで止まる。

- **区別できない入力は、システムがどう解釈したかを入力欄の近くに提示して利用者に判断させる**（`GetMidYearCarryoverDateDescription`）。前年扱いになる場合は「なぜ」と「どうすれば」（登録日の月以前を選ぶ）を併記する
- **提示文言の生成は純関数へ切り出し、`Window` を実体化せずに単体テストできる形にする**（#1794 の「判断を純関数へ切り出す」と同じ形）

## 「全消し＋再生成」を書くときは、消す側ではなく**残す側**を列挙しない（Issue #1739）

コレクションを作り直す処理（`Clear()` してから詰め直す形）で、**再生成しない要素まで巻き添えにしていないか**を確認する。判断の分かれ目は「列挙するのが保持側かクリア側か」で、**保持側の列挙は、要素の種類が増えるたびに更新する義務を生む**。

`MainViewModel.ApplyDataWarnings` は保持する `WarningType` を5種列挙して残りを `WarningMessages.Clear()` していた。Issue #1689 の `BackupStale` と Issue #1058 の `BalanceInconsistency` がその更新から漏れ、どちらも警告再チェックでは再生成されないため、**起動後の最初の返却操作で警告が消えたきりセッション中は復活しない**状態になっていた。

- **対処は「保持リストに足す」ではなく「`Clear()` を撤去してクリア側を列挙する」**。前者は同じ再発を将来も呼び込む（`UPDATE` の SET 句を呼び出し元に引き継がせるのではなく SET 句から外した #1726 と同じ判断）。クリア側の列挙なら、再生成手段を持たない新しい種類は**既定で残る**＝fail-safe に倒れる
- **各生成メソッドは「自分が出す種類だけを入れ替える」形にする**（既存を取り除いてから、条件を満たせば追加する）。他メソッドの事前クリアに依存して「追加のみ」で書くと、①その事前クリアを外した瞬間に重複し、②fire-and-forget で並走したときにも重複する（`CheckIncompleteBusStopsAsync` が実際に両方を踏んでいた）
- **回帰は「列挙型の全値」を走査するテストで固定する**。個別種類ごとのテストでは、新しい種類を足したときに追随漏れが静かに起きる。`Enum.GetValues(typeof(T))` から検査対象を導出すれば、種類の追加が自動的に検査対象になる（`MainViewModelTests` の UT-WARN-KEEP No.3 が参考実装）
- **「消えても再表示される」と早合点しない**。再生成の経路が実在するかを grep で確かめる。`BackupStale` の再判定は起動時と警告クリック時の2箇所だけで、**消えた後はクリックもできない**ため復活手段が無かった
- 種類ごとの生成元・生成/除去の契機は `ICCardManager/docs/design/04_機能設計書.md` §7.4 の表に集約する。新しい `WarningType` を足すときはこの表に1行足し、`ApplyDataWarnings` は触らない

### 反転したら、**除去の責任も生成元へ移る**（同 Issue のコードレビューで判明）

`Clear()` は「再生成されないものを消してしまう」欠陥であると同時に、**それまで誰も掃除していなかったものを掃除する唯一の経路**でもある。撤去すると今度は「消せない要素」が生まれるため、**撤去前に「この `Clear()` が実際に何を掃除していたか」を数え上げる**こと。#1739 では次の4種が該当し、いずれも撤去後に別途手当てが必要だった。

- **母集団から外れた対象**: 生成元が「有効なもの」しか走査しない場合、対象が無効化されると除去経路ごと消える（`BalanceInconsistency` の生成元は `is_deleted = 0` のカードしか見ないため、カードを論理削除すると**クリックしても何も起きない警告**が再起動まで残った）。**母集団を知っている地点**（`RefreshDashboardAsync`）で掃除する
- **生成元が複数あるなら、判定範囲・判定条件を揃える**。同じ種類を2つのメソッドが別条件で管理していると、一方が立てたものをもう一方が黙って消す（全期間で立てた不整合を、表示期間しか見ないメソッドが消していた）。**全消しがある間は「どうせ毎回消える」ので露見しない**
  - 揃えるときに**部分の結果を全体の代用にしない**。残高チェーンは範囲の先頭行を起点扱いして検査を飛ばすため、部分範囲の判定が全期間の判定と一致する保証がない
- **非同期チェックの陳腐化**: fire-and-forget の結果を `await` 後に書き戻す形は、保留中に別経路が最新の結果を確定させると**古い結果で上書きする**。世代番号を採番し、より新しいチェックが始まっていたら結果を捨てる。全消しがある頃は「重複する」だけだった問題が、入れ替えでは「復活する」に変わる
- **再判定の入口は、文言が案内する操作すべてに置く**。「◯◯画面で△△してください」と案内するなら、その画面へ**どの経路から入っても**再判定する（`BackupStale` は警告クリック経由にしか再判定が無く、案内どおり F6 を押した管理者には「復旧したのに消えない」ように見えた）。入口を1つに集約し、他はそこへ委譲する

## 「クリアして再生成」は、再生成が作り直すものを漏れなくクリアする（Issue #1810）

上（#1739）の裏面。再利用する器（既存の Excel シート等）を「クリアして作り直す」とき、クリア対象を**見えるデータ**（セル値・行）だけにすると、生成処理が実行のたびに **add するメタデータ**（改ページ・書式等）が蓄積する。`ClearWorksheetData` はセル値しか消さず、`CheckAndInsertPageBreak` が挿入した改ページ（`PageSetup.RowBreaks`）が残留した。帳票は毎月同一ファイルへ上書きされる（#477）ため、行数が減る再生成（#635 の履歴個別削除・#1458 の履歴統合）で「L2 + RowBreaks.Count」から逆算する翌月の開始ページ番号が飛び、空白領域の改ページで印刷時に白紙ページが出た。

- **列挙の単位は「生成処理が add する文」**。生成側が呼ぶ追加系 API（`AddHorizontalPageBreak` 等）を grep で列挙し、その各々に対応する撤去がクリア側にあるかを見る（#1760 の「画面の動詞ではなくテーブルへの書き込み文で数える」と同じ数え方）
- **蓄積はすぐに露見しない**。行数が同じか増える再生成では症状が出ず、「行数が減る」再生成で初めて表面化する。回帰テストは「同一ファイルへ 2 回出力し、2 回目で行数が減る」形で書く（`ReportServiceTests` の UT-019 No.19 が参考実装）
- **「収まるか」の予約判定で、確定した境界を推定式に代弁させない**（同 Issue の欠陥 2）。印刷プレビューの `GroupRowsByPage` は合計行のスペースを「残り全行＋合計行が収まるか」（`canFitAll`）でのみ予約しており、**最終行に到達した**という確定情報を使っていなかったため、「本文は収まるが合計行を足すと収まらない」最終ページで予約がゼロになり、月計・累計行が体裁のない次ページへ単独ではみ出した。最終行では常に予約する。なお推定式（`canFitAll`）による予約は「収まる場合は溢れ判定が必ず偽になる」ため一度も改ページに影響しないデッドロジックであり、是正時に撤去した — **予約を足すときは、その予約が溢れ判定を実際に動かし得る分岐かを確かめる**。対の回帰テストとして「ちょうど収まる場合は 1 ページのまま」（過剰分割しない）も固定する

## 設定値で生成したものは、設定値で判定する（Issue #1818）

**「設定から組み立てた文字列」を後で判定・抽出する箇所は、同じ設定から導出する。** 生成側だけが設定値を使い、判定側がリテラルを直書きしていると、**既定値のままの環境では偶然一致して潜在化し、設定を変えた組織でだけ壊れる**。この形は #1604（繰越判定の C# 側）→ #1749（同 SQL 側）→ #1818（バスのラベル・プレースホルダ）と **3 度再発している**。

`SummaryText.BusLabel`（既定「バス」）/ `BusPlaceholder`（既定「★」）は摘要の生成側だけが設定値を使い、抽出は `@"バス（(.+?)）"`、未入力判定は `Contains("★")` を直書きしていた。ラベルを「乗合自動車」に変えた組織では統合時にバス停名が消え・入力ダイアログが出ず、プレースホルダを「※」に変えた組織では**バス停名未入力の警告が常に 0 件**になる。

- **導出ヘルパーを設定の持ち主（`SummaryGenerator`）に置き、全消費側を委譲させる**。「各所で `_options.SummaryText.X` を読む」では、生成の書式（ラベル＋全角括弧）と抽出の正規表現が別々に育って再びずれる。**生成 `FormatBusSummary` と抽出 `ExtractBusStopBlocks` を同じクラスの隣り合わせに置く**と、片方だけ変える誤りが目に入る
- **設定値を正規表現へ埋めるときは `Regex.Escape` を通す**。メタ文字を含むラベル（「バス(市営)」等）でパターンが壊れる
- **空設定（`""` / 空白 / null）は既定値へフォールバックする**。空ラベルは抽出パターンを `（(.+?)）` に退化させて**鉄道の括弧まで拾い**、空プレースホルダは `Contains("")` が常に true になって**全履歴が「未入力」**になる（`IsMidYearCarryoverSummary` の不正正規表現フォールバックと同じ方針）。フォールバックが守っている性質は**抽出結果で表明する**（プロパティ値の一致だけでは、退化したパターンが何を拾うかを検査していない）
- **洗い出しは grep で機械的に行う**。#1818 の起票時点の指摘は 9 箇所だったが、実際は 15 箇所あった（`LedgerRepository` のサジェスト SQL・View のコードビハインド・XAML の説明文・テストデータ生成）。**XAML の固定文言と SQL のリテラルは「コードを読む」だけでは視野に入らない**
- **`Data/` 層へは値を引数で渡す**。組織設定由来の値であっても、それが**交通系固有**なら `SummaryGenerator` を参照させない（`domain-boundaries.md` の許可リストは汎用メソッドに限る）。リポジトリは判断を持たず、除外する文字列を受け取る形にする（`GetBusStopSuggestionsAsync(string busStopPlaceholder)`）
- **消費側のテストは必ず既定と異なる値へ設定してから呼ぶ**。既定のままでは直書きのリテラルと設定値が偶然一致し、**修正前のコードでも緑になる**
- **旧値を拾わないことを対のテストで固定する**。片側だけだと「新旧どちらも拾う」広すぎる実装でも緑になる（`error-messages.md` #1757）
- **個別テストは経路の追加に追随できない**ため、ソーステキストの静的検査を対で置く（同 #1764）。検査は**コメントのみ除去し文字列リテラルは残す**（`TestSourceInspection.RemoveCommentsPreservingLines`）— リテラルを捨てる `ToCodeOnly` では検査対象が消え、コメントを残すと**規約の理由を書いたコメント自体**が違反になる（極性の反転）
- **設定変更は既存データを書き換えない**。変更前に「バス（★）」で保存された履歴は、変更後は未入力として検出されない。**運用開始前に決める設定**であることをマニュアルに明記し、途中変更時の手順（先に未入力を解消する）を書く

### `static` は設定の注入を静かに無効化する（Issue #1820）

上の #1818 は「生成側は設定を読むのに判定側がリテラル」という形だった。**同じ乖離は「そもそも設定を読めない場所に処理を置いた」ことでも起きる。**

`ReportService.GetFiscalYearFileName` は `static` のため、注入済みの `_orgOptions` を参照できず `new OrganizationOptions().ReportLayout.FileNameFormat` で既定値をハードコードしていた。同じ帳票の `TitleText` / `ClassificationText` / `UnitText` は設定が効くため、**「一部だけ効かない」という最も紛らわしい状態**になっていた。

- **設定値を使う処理を `static` にしない**。`static` は「引数だけで決まる純関数」の宣言であり、設定値はその引数に含まれない。純関数として書きたいなら**設定値を引数で受け取る**（`ReportFileNameFactory.Build(fileNameFormat, …)`）。呼び出し元から設定を取る形にすると、#1818 と同じ「消費側ごとの再実装」が始まる
- **依存を「省略可能」にしてよいのは、省略時の値が本来の値と一致すると構造的に言えるときだけ**。`ReportService` の `IReportFileNameFactory` は同じ `IOptions<OrganizationOptions>` から導出するため省略可能でよいが、設定を持たない `ReportExportStatusService` で省略可能にすると、**DI の配線漏れが「設定した書式が静かに無視される」形で潜在化**する。後者は必須引数にして落とす
- **書式が設定値になったら、その書式が破り得る保証を数え上げる**。#1703 は「生成名は単一のファイル名であり出力フォルダを脱出しない」を構成要素のサニタイズで保証していたが、**書式そのものがパス構造を持てば同じ保証が書式側から破られる**。sink 側で組み立て結果を検査し、破れていれば既定書式へ倒す。不正な書式（`{3}` / 閉じ括弧の欠落）で `FormatException` にせず既定へ倒すのも同じ判断（管理者の設定ミスで帳票作成を止めない）
- **既定値付きコンストラクタは、`static` と同じ「設定の注入を静かに無効化する」形を作る**（Issue #1955）。`SummaryGenerator(DepartmentType departmentType = DepartmentType.MayorOffice)` は `new SummaryGenerator()` と書けてしまうため、明細 CSV 取込の 2 経路（`CsvImportService.Detail.cs` / `NewLedgerFromSegmentsBuilder`）が既定値のインスタンスで `ledger.summary` を作り直し、企業会計部局の組織でもチャージ行が「役務費によりチャージ」で 6 年保存の台帳へ入っていた。他の経路は設定を注入していたので、**設定が効く経路と効かない経路が混在する**という最も紛らわしい状態だった。
  - **DI シングルトンを注入して済ませない**。起動時に設定を捕捉するシングルトンは、その設定が実行時に変更できるなら**変更後・再起動前の窓**で古い値を配る。「注入したから設定が効く」は、注入元がいつ設定を読んだかまで見て初めて言える（#1955 の時点で `LedgerMergeService` / `LedgerSplitService` / `LendingService` / `LedgerDetailViewModel` の 6 経路がこの窓を持っていた）。読み直す形にするなら、その読み取りがキャッシュ経由かどうかも数える（共有モードでは他 PC の変更が TTL 分だけ遅れる）
  - **窓を閉じる手段は「読み直す」だけではない — 運用中に差し替える形もある**（Issue #1975）。上記 6 経路は貸出・返却のホットパスを含み、引数へ移す案は呼び出し 179 か所へ波及するため、**保存成功時にシングルトンの設定を差し替える**形を採った（`SummaryGenerator.ApplyDepartmentType`。`ApplyTransferStationGroups` #1905 と同じ形）。消費側は無改修で済む。
    - **差し替える値は「世代」として持ち、1 回の処理の先頭で捕捉する**（#1919）。摘要生成は日付ごと・チャージ境界ごとに文言を作るため、各段階が可変フィールドを直接読むと**同じ摘要の中で新旧の文言が混ざる**。
    - **情報源は 1 つに保つ**。差し替え対象をインスタンスが持つなら、静的な世代側にも同じ値を置かない（どちらが正かが失われる）。実装途中に書いた「別の差し替え経路から引き継ぐ」コードは、変異検査で**観測不能**（捕捉時に必ず上書きされる）と判明したので撤去した。**緑のままの変異は、その実装が何も守っていない証拠**。
    - **「既定値をハードコードする API を削除した」で満足しない**。同じ資源へ**別の綴り**で到達できるなら、ガードはその資源で数える（#1843）。#1975 は引数なしの `GetChargeSummary()` を削除したが、`GetChargeSummary(DepartmentType.MayorOffice)` は同じ帰結であり、**修正した PR 自身がその形を 3 か所追加していた**（コードレビューで検出。#1814「修正の中に、修正対象と同じ欠陥への経路を残さない」）。
    - **ガードが「欠陥が実際に住んでいた場所」を見ているか確かめる**（同）。#1919 の静的検査は**世代を引数に取るメソッドだけ**を走査するため、世代を捕捉する側（`Generate` / `GenerateByDate`）は対象外で、#1975 の欠陥はまさにそこにあった。可変フィールドの**参照箇所そのもの**を件数で固定すると、走査対象の定義に依存しない
  - **回帰は「引数の有無」ではなく「引数が設定由来か」で見る**。有無だけを見ると `new SummaryGenerator(DepartmentType.MayorOffice)`（既定値のハードコード ＝ 同じ帰結）が適合として通る（#1786「極性の反転」）
  - **同じ資源へ別の綴りで到達できる形を数える**（#1843）。対象型推論の `SummaryGenerator g = new(…);` は `new\s+SummaryGenerator` に一致しない。また `TestSourceInspection.ExtractInvocationArguments` は照合位置の直後が `(` でないとき**黙って読み飛ばす**ため、オブジェクト初期化子 `new SummaryGenerator { }` は引数ゼロですら数えられない。**照合数と抽出数の差を違反として数える**（#1944「判定できない前方の形は fail-open にしない」）

### 設定項目は「読まれている」ことをリフレクションで固定する（同 Issue）

`TemplateMapping` は 18 項目中 5 項目しか読まれておらず、残り 13 項目は本番コードから一度も参照されていなかった（`ReportService` は同名のローカル `const` と列リテラルを使っていた）。一方で管理者マニュアル §7.4 は設定可能と案内しており、**設定できるのに反映されない状態（dead config）が広告されていた**。

- **未実装なら項目ごと削除する**。「XML doc に未実装と明記して残す」は文言でしか防げず、次に読む人が同じ調査をやり直す（`使われないメソッドは先に作らない`、#1726 の「外した列は明記する」）
- **一部だけ設定化しない**。列番号だけを可変にすると「摘要は別列に出るのに結合セルは B〜D 列のまま」という新たな半端状態を作る。**設定が効く範囲は、その設定だけで完結する単位で切る**（本 Issue はヘッダー行のセル配置に限定した）
- **回帰は `OrganizationOptionsUsageConventionTests` が固定する**。検査対象は**リフレクションで導出**するので、項目を足した人が検査の追加を忘れても自動的に対象へ入る。照合は**所有者ごと**（`ReportLayout.TitleText` の形）に行う — プロパティ名だけで照合すると XAML 由来の同名識別子（`ToastNotificationWindow.TitleText`）を拾って空振りする。検査はコメント除去後に行う（「この項目は未使用」と説明したコメント自体が「使用されている」と判定される極性の反転を避ける）
- **「読まれている」と「効いている」は別**。規約テストは前者だけを見る。後者は消費側の個別テストが**既定と異なる値を設定してから**表明する（#1818 の作法）
- **その規約テストは「読む箇所と読まない箇所が同居している」形を検出できない**（Issue #1956）。`ReportService` はヘッダー 1 ページ目を書く `SetHeaderInfo` だけが `TemplateMapping.PageNumberColumn` を読み、継続ページを書く `SetPageNumber` と前月の最終ページを読む `GetLastPageNumberFromWorksheet` は列 12 を直書きしていた。設定を 11 にすると 1 ページ目は K2・継続ページは L2 へ書かれ、翌月の開始ページ算出が空の L2 を読んで 0 → `IcCard.StartingPageNumber` へフォールバックし、年度を通した通し頁で綴じる物品出納簿の頁が毎月リセットされる。
  - **「書く側」と「読む側」は必ず対で数える**。書く側だけを設定化すると、症状は「値が消える」ではなく「毎月リセットされる」という間接的な形で出るため発見が遅れる
  - **設定値は既定値を持たない引数で貫通させる**（#1955）。既定値を付ければ既存の呼び出しは無修正で通るが、それは「注入し忘れた経路」を静かに温存する形になる
  - **「設定が効く範囲を広げる」修正を書く前に、その設定に依存している固定の資源をすべて数える**（コードレビューで検出）。#1956 の初版はヘッダー行のフォント調整範囲 `A2:L2` を設定側へ広げたが、**印刷範囲・継続ページへのヘッダーコピー・再生成時のクリア範囲は 12 列固定のまま**だったため、13 列目以降に設定した頁は**書き込まれるが印刷されない**。範囲を広げる修正は「対応済みに見せる」だけで、**回帰テストがその非対応の構成をあたかも対応済みであるかのように固定していた**（#1924「主張は実装で検算する」／#1814「修正の中に、修正対象と同じ欠陥への経路を残さない」）。正しい単位は「テンプレートが決める幅の**内側で**列を選ぶ」であって、幅そのものは可変ではなかった
  - **定義域外を既定値へ倒すかどうかは、倒した先が正しいかで決める**。#1820 が不正な `FileNameFormat` を既定書式へ倒せたのは「ファイル名が既定になるだけで帳票の中身は正しい」から。列は倒すと**中身が管理者の意図と違う場所に出る**ため倒さず、帳票を作る前に 3 要素の文言で弾く（#1812「定義域外の入力を黙って別の値に丸めない」）。「フォールバックか例外か」は一般則では決まらない
  - **検証は設定項目 1 つではなく、その設定グループ全体に掛ける**。ページ番号列だけを検証すると、同じ半端な状態がヘッダー行の中に残る

## UI/UX原則
- **一覧の選択（`SelectedItem`）を「操作対象の識別子」として使わない**（Issue #1761）。`SelectedItem="{Binding SelectedX}"` は TwoWay バインドのため、**ViewModel の預かり知らぬところで null に戻る**。選択行の Ctrl+クリック（`SelectionMode=Single` でも選択解除できる）と、`ItemsSource.Clear()`（一覧の再読込）による選択解除の書き戻しの 2 経路がある。編集フォームは `IsEditing` にのみ連動するので開いたままで、入力内容も残る＝**画面の見た目は何も変わらない**
  - **操作対象は主キー（IDm 等）で特定し、`Selected*` は「一覧の選択状態」を表すだけの値として扱う**。編集中に選択が外れてもフォームは閉じない（閉じると入力途中の内容が予告なく消える。選択解除は利用者の明示的な操作以外でも起きる）
  - **`Selected*` の逆参照を `await` をまたがせない**。認証ダイアログ（職員証タッチ待ち）や DB 読み取りの待機中に UI スレッドは入力を処理するため、継続の実行時点で選択状態は変わり得る。`if (Selected == null) return;` の直後、**最初の `await` より前**にローカル変数へ確定させる（#1759 が `StaffManageViewModel.DeleteAsync` で先行して確立した形）。`CanExecute` でボタンが無効化されても、**実行中のコマンドは止まらない**
  - **本プロジェクトは nullable 参照型が有効でないため `SelectedX!` の `!` はコンパイル後に何も残らない**（実行時チェックにならない）。「`!` を付けたから安全」は成立しない
  - **フォールバックの優先順位が、その規約自身の禁止事項へ落ちていないか確かめる**。#1759 は「エラー文言で対象を名指しするときは未保存の入力値を使わない」を定めたが、実装は `Selected != null ? 一覧の値 : 未保存の入力値` で、**選択が外れた瞬間にまさに禁じた形へ落ちていた**。必要な値（一覧の表記）は**編集開始時に退避する**（`.claude/rules/development-conventions.md` #1728 の「フォールバックが書いてあることは、それが機能していることを意味しない」の再演）
  - **洗い出しの単位は「画面の種類」ではなく「`Selected*` を `await` の後ろで参照している箇所」**。#1761 の初版は対象を「`IsEditing` を持つ ViewModel」（`CardManageViewModel` / `StaffManageViewModel` の 2 つ）と定義したが、編集フォームの有無はこの欠陥の条件ではない。**編集を伴わない `SystemManageViewModel.RestoreAsync`（`SelectedBackup`）が同型で残っていた** — リストア前バックアップの作成を挟んだあとに `SelectedBackup.FilePath` を読むため、確認ダイアログで名指ししたのとは別のバックアップで 6 年保存の台帳 DB を上書きし得た。**これは #1760 が「画面の動詞ではなくテーブルへの書き込み文で数える」で記録したのと同じ数え間違い**。横断で洗うときは `grep -n "Selected[A-Za-z]*\." src/**/ViewModels/*.cs` で参照箇所を列挙し、各々が最初の `await` より前かを確認すること
  - **一覧そのものを対象にする一括処理は、「対象の集合」ごと開始時点でスナップショットする**（Issue #1949）。`ReportViewModel.CreateReportAsync` は対象 IDm を `cardIdms` としてスナップショットしていたのに、**カード実体だけを毎周 `SelectedCards.First(c => c.CardIdm == cardIdm)` で引き直していた**。Excel 生成の `await Task.Run(...)` の待機中にチェックが外れると `First()` が一致せず `InvalidOperationException` になり、`catch (OperationCanceledException)` では拾えないため**一括作成全体が未処理例外で終わる**。**一部だけスナップショットする形は、スナップショットしたつもりで残りが動く**（#1855「間接参照の一意性を、参照先の値の相違の代理にしない」と同じ family — IDm という間接参照だけを固定しても、そこから実体を引き直せば固定していないのと同じ）
  - **件数もスナップショットから採る**（同）。完了時の `successCount == SelectedCards.Count` は、処理中に選択が 1 つ増えただけで全件成功を「2/3件（一部失敗）」と誤報する。**「何件処理したか」と「何件を対象にしたか」は同じ集合から数える**
  - **「スナップショットした」と言うなら、その場で読んでいる値をすべて数える**（同。コードレビューで検出）。#1949 の初版は対象カードだけを固定し、**出力先フォルダーと対象年月は現在値のまま**残していた。年月コンボボックスもキーボードで操作でき、引き直すと**旧年月で決めたファイル名**（年度ブック）に対し別の月・別の年度のシートを書き込む。上書き確認で職員が同意した「N月のシートを更新しますか？」がもはや実際の動作を説明していない。出力先は `UpdateSourceTrigger=LostFocus` の TextBox なので、`Directory.Exists` で**検証した値と実際に使う値が食い違う** — 検証より前に確定させる。**一部だけスナップショットする形は、固定したつもりで残りが動くぶん、何もしていない状態より発見が遅れる**（#1814「修正の中に、修正対象と同じ欠陥への経路を残さない」）
  - **周囲のイディオムから外れている箇所は、理由があるか欠陥かのどちらか**（同）。#1949 では同一クラスの `RefreshExportStatusAsync` が既に `capturedFolder` / `capturedYear` / `capturedMonth` を退避しており、`CreateReportAsync` だけが現在値を読んでいた。**同じクラスの隣のメソッドが正解を持っていないか**を先に見る
  - **洗い出しの grep パターン自体が漏れていないか確かめる**（同）。#1761 が定めた `grep -n "Selected[A-Za-z]*[.[]" ViewModels/*.cs` は「後ろに `.` / `[` が続く」形しか拾わず、**値型の単体参照**（`SelectedYear` / `SelectedMonth` / `SelectedExportType`）を構造的に見落とす。#1949 のプレビュー 2 経路（結合ドキュメントに別々の月のデータが混在し、印刷すると月をまたいだ物品出納簿が出る）はこの穴に落ちていた。走査は「各メソッドの最初の `await` より後ろにある `Selected[A-Za-z]*`」で列挙し、代入と同期モーダル直後の読み取りを除いて triage する（#1786「その性質を破れる全経路を列挙する」は、grep パターンという最も素朴なガードにも当てはまる）
  - **前段の判定にも同じスナップショットを渡す**（同）。プリフライト（`RunPreflightAsync`）が自分で `SelectedCards` を読むと、「現在の選択を読む手段」が作成フローの中に残り続ける（#1763）。読む場所を 1 つにすれば、配り忘れる余地が消える
  - **「処理中オーバーレイがあるから選択は変わらない」は成り立たない**。`Visibility="{Binding IsBusy}"` の `Border` が塞ぐのはマウスのヒットテストだけで、キーボードフォーカスは配下のコントロールに残る。方向キーによる選択移動は通る
- **結果メッセージは「画面状態をリセットする処理」のあとに設定し、かつ表示領域がその状態でも生きていることを確かめる**（Issue #1727）。原因は2つ重なり得る:
  - **順序**: `CardManageViewModel.CancelEdit()` のような編集終了処理は `StatusMessage` / `IsStatusError` もクリアするため、`StatusMessage = "登録しました"` → `CancelEdit()` の順に書くと**メッセージは一度も表示されない**
  - **所在**: ステータス欄の `TextBlock` が `Visibility="{Binding IsEditing}"` のパネルの内側にあると、`CancelEdit()`（`IsEditing = false`）で**パネルごと Collapsed になり、順序を直しても見えない**。完了メッセージを出す欄は、その完了処理で消える表示条件に紐付けないこと
  - **ViewModel のテストは前者しか検出できない**。プロパティの値しか見ないため、表示領域が消えていることは分からない。**View 側は XAML テキスト上の静的検証で別途固定する**（`CardManageDialogStatusAreaLayoutTests` が参考実装。「禁止された配置の不在」だけでなく「正しい置き場所の存在」も併せて検査し、抽出範囲が縮んで空振りしないよう抽出の妥当性も表明する）
  - 成功パスの回帰テストを併せて置く。失敗パスだけ直すと、同じ順序ミスを後から再導入しても気付けない
- **自動的に閉じる画面のステータス欄に、利用者の判断を要する警告を出さない**（Issue #1811）。`BusStopInputViewModel.SaveAsync` は未入力・形式・類似の 3 警告を順に `StatusMessage` へ代入し、保存成功で「保存しました」に上書きした直後に `IsSaved` でダイアログが閉じていたため、**3 つのうち少なくとも 2 つは一度も職員の目に触れないまま台帳へ確定**していた（「天神」と「天神南」の取り違え警告がそのまま★なしで確定する）。判断を委ねたい警告は**書き込みの前**に `IDialogService.ShowWarningConfirmation` で全件をまとめて提示し、「いいえ」なら何も書かずに戻る（戻った画面のステータス欄には全文を複数行で残す＝`TextWrapping="Wrap"`）。警告が無いときは確認を挟まない（返却フローを遅くしない）
  - **1 つの `StatusMessage` に複数の警告を順に代入しない**。後の代入が前を消すので「最後の 1 つ」しか残らず、表示されたとしても残りは失われる。複数あるなら結合して 1 回で代入する
  - **`StatusMessage` を見る ViewModel テストは「上書き」を検出できても「読める時間が無い」ことは検出できない**。ダイアログを閉じる契機（`IsSaved` 等）と同じ経路で設定される文言は、その契機より前に利用者が読めるかを設計で保証する
  - **表示されていなかった警告を表示可能にするときは、その検出ロジックが今も妥当かを確かめる**（同 Issue のコードレビューで判明）。表示経路が壊れている間は誤検出が誰の目にも触れないため、検出側は「正しく動いているように見える」まま年単位で放置され得る。#1811 では `IsSimilar` の乗降逆転判定（#1133）が、**後から追加された「↑往復」ボタン（#1570）が意図的に生成する値**を毎回警告する状態になっており、確認ダイアログを入れた瞬間に「往復入力のたびに確認が出る」退行として噴出した。**アプリ自身が生成する入力を自分で警告していないか**を、警告の生成条件と入力の生成経路の両方から確かめること
  - **誤検出を除外したら、除外が広すぎないことを対のテストで固定する**。除外だけを検証すると「対象を無条件に通す」実装でも緑になる（#1757 の「正当な操作を塞いでいないことを対で固定する」の裏返し）。除外は検出関数の側（`DetectSimilarBusStops`）で行い、判定そのもの（`IsSimilar`）は変えないと、既存テストと他の用途を巻き込まずに済む
- **繰り返し発生し得る警告は、集約と除去の両方を持たせる**（Issue #1811）。`OnCardReaderError` は発生のたびに `WarningMessages.Add` し、除去経路がソース全体に無く `HandleWarningClick` にも case が無かったため、読み取り不良のカードを何度も試すと同文言の警告が再起動まで積み上がり、残額不足・長期未返却などの他の警告をスクロール外へ押し出した。04_機能設計書 §7.4 の表で「除去の契機: なし」が許されるのは 1 回しか立たず状態が変わらない種別だけで、繰り返すものは `ReplaceWarnings` で自分の種別を 1 行に入れ替え、回数・最終時刻を文言に載せ、クリックで取り除けるようにする。回数のような「繰り返しの状態」は ViewModel のフィールドではなく警告行自身（`WarningItem.OccurrenceCount`）に持たせると、取り除いた時点で状態も一緒に消える
  - **警告文言に `Exception.Message` を直接載せない**（#1614 と同じ）。`CardReaderException.Message` は英語（`Failed to read card history: …`）で、職員には読めず内部実装の露出になる。`AppException.UserFriendlyMessage` を使い、3 要素（何が／なぜ／どうすれば）で組み立てる
  - **集約すると「件数で多重度を検出していたテスト」の検出力が消える**。#1807 の 2 件は「1 回の Error で警告が 1 件」で二重購読を検出していたが、集約後は常に 1 件になる。`OccurrenceCount == 1` のように**回数を数える別の観測点**へ移して検出力を保つ
- **`BeginBusy` スコープの内側でモーダルダイアログを表示するときは `ViewModelBase.SuspendBusy()` で囲む**（Issue #1793）。`IDialogService` の実装は同期モーダル（`MessageBox.Show`）で職員が閉じるまで呼び出しスレッドをブロックするため、`BusyScope.Dispose()` が走らず `IsBusy=true` のまま残り、**全面オーバーレイと不確定 `ProgressBar` がダイアログの背後で回り続ける**。とくに確認ダイアログは職員の判断を待つ設計であり、背後の「処理中」表示はその判断を妨げる。同じ欠陥は #1383（エクスポート）→ #1784（インポート）→ #1793（F2/F3/F4/F6 の 16 か所）と**3 度再発している**
  - **`SetBusy(false)` で代用しない**。`SetBusy` は `ResetProgress()` 経由で `CancellationTokenSource` を Dispose するため、ダイアログを閉じた後にキャンセルが効かなくなり確定プログレスも巻き戻る。`SuspendBusy` は表示状態（`IsBusy` / `BusyMessage` / `CanCancel` / 進捗3値）だけを退避・復元する
  - **結果表示のみのダイアログは遅延 `Action`（スコープ外で `Invoke`）でもよいが、確認・選択系は戻り値で後続処理が分岐するためその方式では扱えない**。スコープの前へ移す案も、**スコープ内の非同期処理の結果を見て初めて必要性が決まる確認**（リストア前バックアップ失敗時の続行確認）には使えない。1 画面の中でイディオムを割らないこと。使い分けは `ICCardManager/docs/design/03_画面設計書.md` §3.10 の表を正典とする
  - **ダイアログ表示を内包するヘルパーでは、ヘルパーの内側で囲む**。呼び出し側でまとめて囲むと、ヘルパーが行う DB 読み取り・一覧再読込までオーバーレイが外れる
  - **洗い出しは「`_dialogService.Show*` の行」で数えない**。ヘルパーへ切り出された経路（`ShowRegistrationModeDialog` / `NotifyDeleteConflictAsync`）は視野に入らない（#1760「画面の動詞ではなく書き込み文で数える」と同じ数え間違い）。**モーダルの入口も 1 つではない** — `INavigationService.ShowDialog<T>()`（`Window.ShowDialog()`）や `OpenFileDialog.ShowDialog()` も同期モーダルで、`ReportViewModel` の印刷プレビューはこの経路だった
  - **処理中スコープの入口も 1 つではない**。`using var busyScope = BeginCancellableBusy(...)`（using 宣言形）は波括弧を持たず、スコープは**宣言位置から囲みブロックの末尾まで**。「`using (...) { }` の内側」だけを探す検査はこの形を丸ごと見落とす（`ReportViewModel.CreateReportsAsync` が該当）
  - **回帰は静的検査と挙動テストを対で置く**。静的検査（`BusyScopeDialogConventionTests`）は「呼び出しが構文上そのスコープの内側にあるか」しか見えず**ヘルパー経由を素通り**し、挙動テスト（`Callback` で呼び出し時点の `IsBusy` を捕捉）は既存分岐しか通らない。なお静的検査は**遅延 `Action` を違反と誤検出しない**こと（#1793 の初版が誤検出し、規約を守っている #1784 の実装で赤になった）
  - **既存のガードが何を検索語にしているかを、移行先の綴りを決めた時点で確かめる**（Issue #1837）。`BusyScopeDialogConventionTests` の検出パターンは `_dialogService.Show*` / `MessageBox.Show` / `*.ShowDialog*` で、**`_navigationService.Show*` を含んでいなかった**。#1837 が `MessageBox.Show` 直呼びを `_navigationService.Show*` へ移した結果、**移行前は検出されていた約 14 か所が移行によって検出されなくなった**（既に `SuspendBusy` で囲んである `ReportViewModel` の 2 か所を含み、その囲みを外しても誰も気付けない）。是正はガードそのものの意図と無関係な**綴りの違い**で起きるため、コードレビューまで露見しない。**「この呼び出しを見張っているガードは何か」を移行前後の両方の綴りで grep する**こと（#1739「反転したら除去の責任も生成元へ移る」と同じ形。ガードを弱める方向の変更は、機能が変わらないぶん気付きにくい）
    - 検出範囲を広げるときは**誤検出しない範囲に絞る**。`\w+\.Show\w+` のような一般形は非モーダルの `_toastNotificationService.ShowError` まで拾う。フィールド名の許可リスト（`_dialogService` / `_navigationService`）で絞り、**「検出する例」と「検出しない例」をサンプル入力で対に固定する**
  - **`BusyScope` は入れ子に対応する**（Issue #1836）。「書き込み → 一覧再読込 → 結果表示」（#1753 / #1759）の順序では、`BeginBusy` スコープの内側から一覧再読込メソッド（自身も `BeginBusy` を開く）を呼ぶ形が必然的に生まれる（`NotifyDeleteConflictAsync` → `LoadCardsAsync` 等 14 か所）。`ViewModelBase._busyDepth` で深さを数え、**最も外側のスコープが閉じたときだけ** `SetBusy(false)` する
    - **内側スコープは表示にもキャンセル機構にも触れない（外側優先）**。触れると「削除中...」が「読み込み中...」で上書きされ、`Dispose` 側だけ直しても外側の処理が終わるまで内側のメッセージが残る。キャンセル可能を要求された内側スコープは、新しい `CancellationTokenSource` を作らず**外側のトークンを引き継ぐ**（外側がキャンセル不可なら `CancellationToken.None`）
    - **解除を内側で行うと、消えるのは表示だけではない**。`SetBusy(false)` は `ResetProgress()` 経由で `_cancellationTokenSource` を Dispose するため、外側が `BeginCancellableBusy` だと `CancelOperation()` が無言で何もしなくなり `IsCancellationRequested` が常に false になる。**「フラグを落とす」処理が何を道連れにするかを、落とす場所を決める前に見る**
    - **この欠陥は「回帰テストが書けない」という形で先に現れた**。#1793 では `NotifyDeleteConflictAsync` 経由の「モーダル表示中は `IsBusy=false`」テストが**修正前のコードでも緑**になり、静的検査だけで守ることになった。**テストが修正の有無にかかわらず緑になるときは、テストの書き方ではなく被験体側に別の欠陥がある**と疑う。#1836 の挙動テストは「一覧再読込中は `IsBusy=true`」を併せて表明して検出力を戻している
    - **`SuspendBusy`（#1793）とは独立**。あちらは表示状態の退避・復元で深さには関与しない。入れ子の内側で中断・復元しても深さは変わらないことをテストで表明する
    - **深さの加算は状態設定のあとに置く**。`SetBusy` は `PropertyChanged` を上げるため、購読側（バインディング・ハンドラー）の例外でコンストラクタが戻らない可能性がある。先に加算するとコンストラクタが戻らない＝`using` が成立しない経路で**深さが恒久的に漏れ**、長命な ViewModel（`MainViewModel`）では以後オーバーレイが出たままになる。あとから加算すれば、漏れても「次のスコープが最外として扱われて復旧する」従来どおりの挙動に留まる。**カウンタを導入するときは「加算と本処理のどちらが先に失敗し得るか」を見る**
    - **深さは ViewModel ごとの単純なカウンタであり、「入れ子」と「並走」を区別できない**。同一 ViewModel で 2 つの操作が重なると（fire-and-forget の更新が飛んでいる最中にキーボードで別コマンドへ到達する等。#1761 のとおりオーバーレイはマウスしか塞がない）、後発のスコープが「内側」と見なされてメッセージが抑制され、`BeginCancellableBusy` ならキャンセルボタンが出ない。現状 `BeginCancellableBusy` は `ReportViewModel.CreateReportsAsync` の 1 か所のみで、実害は「長い一括作成をキャンセルできない」に留まる。**厳密に解くには操作ごとの識別子が要る**ため、並走が常態になる画面を作るときは本方式の前提を見直すこと
- **`MessageBox` は必ずオーナーウィンドウを渡して表示する**（Issue #1794）。オーナーを渡さないオーバーロード（`MessageBox.Show(message, title, button, image)`）では WPF が `GetActiveWindow()` でオーナーを解決するため、**呼び出しスレッドがフォアグラウンドでないときは NULL**（ownerless）になり、下位のウィンドウが無効化されない。`DialogService` からの表示は private な `Show` へ集約済みで、そこが `Common/DialogOwnerResolver.Resolve()` の結果を渡す
  - **これは #1793 が生んだ欠陥ではなく、#1793 が露出させた欠陥**。処理中オーバーレイ（`Border Grid.RowSpan="6"`）は視覚要素であると同時に**全面クリックシールド**でもあり、`IsBusy=true` の間は下位のボタンへのクリックを遮っていた。#1383 → #1784 → #1793 で「オーバーレイを閉じてから結果ダイアログを出す」構造へ寄せたことで、シールドも同時に外れた。**ある要素を取り除くときは、その要素が副次的に担っていた役割を数え上げる**（#1739 の「反転したら除去の責任も生成元へ移る」と同じ形）
  - **オーナーに `Application.MainWindow` を選ばない**。モーダルダイアログが開いている間、その親（メイン画面）は Win32 レベルで無効化されている（`ShowDialog()` が `EnableWindow(FALSE)` を呼ぶ）。メイン画面をオーナーにすると最前面のダイアログが無効化されず、**オーナーを渡しているのに欠陥がそのまま残る**。「アクティブなウィンドウ → 入力を受け付ける（Win32 `IsWindowEnabled`）ウィンドウのうち最後 → 使用可能な最後のウィンドウ」の順で選ぶ
    - **「モーダル子に塞がれているか」を WPF の `Window.IsEnabled` で判定しない**。`ShowDialog()` も Win32 の `MessageBox` も無効化は `EnableWindow` で行い、WPF の `Window` は `WM_ENABLE` を扱わないため **`IsEnabled` 依存関係プロパティは true のまま変わらない**。`IsEnabled` で書くと全候補が true になり、この段は「最後に生成されたウィンドウ」に退化する（生成順とモーダルの重なり順が一致する間だけ偶然正しく動く。#1794 の初版がこの形で、代役テストは `IsEnabled=false` という本番で起きない状態を検査していた）。判定は P/Invoke の `IsWindowEnabled(hwnd)` で行う
  - **候補は「ハンドルを持つ（表示済みでクローズ前）」ものに限る**。ハンドルを持たない（未表示・クローズ済み）ウィンドウを `MessageBox.Show(owner, ...)` へ渡しても例外にはならず、WPF は**黙って `GetActiveWindow()` へ退化する**＝オーナーを渡したつもりで ownerless になる。判定は `IsLoaded` ではなくハンドルの有無で行う（クローズ後も `IsLoaded` が true のまま残る場合がある）。**`IsVisible` を条件に含めない** — オーナー（メイン画面）を最小化すると Win32 が所有ウィンドウを隠し（`SW_PARENTCLOSING`）、WPF は所有ダイアログの `IsVisible` を false にする。「処理を待つ間にアプリを最小化した」変種では最前面のモーダルダイアログこそが非表示で、含めるとそれだけが候補から落ちて無効化済みのメイン画面がオーナーになる。**解決できないときは従来どおり ownerless で表示する** — 表示しないより望ましい
  - **WPF 以外のウィンドウ（表示中の `MessageBox` / `OpenFileDialog` 等）がアクティブなときは WPF の解決に委ねる**（`DialogOwnerResolver.ShouldDeferToNativeActiveWindow`）。是正前の ownerless は `GetActiveWindow()` をオーナーにしていたため、**入れ子の `MessageBox`（確認ダイアログの表示中に職員証タッチで別の確認が出る等）は外側の `MessageBox` をオーナーとして外側を無効化していた**。ここで WPF ウィンドウを選ぶと外側が押せたまま残る（是正が退行を生む）。アプリが非フォアグラウンドのとき（＝この Issue の故障シナリオ）は `GetActiveWindow()` が NULL なので、この委譲は選択規則を妨げない。**「オーナー無しで正しく動いていた経路」が是正の対象に混ざっていないかを数える**（#1739 の「反転したら除去の責任も生成元へ移る」の裏返し）
  - **候補から「アクティブ化しないウィンドウ」（`ShowActivated="False"`）も外す**。`ToastNotificationWindow` は `Topmost` かつ `ShowActivated="False"` の非モーダルウィンドウで、貸出・返却のたびに**最後に生成されて** `Application.Windows` に載る。除外しないと、**アプリが非フォアグラウンドのとき＝この Issue の故障シナリオそのもの**で「アクティブが無い → 有効なウィンドウのうち最後」の分岐がトーストを選ぶ。害は 3 つ: ①Win32 の `MessageBox` は**オーナーだけ**を無効化するため業務画面は有効なまま残り欠陥が是正されない、②トーストは 3 秒で自動的に閉じ、**オーナーが破棄されると所有ウィンドウも破棄される**ため `MessageBox` が消えて `ShowConfirmation` が無言で「いいえ」を返す、③エラー通知のトーストは `autoClose: false` で残り続けるため①②が持続する
    - **優先順位の正しさは、候補の絞り込みの正しさに乗っている**。#1794 の初版は「アクティブ → `IsEnabled` → 最後」という順位づけを 8 件のテストで網羅したが、**候補を絞る述語（表示済み＋ハンドルあり）は 1 件も検査していなかった**。順位を試すテストは代役オブジェクトの `Usable` フラグを直接与えるため、**本番の述語が何を通すかを一度も通らない**。判断を純関数へ切り出すときは、絞り込み側も同じ粒度で切り出して検査する
    - 判定は型名（`ToastNotificationWindow`）ではなく**性質**（`ShowActivated`）で行う。同種のウィンドウが増えたときに追随漏れが起きるため
  - **`Window.ShowDialog()`（`INavigationService.ShowDialog<T>`）は対象外**。WPF の `ShowDialog` はアプリ内の他ウィンドウをすべて無効化するため、`Owner` は z 順・タスクバー表示にしか効かない。**「モーダル」とひとくくりにせず、`MessageBox` と `ShowDialog` で無効化の範囲が違うことを踏まえて数える**
  - **単体テストで表明できる範囲を先に見極める**。ownerless になったかは `GetActiveWindow()` 依存で xUnit から観測できず、`Window` は STA スレッドでしか生成できない。**「オーナーを選ぶ判断」を WPF 非依存の純関数へ切り出せば規則は網羅でき、`Window` 実体が要るのは「継ぎ目を通っているか」の 1 件で済む**。テスト容易性のための分割ではなく、状態取得と判断が本来別物であることに合わせた分割
  - **ソーステキストの静的検査は、抽出範囲の妥当性を先に表明する**。`TestSourceInspection.ExtractMethodBody` は波括弧の本体を前提とするため、対象メソッドを式形式（`=> ...`）へ変えると「次に現れた別のブロック」を静かに返し、**検査が空振りしたまま緑になる**（#1794 の初版で実際に起きた）
  - **残る直呼び（約34か所）は Issue #1837 が追跡する**。性質の異なる経路（致命エラー・`Window` コードビハインド・業務 ViewModel）を 1 つの PR で触らない。リポジトリ全体の静的検査を入れるのは移行完了後（先に入れると大量の抑制が必要になり #1786 と同じ形骸化を招く）

  - **既定サイズの変更は既存環境には効かない**。メイン画面の位置・サイズは `AppSettings.MainWindowSettings` に保存され次回起動時に復元されるため、効くのは保存された設定を持たない新規インストール時のみ。PR 本文・CHANGELOG にこの但し書きを添えること（「直したのに変わらない」という問い合わせを防ぐ）
  - 測定値と判断根拠は XAML のコメントと画面設計書に残す（次に要素を増やす人が測り直せるようにする。`MainWindow.xaml` のボタン群コメント / `03_画面設計書.md` §3.1.1a が参考実装）

  - **「区別できる」は 1 つの指標では測れない**。①正常視の色差（CIE76 の ΔE）②相対輝度差（グレースケール印刷・ロービジョン）③P・D・T 型それぞれの色覚シミュレーション後の色差、が同時に成り立って初めて言える。#1815 が「その他」に充てた `MutedTextBrush`(#666666) は ① を満たす（ΔE=55.3）のに ② が 0.000 で、積み上げ棒で隣接すると 1 本の帯に見えた。**指標を 1 つ足したら、既存の全ペアを測り直す**
  - **意味色（`PrimaryBrush` / `SuccessActionBrush` / `DangerTextBrush` 等）をグラフの系列色に流用しない**。意味色は「成功／警告／危険」という意味を担うため色数を自由に増やせず、流用する限り「色を足すと意味色の体系と衝突する」状態が続く。系列色は専用キー（`ChartSeries*Brush`）として分離する
  - **色は唯一の手掛かりであってはならない**（4 要素原則の帰結）。積み上げ棒の区画には区切り線、凡例スウォッチには輪郭線を引く。**色を直すことと、色以外の手掛かりを足すことは代替関係ではなく併用する**
  - **「色以外の手掛かり」を足すときも、その手掛かり自体が見えるかを測る**。区切り線が満たすべき条件は 2 つあり、①隣接する 2 つの塗りから見分けられること ②領域の地色から見分けられること。#1855 の初版が選んだ白は ① では最良（塗りとの最小コントラスト 2.25）だが ② が **1.00** で、`CalculateStackedVerticalBars` が最小高さを設けないため **1px 未満の区画が線に覆われて消え**、「値が小さい」ではなく「データが無い」と読めた（**色を直す目的と逆の結果**）。**片方の条件だけを見て決めない**
  - **外部のモデル・係数を引用したら、そのモデルが定義されている空間で計算する**。色覚シミュレーションの変換行列（Machado et al. 2009）は**線形 RGB 上で定義**されているが、#1855 の初版はガンマ補正された sRGB へそのまま掛けていた。**計算は動き、数値も出て、テストも緑になる**が、出てくる値は引用したモデルのものではない。線形／ガンマ・D50／D65・0〜1／0〜255 のいずれかを取り違えると、しきい値の根拠が静かに失われる
  - **アクセシビリティ指標どうしが衝突したら、選ばなかった側を実測値で残す**。Okabe-Ito の橙 #E69F00 は白背景コントラスト 2.25 で WCAG 1.4.11 の 3:1 を下回るが、暗くすると赤緑色覚で朱色 #D55E00 と混同域に入る（ΔEcvd 16.5→1.3 実測）。**「なぜ基準を満たさない値を選んだか」を数値としてテストに置く**と、次に「コントラストを上げよう」とした人がその場で理由に行き当たる
- **内部の区別フラグは、表示の区別を意味しない**（Issue #1858）。月別利用額グラフの集約系列は `MonthlyUsageSeries.IsOther` で内部的に職員系列と区別でき、#1815 で専用色まで割り当てていたが、**凡例・代替一覧・Excel が表示するのは名前の文字列だけ**だったため、氏名が「その他」の職員（`ResolveSeriesName` は職員マスタに無い `ledger.staff_name` をそのまま系列名に使う）が上位に入ると同一表記が 2 行並び、どちらが集約分か判別できなかった。#1855 の「間接参照（キー・ID・パス）の一意性を、参照先の値の相違の代理にしない」の**フラグ版**にあたる
  - **区別はラベル自体に含める**。「その他（N 名）」のように集約の事実を名前へ入れる。衝突回避と情報量の増加（何人分の合算か）が同時に得られるなら、そちらを選ぶ
  - **表示名の組み立ては 1 か所に置き、消費側は組み立て済みの値をそのまま表示する**（`Common/Charting/ChartSeriesNameFormatter` → `MonthlyUsageSeries.Name`）。消費側それぞれが接尾辞を足す形にすると、片方だけ変わる日が来る（#1763「同じ論理的な処理に手段が 2 通りあるか」）
  - **表示名の組み立てを変えたら、旧表示名を保持していた定数は削除する**（同 Issue のコードレビューで判明）。`AdminDashboardService.OtherSeriesName` を「基底名への別名」として残したが、**もはやどの系列の `Name` とも一致しない**ため、将来 `series.Name == OtherSeriesName` と書いた判定は静かに常に偽になる — 本 Issue が消した衝突の裏返しにあたる。残すなら「比較に使えない」ことが型で分かる形にするか、削除する。**未使用の定数は無害ではなく、次に読む人へ誤った契約を提示する**
    - **削除したら、同じ形が近くで復活していないか確かめる**（Issue #1884）。#1858 は `AdminDashboardService.OtherSeriesName` を削除したが、**同値・同スコープの `ChartSeriesNameFormatter.OtherSeriesBaseName` が一つ隣のファイルに残っていた**（書式の材料として `internal const` で公開）。定数の削除は「その名前」ではなく**その値を外から比較できる状態**を消すのが目的なので、洗い出しは `grep` で**値**（`"その他"`）を検索して行う
    - **是正は規約ではなくアクセス修飾子で行う**。`private` へ落とせば、比較に使えない値を比較に使う判定は**そもそも書けない**（#1883 と同じ「食い違った状態を表現できなくする」）。あわせて公開面そのものを規約テストで固定する（`ChartSeriesNameFormatterSurfaceConventionTests`。個別テストは「その定数が存在しないこと」を表明できない）
    - **テストは禁止したい値をリテラルで書く**。`NotBe(本番の定数)` は本番側が値を変えると期待値も一緒に動き、**表明が自己充足して常に緑になる**
  - **衝突ラベルを消したら、それを再生産する経路が残っていないか数える**（Issue #1882）。表示名の組み立て `ChartSeriesNameFormatter.BuildOtherSeriesName` は定義域外（件数 0 以下）で素の「その他」を返しており、**本 Issue が消したはずの衝突ラベルそのもの**をフォールバックとして温存していた。「安全な既定値へ倒す」形は一見無害だが、倒した先が防ごうとしていた状態そのものであることがある（#1814「修正の中に、修正対象と同じ欠陥への経路を残さない」の再演）。**定義域外は黙って別の値へ丸めず `ArgumentOutOfRangeException` で弾く**（#1812）。到達不能な分岐とその回帰テストは「手当てされている」という誤った安心感を与えるため（#1726）、テストは丸めた値ではなく例外を表明し、**対の表明**（基底名を返さないこと／下限の 1 件は受け付けること）を併置する — 片側だけだと「常に投げる」実装でも「例外は投げるが別経路で基底名も返す」実装でも緑になる
  - **同じ数値を「表示名」と「プロパティ」の 2 か所へ別々に書かない**（同）。片方だけ変わる日が来る。件数を持つプロパティを唯一の情報源にし、表示名はそこから導出する
  - **規約でそう書いただけでは、型は何も保証しない**（Issue #1883）。#1858 は上の規約を書き、呼び出し元のコメントにも「件数は DTO を唯一の情報源にし、名前はそこから導出する」と明記したが、`MonthlyUsageSeries` の `Name` / `IsOther` / `AggregatedSeriesCount` は**3 つとも独立した public setter を持つ自動プロパティのまま**で、「件数は 4 なのに名前は『その他（3 名）』」を誰でも作れた。実際、同 Issue が追加したテストのフィクスチャ 3 箇所が両方を手作業で設定しており、**規約を書いた本人のコードが最初の違反者**だった。対処は「唯一の情報源」を `private set` にし、残りを計算プロパティ（`IsOther => AggregatedSeriesCount > 0`、`Name` は件数から導出）にして、**食い違った状態を表現できなくする**こと。導出でない側の setter は無言で捨てず例外にする（捨てると「設定したのに反映されない」形になる）
    - **状態を確定させる経路は 1 つのメソッドに寄せ、そこで定義域を検証する**（`MarkAsAggregated(int)`）。呼び出し元が 3 つを別々の文で組み立てられる限り、片方だけ変わる日が来る（#1763「同じ論理的な処理に手段が 2 通りあるか」）
    - **是正できたかは「コンパイルエラーがどこに出たか」で測れる**。#1883 では本番コードが素通りし、**ずれを作れる場所（テストのフィクスチャ 3 箇所）だけ**が `CS0200` で壊れた。壊れた箇所の一覧が、それまで不変条件を破れた地点の一覧そのものになる。**壊れた箇所が 0 なら、その是正は何も制約していない**
  - **テストのフィクスチャが本番と別の組み立てをしていないか確かめる**。表示名をリテラルで作るフィクスチャは、**本番だけが変わっても緑のまま通る**（#1818「消費側のテストは必ず既定と異なる値へ設定してから呼ぶ」と同じ形）
- **利用者が記憶する属性（系列色）は、母集団が動く添字に紐付けない**（Issue #1857）。管理者ダッシュボードの残高推移グラフは色を `SeriesBrushKeys[i % Length]` で選んでいたが、`i` は**選択済みカードだけを詰め直したリスト**の添字だったため、3 枚描いている状態で 1 枚のチェックを外すと残り 2 枚の色が順送りに入れ替わり、覚えた「青い線＝カード B」がセッション中に崩れた。色は実体（カード）へ確定させ、選択・絞り込みの増減では動かさない。#1855 の「間接参照（キー・ID・パス）の一意性を、参照先の値の相違の代理にしない」と同じ family で、**添字が何を数えているか**を確かめる
  - **「母集団が動く」経路は 1 つではない**（同 Issue のコードレビューで判明）。初版は選択（チェックボックス）の増減だけを塞ぎ、色番号を**そのときの系列リストの添字**から採っていたが、`AdminDashboardService.BuildBalanceSeries` は「期間内にも期間前にも残高が無いカード」を系列ごと落とすため、**集計期間を変えるだけで母集団が動き**、落ちたカードより後ろの色がすべてずれた。**動く添字を潰したつもりで、別の動く添字へ乗り換えていた**形であり、#1786「その性質を破れる全経路を列挙する」の再演にあたる。番号は実体の識別子（IDm）→ 通し番号の対応として**画面が生きている間保持**し、母集団の増減では動かさない
  - **色を実体へ固定した瞬間、衝突は避けられなくなる**。実体の数に上限が無く色数が有限である以上、鳩の巣原理で同色の 2 つを同時に選べる。「安定（選択で動かない）」と「一意（同時に描く系列が別色）」は両立しないため、**色以外の次元**（線種・マーカー形状）を 1 つ足して解く（4 要素原則の帰結）。凡例スウォッチもその次元を表せる図形にする（線種は `Rectangle` では表せない）
  - **凡例は要素を増やさずに済む場所を探す**。折れ線側のラベルは線が重なる期間で読めない。既にある選択リスト（チェックボックス）へ色見本を置けば、リストがそのまま凡例を兼ねる
  - **整合テストは「添字が偶然一致しない」入力で書く**。選択が先頭から連続だと、選択リストの添字と実体の通し番号が一致し、**旧実装でも緑になる**。母集団からずれた要素（6 枚目）を選ぶ形にして検出力を実測する
  - 回帰は `ChartSeriesPaletteTests` が固定する。色値は `AccessibilityStyles.xaml` から読み出し、**テスト側に色値の表を複製しない**（複製すると本番の色を変えても緑のまま通る。#1821「本番の判定に使う閾値をテスト側で作り直さない」の色版）。しきい値と計算式そのものも既知の入力（旧パレットの衝突ペア・白黒のコントラスト 21:1）で固定する
- **`ReturnBackgroundBrush` の用途**: 「返却完了」シグナルに加え、ダイアログの情報ヘッダー・操作ヒント・装飾用途でも兼用する。専用の `HintBackgroundBrush` 等は新設しない設計判断。意味の区別は色ではなくアイコン・テキスト・配置で行う（Issue #1399、`docs/design/03_画面設計書.md` §4.1 参照）
- **`HintForegroundBrush` の用途**: 「💡 ヒント」「⚠ 注意」等の補足説明文の文字色（マテリアル Brown 700 / `#795548`）。背景ブラシに関する Issue #1399 の方針とは独立した「前景色」キー（Issue #1461）
- **設定で変更できる項目をコメントで断定しない**（Issue #1697）。設定項目が後から追加されると、それ以前に書かれた「常に◯◯」という前提のコメントが実装と乖離したまま残る。**コメントは PR 本文・設計書・マニュアルへの記述の元ネタとして参照される**ため、放置すると誤記述が下流へ伝播する（トースト表示位置設定 `AppSettings.ToastPosition` 追加後も「画面右上に表示」というコメントが残り、PR #1696 の本文へ「画面右上に表示される」と伝播した実例がある）。
  - 書き方: 「設定された画面隅（`ToastPosition`。既定は右上）に表示」のように**「設定に従う」＋「既定値」**の形にする。既定値の説明として具体値に言及するのは正当（`AppSettings` の enum コメント、設定画面の ToolTip 等）
  - 回帰は規約テストで固定する（`ToastPositionCommentConventionTests` が参考実装）。「断定表現の不在」だけでなく**「実装が全選択肢を分岐していること」も併せて検証**する。前者だけだと実装が固定値へ退化した際に逆方向の乖離が生まれるため
  - 検査対象が汎用ファイル（`MainViewModel` 等）に及ぶ場合は、対象機能のキーワードを含む行に絞る。「メイン画面右下の警告エリア」のような**別機能の正当な記述を誤検出する**（実際に発生）
  - **「禁止された要素の不在」を検査するときは要素タグで照合する**（Issue #1692）。`NotContain("UniformGrid")` のような単語一致は、「`UniformGrid` は特大文字で切れるため `WrapPanel` を使う」という**設計意図を書いたコメント自体**を違反として検出する（実際に発生）。`NotContain("<UniformGrid")` のようにタグで検査すれば、規約の理由をコードに残しつつ回帰を固定できる

## ICカード関連
- **用語の使い分け（重要）**: 本システムでは「職員証」と「交通系ICカード」の2種類のICカードを扱う。UI文言・マニュアル・コード内のユーザー向けメッセージでは、交通系ICカードを指す場合は必ず**「交通系ICカード」**と記載し、単に「ICカード」とは書かないこと。「ICカード」だけでは職員証と区別がつかずユーザーが混乱する。ただし「ICカードリーダー」等のハードウェア名称、および「ICカード管理」等の画面・機能名（固有名詞）はそのままでよい（用語ガード `UserFacingTextConventionTests` の `AllowedCompounds` がこれらの複合語を許容する）
- 履歴は最大20件まで取得可能
- **カード種別の判別について**: IDmからカード種別（Suica/PASMO等）を自動判別することは技術的に不可能
  - IDmの先頭2バイトは「製造者コード」（カードを製造した会社）であり「カード種別」ではない
  - 同じSuicaでも製造会社が異なれば先頭2バイトは異なる
  - カード種別はユーザーが登録時に手動で選択する
- **未登録カードの処理**: 職員証か交通系ICカードかをユーザーに選択させる
