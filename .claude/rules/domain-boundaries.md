# 交通系固有ロジックの境界（Issue #1695）

## この規約の目的

本システムのコア（タッチ認証 → 貸出/返却 → 出納簿）は、「複数職員でシェアする物品の出納管理」として交通系ICカード以外（社用携帯・鍵・公用車両等）にも通用する構造を持つ。

**今すぐ汎用化はしない。** ただし交通系固有の知識がコアへ染み出すと、将来その選択肢を取り戻すのに大規模改修が必要になる。この規約は「新しいロジックをどこに置くか」を判断するためにある。

境界の全体像（3 リング図と seam カタログ）は `ICCardManager/docs/design/05_クラス設計書.md` §2a を参照。

## 唯一のルール

> **内側のリングに、外側リングの知識を持ち込まない。**

| リング | 中身 |
|--------|------|
| **中心＝汎用コア** | `staff` / 職員認証 / 貸出・返却の状態遷移 / 30秒ルール / `ledger`（受入・払出・残額）/ 繰越・月計・累計 / 操作ログ / バックアップ / 帳票骨格 |
| **中間＝交通系アダプタ** | `ICardReader` 実装 / `CardType` / `LedgerDetail`（乗車駅・降車駅・バス停・残高） |
| **外側＝交通系固有** | 駅名からの摘要組み立て / バス判別 / 往復・乗継・循環判定 / 残高不足パターン検出 / `StationMasterService` / `FelicaHistoryBlockDecoder` |

## 新しいロジックをどこに置くか（決定木）

1. **「交通系ICカードでなくても意味が通るか」を自問する。**
   - 通る（例: 「長期未返却の物品を検出する」「月次で受入と払出を集計する」）→ **汎用コア**へ置いてよい。ただし交通系語彙（駅・バス・チャージ・IDm）で**分岐しない**こと
   - 通らない（例: 「同一駅で出場した場合を循環移動とみなす」）→ 2 へ

2. **その知識は「カードから読み取った生データの解釈」か。**
   - はい → `Infrastructure/CardReader/` に閉じる。上位層へは解釈済みの値（駅名文字列・金額）だけを渡す
   - いいえ → 3 へ

3. **`Services/` の交通系固有クラス（`SummaryGenerator` の固有メソッド群等）に置く。**
   汎用コアからは、抽象的な値（摘要文字列・金額・真偽値）としてだけ受け取る。汎用コア側に `if (isBus)` のような分岐を作らない。

## `SummaryGenerator` の扱い（境界がクラスを貫いている）

`SummaryGenerator` は 1 クラスに汎用と固有が同居している。**クラス名で「固有だから触るな」と判断しないこと。**

| 種別 | メソッド |
|------|---------|
| 汎用（物品出納簿の様式） | `GetLendingSummary` / 繰越各種 / `GetMonthlySummary` / `GetCumulativeSummary` / `GetChargeSummary` / `GetRefundSummary` / `IsMidYearCarryoverSummary` / `GetMidYearCarryoverLikePattern`（SQL 用 LIKE パターン導出、Issue #1749） |
| 交通系固有 | 駅名からの摘要組み立て / バス混在表記 / 往復・乗継・循環判定 / `GetInsufficientBalanceNote` |

- 汎用メソッドは汎用コア（`ReportDataBuilder` / `Models/Ledger` 等）から呼んでよい。実際 22 ファイルから使われている。ただし **`Data/` 配下からの参照は規約テストが完全修飾呼び出し単位で許可管理する**（現在は `GetMidYearCarryoverLikePattern` のみ。設計書 05 §2a.5、Issue #1749）
- **新しいメソッドを追加するときは、どちらの群に属するかを XML doc コメントに書く**。書かないと次に読む人が同じ調査をやり直す
- 固有メソッドを汎用コアから呼びたくなったら、それは汎用コアに固有知識を持ち込もうとしている合図。1 段外側で値を組み立ててから渡す

## 差替コスト「高」の拡張点を作らない

seam カタログ（設計書 §2a.4）の差替コストは、現時点ですべて「低」または「中」で、**「高」に相当する項目は存在しない**。この状態の維持が本規約の実質的なゴール。

「高」＝ コアの構造変更を伴う、の典型:

- 汎用コアのテーブル（`staff` / `ledger`）に交通系固有列を足す
- 貸出・返却の状態遷移そのものを交通系の都合（改札の入出場等）で分岐させる
- 帳票骨格（`ReportRowBuilder` の行生成）に駅・バスの分岐を埋め込む

やむを得ずこうした変更が必要なら、設計書 §2a.4 の seam カタログに「高」の行を追加し、**なぜ避けられなかったかを備考に書く**。黙って増やさない。

## 規約テストとの関係

`DomainBoundaryConventionTests` が既に閉じている境界 3 点を固定している（設計書 §2a.5）。

- テストは**禁止ではなく気づきの装置**。境界を越えた変更が常に誤りとは限らない
- 意図的に境界を変更する場合は、**設計書 §2a.4 の seam カタログを更新したうえで**テストを修正する。テストだけ直して設計書を放置しない
- 検査は**実コード参照のみ**を対象とし、コメント中の言及は除外する。規約の理由をコードコメントに残せるようにするため（`.claude/rules/ui-conventions.md` の「禁止された要素の不在を検査するときは要素タグで照合する」と同じ配慮）

## やらないこと（YAGNI）

本規約は「境界を意識する」レベルに留める。以下は**具体的な横展開ニーズが顕在化するまで行わない**:

- 交通系固有ロジックのインターフェース抽出（`ISummaryGenerator` 等の新設）
- `ic_card` テーブル・`IcCard` モデルのリネーム・汎用化
- プラグイン機構や設定による業務ドメイン切替
