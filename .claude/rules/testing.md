# テストコード作成時の厳守事項

## テストコードの品質
- テストは必ず実際の機能を検証すること
- `true.Should().BeTrue()` のような意味のないアサーションは絶対に書かない
- 各テストケースは具体的な入力と期待される出力を検証すること
- モックは必要最小限に留め、実際の動作に近い形でテストすること

## ハードコーディングの禁止
- テストを通すためだけのハードコードは絶対に禁止
- 本番コードに `if (testMode)` のような条件分岐を入れない
- テスト用の特別な値（マジックナンバー）を本番コードに埋め込まない
- 環境変数や設定ファイルを使用して、テスト環境と本番環境を適切に分離すること

## テスト実装の原則
- テストが失敗する状態から始めること（Red-Green-Refactor）
- 境界値、異常系、エラーケースも必ずテストすること
- カバレッジだけでなく、実際の品質を重視すること
- テストケース名は何をテストしているか明確に記述すること

## 「通るが目的を果たさないテスト」の典型（Issue #1692 で実際に踏んだ）

書いた本人が満足して終わりがちな型。**そのテストが防ぎたいリグレッションを、実際に起こして落ちることを確かめる**のが唯一の検証手段。

- **並列化の回帰は「順序」ではなく「同時実行数」で検出する**。Moq の `MockSequence` は呼び出し順序しか見ないため、`Task.WhenAll` へ書き換えても開始順序は変わらず**素通りする**。リポジトリのモックの戻り値を `Tests/Infrastructure/ConcurrencyProbe` に通し、`MaxConcurrentCalls == 1` を表明すること（`DashboardServiceTests` / `AdminDashboardServiceTests` の Issue #1452 回帰テストが参考実装。計測器は Issue #2108 で 1 つに寄せた）。SQLite は同一接続での並列コマンドを許さないため、この検出力は実害に直結する
- **呼び出し先を別オーバーロードへ切り替える修正では、「切り替え元」のオーバーロードもモックへ設定する**（Issue #1745）。loose な `Mock<T>` は未設定メソッドに**既定値**（`Task<int>` なら 0、`Task<bool>` なら false）を返すため、旧オーバーロードを未設定のままにすると**修正前のコードでは副作用が一切起きない**。「ロールバックされたので DB は 0 行」という表明が、旧コードでは「そもそも 1 行も書かれていないので 0 行」で通ってしまう。#1745 では `InsertAsync(Ledger)`（tx なし＝autocommit）と `InsertAsync(Ledger, SQLiteTransaction)` の**両方**を実リポジトリへ委譲して初めて、修正前コードで 5 件すべてが赤になった
  - あわせて **`Verify(…, Times.Never)` で「旧オーバーロードを呼んでいないこと」を表明する**。行数の表明だけだと、退行したときに「なぜ落ちたか」がテスト名から読み取れない
  - **「モックの既定値で通っていないか」は、修正前のコードへ実際に当てて確かめる**のが唯一の方法（`git checkout origin/main -- <本体ファイル>` → テスト実行 → 復元）。この Issue では 5 件中 5 件が赤になることと、その落ち方（途中行エラー時に 2 行が残存する等）が指摘どおりの症状であることを同時に確認できた
- **成果物を作るテストは、成果物の中身を検査しないかぎり緑のまま壊れる**（Issue #2011）。マニュアル用スクリーンショットの撮影テストは「目的の要素へ到達できた」ことしか表明しておらず、保存した画像の画素を見ていなかった。WPF はウィンドウを表示してから最初の描画が終わるまでクライアント領域が白いままで、**UIA の要素はその前から見える**ため、要素の出現を待っても未描画の白い画像が保存される。実測では、別のビルドを並行させた撮影で**全 25 件が成功しながら 4 枚が白紙**になり、正しい名前で公開候補に並んでいた。**「テストが緑」は「成果物が正しい」ではない**。
  - **検査は成果物そのものに掛ける**。#2011 では `ScreenshotHelper` がサンプル画素の最多色の割合を見て、閾値以上なら未描画とみなして撮り直し、直らなければ `_FAILED.png` へ退避して原因と対処を示す。**閾値は勘ではなく実測から決める**（白紙 0.940〜0.952 / 正常 0.187〜0.726 と、両者の間は広く空いていた）
  - **非同期に読み込む一覧は「一覧が見つかった」を待ちにしない**（同）。DataGrid / ListBox は中身が空でも UIA ツリーに居るので、一覧を探す retry は即座に返る。行の出現まで待つこと。実際、待ったつもりの画像に「集計中...」のオーバーレイが写っていた
  - **対の表明が無いと、投入データの誤りは見えない**（同）。「警告が出ていること」だけを表明し「出ていないこと」を表明していなかったため、警告を消すはずの投入データが消しきれていなくても緑だった。ただし**表明の範囲は投入データが支配できるものに限る** — 環境由来の警告（更新の案内・journal_mode の低下）まで禁止すると、その環境では撮影が原理的にできなくなる
- **成果物を作る仕組みは、成果物が「いつ作られたか」も検査しないかぎり緑のまま壊れる**（Issue #2095）。#2011 の裏返し。マニュアル用スクリーンショットの撮影スクリプトは、完了報告（`✓ 撮影完了: 29 枚（対象 29 枚）`）も公開判定（`-Publish` の `$missing`）も**出力先にそのファイルが存在するかしか見ていなかった**。出力先 `docs/screenshots/auto/` は `.gitignore` 対象で前回の実行の成果物が残り続けるため、撮影が漏れた画像は**残骸がそのまま再公開され、内容が前回と同じなら `git diff` にも現れない**（#2085 / PR #2093 の撮り直しで 2 枚が実際にそうなった。発見したのは人が 1 枚ずつ画像を開いて確かめた結果で、スクリプトは何も教えていない）。
  - **「存在」を「今回作られた」の代理にしない**（#1855「間接参照の一意性を、参照先の値の相違の代理にしない」と同じ family）。生成の**前に**対象の成果物を消しておけば「存在＝今回作られた」が成立し、報告と公開の両方が同じ 1 つの根拠で判定できる。失敗時の切り分け用の副産物（`*_FAILED.png`）も一緒に消す — 前回の失敗痕は今回の切り分けを汚す
  - **ただし事前削除だけでは、別プロセスの消費側へ情報が渡らない**。`-Publish` は撮影を伴わずに単独実行できる設計なので、「今回の対象は何だったか」を知らない。生成側がマニフェスト（撮影開始時刻・作れた／作れなかった名前）を残し、**判定は 1 か所へ寄せる**（#1763）。「事前削除」と「マニフェスト」を両方の場所で別々に判定させない
  - **スキップを成功に畳まない**（#1737「Busy/Locked 以外を false に畳むと原因が分からない」と同じ形）。xUnit の `Skip.If` はテスト成功扱いなので `dotnet test` の終了コードでは「作れなかった」と「作る必要が無かった」が区別できない。報告は「今回作れた N 件 / 対象 K 件」と**作れなかった名前の列挙**に分ける。環境の都合で原理的に作れないもの（`error_no_reader.png` はリーダー未接続でしか撮れない）は失敗にはせず、スキップであることを明示する
    - **区別を付ける場所は「報告」と「下流の受け入れ判定」であって、終了コードではない**。正当なスキップで終了コードを非 0 にすると、正常な開発機で毎回赤くなる（#1786 の「規約が推奨する方向の変更でテストが赤になると、修正者を対象から外す方向へ誘導する」と同じ害）。下流（公開）がその名前を受け付けないことで実害を止める
  - **「作れなかったものを拒む」と「作れたものまで拒む」を取り違えない**（コードレビューで検出）。#2095 の初版は全撮影の `-Publish` も全か無かにしたため、**リーダーを繋いだ開発機では全撮影の公開が恒久的にできなくなっていた**（`error_no_reader.png` が必ずスキップされる）。名指しで対象を絞って走らせたとき（`-Changed`）は全か無か、全件を対象に走らせたときは作れた分だけ進めて残りを名指しで警告する、と**呼び出し方で分ける**。どちらでも「作られていないものは下流へ渡さない」不変条件は変わらない
  - **「対象との一致」を成功の根拠として表示しない**。`N 枚（対象 N 枚）` は**一致しているほど安心させる**のに、その一致は何も保証していなかった。表示するなら一致の根拠（今回作れた件数）で数えたものにする
  - **生成のパスがテストから踏めないなら、判定を生成から切り離してから検査する**（#1794 / #1817 と同じ形）。撮影は実機の GUI を操作するので単体テストから踏めないが、判定を別スクリプトへ出せば挙動テストで固定できる。生成側がそれを実際に使っていることはソーステキストの静的検査が**「禁止された形の不在」と「正しい形の存在」を対で**見る
  - **回帰は「欠陥を突く側」（残骸を公開しない）と「正当な生成を塞いでいない側」（今回作れたものは公開できる）を対で置く**。前者だけだと公開を丸ごと止めた実装でも緑になる。2 つの防御（事前削除とマニフェスト検証）は**別々の入力で効く**ので、検出力は片方ずつ変異させて実測する
  - **事前削除の対象は「仕様に載っている名前」に限る**。出力先は引数で差し替えられるため、パス区切り・親ディレクトリ参照・拡張子違いを含む値は入口で拒否し、利用者が別用途で置いたファイルを消さない
- **開発機の実データに触れるテスト基盤は、退避を「起動手順の入口で 1 回」にする**（Issue #2062）。UI テストの `AppFixture` は起動のたびに「DB があれば退避する」を繰り返していたため、`LaunchWithSeed` が内部で 2 度目の起動をした時点で**投入済み DB が元の DB の退避ファイルを上書き**し、撮影のたびに開発機の `iccard.db` が撮影用データに置き換わっていた。コメントは「正しくリストアされる」と述べ、撮影テストはすべて緑だった — 守るべき成果物（利用者の DB）を誰も検査していなかった
  - **入れ子になる処理に退避を持たせない**。退避の責任はガード（`UiTestDatabaseGuard`）1 つに置き、内側の起動は受け取るだけにする
  - **失敗経路・中断・「元が無かった」も復元の対象に数える**。復元の書き戻しに失敗したら退避ファイルを消さず、次回の退避より先に書き戻す。SQLite の付随ファイル（`-journal` 等）は DB と対で扱う（残ったジャーナルは書き戻した DB をロールバックする）
  - **手順はアプリを起動せずに検証できる形へ切り出す**（`AppFixture.LaunchWithSeedCore`）。UI テストは CI で走らないため、起動を差し替えられないと回帰を CI に置けない
- **「CI で実行される」と書いたら、CI がそのテストを実際に選んでいるかを確かめる**（Issue #2099）。#2062 は上のとおり GUI 不要の形へ切り出し、doc コメントに「CI でも実行される」と書いたが、**UITests の csproj はソリューション単位の実行から自分を外している**（`BuildingSolutionFile` 条件で `IsTestProject=false`）ため、CI の `dotnet test`（ソリューション単位）には `--filter` 以前にプロジェクトごと含まれていなかった。切り出しは正しかったのに、回帰は一度も CI に置かれていなかった
  - **filter はプロジェクトの選択より後に効く**。「`Category!=UI` で除外しているから、Category の無いテストは走る」は、そのプロジェクトが実行対象に入っているときにしか成り立たない。確かめる手段は CI のログに**そのテスト名が出ているか**であって、filter 式を読むことではない
  - **CI 構成も静的検査で固定する**（`CiWorkflowConventionTests`）。直接実行が必要なプロジェクトは sln と csproj から導出し、ci.yml がそれを csproj 指定で実行していることを見る。あわせて、テストの両構成（Release / Debug）・`--blame-hang-timeout`・`timeout-minutes` を固定する。**「すべての〜」を名乗る検査の走査対象は、名前どおりの範囲から導出する** — ハング対策と timeout の検査は ci.yml しか読んでおらず、release.yml のテストにハング対策が無かった（Issue #2116。`.github/workflows` 全体へ広げた）。`${{ }}` の式の中にだけあるフラグは片方の構成でしか付かないので、「必ず付いていること」は式を取り除いた部分で見る
  - **ロックファイルは CI がロックモードで読まない限り何も固定しない**（Issue #2117）。素の `dotnet restore` は食い違いをロックファイルの書き換えで黙って吸収するため、Dependabot が本体のロックファイルだけを更新した PR（#1713）で、本体を参照するテスト・DebugDataViewer のロックファイルが古いまま残っていた。全ワークフローの復元は `--locked-mode`、後続の build/test/publish/format は `--no-restore`（`--no-build`）で、アクションは commit SHA で固定する（`CiWorkflowConventionTests` が固定）。ロックファイルの中身は SDK の版と OS でも変わる（SDK 10 は RID `win-x86`・暗黙の参照なし、Linux は RID の節なし）ので、SDK は `global.json` で固定し、再生成は Windows で行う — **setup-dotnet で版を入れても、global.json が無ければランナーに入っている最新の SDK が使われる**。カバレッジは閾値で合否を決めず実測値をサマリーへ出すだけにする — 行カバレッジは「テストが何を表明しているか」を測らない
  - **デッドロックを検出するテストは上限付きで待つ**（`Task.WhenAny` とタイムアウト。`LendingServiceReturnDeadlockTests` が参考実装）。素の `await` や `Task.WhenAll` では、本当にデッドロックしたとき失敗ではなく停止になる。「テスト全体のタイムアウトで失敗する」とコメントに書いても、xUnit にテスト単位の既定のタイムアウトは無い
- **単体テストも開発機の実データに触れ得る — 置き場所の解決を 1 か所へ寄せ、テストプロセスの入口で差し替える**（Issue #2098）。#2062 は UI テスト基盤の話だったが、単体テストも `C:\ProgramData\ICCardManager` 配下を書き換えていた。既定の保存先へ空の DB のバックアップを作って**同じ実行の世代削除が本物の自動バックアップを間引き**、`database_config.txt`（共有モードの DB パス）を**退避せずに削除**し、エラーログへ架空の「リストア」エラーを追記していた。いずれも本番コードが `CommonApplicationData` から個別にパスを組み立てていて、**テストから差し替える手段が無かった**ことが根本原因
  - **差し替えはテストごとではなく、プロセスの入口で 1 回**（`Tests/Infrastructure/TestAppDataIsolation` のモジュール初期化子 → `AppDataPaths.RedirectRootDirectory`）。テストごとに退避・復元すると並列実行で入れ子になり、#2062 と同じ「退避ファイルの上書き」を作る。入口で差し替えれば、**まだ誰も気付いていない経路**（`FileLoggerProviderTests` が本物の配下にフォルダーを作っていた、`new DbContext()` が本物のフォルダーを作成していた）もまとめて塞がる
  - **プロセス単位の差し替えは、テスト間の独立までは作らない**。同じプロセスの中では置き場所を共有するので、ファイルを書き換えるテストは**テストごとの一時フォルダーを注入**する（`SettingsViewModel` の internal コンストラクタ）。共有の置き場所で書き換えると、並列に走る別クラスがそのファイルを読んで実行順に依存する
  - **「例外が出ない」だけのテストは、書き込みを検査していないだけでなく、書き込み先も検査していない**。`LogException` のテストは `NotThrow` しか見ておらず、本体を `return;` にしても緑のまま本物のログへ書いていた。**書いた内容を読み返す形に直すと、書き込み先も同時に表明できる**（`ErrorDialogHelper.LogDirectory` が差し替え先の配下にあること）
  - **回帰は静的検査で「本番は 1 か所だけが解決する」「テストは直接参照しない」と、「差し替えが実在する」を対で固定する**（`AppDataPathsConventionTests`）。前者だけだと、モジュール初期化子を外した実装でも緑になる
- **本番の判定に使う閾値を、テスト側で作り直さない**（Issue #1821）。同じ意味に見える式でも処理系が違えば境界が食い違う。6年保持の削除条件は SQL の `date('now', '-6 years', 'localtime')` だが、テストが `DateTime.Now.AddYears(-6)` で境界日を組み立てていたため、**うるう日（2/29）に実行したときだけ**赤くなる状態だった（.NET は 6 年前を 2/28 へ丸め、SQLite は 2/29 を 3/1 へ正規化する）。閾値は**本番と同じ場所に評価させて取得する**（`DbContextCleanupTests.GetRetentionThresholdDate` は実接続で同じ式を SELECT する）。これで「テスト側の再実装がいつか本番とずれる」という形ごと無くなる
  - **乖離そのものを 1 件のテストで固定する**。閾値を本番から取ると、正常時は両者が一致するため「なぜこの手間が要るのか」がコードから読み取れなくなる。`date('2028-02-29', '-6 years')` = `2022-03-01` と `AddYears(-6)` = `2022-02-28` を並べて表明しておくと、次に読む人が調査をやり直さずに済む
  - **日付・時刻に限らない**。丸め・切り捨て・照合順序・数値の精度など、**C# と SQLite の両方に実装がある演算**はすべて同じ罠を持つ
- **現在時刻に依存する本体は、時計を注入して固定日時で検証する**（Issue #2100）。本体が `DateTime.Now` を直接読むと、テストの結果は**実行した月・時刻で変わる**。カード登録の繰越テストは 1 月にだけ必ず赤くなり（「1 月から繰越」の開始日が当年 2/1 になり、「今日」の履歴がすべて除外される）、隣のテストは同じ 1 月に「履歴あり」の経路を通らないまま緑だった。デバッグ用テストデータの年度境界テストは、境界が生成範囲に入らない 10〜3 月の実行では**何も検証せずに緑**だった
  - **期待値を本体と同じ式から作らない**。`SelectLastMonth_InJanuary_…` は期待値を本体と同じ `Now.AddMonths(-1)` から作り、if/else の両分岐で同じ検証をしていたため、年をまたぐ誤りを 1 月にしか検出できなかった。固定日時を与え、期待値はリテラルで書く
  - **「今日」をテスト側と本体側で別々に評価しない**。0 時をまたいだ瞬間に別の日になる。本体と同じ時計から取る（`Tests/Infrastructure/Timing/FixedSystemClock`）
  - **境界は Theory の固定データで明示する**（1 月・年度末・年度初め・うるう年・日付が変わる直前直後）。既定の固定日時は過去の年に置く — 時計を無視する実装へ戻ったとき食い違って赤くなる
  - **foreach で検証するなら、先に対象件数を表明する**。対象が空の foreach は何も検証せずに緑になる
  - **比較相手が実時刻なら、注入した時計を使わない**（バックアップ一時ファイルの鮮度判定はファイルシステムの更新日時と比べる）
  - **クラスモックされる型に時計を足すときは、省略可能引数にしない**。`new Mock<BackupService>(a, b, c)` は引数の個数でコンストラクタを探すため、省略可能引数では一致しない。internal のコンストラクタを足す
- **例外の表明の「裏返し」を戻り値で書かない**（Issue #1882）。`string produced = null; act = () => produced = Sut(0); act.Should().Throw<T>(); produced.Should().BeNull();` の後半は、C# で `throw` と `return` が同時に起きない以上**必ず自明に真**であり、検出力を持たない。想定した退行（`return 既定値;` へ緩める）が捕まるのは前半の `Throw` が落ちるからで、後半は 1 度も働かない。**対の表明は「反対側の状態」ではなく「別の観測軸」で書く** — #1882 は「定義域外で基底名を返さないこと」ではなく「**定義域内のどの件数でも基底名と一致しないこと**」（1〜100 と `int.MaxValue` を走査）へ置き換えて検出力を得た（1 点だけの表明では、書式から接尾辞が落ちる退行を大きな入力で見逃す）
- **後処理を成功させる前提のテストは、後処理が失敗する状況を検査していない**（Issue #1954）。「コミット後の失敗を案内する」分岐のテストで、案内より後ろに走る一覧再読込・ダッシュボード更新を**すべて成功するようスタブする**と、その分岐が対象とする故障（案内と再読込が**同じ原因**で失敗する）を一度も通らない。#1954 の初版はこの形で、通知を再読込の後ろへ戻す変異でも緑のままだった（`db-write-conventions.md` #1727「エラー通知を、失敗したサブシステムに依存させない」／「テストも『1 か所だけ壊れる』前提を置かず、障害が波及したケースを 1 件書く」の再演）
  - **失敗注入は、検査したい全分岐に届く場所へ置く**。#1954 では成功分岐が `RefreshDashboardAsync`（`ICardRepository.GetAllAsync`）まで進むのに対し、失敗分岐は `LoadHistoryLedgersAsync`（`GetPagedAsync`）だけで、しかも `HistoryCard == null` なら**早期 return する**。片方だけ落とすと**一方の経路では故障がそもそも起きず、修正前のコードでも緑になる**（実際そうなっており、変異を当てて初めて分かった）。分岐ごとに「この経路は実際にどのリポジトリを叩くか」を確かめてから注入点を選ぶ
- **「スレッドの同一性」で環境を模擬しない — 模擬の土台にはスレッドプール外のスレッドを使う**（Issue #1961）。`DbContext.IsOnUiThread` を「テスト本体のスレッドの `ManagedThreadId` と一致するか」で差し替える形は、テスト自身がプールのスレッド上で走るため、`await` で解放されたそのスレッドを**プールが SUT の `Task.Run` に再利用**した瞬間にオフロード先が UI と判定され、間欠的に赤くなる。UI 役は `new Thread(...)`（プール外）で作れば、`Task.Run` の実行先になり得ないので一致が原理的に起こらない。専用スレッドは SUT の Task 完了まで生かすこと（終了すると `ManagedThreadId` は別スレッドへ再利用され得る）。
  - **「間欠的に赤い」の裏に「常に緑で何も守っていない」が同居していることがある**。#1961 のテストは、`ExecuteAutoBackupAsync` が `ResolveBackupFolderAsync`（内部で `Task.Run` を `ConfigureAwait(false)` で await）を通るため**継続が必ずプールへ移り**、守っているはずの `Task.Run(BackupDatabaseTo)` を丸ごと削除しても緑だった。**間欠失敗を調べるときは、まず「そのテストは正しい退行を検出できるか」を変異で実測する** — 揺らぎを消しただけでは、何も検査しないテストを安定させることになる。
  - **模擬が SUT へ届いていることを対で表明する**。「正しい実装で緑」だけでは、模擬を丸ごと外した実装でも緑になる。「模擬を極端側へ振ると赤くなる」（#1961 では *どのスレッドも UI と判定させると `null` を返す*）を 1 件置く。
- **失敗を戻り値（`null` / `false`）で表すメソッドのテストに `NullLogger` を渡さない**（Issue #1961）。ガードの発火・I/O 失敗・権限失敗がすべて同じ戻り値へ畳まれる（#1737）うえ、**サービスが記録した理由まで一緒に捨てる**ため、CI が赤くなっても run のログから切り分けられない。`Tests/Infrastructure/RecordingLogger<T>` を渡し、`FormatEntries()` をアサーションの `because` へ載せる。
- **同時実行・ロック・トランザクションのテストは、競合を「実際に起こして」から表明する**（Issue #2103）。名前が「同時」「並列」「ロック」「トランザクション」でも、次の形では競合が一度も起きず、守りたいガードを丸ごと消しても緑になる
  - **モックが完了済みの Task を返すと、`Task.WhenAll(task1, task2)` は直列に走る**。1 件目は同期的に最後まで走り切ってから 2 件目が始まり、「1 件だけ成功」はモックの状態遷移が弾いているだけになる。1 件目を**ロックの内側**（台帳の書き込み等）で `TaskCompletionSource` により止め、**止めている間に** 2 件目が「待機している」「まだ状態を読んでいない」ことを表明してから解放する（`LendingServiceTests` の `BlockFirstCallGate`）
  - **SQLite の競合は、同じ接続を共有させると起きない**。同じ `DbContext` の接続は接続リースのセマフォで直列化されるため、CAS を「SELECT してから UPDATE」の 2 文へ退行させても緑になる。**ファイル DB に別々の `DbContext`（別 PC 相当）**を向け、開始合図で一斉に走らせる。割り込みは確率的なので回数を重ねる（`SettingsRepositoryTests` の VACUUM ロック）
  - **ADO 層の再試行が、検査したい待機を肩代わりすることがある**。System.Data.SQLite は SQLITE_BUSY を受けると `CommandTimeout`（既定 30 秒）の間自前で再試行するため、`PRAGMA busy_timeout` を消しても書き込みは成功する。busy_timeout を観測するならコマンドの `CommandTimeout = 0` にする
  - **トランザクションの受け渡しを `null` で検査しない**。`Verify(..., tx)` の `tx` が `null` だと、受け取った tx を捨てて `null` を渡す実装とも一致する。インメモリ SQLite で実際に `BeginTransaction()` した非 null の tx を渡し、参照の同一性を表明する
  - **「失敗したら巻き戻す」をモックのリポジトリで検査しない**。書き込みが DB に届いていなければ、失敗分岐で `Commit()` しても観測できない。片方の書き込みを実リポジトリへ委譲し、**DB を読み返して**表明する（#1745 と同じ判断）
  - **拒否の理由がガードであることを、別の失敗要因を取り除いて確かめる**。リストアの共有モード判定は、開いたままのハンドルで `File.Move` が失敗することでも `false` になっていた。`FileShare.Delete` 付きのハンドルなら名前の変更は妨げないので、ガードだけが拒否の理由になる。対の表明（ガードが効かないモードでは同じ条件で成功する）を置く
  - **状態をリフレクションで作ってから入力を与える形は、その状態へ至る経路を検査していない**。「処理中は読み取りを無視する」は、処理の await 中に 2 件目が届く形で再現する。テスト用ディスパッチャーは用途で選ぶ — その場で走り切る `SynchronousDispatcherService` では await 中の割り込みも「`InvokeAsync` の後に立てたフラグを処理が読む」順序依存も再現しないので、本番と同じく後で実行する `DeferredDispatcherService` を使う。ただしこの代役は同期コンテキストを持たず、await の後の続きはスレッドプールで走る（UI スレッドのキューへ戻る本番とは違う）。止めた処理を解放したら `WaitForPendingAsync` で完了を待ってから表明する
  - **並行テストで集めた例外は、特定の型だけを表明しない**。`OfType<ObjectDisposedException>()` だけを見ると、同じ競合から生じる別の例外（NullReference・SemaphoreFull）を握りつぶす
  - **変異が挙動を変えないことがある（等価変異）**。`MainViewModel` の処理中ガードは、後続の `switch` に処理中の分岐が無いため、消しても挙動が変わらない。テストでは検出できないので、観測できる性質（2 件目が何も起こさない）を壊す変異で検出力を測り、等価であることを記録しておく
- **実時間の待機を、検証したい仕様の代わりにしない**（Issue #2108）。リトライのバックオフを実際に待つテストは 1 件で数秒〜約 9 秒かかるうえ、「何ミリ秒待ったか」は何も表明していなかった。待機は差し替え口（`DbContext.RetryDelayAsync`）を通し、テストでは記録器（`Tests/Infrastructure/Timing/RecordingRetryDelay`）で**要求された待機時間の列**を表明する
  - **待機時間の配列を 0 へ差し替えない**。配列の長さはリトライ回数、値はバックオフの仕様そのもので、差し替えると検証したいものが消える。**差し替えるのは「待つ」動作だけ**
  - **差し替え口の既定は実時間で確かめる**。既定が待たない実装へ変わると、差し替えたテストはすべて緑のまま本番のバックオフが消える。既定だけは下限（要求時間 − タイマー分解能）で 1 件表明する
  - **「到達したら次へ」を固定時間で待たない**。`Task.Delay(30)` で「1 件目がロックを取った頃」を待つ形は、遅いマシンで 2 件目が先にロックを取る。モックの `Callback` で合図を立て、上限付きで待つ（上の「fire-and-forget の完了を固定時間の待機で待たない」と同じ）
  - **本体が await 済みの処理の後ろに `Task.Delay` を置かない**。削除しても表明の結果は変わらず、待ち時間だけが残る。置く前に、待っている相手が本当に非同期に走っているかを本体で確かめる
  - **busy_timeout を待つテストは、待機を 0 にしても失敗が確定的に起きる形で書く**。読み取りトランザクションが共有ロックを保持していれば VACUUM は必ず失敗するので、「成否はタイミング依存」として `NotThrow` だけを見る理由は無い。戻り値とログの両方を表明し、ロックを解けば成功することを対で置く
- **本番ソースの全走査は `ProductionSourceFiles` で 1 回にする**（Issue #2108）。規約テストはそれぞれが本番ソース全体（約 4MB）を読み込み・サニタイズし直しており、Theory の各ケースで読み直すもの・ファイルごとに親方向の探索を繰り返すものもあった。読み込み結果と `ToCodeOnly` 等のサニタイズ結果は `ProductionSourceFiles.CSharp` / `.Xaml` がプロセスで 1 回だけ作って共有する。重い集計（コントラスト検査の文字色の収集など）はクラス内で `Lazy` にする
  - **ビルド出力のディレクトリへは降りない**。開発機の `obj` には WPF の一時プロジェクト（`*_wpftmp`）の残骸が千件単位で溜まり得るので、列挙してからパスで捨てる形では走査そのものが重い
  - **キャッシュを走査の唯一の入口にしたら、キャッシュが縮まないことを固定する**。ここがファイルを取りこぼすと、規約テストはすべて「違反ゼロ」で緑のまま無力化する（`ProductionSourceFilesTests`）
- **重複しているテストは、純関数の側に寄せて片方を消す**（Issue #2108）。同じ純関数を同じ観点で検証するテストが 2 か所にあると、次に仕様を変える人が片方だけを直す。**消す前に、消す側にしか無い観点（空の入力・日付なしの混在など）を寄せ先へ移す**。名前と中身が食い違う重複（「引数なしなら既定」と名乗りながら既定値を明示して呼ぶ）は、名乗っている性質が本体に存在するかを確かめてから消す
- **`await act.Should().NotThrowAsync()` だけで終わらせない**。「例外が出ない」は結果を何も検証していない。返り値・副作用のどちらかを必ず具体値で表明する
- **fire-and-forget の完了を固定時間の待機で待たない**。`Task.Delay(50)` は遅いマシンで不安定になる。モックの `Callback` で `TaskCompletionSource` を立て、`Task.WhenAny` に十分長いタイムアウト（5秒程度）を添えて待つ
- **STA スレッドの完了待ちは、上限の倍率ではなく競合の側を減らす**（Issue #2083）。WPF の `Window` / `FlowDocument` を扱うテストは `Thread.Join` 以外に完了を待つ手段が無いが、待っているのは**計算時間ではなくスケジューリング**である。GitHub ホストランナーは 2 コア共有で、STA スレッドは初回に `PresentationFramework` の初期化を伴うため他のテストコレクションと CPU を奪い合う。実測 0.1 秒に対して上限 30 秒（約 290 倍の余裕）がありながら PR #2082 の CI で打ち切られた ― **この比なら、倍率を増やしても根治しない**。STA を要するテストは `Tests/Infrastructure/StaTestRunner` を使い、`[Collection(StaThreadCollection.Name)]`（`DisableParallelization = true`）で並列実行の相手そのものを減らす。
  - **打ち切ったときに何が残るかを設計する**。旧実装の `because` は「STA スレッドが時間内に完了すること」だけで、**検証対象の値には一度も到達していない**のに、ログだけを見た人は「印刷プレビューが壊れた」と読む。経過時間・完了した段階（`StaStageLog.Complete`）・「この失敗は検証対象の不具合を意味しない」という断りを添える（「`NotBeEmpty()` で止めない」と同じ趣旨）。
  - **間欠的に赤いテストを見たら、まず同じヘルパーの複製を数える**。#2083 では同一の `RunOnSta` が 2 箇所にバイト単位で複製されており、待ち方の方針を変える人が片方を取りこぼす形だった（#1763）。**寄せてから方針を 1 回だけ決める**。
  - **「フレーキーだから」と上限を伸ばす前に、そのテストが正しい退行を検出できるかを変異で確かめる**（#1961 の「間欠的に赤い」の裏に「常に緑で何も守っていない」が同居する）。
- **`NotBeEmpty()` / `NotBeNull()` で止めない**。例: 積み上げ棒グラフの Y 軸目盛りを `NotBeEmpty` で確認しても、「系列ごとの最大値でスケールを作る」誤り（正しくは月合計）を検出できない。具体値まで表明する
- **同じ規約の検査を 2 か所に書かない**。用語ガード（「ICカード」単独表記の禁止）は `UserFacingTextConventionTests` が `src` 配下の全 XAML（要素内容・属性値）と全 `.cs` の文字列リテラルを走査しており（Issue #2101 で `Views/` の属性値と ViewModels の一部の呼び出しから拡大）新画面も自動で対象になる。画面ごとに簡易版を重ねると許容複合語の定義が分かれ、片方だけ更新されたときに検査が食い違う
  - **検査の下請け処理（ソースのサニタイズ・波括弧対応の抽出）も同じ**。`TestSourceInspection` の XML doc は「新規の規約テストは本ヘルパーを使い、複製をこれ以上増やさないこと」と明記しているが、Issue #1764 の初版はこれを見落として 4 つ目の私的コピーを書き、**そのヘルパーが既に解決済みだった欠陥をそのまま再現した**（行単位で剥がす実装は複数行にまたがる `@"..."` を追えず、2 行目以降がコードとして扱われて波括弧の対応がファイル末尾まで狂う ＝ ガードが緑のまま無力化する）。**重複の回避は整理整頓ではなく正しさの問題**である。静的検査を書く前に `tests/ICCardManager.Tests/TestSourceInspection.cs` と `TestPaths.cs` を読むこと
  - **リテラルの中身そのものを検査する場合は `ExtractMethodBodyPreservingLiterals` を使う**（Issue #1960）。SQL を検査対象にするとリテラルを残す必要があるが、`ExtractMethodBody` は `ToCodeOnly` 済みの入力を前提に波括弧の対応で切り出すため、補間 SQL（`IN ({string.Join(", ", names)})`）や正規表現のような**波括弧を含むリテラルが 1 つ入るだけで抽出範囲が黙って隣のメソッドまで伸びる**。実測では「列の集合」を見るテストは緑のままで、対の表明だけが落ちた ― **ガードが別の場所を見ていることは、ガード自身の失敗としては現れない**。サニタイズ前提を XML doc に書くだけでは守れないので、前処理はヘルパーの内側に閉じる。あわせて**シグネチャの照合は空白を無視し、複数一致は例外にする** ― 改行・字下げを直書きしたマーカーは対象を整形しただけで落ち（#1786）、逆に空白を無視すると薄いラッパーのオーバーロードにも一致して**守りたいメソッドを一度も検査しない**
  - **行番号を報告する検査には `ToCodeOnlyPreservingLines` を使う**（`ToCodeOnly` は複数行ブロックコメントを空白 1 文字へ畳むため行番号がずれる）
- **ガードの「検出漏れ」は緑になる — 対象の絞り込みが fail-open になっていないか確認する**（Issue #1764）。検査対象のファイルを「特定のトークンを含むもの」で絞ると、**そのトークンの表記ゆれ（`this.` 修飾など）を持つファイルは走査から丸ごと外れ、1 件も検査されないままテストが緑になる**。絞り込みの条件は検出側の条件と同一にし、表記ゆれを含めて拾えることをサンプル入力で固定する
  - **「ファイル名で列挙しない」を守っても、導出の軸が実データの一形態しか見ていなければ同じ**（Issue #2083）。トップレベルのクラスを「行頭にある `class` 宣言」で導出した検査は、**ブロック形式の `namespace`（本プロジェクトに 23 ファイル実在）では宣言が字下げされるため、そのファイルから 1 クラスも拾わない**。しかも既知の対象が残る限り「走査が非空」の空振り検出も緑のままになる。ソーステキストから構造を導出するときは、**同じ意味を持つ別の書き方**（ファイルスコープ／ブロック形式の名前空間、`record` / `struct`、ネストと字下げ）を数え上げてから軸を決め、**抽出ロジック自体をサンプル入力で固定する**。字下げを許すだけではネストを拾うので、位置ではなく**波括弧の深さ**のような構造で判定する
- **違反の確定を早まらない**（同）。「禁止された順序」を検出する検査は、途中の状態だけを見て確定させると**規約を守っているコードで赤になる**（`StatusMessage = string.Empty;` → `CancelEdit();` → 完了メッセージ設定は正しい形だが、`CancelEdit()` を見た時点で確定させると違反になる）。判定に必要な範囲（ブロック・メソッド）の終わりまで遅らせること。誤検出はガード自体の寿命を縮める（#1786 の「規約が推奨する方向の変更でテストが赤になると、修正者を『対象から外す』方向へ誘導する」と同じ害）
- **走査を「読み飛ばす」処理は、読み飛ばした範囲に検査対象が無いことの証明にならない**（Issue #2101）。`ConfigureAwaitConventionTests` は外側の await 式を検査したあと式の末尾まで一気に進んでいたため、`ExecuteWithRetryAsync(async () => { … })` のラムダ本体（貸出・返却トランザクションの中心）の await を一度も走査しておらず、しかも内側の `ConfigureAwait` が外側の付け忘れを「式の中に ConfigureAwait がある」として適合扱いにしていた。**判定の範囲（外側の式のどこを見るか）と走査の範囲（次にどこから探すか）を別々に決める**
  - **検出の基点を `.git` に置かない**。git worktree では `.git` がファイルになり、`Directory.Exists(".git")` で親をたどる探索はリポジトリ内の worktree で**本体の作業ツリーを黙って検査する**（worktree で入れた違反が緑のまま通る）。基点は `TestPaths` から取り、`.git` の直書きは `TestPaths` の 1 か所に限る（`TestRootResolutionConventionTests`）
  - **「ファイルをまたぐ重複」を「重複」の代理にしない**。`ErrorCodeUniquenessConventionTests` は `Location` の相違で重複を判定していたため、同じファイル内で同じコードを 2 回使っても緑だった
  - **判定を実データのループとサンプル固定で二重に書かない**。サンプル側の関数だけを固定しても、ループ側の条件を緩めた変更は緑のまま通る（`BusyScopeDialogConventionTests`）
- **XAML の静的検査は、対象要素を 1 つに絞ってから属性を調べる**（Issue #2102）。ファイル全体への正規表現は、非貪欲でも**マッチの開始位置**が最初の `<TextBlock` に固定されるため、前にある自己終了タグから本体をまたいで別要素の属性を拾う（ステータス欄の Wrap を消しても、備考欄の Wrap に一致して緑だった）。`Views/Helpers/XamlElementInspection` の `EnumerateElements` / `EnumerateEnclosingElements` / `GetAttribute` を使う
  - **照合の前に必ず `StripXmlComments` を通す**。「`IsCancel="True"` は付けない」というコメントに一致して合格していた検査は、コメントを言い換えた人を**規約と逆の方向へ修正させる**（#1692 の極性の反転）
  - **順序を比べるなら、比較範囲（`<DataGrid.RowStyle>` 等）を切り出してから位置を比べる**。ファイル全体の `IndexOf` は最初の出現、つまり別の場所を返す
  - **表示用の値を、実際に適用される値の代理にしない**。最小文字サイズを設定画面の表示値から読むと、適用側（`App.ApplyFontSize`）を変えても緑になる
  - **検査を正しく直すと本番の違反が見つかることがある**。その場で直せないものは別 Issue を名指しした許可リストで固定し、**許可リストの各行がまだ違反であること**を対で表明する（解消したのに残った許可は、次の退行を黙って通す）
- **ガードで止まったことは、後続を「成功する側」に設定してから表明する**（Issue #2104）。認証ゲートの後ろにある確認ダイアログを未設定（loose モックの既定値 false ＝「いいえ」）のままにすると、ゲートを消しても確認で止まり、「統合しなかった」は別の理由で成り立つ。後続（確認・読み取り・書き込み）をすべて通る準備をしてから、そのガードの条件だけを崩し、**直後の処理が `Times.Never`** であることを見る。同じ準備でガードを通したときに最後まで進む対のテストも置く
- **2 つの経路に同じ値を仕込まない**（同）。事前読取の残高と再読取の残高、並べ替え前後の候補の順序、全項目で同じ詳細文言、DB の残高とちょうど一致する「前行残高＋受入」 — どれも経路を取り違えた実装で同じ結果になる。**経路ごとに異なる値**を置き、どちらを通ったかが結果から読めるようにする。上限の検査は上限を超える入力で行う（候補がすべて別の上限で先に止まる入力では、全体の上限に一度も届かない）
- **モックが「本体のコードを実行しない」箇所を数える**（同）。メッセンジャーをモックにすると、コンストラクターで登録した受信ハンドラーは一度も走らない（本物の `WeakReferenceMessenger` を渡す）。`ShowDialogAsync` のモックは初期化用の `Func` を実行しないので、ダイアログへ渡す引数を変えても緑になる（`Callback` で `Func` を捕まえ、ダイアログへ適用する。`Window` を実体化できないときは `FormatterServices.GetUninitializedObject` で確保して ViewModel だけを差し込む — `MainViewModelTests.CreateCompanionCountDialogWithoutWindow`）。テスト内に受信側の処理を書き写したテストは、本体の処理を検証していない
- **スキップ・除外を検証するテストは、「スキップしなければ結果が変わる入力」で書く**（Issue #2105）。帳票の事前チェックの「紙出納簿移行月は検算しない」は、挿入後のデータでも検算が合っていたため、スキップを消しても警告が出ず緑だった。入力を作り直したら、**同じ入力で条件だけを外すと結果が変わる対のテスト**を置いて、入力が偶然に整合していないことを表明する（摘要だけを差し替えると警告が出る）
- **否定の表明（`NotContain`）は、否定している文言が今の本体に存在するかを確かめる**（同）。既定分岐の文言が「予期しない**問題**」へ変わった後も `NotContain("予期しないエラー")` が 5 か所に残り、原理的に失敗しなかった。また否定の表明だけでは、退行が**別の整備済み文言**へ落ちた場合を検出できない（SQLite 例外のラップを外すと、#1986 で入った SQLite 用の分岐の文言になり、否定の表明をすべて満たす）。どの経路を通ったかを表明したいなら、その経路の文言と**完全一致**で比べる。摘要も同じで、部分一致は余分な区間の混入・並びの誤り・区間の脱落を見逃すため `Be(...)` で比べる
- **ロールバックは「件数 0」ではなく「書き込みが残らないこと」で観測する**（同）。`ImportedCount = 0` は本体が失敗時に代入する値で、コミットしてもロールバックしても同じになる。トランザクション内へ事前に 1 行書いておき、処理後に残っているかで見分ける（`CsvImportServiceTests.UseObservableTransaction`）。対の表明（成功時はその行が残る）を置かないと、観測手段が常に 0 を返す誤りに気付けない
- **設定値・引数で判定する本体は、既定値と異なる値で試し、既定値なら結果が変わる行を置く**（Issue #2106）。管理者ダッシュボードの残額警告は既定値と同じ 10,000 円、長期未返却は既定の 14 日でしか試しておらず、設定を読まずに `new AppSettings().WarningBalance` を使う実装・引数を無視して定数を使う実装でも緑だった（#1818）。しきい値 7,000 円なら「7,001 円・10,000 円は警告しない」行が、既定値で判定する実装を落とす。写像のテストも同じで、「全項目を写像する」と名乗るテストに既定値のままの項目があれば、その写像を消しても緑になる。写像は対応するプロパティの集合をリフレクションで走査して漏れを検出する（`DtoMapperTests`。`LedgerClonerCoverageTests` と同じ作法）
- **テストが、検証したい効果を自分で作らない**（同）。「失敗した Task の例外を観測済みにする」テストが `faulted.Exception` を読むと、その読み取り自体が例外を観測済みにするため、本体を空にしても緑になる。Task は下請けメソッドの中で作って手放し、GC 後の `TaskScheduler.UnobservedTaskException` の発火有無で観測する。GC が回ったことは、観測しない対照の Task が発火することで対に表明する（`DispatcherObservationTests`）。継続（`ContinueWith`）の中で投げた例外は呼び出し元へ届かないので、`NotThrow` は継続の中の try/catch を消しても緑になる
- **差し替えた継ぎ目は、受け取った引数を記録する**（同）。`protected virtual` の実測メソッドを固定値で差し替えると、本体が誤ったパスを渡しても結果が変わらない。受け取った値を記録して表明し、引数が無いときは本番と同じ側（「特定できない」）を返す（`ConnectionDiagnosticsServiceTests`）
- **部分一致の数値比較は、区切りを含めた完全な文言か構造化した値で比べる**（同）。`Contain(",0")` は管理番号 `,001` に、`Contain("1")` は「11件」に、`Contain("0")` は「-100」に一致する。CSV は列を分割して比べる。BOM のように読み込み側が吸収する性質は、読み込みを経ずにバイト列で見る（`Encoding.UTF8` の `ReadAllText` は BOM を読み飛ばす）
- **検出が確率的な回帰テストは、機会を増やし、確率的であることを書く**（同）。シード採番の `Interlocked.Increment` → `++` の退行は、採番が競合したときにしか重複を生まない。一斉起動を繰り返して機会を増やし、変異で実測した検出率をコメントに残す。1 回の緑を退行が無いことの証明として扱わない
- **テストを直すと、テストが通っていた本当の理由が分かることがある**（Issue #2105）。事前読取の履歴を「使う」テストは、重複判定の準備（`GetExistingDetailKeysAsync`）が無く、実際には 1 件も取り込んでいなかった。表明を足して赤になったら、本体を疑う前に準備が本番の経路を最後まで通しているかを確かめる
- **テストが使う固定値を本番の判定に紐付ける**。本番側が生成メソッドを持たないリテラル（例: 摘要「新規購入」）は、テスト側にも同じリテラルを書くと**両者の乖離を検出できない**。`Ledger.IsCarryover` のような本番の述語がその値を認識することを別テストで表明する。生成メソッドがある場合（`SummaryGenerator.GetMidYearCarryoverSummary` 等）は必ず生成結果を使う
- **モック構成が実 DB で成立し得るかを確かめる**（Issue #1728）。`ReportDataBuilderTests.SetupBasicMonth` は「前月に台帳あり／年度範囲は空」を仕込むが、年度範囲は前月を包含するため**実 DB では作れない状態**だった。矛盾した前提の上に立つテストは、実運用で起きる状態（年度内が丸ごと空）を一度も通らないため、そこに潜むバグを素通りさせる。既存ヘルパーを流用する前に「この組み合わせは実際に作れるか」を自問し、作れないなら専用ヘルパーを新設する（`SetupIdleFiscalYear`）
- **サービスをまたぐ不変条件は、実際に接続して表明する**（Issue #1728）。「帳票の集計を直したのでプリフライトの誤警告も消える」ことは、`ReportPreflightChecker` へ手組みの `MonthlyReportData` を渡すテストでは表現できない（修正前後で入力が同じになる）。上流の実出力を下流へ通すこと
- **手動確認をお願いする前に、成果物そのものを検証できないか検討する**（Issue #1728）。「実機で用意しにくいデータの帳票」は人手に頼りたくなるが、`ReportServiceTests` は ClosedXML で実際に Excel を書き出してセル値を読み返している。出力物を機械検証できるなら、手動確認は印刷プレビューの体裁など本当に目視が要る範囲まで絞れる

## 実装前の確認
- 機能の仕様を正しく理解してからテストを書くこと
- 不明な点があれば、仮の実装ではなく、ユーザーに確認すること

## テスト追加・修正時
- テスト設計書（`docs/design/07_テスト設計書.md`）も同期更新すること
- Stop hook（`.claude/hooks/check-doc-sync.sh`）がコード変更のあるセッション終了時に「ドキュメント更新が必要か」の自己確認プロンプトを注入する。テスト設計書の同期漏れもこの自問で検出されやすくなる。環境変数 `SKIP_DOC_SYNC_CHECK=1` でバイパス可
- 件数表 §1.1a の同期は CI で自動検証される（`.github/workflows/test-count-sync-check.yml`、Issue #1546）。乖離があると PR がブロックされる。
- **§2 のクラス別件数（``| `Namespace/ClassTests` | 件数 | 観点 |`` 形式の行）も同じ CI で検証される**（Issue #1889）。走査範囲は `## 2.` 見出しから次の `##` 見出しまでで、件数セルの書式から外れた行（`| 12 件 |` / `| **12** |` / 名前セルに注記が付いた行）は読み飛ばさず fail する。ただし**検証されるのは「表に既に載っている行」だけ**で、テストクラスを新設して §2 へ行を足し忘れた場合は検出できない。**クラスを新設したら §2 へ行を足すのは手作業**であり、CI が緑であることはその漏れが無いことを意味しない。
