# テストコード作成時の厳守事項

## テストコードの品質
- テストは必ず実際の機能を検証すること
- `true.Should().BeTrue()` のような意味のないアサーションは絶対に書かない
- 各テストケースは具体的な入力と期待される出力を検証すること
- モックは必要最小限に留め、実際の動作に近い形でテストすること

## ハードコーディングの禁止
- テストを通すためだけのハードコードは絶対に禁止
- 本番コードに `if (testMode)` のような条件分岐を入れない
- テスト用の特別な値（マジックナンバー）を本番コードに埋め込まない
- 環境変数や設定ファイルを使用して、テスト環境と本番環境を適切に分離すること

## テスト実装の原則
- テストが失敗する状態から始めること（Red-Green-Refactor）
- 境界値、異常系、エラーケースも必ずテストすること
- カバレッジだけでなく、実際の品質を重視すること
- テストケース名は何をテストしているか明確に記述すること

## 「通るが目的を果たさないテスト」の典型（Issue #1692 で実際に踏んだ）

書いた本人が満足して終わりがちな型。**そのテストが防ぎたいリグレッションを、実際に起こして落ちることを確かめる**のが唯一の検証手段。

- **並列化の回帰は「順序」ではなく「同時実行数」で検出する**。Moq の `MockSequence` は呼び出し順序しか見ないため、`Task.WhenAll` へ書き換えても開始順序は変わらず**素通りする**。リポジトリのモックに保持区間を計測させ `maxConcurrentCalls == 1` を表明すること（`DashboardServiceTests` / `AdminDashboardServiceTests` の Issue #1452 回帰テストが参考実装）。SQLite は同一接続での並列コマンドを許さないため、この検出力は実害に直結する
- **呼び出し先を別オーバーロードへ切り替える修正では、「切り替え元」のオーバーロードもモックへ設定する**（Issue #1745）。loose な `Mock<T>` は未設定メソッドに**既定値**（`Task<int>` なら 0、`Task<bool>` なら false）を返すため、旧オーバーロードを未設定のままにすると**修正前のコードでは副作用が一切起きない**。「ロールバックされたので DB は 0 行」という表明が、旧コードでは「そもそも 1 行も書かれていないので 0 行」で通ってしまう。#1745 では `InsertAsync(Ledger)`（tx なし＝autocommit）と `InsertAsync(Ledger, SQLiteTransaction)` の**両方**を実リポジトリへ委譲して初めて、修正前コードで 5 件すべてが赤になった
  - あわせて **`Verify(…, Times.Never)` で「旧オーバーロードを呼んでいないこと」を表明する**。行数の表明だけだと、退行したときに「なぜ落ちたか」がテスト名から読み取れない
  - **「モックの既定値で通っていないか」は、修正前のコードへ実際に当てて確かめる**のが唯一の方法（`git checkout origin/main -- <本体ファイル>` → テスト実行 → 復元）。この Issue では 5 件中 5 件が赤になることと、その落ち方（途中行エラー時に 2 行が残存する等）が指摘どおりの症状であることを同時に確認できた
- **本番の判定に使う閾値を、テスト側で作り直さない**（Issue #1821）。同じ意味に見える式でも処理系が違えば境界が食い違う。6年保持の削除条件は SQL の `date('now', '-6 years', 'localtime')` だが、テストが `DateTime.Now.AddYears(-6)` で境界日を組み立てていたため、**うるう日（2/29）に実行したときだけ**赤くなる状態だった（.NET は 6 年前を 2/28 へ丸め、SQLite は 2/29 を 3/1 へ正規化する）。閾値は**本番と同じ場所に評価させて取得する**（`DbContextCleanupTests.GetRetentionThresholdDate` は実接続で同じ式を SELECT する）。これで「テスト側の再実装がいつか本番とずれる」という形ごと無くなる
  - **乖離そのものを 1 件のテストで固定する**。閾値を本番から取ると、正常時は両者が一致するため「なぜこの手間が要るのか」がコードから読み取れなくなる。`date('2028-02-29', '-6 years')` = `2022-03-01` と `AddYears(-6)` = `2022-02-28` を並べて表明しておくと、次に読む人が調査をやり直さずに済む
  - **日付・時刻に限らない**。丸め・切り捨て・照合順序・数値の精度など、**C# と SQLite の両方に実装がある演算**はすべて同じ罠を持つ
- **例外の表明の「裏返し」を戻り値で書かない**（Issue #1882）。`string produced = null; act = () => produced = Sut(0); act.Should().Throw<T>(); produced.Should().BeNull();` の後半は、C# で `throw` と `return` が同時に起きない以上**必ず自明に真**であり、検出力を持たない。想定した退行（`return 既定値;` へ緩める）が捕まるのは前半の `Throw` が落ちるからで、後半は 1 度も働かない。**対の表明は「反対側の状態」ではなく「別の観測軸」で書く** — #1882 は「定義域外で基底名を返さないこと」ではなく「**定義域内のどの件数でも基底名と一致しないこと**」（1〜100 と `int.MaxValue` を走査）へ置き換えて検出力を得た（1 点だけの表明では、書式から接尾辞が落ちる退行を大きな入力で見逃す）
- **`await act.Should().NotThrowAsync()` だけで終わらせない**。「例外が出ない」は結果を何も検証していない。返り値・副作用のどちらかを必ず具体値で表明する
- **fire-and-forget の完了を固定時間の待機で待たない**。`Task.Delay(50)` は遅いマシンで不安定になる。モックの `Callback` で `TaskCompletionSource` を立て、`Task.WhenAny` に十分長いタイムアウト（5秒程度）を添えて待つ
- **`NotBeEmpty()` / `NotBeNull()` で止めない**。例: 積み上げ棒グラフの Y 軸目盛りを `NotBeEmpty` で確認しても、「系列ごとの最大値でスケールを作る」誤り（正しくは月合計）を検出できない。具体値まで表明する
- **同じ規約の検査を 2 か所に書かない**。用語ガード（「ICカード」単独表記の禁止）は `UserFacingTextConventionTests` が `Views/` 配下を再帰走査しており新画面も自動で対象になる。画面ごとに簡易版を重ねると許容複合語の定義が分かれ、片方だけ更新されたときに検査が食い違う
  - **検査の下請け処理（ソースのサニタイズ・波括弧対応の抽出）も同じ**。`TestSourceInspection` の XML doc は「新規の規約テストは本ヘルパーを使い、複製をこれ以上増やさないこと」と明記しているが、Issue #1764 の初版はこれを見落として 4 つ目の私的コピーを書き、**そのヘルパーが既に解決済みだった欠陥をそのまま再現した**（行単位で剥がす実装は複数行にまたがる `@"..."` を追えず、2 行目以降がコードとして扱われて波括弧の対応がファイル末尾まで狂う ＝ ガードが緑のまま無力化する）。**重複の回避は整理整頓ではなく正しさの問題**である。静的検査を書く前に `tests/ICCardManager.Tests/TestSourceInspection.cs` と `TestPaths.cs` を読むこと
  - **行番号を報告する検査には `ToCodeOnlyPreservingLines` を使う**（`ToCodeOnly` は複数行ブロックコメントを空白 1 文字へ畳むため行番号がずれる）
- **ガードの「検出漏れ」は緑になる — 対象の絞り込みが fail-open になっていないか確認する**（Issue #1764）。検査対象のファイルを「特定のトークンを含むもの」で絞ると、**そのトークンの表記ゆれ（`this.` 修飾など）を持つファイルは走査から丸ごと外れ、1 件も検査されないままテストが緑になる**。絞り込みの条件は検出側の条件と同一にし、表記ゆれを含めて拾えることをサンプル入力で固定する
- **違反の確定を早まらない**（同）。「禁止された順序」を検出する検査は、途中の状態だけを見て確定させると**規約を守っているコードで赤になる**（`StatusMessage = string.Empty;` → `CancelEdit();` → 完了メッセージ設定は正しい形だが、`CancelEdit()` を見た時点で確定させると違反になる）。判定に必要な範囲（ブロック・メソッド）の終わりまで遅らせること。誤検出はガード自体の寿命を縮める（#1786 の「規約が推奨する方向の変更でテストが赤になると、修正者を『対象から外す』方向へ誘導する」と同じ害）
- **テストが使う固定値を本番の判定に紐付ける**。本番側が生成メソッドを持たないリテラル（例: 摘要「新規購入」）は、テスト側にも同じリテラルを書くと**両者の乖離を検出できない**。`Ledger.IsCarryover` のような本番の述語がその値を認識することを別テストで表明する。生成メソッドがある場合（`SummaryGenerator.GetMidYearCarryoverSummary` 等）は必ず生成結果を使う
- **モック構成が実 DB で成立し得るかを確かめる**（Issue #1728）。`ReportDataBuilderTests.SetupBasicMonth` は「前月に台帳あり／年度範囲は空」を仕込むが、年度範囲は前月を包含するため**実 DB では作れない状態**だった。矛盾した前提の上に立つテストは、実運用で起きる状態（年度内が丸ごと空）を一度も通らないため、そこに潜むバグを素通りさせる。既存ヘルパーを流用する前に「この組み合わせは実際に作れるか」を自問し、作れないなら専用ヘルパーを新設する（`SetupIdleFiscalYear`）
- **サービスをまたぐ不変条件は、実際に接続して表明する**（Issue #1728）。「帳票の集計を直したのでプリフライトの誤警告も消える」ことは、`ReportPreflightChecker` へ手組みの `MonthlyReportData` を渡すテストでは表現できない（修正前後で入力が同じになる）。上流の実出力を下流へ通すこと
- **手動確認をお願いする前に、成果物そのものを検証できないか検討する**（Issue #1728）。「実機で用意しにくいデータの帳票」は人手に頼りたくなるが、`ReportServiceTests` は ClosedXML で実際に Excel を書き出してセル値を読み返している。出力物を機械検証できるなら、手動確認は印刷プレビューの体裁など本当に目視が要る範囲まで絞れる

## 実装前の確認
- 機能の仕様を正しく理解してからテストを書くこと
- 不明な点があれば、仮の実装ではなく、ユーザーに確認すること

## テスト追加・修正時
- テスト設計書（`docs/design/07_テスト設計書.md`）も同期更新すること
- Stop hook（`.claude/hooks/check-doc-sync.sh`）がコード変更のあるセッション終了時に「ドキュメント更新が必要か」の自己確認プロンプトを注入する。テスト設計書の同期漏れもこの自問で検出されやすくなる。環境変数 `SKIP_DOC_SYNC_CHECK=1` でバイパス可
- 件数表 §1.1a の同期は CI で自動検証される（`.github/workflows/test-count-sync-check.yml`、Issue #1546）。乖離があると PR がブロックされる。
- **§2 のクラス別件数（`| `Namespace/ClassTests` | 件数 | 観点 |` 形式の行）も同じ CI で検証される**（Issue #1889）。ただし**検証されるのは「表に既に載っている行」だけ**で、テストクラスを新設して §2 へ行を足し忘れた場合は検出できない。**クラスを新設したら §2 へ行を足すのは手作業**であり、CI が緑であることはその漏れが無いことを意味しない。
