# 主要な業務ロジック

## 状態遷移
1. **職員証タッチ待ち** → 職員証タッチ → **交通系ICカードタッチ待ち**
2. **交通系ICカードタッチ待ち** → 交通系ICカードタッチ → 貸出or返却処理 → **職員証タッチ待ち**
3. タイムアウト（60秒） → **職員証タッチ待ち**

## 貸出・返却フロー
1. 職員証タッチ → IDm記録、状態遷移
2. 交通系ICカードタッチ → 状態判定
   - 未貸出(is_lent=0) → 貸出処理
   - 貸出中(is_lent=1) → 返却処理
3. 30秒以内に同一カード再タッチ → 逆処理（貸出→返却、返却→貸出）

> **「30秒」は既定値で変更可能**: しきい値は `AppOptions.RetouchWindowSeconds`（既定 `AppConstants.DefaultCardRetouchTimeoutSeconds = 30`）で設定できる。本書で「30秒」と書く箇所はこの既定値を指す。
>
> **逆処理は「職員証タッチ待ち」状態でも発生する**: 上記フローは線形に見えるが、再タッチ逆処理は交通系ICカードタッチ待ち状態に限定されない。職員証を再タッチせずに同一の交通系ICカードを時間内に再タッチした場合も、`MainViewModel.HandleCardInStaffWaitingStateAsync` が `IsRetouchWithinTimeout` を判定して `Process30SecondRuleAsync`（逆処理）を実行する。

### 逆処理を「誰の操作」として記録するか（Issue #1729）

`IsRetouchWithinTimeout` は**交通系ICカードの IDm しか見ない**（職員証は判定条件に含まれない）。したがって**前回とは別の職員が続けて操作した場合も逆処理が発動する**。誰の操作として記録するかは操作者の確定状況で決まる。

| 再タッチ時の状態 | `_currentStaffIdm` | 記録する操作者 |
|------------------|--------------------|----------------|
| ICカードタッチ待ち（職員証タッチ済み） | 確定済み | **いまタッチした職員**（上書き禁止） |
| 職員証タッチ待ち | null | 前回操作者（`_lastProcessedStaffIdm`）で補完 |
| 職員証タッチ待ち かつ 前回操作者も null | null | 記録せずエラー通知 |

- **「無い値の補完」と「有る値の上書き」を同じ代入文で書かない**。`Process30SecondRuleAsync` の `_currentStaffIdm = _lastProcessedStaffIdm;` は「操作者不在時の補完」が意図（XML コメントもその趣旨）だったが、無条件代入だったため職員証タッチ済みの経路では**確定済みの操作者を捨てて前回操作者に差し替えていた**。`ledger.StaffName` / `ic_card.lender_idm` / `operation_log` が実際の操作者と食い違い、長期未返却の督促も誤った職員へ向かう
- **「意図が補完なら、補完の条件を書く」**。`if (string.IsNullOrEmpty(_currentStaffIdm))` を付けるだけで意図とコードが一致する。コメントで意図を書いても、コードが無条件なら無条件に動く
- **null 判定を経路判定の代理に使うなら、その等価性を確かめて明記する**。`AppState.WaitingForStaffCard` へ遷移する経路は `MainViewModel.ResetState()` ただ 1 つで、そこで `_currentStaffIdm` は必ず null になるため「未確定＝職員証タッチ待ち経路」が成立する。この前提が崩れる遷移を足すときは本規則を見直すこと
- **エラー分岐（操作者が現在も前回も不明）は到達可能**。仮想タッチ（Issue #1577）は `LendingService.ReturnAsync` を直接呼ぶため `LastProcessedCardIdm` は立つが `MainViewModel` の前回操作者は立たない。「到達不能だから」と削らない
- **30秒ルールの武装（`LastProcessedCardIdm` / `LastProcessedTime` / `LastOperationType`）は台帳への記録が確定した直後に行う**（Issue #1805）。`ReturnAsync` はコミット後に残額の解決・残額警告の DB I/O を持つため、その後ろに置くと後処理の失敗で「返却は記録済みなのに未武装・`Success=false`」になり、「返却失敗・もう一度タッチ」の案内どおりに再タッチした職員の操作が貸出として新規に記録される。`Success` は「記録が確定した」ことだけを表し、付帯情報（残額・残額警告）の欠落は `LendingResult.HasPostCommitFailure` で別途伝える（詳細は `db-write-conventions.md` の「コミット確定後の後処理を、成否の判定に巻き込まない」）
- **操作者の帰属はテストで表明する**。`CurrentState` や「例外が出ない」ではなく、**台帳に記録された IDm・氏名**（`ledger.LenderIdm` / `StaffName`）と `UpdateLentStatusAsync` の第4引数を具体値で検証する（`MainViewModelIntegrationTests` の `Retouch30Sec_*` 3件が参考実装）

### 返却時に記録する利用履歴の下限は「導入行の日付」（Issue #2237）

返却時は、交通系ICカードに残る直近 20 件のうち**カードの導入行（`Ledger.IsInitialRecordSummary`）の日付以降**を記録する（`LendingService.ResolveUsageLowerBound`）。貸出日の前後は問わない。導入行が無いカードだけ、従来どおり貸出日の 7 日前まで。

- **下限は「台帳が計上済みである境界」から決める。時間の幅で決めない**。旧実装の「貸出日の 7 日前」は根拠が無く、7 日より古い未記録の利用を捨てる一方、登録から 7 日以内に貸し出すと導入行より前（＝導入行の残高に含まれる）利用を取り込んで二重に計上していた
- **二重記録の防止は下限ではなく既存明細との照合（#326）の役目**。照合の取得範囲は抽出した履歴の最古日から決まるので、下限を広げても追随する。下限で照合を兼ねようとしない
- **照合できない記録済みの利用は、下限で守る**。明細を持たない利用行（履歴の「追加」で手入力した行など）は照合のキーを持たないので、その最新日の翌日より前は記録しない（`GetLatestLedgerDateWithoutDetailsAsync`）。ただし**貸出日を超えない**（貸出当日・未来日付の手入力の行で、今回の貸出中の利用をすべて捨てないため）。照合の範囲も台帳行の日付だけでなく明細の利用日で拾う（日付をまたぐ統合がある）
- **導入行が認識できないときは、挙動を変えない側へ倒す**。どこまでが計上済みかの根拠が無いまま下限を外すと、計上済みの利用を取り込み得る
- 詳細（帰属・削除した行・締めた月の扱い）は 04_機能設計書 §2.4.1

### 履歴を読めなかった返却は記録しない — 「カードが載っていない」は正常なゼロ件ではない（Issue #2301）

返却は `ICardReader.TryReadHistoryAsync` が `Fail` なら記録せずに中断する（カードは貸出中のまま、「職員証のタッチから」やり直す案内。30秒ルールも武装しない）。`Ok` の空リストは**対象のカードを最後まで読めて利用が本当に 0 件**だった場合に限る。

- **「区別できる」と宣言した Result 型の中で、失敗を成功へ畳まない**。`TryReadHistoryAsync` は #1169 で「リーダーエラーと履歴ゼロ件を区別できる」として入れたのに、読み取り前の IDm の不一致（別のカード）を「既存挙動の維持」として `Ok(空)` にしていた。区別の目的は呼び出し元（返却）が記録してよいかを決めることであり、載っていない状態は記録してよい側ではない
- **外部ライブラリの振る舞いを推測で書かず、確かめる**。Issue と初版の修正は「felicalib はカード無しで null を返す」「読めなかったブロックを null で返す」を前提にしていたが、FelicaLib.DotNet 1.2.67 を逆アセンブルするとどちらも例外を投げ、かつ呼び出しのたびにポーリングし直すため**確認の後に載せ替えると別のカードの履歴を読む**ことが分かった。読み取りの後にも IDm を確かめるのはこのため（`FelicaCardReader.ReadHistoryCore`）
- **カードが離れたことはリーダーの故障ではない**。返却（`TryReadHistoryAsync`）では `Error` イベント（警告エリアの「カードリーダーエラー」）を発火せず、トーストも「交通系ICカードが離れました」とする（`CardReaderException.IsCardRemoved`）。利用者に見える表示まで直さないと、修正の説明（故障ではない）と画面（故障と言う）が食い違う
- **ある経路の不具合を直すために、同じメソッドを共有する別の経路の挙動を変えない**。後方互換の `ReadHistoryAsync`（カード登録時の事前読み取り）は従来どおり読み取りの前・途中の例外で `Error` を発火し、後の確認ができなかっただけなら読めた明細を返す。利用者に見える挙動で変えたのは、後の確認で**別のカード**が載っていた場合だけ（別のカードの履歴を登録しないため、空のリスト）
- felicalib は `IFelicaDevice` の継ぎ目で差し替えて単体テストで再現する（04_機能設計書 §2.4）

### 返却確認 — 返却直後の履歴自動表示（Issue #1907）

返却後処理（バス停名入力 → 同行者数入力）の**後**に、返却したカードの履歴をメイン画面へ自動表示し、今回記録した行を強調して確認を促す（`HistoryPanelViewModel.ShowReturnHistoryReviewAsync`。設定 `AppSettings.ShowHistoryOnReturn`、既定 有効）。

- **閉じる契機は次の職員証タッチ**（`CloseReturnHistoryReviewIfUntouched`）。秒数で閉じる方式（#2009）は「複数行を読んでいる途中で閉じる」故障を避けられないため採らない。**職員が履歴エリアを操作したら閉じない**（`MarkReturnHistoryReviewTouched`。手動で開いた履歴と同じ扱い）
- **#186（カードタッチでメイン画面を変更しない）の意図的な例外**。閉じる・置き換えるのは本システム自身が自動で開いたパネルに限り、職員が使っている履歴（手動で開いた／返却確認を操作した）は**表示中のカードが同じでも**奪わずトーストで促す（同じカードの行を統合のためにチェックしている最中に別の職員がそのカードを返却し得る。#1923）
- **返却後の設定読み取りは 1 回**（バス停入力・同行者数入力・返却確認で共有）。コミット後の I/O を増やさない（#1805）
- **表示期間の開始日は月の 1 日へ丸める**（コードレビューで検出）。前月以前の利用（3/31 乗車・4/1 返却）へ遡るとき、日付単位の開始日を渡すと `GetPrecedingBalanceAsync` が返す「その月の 1 日より前の残高」が合成する繰越行（#1155）と残高チェーンのシード（#1740）の両方でずれ、隠れた行のぶん画面上の「受入 − 払出 = 残額」が合わなくなる。シードの誤りは循環する日でチェーンを回転させ得る（#1999）。**期間を月単位で扱う画面に日付単位の値を渡さない**
- 詳細は 04_機能設計書 §4.6・03_画面設計書 §3.7「返却確認」

## バス利用判別ロジック
```
IF entry_station（乗車駅）が空欄 AND
   exit_station（降車駅）が空欄 AND
   is_charge = false AND
   is_point_redemption = false
THEN
   → バス利用（is_bus = true）
```

- **この条件の否定要因（`is_point_redemption`）が後から立つなら、判定もやり直す**（Issue #1948）。`FelicaHistoryBlockDecoder.Decode` は `isBus` を Issue #942 の暗黙的ポイント還元フォールバック（金額の符号で還元と判定する）より**前に**確定しており、フォールバックが後から `isPointRedemption` を立てても `isBus` は再計算されなかった。結果、業務ルール上あり得ない `IsBus && IsPointRedemption` の複合状態が 6 年保存の `ledger_detail` に入っていた。
  - **「後段が優先順位で吸収している」を実害なしの根拠にしない**。#1253 はこの複合状態を「`SummaryGenerator` が `!IsPointRedemption` でフィルタするため実害なし」としてテストで固定していたが、その根拠は**摘要生成しか見ていない**。`RouteDisplayFormatter` はポイント還元をバスより先に判定するので同様に無害だが、`BusStopInputViewModel` は 4 箇所すべてが `d => d.IsBus` だけで対象を絞る。履歴統合（`LedgerMergeService`）でバス利用行とポイント還元行が 1 行になると、この複合状態がバス停名入力に幽霊行として並び、入力しても摘要には現れず `ledger_detail.bus_stops` にだけ値が残る。**「順序で吸収している」は消費側の数だけ検算が要り、消費側が増えるたびに再発する**（#1883「食い違った状態を表現できなくする」／#1763「同じ判断を配らない」）
  - **設計書が「意図した順序」を書き、実装が別の順序で動いていた**。04_機能設計書 §6.3 は「§4 の判別より前にこの補正が適用される」と書いていたが、金額計算に前レコードの残高が要るため実装は逆順だった。**順序に依存する不変条件は、設計書の記述と実装の実行順を突き合わせて確かめる**
  - **回帰は「欠陥を突く側」（バス判定の 2 経路それぞれ）と「正当なバス判定を潰していない側」（残高減少の通常利用／前回レコードなしでフォールバック非発動）を対で置く**。後者が無いと `isBus` を無条件に `false` にした実装でも緑になる。あわせて入力の全域（利用種別 × 駅コード × 残高増減 × リゾルバ）を走査する不変条件テストを 1 件置く（#1812）

## 同一とみなす駅・バス停（同一視グループ、Issue #1905）

同一視グループ（`SummaryRules.TransferStationGroups`）は駅名の文字列比較だけで判定するため、**バス停にもそのまま効く**。設定の正は DB（`settings` のキー `transfer_station_groups`）で、システム管理画面（F6）→「摘要の設定」から編集する。`AppSettings` の一括保存には含めない（#1726）。

乗継統合・往復検出・同一視の実装上の規約（世代の捕捉、候補探索、循環の扱い、括弧の抽出など）は `summary-generation.md` にある（条件付きロード）。**`SummaryGenerator` / `LedgerMergeService` / 摘要を読み返すコードを変更する前に読むこと。**

## 不整合を「報告する行」と「直すべき行」は一致しない（Issue #2007）

残高チェーンの検査（`LedgerConsistencyChecker`）は「前行の残額 ＋ 受入 − 払出 ≠ 当行の残額」となった**当行**を報告する。
だが導入行（カード登録時の「新規購入」「○月から繰越」「前年度より繰越」。`Ledger.IsInitialRecord`）の残高は
**手入力の繰越額がカード実残高より優先**して書かれ（`BuildInitialLedgerAsync`）、以後の利用行はカード由来で正しいため、
導入時の誤りではチェーンが**導入行の直後の 1 か所だけ**で切れ、報告されるのは**正しい 2 行目**になる。

- **検知結果をそのまま強調・案内すると、正しい行を誤った行に合わせて書き換える誘導になる**。原因の形状を名指しできるときは、
  報告位置ではなく直すべき行（導入行）と直すべき値（直後の残額 − 受入 ＋ 払出）を示す（`DetectInitialBalanceCorrection`）
- **形状の判定は厳密に**。親不整合が 2 行目の 1 件だけ・詳細不整合は 2 行目の先頭明細の写像だけ・逆算が 0 以上。
  複数箇所で切れている・先頭が導入行でない形は 1 行の訂正で直らないので提案しない
- **導入行は受入と残額の両方を持つ**（○月から繰越は受入 0）。片方だけ直すと帳票の「受入 − 払出 = 残額」が崩れたまま残るため、
  1 操作で揃える手段（「逆算した金額を適用」）を用意し、受入 ≠ 残額は保存前に警告する。「受入も直すか」の判断は
  `BuildInitialLedgerAsync` の `hasIncome` と同じ `Ledger.InitialRecordCarriesIncome` 1 つに寄せる（#1763）
- **付け替えたマーカーの意味は、摘要ではなくマーカー自身のフラグで表す**（コードレビューで検出）。摘要で分岐すると、
  CSV 取込や編集で導入行が先頭でなくなった場合に、前方計算の期待値を「逆算した残高」と偽って案内する（#1883）
- **直すべき行が表示期間の外にあり得るなら、案内は期間ごと連れて行く**。導入行は何年も前になり得るため、警告クリックは
  導入行の日付から履歴を開く。期間ラベルも範囲表記にしないと「その月を表示中」と読まれる
- **自動修正はしない**。逆算値が正しいのは「後続がカード由来」という前提の上でしかなく、6 年保存の台帳を黙って書き換えない

## 残額警告のしきい値の境界は「以下」（Issue #1998）

残額が `AppSettings.WarningBalance`（既定 10,000 円）**以下**のとき警告する。判定は
`Common/BalanceWarningPolicy.IsLowBalance` ただ 1 つで、返却トースト（`LendingService`）・
残額ダッシュボード（`DashboardService`）・管理者ダッシュボード（`AdminDashboardService`）・
警告一覧（`WarningService`）はすべてこれに委譲する。

- **判定を 1 か所へ寄せても、その判定を「説明する文言」は寄らない**（Issue #2077）。#1998 の是正から
  返却トーストの文言だけが `⚠️ 残額不足（<10,000円）` のまま残り、しきい値ちょうどの残額に対して
  **満たしていない条件を理由として表示**していた。#1998 の静的検査は比較演算子しか見ないので、
  表記の食い違いは**原理的に検出対象外**だった。文言の生成も同じクラス
  （`BalanceWarningPolicy.FormatLowBalanceNotice`）へ置き、境界を動かすときに判定と表記の
  両方が視野に入るようにする（#1763）。**境界を動かす修正では「その境界を述べている文言」を
  併せて数える**
  - **核（`FormatLowBalanceThresholdLabel`）と装飾（トーストの `⚠️ `）は分ける**。境界を述べる表記は
    管理者ダッシュボードの Excel 出力（集計見出し）にもあり、装飾を焼き込んだ文言しか無いと再利用できない。
    **再利用できない形にすると、「判定と表記が同じ場所にある」という目的が消費側の数だけ半分ずつ失われる**
    （コードレビューで検出）
  - 表記は `≦` ではなく「10,000円以下」と書く。Excel 出力の見出し（`残額不足（N円以下）`）・
    管理者マニュアルと同じ語彙で、読み手は庶務担当者である（#1817「近くにある既存文言の語彙に揃える」）
  - 回帰は**リテラルの固定**と**「文言が示す境界と判定の境界が一致すること」**を分けて表明する。
    前者だけだと判定側を「未満」へ戻した実装でも緑になる。文言を組み立て直す 2 か所目が現れないことは
    静的検査（`BalanceWarningNoticeTextConventionTests`）が「禁止形の不在」と「委譲の存在」を対で見る
- **比較を各サービスへ書くと、1 か所だけ境界がずれる**。しきい値ちょうどの残額で返却したとき、
  トーストは警告を出さないのにダッシュボードと警告一覧は残額不足と表示する——**同じ操作の直後に、
  同じカードについて「警告なし」と「警告あり」が並ぶ**。チャージは千円単位なので境界ちょうどは日常的に発生する
- **「4 箇所を揃える」ではなく「1 か所へ寄せる」**。揃えるだけでは 5 か所目が増えたときに同じ形が再発する。
  `IcCard.IsInOperation` へ寄せた #1947 と同じ判断（#1763「同じ判断を配らない」）
- **設計書とテストが食い違ったら、どちらが仕様の宣言かを見る**。04_機能設計書 §7.1 の設定値表・
  03_画面設計書・管理者マニュアル・Excel 出力見出しはいずれも「以下」で、`<` を支持していたのは
  既存テスト 1 件と、それを転記した 07_テスト設計書のテストカタログ行だけだった。
  **テストカタログは業務ルールの宣言ではなく既存テストの写し**であり、テストが仕様を後追いで固定した形
- **しきい値判定は交通系固有ではない**（「補充が必要な物品を見つける」判定）ため `Common` に置く
  （`domain-boundaries.md` の決定木①）
- **回帰は「境界の挙動」と「判定の所在」を別々に固定する**。後者（`BalanceWarningComparisonConventionTests`）は
  「直書きの比較の不在」と「4 サービスが共通の判定を使っていること」を対で表明する — 前者だけだと
  4 か所から判定を丸ごと消した実装でも緑になる

## 複数名利用の「外N名」は導出であって保存値ではない（Issue #1906）

複数名が同一経路を 1 枚の交通系ICカードで利用した場合、物品出納簿の氏名欄は「博多 花子 外１名」とまとめて記載する（物品会計事務の手引き）。人数は `ledger.companion_count`（本人を含まない同行者数、既定 0）に保存し、**「外N名」の文字列は `Common/StaffNameFormatter.Format` が表示時に導出する**。

- **`staff_name` には「外N名」を書き込まない**。書き込むと職員マスタとの照合（行編集の `SelectedStaff` 復元、管理者ダッシュボードの系列名解決）が壊れ、CSV の往復で氏名が変質する（#1808）。消費側（履歴一覧 `LedgerDto.DisplayStaffName`・帳票 `ReportRowBuilder`）はそれぞれ導出する
- **入力経路は返却時ダイアログ（`CompanionCountInputDialog`、バス停名入力の後）と履歴の行編集の 2 つ**。返却時は 1 以上の行だけ `UpdateCompanionCountAsync` で書く（0 は INSERT 済み）。保存に失敗しても返却は記録済みなので「再タッチ」と案内しない（#1725）
- **返却フローに置く入力ダイアログは、放置されたときの出口を必ず用意する**（Issue #2009）。本システムは 1 台のカードリーダーを複数職員で共有するため、開いたままのダイアログは**次の職員の貸出・返却を物理的に塞ぐ**。既定 30 秒（`AppConstants.DefaultCompanionCountInputTimeoutSeconds` / 設定 `AppSettings.CompanionCountInputTimeoutSeconds`）で「外0名」として自動的に閉じ、書き込みは行わない（返却時に 0 で INSERT 済み）。ほとんどの利用が単独乗車であることが「無操作＝0」と解釈してよい根拠であり、**この前提が成り立たない入力（バス停名・金額）へ同じ設計を持ち込まない**
  - **自動で閉じる機能の主要な故障は「入力途中で閉じること」**。入力した値が保存されないまま失われる。取り消しの検知は入力欄の変更（`Items` の `PropertyChanged`）だけでなく、**キー・クリック・ホイールのすべて**（`PreviewKeyDown` / `PreviewMouseDown` / `PreviewMouseWheel`）で行う。複数行を読むためのスクロールはクリックを伴わないため、`PreviewMouseDown` だけでは拾えない
  - **「常に尋ねる／尋ねない」を別のフラグにしない**。秒数 1 つで表し、**0 を「自動的に閉じない（必ず尋ねる）」**とする。フラグと秒数を別々に持つと矛盾する組み合わせを表現できてしまう（#1763 / #1883）。既存の「スキップ」設定（ダイアログ自体を出さない）とは目的が違うので併存させ、スキップ有効時は秒数欄を操作不可にする
  - **カウントダウンは View ではなく ViewModel に置く**。`DispatcherTimer` を View へ直書きすると、境界（期限の 1 つ手前では閉じない／期限で閉じる）を単体テストで固定できない。`ITimerFactory` を注入すれば `TestTimer.SimulateTicks` で実時間を待たずに検証できる
  - **連続していない許容範囲を `NumericRangeValidationRule`（Min〜Max）で近似しない**。「0 または 5〜300」を Min=0 / Max=300 と書くと 1〜4 が**入力時だけ妥当に見えて保存時に弾かれる**。判定と文言は 1 か所（`Common/CompanionCountTimeoutRange`）へ置き、入力時のルールと保存時の `ValidationService` の両方が委譲する。回帰は「全入力で両者の判定が一致すること」を走査して固定する — 個別の境界テストだけでは、2 つの実装が別々にずれても互いの期待値どおりで緑になる
  - **回帰は「閉じる側」と「閉じない側」を対で置く**。前者だけだと「常に即閉じる」実装でも緑になる。検出力は変異で実測する（購読を外すと「入力を始めたら取り消す」1 件だけが赤）
- **摘要は変えない**。CSV は利用者列を生の氏名のまま出し、専用列「同行者数」（末尾）で往復させる。列を持たない旧形式は 0 として取り込む
- 統合は**統合対象の最大値**を引き継ぎ（統合元はスナップショットに含める）、分割は両行へ引き継ぐ。`OperationLogExcelExportService.GetFieldNameMap` に `CompanionCount` を載せる（#1726）
- **統合が再計算する値は、統合の `UPDATE` と取り消しの復元 `UPDATE` の両方の SET 句に載っているかを対で確かめる**（Issue #1942）。`companion_count` は両方から抜けており、`LedgerMergeService` が Max で決めた値は in-memory の統合先にしか残らなかった（画面と `operation_log` の `AfterData` は「外2名」、DB は 0）。**統合側だけを直すと欠陥は消えず取り消し側へ移る** — 統合が 0 のままだった間は復元も 0 で一致するため、取り消し側の欠落は統合を直すまで観測できない。#1726「SET 句はその経路で本当に編集する列に限る」の裏返しであり、列の集合は静的検査（`LedgerMergeUpdateColumnConventionTests`）でリテラルの期待値として固定する（個別の挙動テストは列の増減に追随できない）

## 残高不足時の特殊処理
残高が不足して不足分を現金でチャージした場合の処理：
- **通常の考え方**: 「チャージ140円」+「鉄道210円」の2行
- **実際の処理**: 1行にまとめる
  - 払出金額: 運賃 - チャージ額（カードの元残高から充当した金額。例: 210-140=70円）
  - 残額: 利用後の実残高（ぴったりチャージなら0円、端数チャージなら端数が残る。例: 6円）
  - 備考: 「支払額210円のうち不足額140円は現金で支払（旅費支給）」
  - ※不足額 = チャージ額（実際に現金で支払った金額）

## 月次帳票（物品出納簿）
- 利用日ごとに1行（チャージと利用は別行）
- 貸出中レコード（`is_lent_record = 1`、摘要「（貸出中）」）は出力しない。**判定は摘要ではなくフラグで行う**（Issue #2044）。摘要は組織設定 `SummaryText.LendingSummary` から生成した文字列なので、貸出中に設定を変えると既存の貸出中レコードは旧文言のまま残り、`Summary != GetLendingSummary()` の除外をすり抜けて「0円／0円」の行が物品出納簿へ出ていた。**保存済みの行を「現在の」設定値で判定しない** — `service-conventions.md`「設定値で生成したものは、設定値で判定する（#1818）」は判定側がリテラルを直書きする形を禁じたが、その逆（生成した時点と判定する時点で設定が違う）も同じだけ壊れる。行が何であるかを行自身が持っているなら、それを使う（`ReportPreflightChecker` と母集団も揃う）。静的検査 `LentRecordSummaryComparisonConventionTests` が摘要との比較の不在を固定する
  - **CSV の往復でも貸出中レコードを通常の行にしない**（Issue #2307）。利用履歴 CSV には貸出中フラグの列が無く、出力が貸出中レコードを含めていたため、返却後（貸出中レコードは物理削除済み）に取り込み直すと ID の行が見つからず `is_lent_record = 0` の新規の行として入り、上の除外をすり抜けて印字された。**フラグを持つ行を、フラグを運べない形式へ出すときは、出す側で除くか列を足す** — 運べない属性は受け取る側で既定値（false）になる。出力はフラグで除き、取り込みは二重化として摘要で拒否する（`LedgerCsvLentRowPolicy`。CSV の行はフラグを持たないので摘要しか手掛かりが無く、上の静的検査はこの 1 か所だけを、比較を含むソースの行の集合まで固定して認める。現在の設定の文言と既定の文言の両方と照合する）。**拒否は台帳を変える行に限る** — 以前の取り込みで既に混入した「（貸出中）」の行と全項目一致する行・ID の無い行で重複キーが一致する行（どちらもスキップ）まで拒否すると、今まで通っていた往復が止まる。「台帳を変えないか」は取り込みとプレビューが同じ関数（`LeavesLedgerUnchanged`）で決める — 経路ごとに別実装だと、拒否するかが経路で食い違う
- 年度末（3月）: 月計 → 累計 → 次年度繰越
- 年度初め（4月）: 前年度繰越 → 通常データ

### 集計ルール（Issue #1494）

「前年度より繰越」レコードは DB に保存されず `CarryoverRowData` として表示用に in-memory 合成されるため、月計・累計の集計には明示的に加算する必要がある。

- **4月計の受入金額** = 当月の受入合計（「○月から繰越」レコード除外） ＋ 前年度繰越額
- **5月以降の年度累計の受入金額** = 年度内の受入合計（「○月から繰越」レコード除外） ＋ 前年度繰越額（＋ 紙出納簿移行時のみ `CarryoverIncomeTotal`）
- 紙の出納簿様式での「受入 − 払出 = 残額」が月計・累計のいずれでも成立すること
- 紙出納簿から年度途中で移行したカード（Issue #510）では「○月から繰越」レコードが DB に `Income=残高` で保存される運用がある。これを月計・累計の `Sum` に含めると前月の累計と二重計上になるため、`SummaryGenerator.IsMidYearCarryoverSummary` で **集計から除外する**
- `IsMidYearCarryoverSummary` は集計フィルタ（ReportDataBuilder）と表示時の Income 空欄制御（ReportRowBuilder）の両方で使用される
- 紙出納簿移行カードの `CarryoverIncomeTotal` / `CarryoverExpenseTotal`（Issue #1215）は **5月以降の年度累計** にのみ加算される。4月は累計行を省略し月計が累計を兼ねる設計（Issue #813）のため、4月帳票には紙時代累計を反映しない（運用上は「4月計の Income には当月チャージ＋前年度繰越のみ表示。紙時代累計は5月以降の累計行で確認」）
